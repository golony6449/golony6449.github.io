# 1장 웹 개발자의 사고 전환

## 이 장에서

웹 서비스를 만들던 습관을 임베디드에 그대로 가져오면 자주 틀린다. 이 장은 그 어긋남을 미리 보여 주는 지도다. 프로토콜의 세부는 2장부터 이어지고, 여기서는 **관점**만 다룬다.

웹에서 우리는 요청과 응답, JSON, 데이터베이스, 큐, `setTimeout`, `try/catch`, 로그와 APM, CI/CD, 서버 재시작 같은 개념에 익숙하다. 임베디드에도 대응하는 개념이 있지만, 같은 이름으로 불러서는 안 될 만큼 다르다. 예를 들어 웹의 `setTimeout`은 "이벤트 루프가 한가할 때 실행되는 최소 지연"에 가깝지만, 모터 제어의 타이머는 "정해진 시간 안에 반드시"를 뜻한다.

이 장을 읽고 나면 다음 질문에 답할 수 있어야 한다.

- 웹의 어떤 습관을 버려야 하는가?
- 웹의 어떤 습관은 그대로 가져와도 되는가?
- 통신이 안 될 때 어느 계층부터 봐야 하는가?

## 1.1 한눈에 보는 대응표

먼저 전체 지도를 펼쳐 보자. 이 표는 이 책 전체에서 계속 참조한다.

| 웹에서 익숙한 것 | 임베디드에서의 대응 | 차이의 핵심 |
|---|---|---|
| HTTP 요청/응답 | UART 바이트 스트림 + 프레이밍 | 스트림에는 메시지 경계가 없다. 직접 만든다 |
| JSON/XML | 고정 길이 바이너리, TLV, 비트 필드 | 스키마가 코드와 데이터시트에 흩어져 있다 |
| REST 엔드포인트 | 명령 코드, 레지스터 주소 | "주소"가 메모리·CAN ID·I2C 주소로 겹쳐 쓰인다 |
| 데이터베이스 | 플래시·EEPROM·NVS | 쓰기 횟수 제한, 쓰기 중 전원 차단 위험 |
| 큐·메시지 브로커 | 링 버퍼, 인터럽트 | 생산자와 소비자가 ISR과 메인 루프로 나뉜다 |
| `setTimeout`/Promise | 타이머, 워치독, 실시간 마감 | 늦으면 데이터를 잃거나 기계가 멈춘다 |
| `try/catch` | 오류 코드, 재시도, 안전 상태 | 예외를 받아 줄 상대가 없고, 던져도 복구가 어렵다 |
| 로그·APM | UART 로그, LED, 로직 분석기 | 로그를 볼 수 없는 현장이 많다 |
| CI/CD·무중단 배포 | 펌웨어 플래싱·OTA | 잘못 올리면 벽돌. 롤백을 미리 설계한다 |
| 서버 재시작 | 리셋·전원 재인가 | 액추에이터 상태는 재시작해도 그대로 남는다 |
| ms 단위 타임아웃 | µs~ms 단위 지터 | 스케줄러가 아니라 하드웨어가 시간을 정한다 |

표의 각 행은 이 책의 장과 연결된다. 이제 각 차이를 하나씩 풀어 보자.

## 1.2 메시지가 아니라 바이트가 온다

### 웹에서는 경계가 공짜였다

HTTP를 생각해 보자. TCP 자체는 바이트 스트림이지만, 그 위에 HTTP라는 프레이밍이 있다. `Content-Length` 헤더가 본문의 길이를 알려 주고, 청크 인코딩에는 `Transfer-Encoding`이 붙는다. 브라우저와 서버는 이 규칙으로 "여기서부터 여기까지가 한 요청"을 결정한다. 우리는 그 경계를 직접 만들 일이 거의 없다.

UART 같은 바이트 스트림에는 그런 프레이밍이 없다. `read()` 한 번이 메시지 하나라는 보장이 없다. 한 번의 송신이 여러 번의 수신으로 쪼개지고, 여러 송신이 한 번의 수신으로 뭉친다.

```text
송신 측이 4바이트를 한 번에 썼다:  [01] [2A] [00] [64]

수신 측 read()가 돌려줄 수 있는 것:
  [01 2A]  [00 64]          ← 두 번에 나뉨
  [01]  [2A 00 64]          ← 앞이 한 바이트만
  [01 2A 00 64]             ← 운 좋게 한 번에
```

**"한 번 읽었는데 프레임이 안 맞는다"는 대부분 상대 버그가 아니라 정상 동작이다.** 이 사실을 모르면 존재하지 않는 버그를 쫓게 된다.

차량 진단에서도 같은 일이 일어난다. ELM327 어댑터에 `010C`(엔진 회전수 요청)를 보내면 응답은 대략 이런 줄로 온다.

```text
41 0C 1A F8
```

하지만 시리얼에서 `read(64)`를 한 번 호출했을 때 받는 것은 다음과 같을 수 있다.

```text
b"41 0C 1A"     ← 먼저 도착한 부분
b" F8\r\r>"     ← 나중에 도착한 부분과 프롬프트
```

심지어 `\r` 하나만 먼저 올 수도 있다. ELM327은 응답 끝에 캐리지 리턴(`\r`)을 붙이고, 마지막에 프롬프트 `>`를 보낸다. 이 **줄 경계와 프롬프트**를 기준으로 읽어야 한다. "응답 한 줄이 한 번의 `read()`로 온다"고 가정하면 첫 요청부터 어긋난다. 9장에서 이 읽기 루프를 제대로 만든다.

### 하드웨어가 경계를 만들어 주는 경우도 있다

모든 버스가 그런 것은 아니다. I2C는 START/STOP, SPI는 CS, CAN은 SOF/EOF로 하드웨어가 트랜잭션·프레임 경계를 만든다. CAN은 CRC로 오류를 검출한다. 이런 버스에서는 "한 번의 트랜잭션"이 비교적 명확하다.

그래도 안심할 수는 없다. 여러 프레임에 걸친 애플리케이션 메시지(예: ISO-TP로 나눈 긴 진단 메시지)는 직접 조립해야 하고, 경계가 깨졌을 때의 복구도 설계해야 한다. 하드웨어가 만들어 주는 경계는 **한 계층 아래의 경계**일 뿐, 애플리케이션 메시지의 경계와 항상 일치하지는 않는다.

### 그래서 프레이밍을 설계한다

프로토콜을 설계할 때는 경계를 만드는 규칙과, 경계가 깨졌을 때 다시 맞추는 절차를 **함께** 정한다.

- 경계 규칙: 구분자, 길이 접두, 고정 크기, COBS, SLIP 등
- 복구 절차: 재동기화, 최대 길이 검증, 부분 프레임 타임아웃

웹에서 `Content-Length`와 `Transfer-Encoding`을 신경 쓰던 감각이 그대로 쓸모 있다. 다만 여기서는 그 헤더를 직접 만들고 직접 검증한다. 3장에서 이 규칙들을 자세히 다룬다.

## 1.3 데이터는 자기 설명적이지 않다

JSON은 키와 타입이 데이터 안에 있다. `{"temperature": 25.3}`를 받으면 무엇을 뜻하는지, 어떤 타입인지, 단위가 무엇인지 데이터만 보고 알 수 있다. 물론 스키마 문서가 필요하긴 하지만, 적어도 필드 이름은 payload 안에 있다.

임베디드 페이로드는 보통 `[0x01, 0x2A, 0x00, 0x64]`처럼 **위치와 길이와 의미를 약속으로만** 안다. 같은 4바이트도 해석에 따라 전혀 다른 값이 된다.

| 해석 | 값 |
|---|---|
| 빅 엔디언 unsigned 32비트 | 19,529,828 |
| 리틀 엔디언 unsigned 32비트 | 1,677,732,353 |
| 빅 엔디언 signed 16비트(앞 2바이트 `01 2A`) | 298 |
| 0.1 단위 스케일이 적용된 16비트 온도 | 29.8°C |
| 비트 필드 | `0000 0001 0010 1010` |

물론 이 중 어느 해석이 맞는지는 프로토콜 문서가 정한다. 중요한 것은 **바이트를 보는 순간 "이게 무슨 형식인가"를 먼저 확인해야 한다**는 점이다. 엔디언, 부호, 폭, 스케일, 단위를 확인하지 않고 값을 읽으면 65,536배 틀리거나 부호가 뒤집힌 값을 조용히 받게 된다.

OBD-II는 이 차이를 아주 잘 보여 준다. 똑같이 `41`로 시작하는 응답이라도 두 번째 바이트가 PID다.

```text
41 0C 1A F8    PID 0C: 엔진 회전수 = (0x1A × 256 + 0xF8) / 4 = 1726 rpm
41 0D 50       PID 0D: 차속 = 0x50 = 80 km/h
41 05 7B       PID 05: 냉각수 온도 = 0x7B − 40 = 83 °C
41 42 3A 98    PID 42: 모듈 전압 = (0x3A × 256 + 0x98) / 1000 = 15.0 V
```

`41`은 "Mode 01 요청에 대한 긍정 응답"이고, `0C`·`0D`·`05`·`42`는 각각 다른 PID다. PID마다 데이터 길이와 공식이 다르다. PID 0D는 1바이트, PID 0C는 2바이트, PID 42는 2바이트를 1000으로 나눈다. **PID 번호를 확인하지 않고 두 번째 바이트부터 해석하면 전부 틀린다.**

제조사 고유 DID는 더 심하다. 같은 `22 B0 02` 응답이라도 계기판(7C6)에서는 주행거리이고, 다른 제어기에서는 전혀 다른 값일 수 있다. DID 뒤 데이터의 **바이트 오프셋**까지 문서로 확인해야 한다. 10장에서 이 함정을 실제 쏘렌토 데이터로 다룬다.

정수 폭도 다르다. AVR의 `int`는 16비트다. `long`을 32비트로 가정하지 말고 `stdint.h`의 `uint8_t`/`int16_t`/`uint32_t`를 쓴다. 구조체를 그대로 바이너리로 보내면 패딩·정렬·엔디언 때문에 상대와 어긋난다. 직렬화는 필드별로 명시적으로 한다. 3장에서 엔디언과 비트 필드를 더 자세히 다룬다.

## 1.4 타이밍과 실시간성

웹의 "빠르면 좋다"와 임베디드의 "정해진 시간 안에 반드시"는 다르다. 실시간성은 평균 속도가 아니라 **최악의 경우 지연(bounded worst case)**이다. 평균 1ms인 시스템도 가끔 100ms 멈추면 모터 제어에는 쓸 수 없다.

### `sleep(1)`은 1초 동안 아무것도 못 한다

웹에서 `await sleep(1000)`은 그동안 다른 요청을 처리할 수 있다. 임베디드의 `delay(1000)`은 그 1초 동안 입력도, 통신도, 센서 읽기도 하지 못한다. 메인 루프에서 `delay()`를 쓰면 입력을 놓치고 워치독에 걸린다.

대신 상태 기계와 `millis()` 같은 비차단 패턴을 쓴다. "마지막 실행 시각"을 기억해 두고, 지금 시각과의 차이가 주기를 넘었을 때만 일을 한다.

```c
if (now - last >= period) {
    last = now;
    do_periodic_work();
}
```

이 코드의 자세한 형태는 13장에서 다룬다.

### 센서에도 준비 시간이 있다

센서에는 샘플링 주기, 변환 시간, 준비 시간이 있다. 데이터시트의 타이밍 표를 보고 "읽고 나서 언제 다음 읽기가 가능한지"를 지킨다. 아무리 코드가 빨라도 센서가 아직 변환 중이면 엉뚱한 값을 읽는다.

### 물리적인 것에는 바운스와 관성이 있다

버튼·릴레이·모터에는 바운스와 관성이 있다. 소프트웨어 디바운스, 램프, 데드타임 같은 물리 보정이 필요하다. 웹의 이벤트 디바운스와 비슷하지만, 목적은 사용자 입력의 연타 방지가 아니라 **노이즈 제거**다.

### 타임아웃은 최악의 시간으로 정한다

통신 타임아웃은 "상대가 응답할 최악의 시간 + 여유"로 정한다. 짧으면 정상 응답을 버리고, 길면 고장을 늦게 발견한다. 고정 1초를 모든 장치에 쓰는 것은 거의 항상 틀린다.

차량 진단에서는 이 타임아웃이 여러 층에 겹친다.

- ELM327이 차량에 요청을 보내고 응답을 기다리는 시간(`AT ST`)
- CAN ECU가 응답을 준비하는 시간
- ISO-TP 다중 프레임 사이의 최소 간격(STmin)
- PC가 ELM327의 프롬프트 `>`를 기다리는 시간

ELM327 클론에서 `NO DATA`가 뜨는 데 대략 0.2초가 걸린다는 관찰이 있다(실차 기록). 같은 PID라도 ECU가 바쁘면 `7F 22 78`(응답 대기)을 먼저 보내고 나중에 진짜 응답을 보낼 수 있다. 이때 성급히 재요청하면 버스와 어댑터에 요청이 쌓인다. 타임아웃은 "가장 느린 정상 응답"을 기준으로 잡고, `78`은 실패가 아니라 "기다려 달라"로 처리한다.

## 1.5 메모리와 CPU가 작고, GC가 없다

MCU는 RAM이 수 KB에서 수백 KB다. 1MB면 큰 편이다. 웹에서 당연한 문자열 연결, 객체 할당, 라이브러리 몇 개가 곧바로 한계가 된다. 가비지 컬렉터도 없으므로 "언젠가 정리해 주겠지"가 통하지 않는다.

### 동적 할당은 조각화와 실패를 부른다

가능하면 정적 버퍼, 풀, 링 버퍼를 쓴다. 특히 인터럽트 안에서 `malloc`/`free`/`printf`를 쓰지 않는다. `printf`는 내부 버퍼와 포맷팅에 메모리와 시간을 쓴다. ISR에서 하면 안 되는 일은 13장에서 다시 정리한다.

### 스택 오버플로는 예외가 아니다

스택 오버플로는 예외가 아니라 **조용한 메모리 손상**이다. 큰 배열을 지역 변수로 두지 않고, RTOS 태스크 스택을 넉넉히 잡고, 사용량을 측정한다. "컴파일된다"와 "들어간다"는 다르다.

### 부동소수점이 없을 수도 있다

부동소수점이 느리거나 아예 없는 MCU가 있다. 정수 스케일(예: 0.1°C → 1)로 계산하면 빠르고 예측 가능하다. 표시할 때만 나누기나 포맷팅을 한다.

### 실제 사용량을 본다

웹의 "메모리는 넉넉하다"를 버리고 `size` 명령, 맵 파일, 스택 하이워터마크로 실제 사용량을 본다. 13장에서 메모리 영역과 측정 방법을 자세히 다룬다.

차량 어댑터도 작은 컴퓨터다. ELM327 데이터시트에는 RS232 송신 버퍼가 512바이트라고 적혀 있다. CAN 버스에서 응답이 빠르게 쏟아지는데 PC가 천천히 읽으면 버퍼가 차고 `BUFFER FULL`이 뜬다. 긴 VIN·Calibration ID 응답을 연속으로 받을 때 실제로 겪는 일이다. 이때는 보율을 높이거나, 헤더·공백 출력을 끄거나, 수신 필터로 필요한 ID만 받는다. "어댑터가 이상하다"가 아니라 **소비자가 생산자를 못 따라가는 문제**다. 9장과 14장에서 이 증상을 다시 다룬다.

## 1.6 OS가 없거나, 있어도 얇다

베어메탈(bare metal)은 `main()` 앞의 스타트업 코드, 초기화, 무한 루프가 전부다. 프로세스·가상 메모리·파일 시스템·스케줄러가 없다. "서버를 재시작한다"는 개념도 없고, 그냥 리셋이다.

### 동시성은 인터럽트로 만든다

동시성은 보통 **인터럽트**로 만든다. ISR은 최대한 짧게 하고, 공유 변수는 `volatile`로 표시하며, 읽기-수정-쓰기는 원자성을 직접 보장한다.

여기서 가장 흔한 오해가 있다. **`volatile`은 원자성을 주지 않는다.** `volatile`은 "컴파일러가 매번 메모리에서 읽게" 할 뿐, "읽는 동안 ISR이 끼어들지 못하게" 하지 않는다. 16비트 변수를 8비트 CPU에서 읽는 도중 ISR이 쓰면 반쪽 값이 나올 수 있다.

### RTOS를 쓰면 문제가 사라지는 게 아니다

RTOS를 쓰면 태스크·큐·뮤텍스·우선순위가 생기지만, 우선순위 역전과 스택 크기 문제도 함께 온다. 태스크가 많다고 좋은 게 아니다. 태스크마다 스택과 컨텍스트 스위치 비용이 든다.

### 한 곳의 크래시가 전체를 멈춘다

프로세스 격리가 없으므로 한 곳의 크래시가 전체를 멈춘다. 경계 검사, 워치독, 안전 상태 복귀를 코드에 넣는다. 웹에서 프로세스 하나가 죽어도 나머지가 살아 있는 것과 정반대다.

## 1.7 하드웨어 상태가 프로그램 상태다

웹 버그는 대부분 코드와 데이터에 있다. 임베디드 버그는 **배선, 접지, 전원, 전압 레벨, 온도, 커넥터 접촉, 노이즈**에 있다. 코드를 아무리 읽어도 배선이 반대면 답이 나오지 않는다.

- "내 책상에서는 된다"는 의미가 없다. 같은 코드가 다른 전원, 다른 케이블, 다른 보드에서 다르게 동작한다. 재현 조건에 하드웨어를 적는다.
- 전원이 끊기면 변수는 사라지고 액추에이터는 마지막 상태에 남는다. 재부팅 후 안전한 상태로 가는 절차(부트로더, 릴레이 초기화, 모터 정지)를 설계한다.
- 가끔만 나는 문제는 타이밍·전원·접지가 원인인 경우가 많다. 코드만 들여다보지 말고 계측기로 신호를 본다. 14장에서 도구 사용법을 다룬다.

차량은 이 원칙이 극단적으로 나타나는 환경이다. OBD-II 포트의 16번 핀은 배터리 +12V, 4·5번은 접지, 6·14번은 CAN_H/CAN_L이다. 시동을 걸면 전압이 순간적으로 떨어지고, 충전기가 연결되어 있으면 접지 전위가 흔들린다. 실제 기록에는 주행 중 USB 어댑터가 끊긴 사례가 있고, Windows 이벤트 로그에 `USB\VID_1A86&PID_7523` 장치가 버스에서 누락된 것으로 남아 있었다. 크랭킹 때 끊긴 사례는 노트북 충전 전원 변화와 시점이 겹쳤지만, 그것이 원인이라고 단정할 수는 없다. **원인을 코드에서 찾기 전에 전원·접지·커넥터·USB 케이블을 먼저 본다.** 전압·전류·접지의 기본은 4장, 차량 12V의 실제 범위와 보호는 15장에서 다룬다.

이 장을 읽는 동안 "내 코드가 맞는데?"라는 생각이 들면, 그 문장을 "내 코드와 하드웨어와 환경 중 어딘가가 틀렸다"로 바꿔 보자.

## 1.8 오류는 예외가 아니라 계층이다

임베디드 디버깅은 아래에서 위로 올라간다. 위에서부터 보면 시간을 낭비한다.

```text
1. 전원   전압, 전류, 극성, 브라운아웃
2. 접지   공통 접지, 접지 루프, 절연
3. 배선   TX/RX, 극성, 커넥터, 냉납
4. 레벨   3.3V/5V, RS-232/RS-485/TTL, 종단
5. 설정   보율, 8N1, I2C 주소, CAN 비트레이트
6. 프레이밍 경계, 길이, 체크섬, 엔디언
7. 의미   명령 코드, 스케일, 상태 전이
8. 타이밍 타임아웃, 샘플링, 워치독
```

웹의 스택 트레이스에 해당하는 것이 임베디드에는 거의 없다. 대신 **원시 바이트 로그**, 오실로스코프/로직 분석기 파형, 워치독 리셋 원인 레지스터가 단서다.

차량에서 "값이 안 온다"는 증상은 이 순서로 좁힌다.

```text
1. 전원   OBD 16번 핀 12V, 4·5번 접지, 시동 상태
2. 접지   차체 접지와 노트북 접지, USB 절연
3. 배선   OBD 커넥터 체결, 6/14번 핀, 어댑터 케이블
4. 레벨   CAN_H/CAN_L, 120Ω 종단(차량에는 이미 있음)
5. 설정   ATSP0/ATSP6, 보율 38400/115200, 8N1
6. 프레이밍 ELM327 줄 끝 \r, 프롬프트 >, ISO-TP PCI
7. 의미   PID 번호, DID, 바이트 오프셋, 스케일
8. 타이밍 NO DATA 대기, 0x78 응답 대기, STmin
```

`NO DATA`가 나왔다고 바로 파서를 고치지 않는다. 먼저 시동이 켜져 있는지, `ATSP0`로 프로토콜을 찾았는지, `ATDPN`이 `A6`인지, 헤더를 잘못 잡지 않았는지 확인한다. 9장에서 이 체크리스트를 실제 명령과 함께 다시 쓴다.

로그는 파싱 후 값이 아니라 **원시 바이트와 타임스탬프**를 남긴다. 나중에 파서가 틀렸다는 사실을 알게 되는데, 그때 원본이 없으면 복구할 수 없다. 이 습관은 3장의 파서 테스트와 14장의 로깅에서 다시 나온다.

## 1.9 재시도와 멱등성

UART 단일 링크는 보통 바이트 순서를 지키지만, 버퍼 오버플로·재전송·게이트웨이/무선 구간을 거치면 손실·중복·순서 뒤바뀜이 생길 수 있다. 여기서 웹 개발자가 자주 하는 실수가 나온다.

**타임아웃 후 재전송을 넣으면 같은 명령이 두 번 실행될 수 있다.** "램프 켜기"는 두 번 실행해도 되지만 "토출량 10 mL 추가"는 두 번 실행하면 안 된다.

- 명령마다 멱등성을 표시한다. "절대값 설정"은 멱등하고, "증가"는 멱등하지 않다.
- 시퀀스 번호나 트랜잭션 ID로 중복을 걸러 낸다.
- 응답이 없을 때 바로 재시도하지 말고, 상대가 처리 중일 수 있음을 고려한다.
- 재시도 간격과 최대 횟수를 정하고, 실패 시 안전 상태로 간다.

타임아웃 후 늦게 도착한 응답을 다음 요청의 응답으로 오인하는 것도 흔한 버그다. 요청 ID를 응답에 포함시켜 매칭한다. 3장에서 이 내용을 더 자세히 다룬다.

OBD-II는 여기에 **PID 에코**가 있다. `010C`에 대한 응답은 `41 0C ...`로 시작하므로, 어느 요청의 응답인지 PID로 구분할 수 있다. 다중 PID 요청(`01 0C 0D 05`)을 보냈으면 응답에 여러 PID가 섞여 오고, 요청한 순서와 응답 순서가 다를 수 있다. PID별로 파싱해야 한다.

읽기 요청은 재시도해도 차량 상태를 바꾸지 않는다. 하지만 재시도 간격을 두지 않고 연속으로 보내면 ELM327 버퍼가 차거나 ECU가 바쁘다는 `7F ... 78` 응답을 받는다. **읽기 요청도 예절이 필요하다.** 반면 쓰기·루틴 요청은 재시도 자체가 위험하다. 11장에서 이 경계를 다룬다.

## 1.10 배포와 관측

펌웨어에는 버전, 빌드 시각, 깃 커밋을 넣는다. 부팅 로그에 남기면 현장에서 "어떤 펌웨어인지" 바로 확인할 수 있다. 웹의 배포 태그와 같은 역할이지만, 장치에는 `git log`를 칠 수 없다.

OTA(Over-The-Air)는 전원 차단, 다운로드 중단, 검증 실패를 전제로 설계한다. A/B 파티션과 롤백, 서명 검증을 함께 설계한다. "잘못 올리면 벽돌"은 농담이 아니다.

리셋 원인(전원 인가, 워치독, 소프트웨어, 브라운아웃)을 저장해 두면 간헐 장애를 좁힐 수 있다. 웹의 헬스 체크에 해당하는 것은 하트비트, 카운터, 마지막 오류 코드다. 주기적으로 올려 보내거나 로컬에 남긴다.

차량 로거를 만든다면 로그 헤더에 다음을 남긴다.

```text
앱 버전, Git 커밋, ELM327 버전(ATI), 프로토콜(ATDPN), 포트/보율,
차량 식별자는 해시 또는 별칭, 세션 시작 시각, 샘플 주기
```

VIN은 로그 헤더에 그대로 남기지 않는다. 공개 저장소에 올릴 일이 있다면 더더욱 그렇다. 로그에는 **원시 요청/응답 hex와 단조 시각**을 남기고, 파싱된 값은 별도 열로 둔다. 나중에 공식이 틀렸다는 것을 발견해도 원본이 있으면 다시 계산할 수 있다.

## 1.11 웹에서 그대로 가져와도 되는 것

여기까지 읽으면 임베디드는 모든 것이 다른 세계처럼 보일 수 있다. 하지만 웹 개발자의 자산은 생각보다 많이 통한다.

- Git, 이슈 트래킹, 코드 리뷰, 테스트 자동화, 린터, CI는 그대로 쓸모 있다.
- 상태 기계, 의존성 주입, 계층 분리, 인터페이스 뒤에 하드웨어 숨기기, 목(mock)으로 테스트하기는 임베디드에서도 강력하다.
- 특히 **하드웨어 접근을 얇은 인터페이스로 분리**하면 PC에서 파서·상태 기계를 단위 테스트할 수 있다. 이 습관이 디버깅 속도를 크게 바꾼다.
- 문서화도 그대로다. 핀 배치, 전압, 보율, 프로토콜 버전, 케이블 색을 적어 두지 않으면 다음 주에 자신도 모른다.

## 1.12 첫 30분 체크리스트

새 장치를 처음 연결했을 때, 코드를 쓰기 전에 다음을 확인한다.

- [ ] 전원 전압과 극성을 멀티미터로 확인했는가
- [ ] 두 장치의 접지가 연결되어 있는가
- [ ] TX/RX(또는 A/B, CAN_H/CAN_L)를 교차/극성 확인했는가
- [ ] 논리 레벨(3.3V/5V/RS-232/RS-485)이 맞는가
- [ ] 보율·8N1·비트레이트·I2C 주소가 상대와 같은가
- [ ] 포트를 다른 프로그램이 잡고 있지 않은가
- [ ] 원시 바이트를 타임스탬프와 함께 보고 있는가
- [ ] 한 계층씩 확인했는가(전원 → 배선 → 설정 → 프레이밍 → 의미)

차량이라면 다음을 더 확인한다.

- [ ] 차량이 안전한 곳에 정차해 있고, 기어가 P(또는 N), 주차 브레이크가 걸려 있는가
- [ ] 시동 상태(OFF/ACC/ON/엔진 시동)를 기록했는가
- [ ] OBD-II 커넥터가 끝까지 체결됐는가
- [ ] 어댑터의 전원 램프가 켜지는가
- [ ] `ATI`로 어댑터가 응답하는가
- [ ] `ATSP0` 뒤 `ATDPN`이 예상 프로토콜(예: `A6`)인가
- [ ] `ATRV`로 배터리 전압을 봤는가(대략 12V 이상, 시동 중 13~14V대)
- [ ] 읽기 요청만 보내고 있는가

이 체크리스트는 2장부터 14장까지의 실습에서 계속 다시 나온다. 처음에는 번거롭게 느껴지지만, 한 번 익숙해지면 "어디까지 확인했는가"를 기억하는 가장 빠른 방법이 된다.

## 예시: 같은 4바이트, 네 가지 질문

프로토콜 문서 없이 `01 2A 00 64`를 받았다고 하자. 이때 던져야 할 질문은 다음과 같다.

1. **경계**: 이 4바이트가 한 메시지인가? 길이 필드는 어디에 있는가?
2. **엔디언**: `01 2A`를 0x012A로 읽어야 하는가, 0x2A01로 읽어야 하는가?
3. **부호와 폭**: 16비트인가 32비트인가? signed인가 unsigned인가?
4. **스케일**: 0.1 단위인가, 1 단위인가? 단위는 °C인가, mm인가?

이 질문에 답하지 못하면 그 값을 대시보드에 올려서는 안 된다. 웹이라면 JSON 키를 보고 추측이라도 할 수 있지만, 여기서는 추측이 곧 버그다.

## 예시: 첫 OBD-II 요청을 손으로 해 보기

차량 없이도 흐름을 익힐 수 있도록, ELM327과의 첫 대화를 그대로 적어 둔다. 실제 응답은 어댑터·차량마다 다르다.

```text
>ATZ
ELM327 v1.5        ← 클론이 보고하는 버전. v1.5는 실제 ELM Electronics 버전이 아니다
>ATE0
OK                 ← 에코 끄기
>ATL0
OK                 ← 줄바꿈(LF) 끄기. 응답은 \r로 끝난다
>ATSP0
OK                 ← 프로토콜 자동 검색
>ATDPN
A6                 ← 자동 검색 후 ISO 15765-4 CAN 11비트 500k 선택
>0100
41 00 BE 1F A8 13  ← 지원 PID 비트마스크
>010C
41 0C 1A F8        ← 엔진 회전수
```

`0100`의 응답 `BE 1F A8 13`을 풀면 다음과 같다.

```text
BE 1F A8 13 = 1011 1110 0001 1111 1010 1000 0001 0011
              ↑ ↑ ↑ ↑  ...
              | | | └ PID 04 지원
              | | └── PID 03 지원
              | └──── PID 02 미지원
              └────── PID 01 지원
```

비트 순서와 PID 번호의 대응은 9장에서 코드로 만든다. 여기서 기억할 것은 **요청 한 줄, 응답 한 줄, 그리고 그 사이의 프롬프트**라는 구조다. 이 단순한 구조가 2장 UART, 3장 프레이밍, 7장 CAN을 거치면서 점점 깊어진다.

## 흔한 실수

| 실수 | 증상 | 올바른 접근 |
|---|---|---|
| `read()` 한 번이 메시지 하나라고 가정 | 프레임이 어긋나고 파서가 멈춤 | 부분 수신·합쳐짐을 가정하고 상태 기계 파서를 쓴다 |
| JSON처럼 키를 찾으려 함 | payload에서 필드 이름을 찾다 실패 | 위치·길이·스케일을 문서화하고 순서대로 읽는다 |
| 웹의 ms 타임아웃 감각 | 느린 장치에서 정상 응답을 버림 | 최악 처리 시간 + 여유로 타임아웃을 정한다 |
| "메모리는 넉넉하다" | 힙 단편화, 스택 손상 | 정적 버퍼·풀·링 버퍼, 사용량 측정 |
| 코드만 의심 | 배선 반대·접지 누락을 오래 못 찾음 | 전원→접지→배선→레벨→설정 순서로 본다 |
| 응답이 없으면 즉시 재시도 | 같은 명령이 두 번 실행됨 | 멱등성·시퀀스 번호·재시도 정책 |
| `volatile`을 원자성으로 착각 | 반쪽 값, 간헐 오류 | 인터럽트 차단·원자 연산·더블 버퍼 |
| 로그를 파싱 후 값으로만 저장 | 파서 버그를 나중에 발견해도 원인 추적 불가 | 원시 hex와 단조 시각을 남긴다 |
| 재시작 후 액추에이터를 초기화하지 않음 | 재부팅 후 모터·릴레이가 위험한 상태 | 부팅 시 안전 상태로 가는 절차를 넣는다 |
| "내 책상에서는 된다" | 현장에서만 재현되는 문제 | 전원·케이블·보드·온도를 재현 조건에 기록 |
| OBD 응답을 PID 확인 없이 해석 | 차속을 회전수로, 온도를 전압으로 읽음 | `41 <PID>`의 PID와 길이·공식을 먼저 확인한다 |
| ELM327 응답 한 줄을 `read()` 한 번으로 가정 | 첫 요청부터 파싱 실패 | `\r`과 프롬프트 `>` 기준으로 읽는다 |
| `NO DATA`를 파서 버그로 판단 | 엉뚱한 코드를 고침 | 시동·프로토콜·헤더·PID 지원 여부를 먼저 본다 |

| VIN·위치를 로그에 그대로 저장 | 개인정보·추적 위험 | 해시/별칭을 쓰고 원본은 분리 보관한다 |

## 장 요약

- 웹의 요청/응답·JSON·DB·큐·타이머·예외·배포 습관은 임베디드에서 **대응 개념은 있지만 의미가 다르다.**
- 바이트 스트림에는 메시지 경계가 없다. 경계를 만드는 규칙과 재동기화 절차를 함께 설계한다.
- 데이터는 자기 설명적이지 않다. 엔디언·부호·폭·스케일을 확인하기 전에는 값을 믿지 않는다.
- 실시간성은 평균이 아니라 최악의 경우다. `delay()` 대신 상태 기계와 시각 비교를 쓴다.
- 메모리와 CPU가 작고 GC가 없다. 동적 할당을 줄이고 스택을 측정한다.
- OS가 없거나 얇다. 인터럽트와 `volatile`의 한계를 이해하고, 워치독과 안전 상태를 넣는다.
- 버그는 코드보다 전원·접지·배선·레벨에 숨어 있다. 계층 순서로 확인한다.
- 재시도에는 멱등성과 중복 제거가 필요하다.
- 펌웨어에는 버전과 리셋 원인을 남기고, OTA는 롤백을 전제로 설계한다.
- Git·테스트·상태 기계·계층 분리는 그대로 가져와도 된다.
- OBD-II 응답은 `41 <PID>`의 PID와 길이·공식을 확인해야 한다. 같은 바이트도 PID마다 뜻이 다르다.
- 차량 문제는 코드보다 전원·접지·커넥터·프로토콜 설정에서 먼저 찾는다.

다음 장에서는 가장 기본이 되는 UART를 다룬다. "보율이 뭐지"에서 시작해, ELM327과 PC가 실제로 비트를 주고받는 모습을 본다.

## 연습 문제

### 1. (기초) 같은 4바이트, 다른 값

OBD-II 응답 `41 0C 1A F8`이 왔다. PID `0C`는 엔진 회전수이고 공식은 `(256A + B) / 4`다.

1. 정상 해석한 rpm을 구하라.
2. 같은 바이트를 리틀 엔디언으로 읽어 `F8 1A`로 해석하면 몇 rpm인가?
3. 두 값 중 실제 엔진 회전수로 가능한 것은 어느 쪽인가?

### 2. (중급) 최악의 시간 계산

1초 주기로 세 PID를 순서대로 읽는 루프가 있다. 요청 하나의 정상 왕복이 80ms, 파싱이 5ms, 화면 갱신이 10ms다. 응답이 없을 때는 PID마다 300ms 타임아웃이 걸린다.

1. 정상일 때 한 주기는 몇 ms인가?
2. 세 PID가 모두 타임아웃되면 한 주기는 몇 ms인가?
3. 1초 주기를 지킬 수 있는가? 지킬 수 없다면 어떻게 설계를 바꿔야 하는가?

### 3. (중급) 2KB RAM에 무엇을 넣을까

MCU의 RAM이 2KB다. 전역 변수가 300B, 스택에 512B, 수신 버퍼에 512B를 쓰고 있다.

1. 남는 공간은 몇 B인가?
2. 여기에 1KB 힙 버퍼를 동적 할당할 수 있는가?
3. 동적 할당이 실패했을 때를 대비한 설계를 한 줄로 쓰라.

### 4. (기초) 차량에서만 값이 0

벤치에서는 rpm이 잘 나왔는데, 차량에 붙이자 모든 값이 0으로 보인다. 확인 순서를 `전원 → 접지 → 배선 → 레벨 → 설정 → 프레이밍 → 의미 → 타이밍`에 맞춰 네 단계만 쓰라.

### 5. (중급) 재시도해도 되는 요청

다음 요청을 통신 오류로 재시도해도 되는가?

1. `01 0C`(현재 rpm 읽기)
2. `03`(저장 DTC 읽기)
3. `04`(DTC 삭제)

이유를 멱등성 관점에서 설명하라.

## 정답과 해설

### 1.

1. `(0x1A × 256 + 0xF8) / 4 = (26 × 256 + 248) / 4 = 6904 / 4 = 1726 rpm`
2. `F8 1A`를 리틀 엔디언 16비트로 읽으면 `0xF81A = 63514`, `/4 = 15878.5 rpm`
3. 1726 rpm이 현실적이다. 15878 rpm은 승용 디젤 엔진의 정상 범위를 크게 벗어난다. **바이트 순서를 확인하기 전에는 값을 믿지 않는다.**

### 2.

1. `3 × (80 + 5) + 10 = 265ms`
2. `3 × 300 = 900ms`(파싱·화면 갱신을 더하면 900ms를 넘는다)
3. 정상일 때는 1초를 지킬 수 있지만, 모두 타임아웃되면 지킬 수 없다. 타임아웃을 줄이거나, PID를 한 주기에 다 읽지 말고 **한 주기에 하나씩 번갈아 읽는 상태 기계**로 바꾼다. 읽기 스레드와 표시를 분리하고, 마지막 성공 시각을 함께 표시한다.

### 3.

1. `2048 − 300 − 512 − 512 = 724B`
2. 없다. 1KB는 남은 724B보다 크다. 게다가 힙 단편화로 더 일찍 실패할 수 있다.
3. 정적 버퍼를 쓰고, 크기를 컴파일 시점에 고정하며, 넘치면 오래된 데이터를 버리는 정책을 둔다.

### 4.

예: ① 배터리 전압과 어댑터 LED를 확인한다. ② OBD 4/5번 접지와 공통 접지를 확인한다. ③ 6/14번 CAN 배선과 커넥터를 확인한다. ④ `ATDPN`으로 프로토콜과 보율을 확인한다. 여기까지 정상인데 값이 0이면 PID 공식·바이트 순서·시동 상태를 본다.

### 5.

1. 재시도 가능하다. 현재 값을 읽는 요청은 상태를 바꾸지 않는다.
2. 재시도 가능하다. DTC 목록을 읽기만 한다.
3. 재시도하면 안 된다. 삭제는 멱등해 보이지만, **진단 근거와 readiness를 잃는 부작용**이 있다. 통신 오류로 실제 삭제가 됐는지 확실하지 않은 상태에서 반복하는 것은 더 위험하다. 이 책에서는 `04` 자체를 보내지 않는다.
