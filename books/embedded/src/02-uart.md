# 2장 UART: 가장 단순한 시리얼

## 이 장에서

UART(Universal Asynchronous Receiver/Transmitter)는 가장 흔한 "시리얼 통신"이다. 클록 선 없이 양쪽이 약속한 속도로 비트를 주고받는다. 웹의 소켓보다 훨씬 단순하지만, 그 단순함 때문에 **설정이 하나만 틀려도 조용히 깨진다.**

웹 개발자에게 UART는 낯설게 느껴질 수 있다. 하지만 "연결이 열려 있고, 바이트를 쓰고, 바이트를 읽는다"는 점만 보면 TCP 소켓과 닮았다. 다른 점은 TCP/IP 스택도, 포트 번호도, HTTP 프레이밍도 없다는 것이다. 전선 두 개와 약속된 속도만 있다. 그래서 UART를 이해하면 "프로토콜이란 무엇인가"를 가장 낮은 층에서부터 보게 된다.

이 장에서 다루는 것:

- 8N1 프레임이 실제로 어떻게 생겼는가
- 보율(baud rate)과 클록 오차
- TTL·RS-232·RS-485의 전기적 차이
- TX/RX 교차, 공통 접지, 흐름 제어
- USB-UART 어댑터와 COM 포트
- pyserial로 첫 바이트를 주고받는 방법

## 2.1 프레임 구조: 8N1

UART는 평소 선이 high(idle)이고, 한 바이트를 다음과 같이 보낸다.

```text
idle  start   D0   D1   D2   D3   D4   D5   D6   D7   stop  idle
 1      0     b0   b1   b2   b3   b4   b5   b6   b7    1     1
```

- start bit는 항상 0이다. 수신측은 high에서 low로 떨어지는 에지를 보고 프레임의 시작을 잡는다.
- 데이터는 보통 **LSB부터** 전송한다.
- stop bit는 항상 1이다. 수신측은 stop bit가 1인지 확인해 프레임 오류를 검출한다.

`8N1`은 **데이터 8비트, 패리티 없음(None), stop 1비트**를 뜻한다. 가장 흔한 설정이다. "8N1"이라는 표기는 시리얼 포트 설정 화면에서 자주 보게 된다.

### 예: 문자 `A`를 보내면

`A`의 ASCII 코드는 `0x41`, 이진수로 `0100 0001`이다. UART는 LSB부터 보내므로 전선 위에서는 다음과 같이 된다.

```text
비트:   start  D0  D1  D2  D3  D4  D5  D6  D7  stop
값:       0     1   0   0   0   0   0   1   0    1
의미:           b0  b1  b2  b3  b4  b5  b6  b7
```

`0x41`의 비트를 LSB부터 나열하면 `1, 0, 0, 0, 0, 0, 1, 0`이다. 이렇게 start와 stop을 포함해 총 10비트가 한 바이트를 이룬다.

### 패리티와 다른 설정

- 패리티(Even/Odd)는 1비트 오류 검출이지만 정정은 못 한다. PC·디버그 시리얼에서는 드물지만, Modbus RTU 같은 산업용 프로토콜은 Even 패리티를 흔히 쓴다.
- 데이터 7비트, stop 2비트를 쓰는 장비도 있다. 상대 매뉴얼의 `8N1` 표기를 그대로 맞춘다.
- 패리티가 있어도 프레임 오류를 모두 잡지는 못한다. 오류 검출이 중요하면 프로토콜에 CRC를 넣는다. 3장에서 다룬다.

## 2.2 보율(baud rate)

보율은 **초당 심볼 수**다. UART는 1심볼이 1비트라 bps와 같다고 봐도 된다.

8N1은 바이트당 10비트(시작 1 + 데이터 8 + 정지 1)를 쓴다. 115200 baud면 이론상 약 **11,520바이트/초**다. 프로토콜 오버헤드와 처리 시간은 별도다. 9600 baud라면 약 960바이트/초다.

흔한 값은 다음과 같다.

```text
9600, 19200, 38400, 57600, 115200, 230400, 460800, 921600
```

**115200**이 기본값처럼 쓰인다. 장치가 115200으로 통신하지 않으면 9600으로 낮춰 원인을 분리해 볼 수 있다.

### 클록 오차

양쪽 클록 오차의 합이 **±2% 안팎**이면 안전하다고 보는 경험칙이 있다. 3%를 넘으면 프레임 오류가 늘기 시작한다. 정확한 한계는 데이터시트의 샘플링 방식과 프레임 길이에 따라 다르다.

MCU의 보율은 클록에서 나눠 만든다. 클록 설정이 틀리면 보율도 틀어진다. 내부 RC 오실레이터로 동작하는 보드에서 고속 시리얼이 깨지는 이유가 여기에 있다. 정확한 통신에는 크리스탈을 쓰는 편이 좋다.

### 왜 "약"이라고 했나

보율은 이론값이고, 실제 전송에는 start/stop 비트, 상대의 처리 시간, USB-UART 내부 버퍼 지연이 더해진다. "115200이면 1초에 11,520바이트를 받는다"는 계산은 순수 전송 시간일 뿐이다. 애플리케이션의 처리 속도가 더 느리면 링 버퍼가 넘친다. 7장에서 이 문제를 다룬다.

## 2.3 전압 레벨: TTL, RS-232, RS-485

같은 "시리얼"이라도 전기 신호가 완전히 다르다. **선을 바로 연결하면 장치가 상할 수 있다.**

| 구분 | 신호 | 레벨 | 특징 |
|---|---|---|---|
| TTL/CMOS UART | 단일 종단 | 0V / 3.3V 또는 5V | MCU·센서·USB-UART 어댑터. 비반전 |
| RS-232 | 단일 종단, 반전 | mark(1) −3~−15V, space(0) +3~+15V | 옛 PC COM 포트. TTL과 직결 금지 |
| RS-485 | 차동(A/B) | 차동 전압 | 반이중 다중 드롭, 산업용. 종단 120Ω |

### TTL/CMOS

MCU와 센서, USB-UART 어댑터가 쓰는 레벨이다. 3.3V 장치와 5V 장치를 연결할 때는 다음을 확인한다.

- 3.3V UART를 5V TTL 입력에 넣는 것은 보통 동작한다. 5V TTL의 VIH가 2.0V라서 3.3V를 high로 인식하기 때문이다.
- 하지만 5V CMOS 입력(VIH ≈ 0.7 × VDD = 3.5V)에는 3.3V가 모자랄 수 있다.
- 반대 방향(5V → 3.3V)은 과전압이다. 레벨 시프터나 분압이 필요하다.
- 핀이 5V tolerant인지는 데이터시트에서 확인한다. "5V tolerant"는 입력 핀에 한정된 경우가 많고, 전원 핀에 5V를 넣어도 된다는 뜻이 아니다.

### RS-232

옛 PC의 9핀 COM 포트가 쓰는 레벨이다. 논리가 반전되어 있고 전압 범위도 TTL과 다르다. `MAX3232` 같은 트랜시버로 TTL과 변환한다. PC의 9핀 포트가 있으면 그 안에 이미 트랜시버가 있다. **RS-232를 TTL 핀에 직결하면 장치가 상한다.**

### RS-485

차동 신호를 쓰는 산업용 버스다. `MAX485`/`SN65HVD` 같은 트랜시버가 필요하고, 송신할 때만 DE를 켰다가 놓아야 한다. 반이중이므로 **말하는 쪽이 하나뿐인지** 프로토콜이 보장해야 한다.

- 양 끝에 120Ω 종단을 두고, 필요하면 바이어스 저항으로 idle 상태를 정한다.
- 표준은 32 unit load지만 1/8 load 트랜시버를 쓰면 더 많이 붙일 수 있다(확인 필요).
- A/B 표기는 제조사에 따라 반대일 수 있다. 통신이 안 되면 A/B를 바꿔 본다. 9장의 실습에서 이 함정을 다시 다룬다.

## 2.4 배선: 교차, 공통 접지, 흐름 제어

### TX와 RX는 교차한다

**TX → RX, RX → TX**로 연결한다. 내보내는 선이 상대의 받는 선으로 가야 한다.

```text
PC/USB-UART                    보드
   TX  ───────────────────────→  RX
   RX  ←───────────────────────  TX
   GND ────────────────────────  GND
```

보드에 적힌 TX/RX가 "이 보드 기준"인지 "상대 기준"인지 헷갈리기 쉽다. 멀티미터로 idle 전압을 재면 TX 선이 high인 쪽을 찾을 수 있다. 8장에서 이 측정을 다룬다.

### 공통 접지가 필수다

TTL UART는 전압이 접지를 기준으로 하므로 **공통 접지가 필수**다. 접지가 없으면 기준이 떠서 쓰레기 값이 나오거나 핀이 상한다. 절연 어댑터를 쓰면 접지를 공유하지 않아도 된다. 차량·산업 장비처럼 접지 전위가 다른 환경에서는 절연이 특히 중요하다.

### 흐름 제어는 대부분 `none`

- 하드웨어 흐름 제어는 RTS/CTS 선을 추가로 연결한다. 상대가 "잠깐 보내지 마"라고 알려 주는 방식이다.
- 소프트웨어 흐름 제어(XON/XOFF)는 `0x11`/`0x13`을 데이터 안에 섞는다. 바이너리 프로토콜에는 부적합하다. payload에 같은 값이 들어가면 흐름 제어 문자로 오인되기 때문이다.
- USB-UART 어댑터 중에는 RTS/CTS가 나오지 않는 것이 많다. ESP32처럼 흐름 제어를 켜는 장치는 어댑터의 핀 노출을 확인한다.

### 케이블 길이

케이블 길이는 TTL에서 짧게(수십 cm~수 m, 보율과 환경에 따라 다름), RS-232는 15m 안팎, RS-485는 낮은 속도에서 1km 이상도 가능하다. 모두 경험칙이며 속도·노이즈·접지에 좌우된다. "RS-485니까 1km"가 아니라 "낮은 속도와 좋은 설치 조건에서 1km"라고 이해해야 한다.

## 2.5 USB-UART 어댑터와 COM 포트

PC에는 UART가 직접 나오지 않는다. USB를 UART로 바꿔 주는 어댑터를 쓴다.

### 대표 칩

| 칩 | 특징 |
|---|---|
| CH340 | 저렴, 드라이버 필요, 클론 주의 |
| CP2102/CP2104 | Silicon Labs |
| FT232 | FTDI, 안정적, 가품 주의 |
| PL2303 | 오래됨, 클론 드라이버 문제 |

### 운영체제별 포트 이름

- Windows: `COM3` 같은 이름
- Linux: `/dev/ttyUSB0`(USB-UART 브리지) 또는 `/dev/ttyACM0`(CDC-ACM)
- macOS: `/dev/cu.usbserial-*`(USB-UART 브리지) 또는 `/dev/cu.usbmodem*`(CDC-ACM)

### 어댑터를 쓸 때의 함정

- 어댑터의 전압 점퍼(3.3V/5V)는 보통 **TX 신호 레벨**을 바꾸지만, 점퍼가 VCC 출력만 바꾸고 TX는 고정인 제품도 있다. 연결 전에 TX idle 전압을 멀티미터로 확인한다.
- VCC 핀은 출력인 경우가 많고 전류가 작다. 모터·릴레이는 어댑터 전원으로 돌리지 않는다.
- USB 케이블 중에는 전원만 연결된 **충전 전용 케이블**이 있다. 장치가 인식되지 않으면 케이블부터 바꿔 본다. 데이터 선이 없는 케이블은 아무리 드라이버를 설치해도 포트가 나타나지 않는다.
- Arduino/ESP32 보드는 포트를 열 때 DTR/RTS 토글로 리셋될 수 있다. 첫 줄이 사라지거나 부트로더에 들어가면 이 동작을 의심한다.
- Windows는 같은 COM 포트를 두 프로그램이 동시에 열 수 없다. 시리얼 모니터를 켜 둔 채 스크립트를 실행하면 `Access is denied`가 난다. 이 오류를 보면 코드보다 **포트를 잡고 있는 다른 프로그램**을 먼저 확인한다.

## 2.6 설정 항목

pyserial 기준으로 다음이 모두 맞아야 한다.

| 항목 | 보통 값 | 틀리면 |
|---|---|---|
| 포트 | COM5, /dev/ttyUSB0 | 열리지 않거나 엉뚱한 장치 |
| 보율 | 115200 | 쓰레기 문자, 프레임 오류 |
| 데이터 비트 | 8 | 문자 깨짐 |
| 패리티 | N | 프레임 오류 |
| stop 비트 | 1 | 프레임 오류 |
| 흐름 제어 | none | 송신 정지, 데이터 유실 |
| 타임아웃 | 0.1~1초 | 영원히 블록, 또는 너무 일찍 포기 |

이 표는 "설정 하나만 틀려도 조용히 깨진다"는 말의 구체적인 모습이다. 특히 보율과 8N1은 상대 매뉴얼을 그대로 따라야 한다. "아마 115200이겠지"로 시작하지 말고 문서를 확인한다.

## 2.7 흔한 증상과 원인

| 증상 | 먼저 볼 것 |
|---|---|
| 아무것도 안 옴 | TX/RX 반대, 접지 누락, 포트 오선택, 충전 전용 케이블 |
| 깨진 문자(`�`, `ÿ`) | 보율 불일치, 8N1 불일치, 클록 설정 오류 |
| 가끔씩만 깨짐 | 접지 불량, 노이즈, 케이블 길이, 전원 불안정 |
| 첫 바이트만 사라짐 | 포트 열 때 보드 리셋, 상대가 초기화 중 |
| 한쪽만 보내고 못 받음 | TX/RX 교차 오류, 흐름 제어, 상대가 반이중 |
| 포트가 사라짐 | USB 전원/케이블, 드라이버, 커넥터 접촉 |
| `Access is denied` | 다른 프로그램이 포트를 잡고 있음 |

증상별로 "코드를 고칠 것"이 거의 없다는 점에 주목하자. UART 문제의 대부분은 전기·배선·설정에서 나온다.

## 2.8 UART와 다른 버스

- **UART**: 비동기, 점대점, 주소 없음, 선 2개(TX/RX) + 접지. 케이블로 나가는 통신, 디버그 콘솔, GPS, 모뎀, RS-485 변환에 적합하다.
- **USART**: 동기 모드(클록 선)도 지원하는 UART 변형이다. 보통은 비동기 UART로 쓴다.
- **I2C**: 동기, 2선, 주소 있음, 보드 안 센서·레지스터. 4장에서 다룬다.
- **SPI**: 동기, 4선, CS로 선택, 고속, 보드 안 플래시·디스플레이. 4장에서 다룬다.
- **CAN**: 차동, 다중 마스터, 중재, 차량·산업. 5장에서 다룬다.

UART에는 주소 개념이 없다. 여러 장치를 한 선에 묶으려면 RS-485 같은 물리 계층과 Modbus 같은 주소 지정 프로토콜이 필요하다. 6장에서 Modbus를 다룬다.

## 2.9 최소 파이썬 예제(uv)

먼저 프로젝트를 만든다.

```bash
uv init uart-demo
cd uart-demo
uv add pyserial
```

다음은 포트를 열고 `ping`을 보낸 뒤 한 줄을 읽는 예제다.

```python
import serial

PORT = "COM5"  # Linux: "/dev/ttyUSB0" 또는 "/dev/ttyACM0", macOS: "/dev/cu.usbserial-..." 또는 "/dev/cu.usbmodem..."

with serial.Serial(PORT, baudrate=115200, bytesize=8, parity="N",
                   stopbits=1, timeout=1) as ser:
    ser.reset_input_buffer()
    ser.write(b"ping\r\n")
    line = ser.readline()
    print(repr(line))
```

- `timeout=1`은 읽기 최대 대기 시간이다. `readline()`은 개행을 만나거나 타임아웃이 되면 지금까지 받은 것을 돌려준다.
- 쓰기 직후 바로 읽지 말고 상대의 처리 시간을 기다린다. 필요하면 `time.sleep()`보다 프로토콜 타임아웃을 쓴다. 고정 `sleep`은 빠른 장치에서도 똑같이 기다리게 만든다.
- 바이너리 프로토콜이면 `readline()` 대신 `read(1)`/`read(n)`과 직접 만든 파서를 쓴다. `readline()`은 개행이 payload에 우연히 들어갈 수 있어 바이너리에 부적합하다.
- `reset_input_buffer()`는 포트를 연 직후 이전에 쌓인 데이터를 버린다. 보드가 리셋되며 남긴 부트 메시지가 첫 응답에 섞이는 것을 줄여 준다.

```bash
uv run python uart_demo.py
```

파일 이름은 예시다. `uv run`은 프로젝트 가상환경에서 실행하므로 `pyserial`이 설치된 인터프리터를 따로 찾을 필요가 없다.

## 2.10 루프백으로 어댑터만 시험하기

코드를 쓰기 전에 어댑터와 드라이버가 살아 있는지 확인하고 싶다면 TX와 RX를 점퍼로 직접 연결한다.

```python
import serial

PORT = "COM5"

with serial.Serial(PORT, 115200, timeout=1) as ser:
    ser.write(b"loopback")
    ser.flush()
    print(ser.read(8))   # b"loopback"이 나와야 한다
```

- 어댑터 자체가 살아 있는지, 드라이버가 붙었는지, 보율이 맞는지를 한 번에 확인한다.
- 여기서 실패하면 보드나 프로토콜을 의심하기 전에 어댑터·케이블·드라이버를 먼저 본다.
- 두 개의 USB-UART를 TX-RX/GND로 교차 연결하면 양방향 시험을 할 수 있다.

## 흔한 실수

| 실수 | 결과 | 확인 |
|---|---|---|
| TX끼리, RX끼리 연결 | 아무것도 안 옴 | TX→RX로 교차 |
| 공통 접지 누락 | 쓰레기 값, 간헐 오류 | GND 연속성 |
| 보율만 맞추고 8N1을 무시 | 프레임 오류, 깨진 문자 | 데이터/패리티/stop 비트 |
| RS-232를 TTL에 직결 | 장치 손상 | MAX3232 등 트랜시버 |
| 5V 신호를 3.3V 핀에 직결 | 핀 손상, 발열 | 레벨 시프터/분압, 5V tolerant 확인 |
| 충전 전용 USB 케이블 | 포트가 안 보임 | 데이터 케이블로 교체 |
| 시리얼 모니터를 켜 둔 채 스크립트 실행 | `Access is denied` | 포트 점유 프로그램 종료 |
| `read()` 반환 길이를 확인하지 않음 | 일부만 받고 파싱 실패 | 반환값과 타임아웃 확인 |
| `readline()`으로 바이너리 읽기 | payload의 개행에서 끊김 | `read(n)` + 파서 |
| `write()` 후 상대가 받았다고 단정 | 간헐 실패 | `flush()`, 처리 시간, 응답 대기 |

## 장 요약

- UART는 클록 선 없이 약속된 보율로 비트를 주고받는 비동기 점대점 통신이다.
- 8N1은 데이터 8비트, 패리티 없음, stop 1비트다. 한 바이트에 10비트를 쓴다.
- 보율과 8N1이 양쪽에서 같아야 한다. 클록 오차가 크면 프레임 오류가 늘어난다.
- TTL·RS-232·RS-485는 전기적으로 완전히 다르다. 직결하지 말고 트랜시버·레벨 시프터를 쓴다.
- TX→RX로 교차하고, 공통 접지를 연결한다. 흐름 제어는 대부분 `none`이다.
- USB-UART 어댑터의 전압 점퍼, 충전 전용 케이블, 포트 점유를 확인한다.
- `read()`는 원하는 만큼 오지 않을 수 있다. 바이너리는 `read(n)`과 직접 만든 파서로 읽는다.
- UART에는 주소가 없다. 여러 장치를 묶으려면 RS-485와 Modbus 같은 상위 계층이 필요하다.
