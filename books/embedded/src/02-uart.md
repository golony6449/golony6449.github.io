# 2장 UART: 가장 단순한 시리얼

## 이 장에서

UART(Universal Asynchronous Receiver/Transmitter)는 가장 흔한 "시리얼 통신"이다. 클록 선 없이 양쪽이 약속한 속도로 비트를 주고받는다. 웹의 소켓보다 훨씬 단순하지만, 그 단순함 때문에 **설정이 하나만 틀려도 조용히 깨진다.**

웹 개발자에게 UART는 낯설게 느껴질 수 있다. 하지만 "연결이 열려 있고, 바이트를 쓰고, 바이트를 읽는다"는 점만 보면 TCP 소켓과 닮았다. 다른 점은 TCP/IP 스택도, 포트 번호도, HTTP 프레이밍도 없다는 것이다. 전선 두 개와 약속된 속도만 있다. 그래서 UART를 이해하면 "프로토콜이란 무엇인가"를 가장 낮은 층에서부터 보게 된다.

이 장에서 다루는 것:

- 8N1 프레임이 실제로 어떻게 생겼는가
- 보율(baud rate)과 클록 오차
- TTL·RS-232·RS-485의 전기적 차이
- TX/RX 교차, 공통 접지, 흐름 제어
- USB-UART 어댑터와 COM 포트
- pyserial로 첫 바이트를 주고받는 방법
- ELM327 OBD 어댑터와 PC 사이의 시리얼 대화(AT 명령, 프롬프트 `>`, 줄 끝 `\r`)

## 2.1 프레임 구조: 8N1

UART는 평소 선이 high(idle)이고, 한 바이트를 다음과 같이 보낸다.

```text
idle  start   D0   D1   D2   D3   D4   D5   D6   D7   stop  idle
 1      0     b0   b1   b2   b3   b4   b5   b6   b7    1     1
```

- start bit는 항상 0이다. 수신측은 high에서 low로 떨어지는 에지를 보고 프레임의 시작을 잡는다.
- 데이터는 보통 **LSB부터** 전송한다.
- stop bit는 항상 1이다. 수신측은 stop bit가 1인지 확인해 프레임 오류를 검출한다.

`8N1`은 **데이터 8비트, 패리티 없음(None), stop 1비트**를 뜻한다. 가장 흔한 설정이다. "8N1"이라는 표기는 시리얼 포트 설정 화면에서 자주 보게 된다.

### 예: 문자 `A`를 보내면

`A`의 ASCII 코드는 `0x41`, 이진수로 `0100 0001`이다. UART는 LSB부터 보내므로 전선 위에서는 다음과 같이 된다.

```text
비트:   start  D0  D1  D2  D3  D4  D5  D6  D7  stop
값:       0     1   0   0   0   0   0   1   0    1
의미:           b0  b1  b2  b3  b4  b5  b6  b7
```

`0x41`의 비트를 LSB부터 나열하면 `1, 0, 0, 0, 0, 0, 1, 0`이다. 이렇게 start와 stop을 포함해 총 10비트가 한 바이트를 이룬다.

### 패리티와 다른 설정

- 패리티(Even/Odd)는 1비트 오류 검출이지만 정정은 못 한다. PC·디버그 시리얼에서는 드물지만, Modbus RTU 같은 산업용 프로토콜은 Even 패리티를 흔히 쓴다.
- 데이터 7비트, stop 2비트를 쓰는 장비도 있다. 상대 매뉴얼의 `8N1` 표기를 그대로 맞춘다.
- 패리티가 있어도 프레임 오류를 모두 잡지는 못한다. 오류 검출이 중요하면 프로토콜에 CRC를 넣는다. 3장에서 다룬다.

## 2.2 보율(baud rate)

보율은 **초당 심볼 수**다. UART는 1심볼이 1비트라 bps와 같다고 봐도 된다.

8N1은 바이트당 10비트(시작 1 + 데이터 8 + 정지 1)를 쓴다. 115200 baud면 이론상 약 **11,520바이트/초**다. 프로토콜 오버헤드와 처리 시간은 별도다. 9600 baud라면 약 960바이트/초다.

흔한 값은 다음과 같다.

```text
9600, 19200, 38400, 57600, 115200, 230400, 460800, 921600
```

**115200**이 기본값처럼 쓰인다. 장치가 115200으로 통신하지 않으면 9600으로 낮춰 원인을 분리해 볼 수 있다.

### 클록 오차

양쪽 클록 오차의 합이 **±2% 안팎**이면 안전하다고 보는 경험칙이 있다. 3%를 넘으면 프레임 오류가 늘기 시작한다. 정확한 한계는 데이터시트의 샘플링 방식과 프레임 길이에 따라 다르다.

MCU의 보율은 클록에서 나눠 만든다. 클록 설정이 틀리면 보율도 틀어진다. 내부 RC 오실레이터로 동작하는 보드에서 고속 시리얼이 깨지는 이유가 여기에 있다. 정확한 통신에는 크리스탈을 쓰는 편이 좋다.

### 왜 "약"이라고 했나

보율은 이론값이고, 실제 전송에는 start/stop 비트, 상대의 처리 시간, USB-UART 내부 버퍼 지연이 더해진다. "115200이면 1초에 11,520바이트를 받는다"는 계산은 순수 전송 시간일 뿐이다. 애플리케이션의 처리 속도가 더 느리면 링 버퍼가 넘친다. 13장에서 이 문제를 다룬다.

## 2.3 전압 레벨: TTL, RS-232, RS-485

같은 "시리얼"이라도 전기 신호가 완전히 다르다. **선을 바로 연결하면 장치가 상할 수 있다.**

| 구분 | 신호 | 레벨 | 특징 |
|---|---|---|---|
| TTL/CMOS UART | 단일 종단 | 0V / 3.3V 또는 5V | MCU·센서·USB-UART 어댑터. 비반전 |
| RS-232 | 단일 종단, 반전 | mark(1) −3~−15V, space(0) +3~+15V | 옛 PC COM 포트. TTL과 직결 금지 |
| RS-485 | 차동(A/B) | 차동 전압 | 반이중 다중 드롭, 산업용. 종단 120Ω |

### TTL/CMOS

MCU와 센서, USB-UART 어댑터가 쓰는 레벨이다. 3.3V 장치와 5V 장치를 연결할 때는 다음을 확인한다.

- 3.3V UART를 5V TTL 입력에 넣는 것은 보통 동작한다. 5V TTL의 VIH가 2.0V라서 3.3V를 high로 인식하기 때문이다.
- 하지만 5V CMOS 입력(VIH ≈ 0.7 × VDD = 3.5V)에는 3.3V가 모자랄 수 있다.
- 반대 방향(5V → 3.3V)은 과전압이다. 레벨 시프터나 분압이 필요하다.
- 핀이 5V tolerant인지는 데이터시트에서 확인한다. "5V tolerant"는 입력 핀에 한정된 경우가 많고, 전원 핀에 5V를 넣어도 된다는 뜻이 아니다.

### RS-232

옛 PC의 9핀 COM 포트가 쓰는 레벨이다. 논리가 반전되어 있고 전압 범위도 TTL과 다르다. `MAX3232` 같은 트랜시버로 TTL과 변환한다. PC의 9핀 포트가 있으면 그 안에 이미 트랜시버가 있다. **RS-232를 TTL 핀에 직결하면 장치가 상한다.**

### RS-485

차동 신호를 쓰는 산업용 버스다. `MAX485`/`SN65HVD` 같은 트랜시버가 필요하고, 송신할 때만 DE를 켰다가 놓아야 한다. 반이중이므로 **말하는 쪽이 하나뿐인지** 프로토콜이 보장해야 한다.

- 양 끝에 120Ω 종단을 두고, 필요하면 바이어스 저항으로 idle 상태를 정한다.
- 표준은 32 unit load지만 1/8 load 트랜시버를 쓰면 더 많이 붙일 수 있다(확인 필요).
- A/B 표기는 제조사에 따라 반대일 수 있다. 통신이 안 되면 A/B를 바꿔 본다. 36장의 실습에서 이 함정을 다시 다룬다.

## 2.4 배선: 교차, 공통 접지, 흐름 제어

### TX와 RX는 교차한다

**TX → RX, RX → TX**로 연결한다. 내보내는 선이 상대의 받는 선으로 가야 한다.

```text
PC/USB-UART                    보드
   TX  ───────────────────────→  RX
   RX  ←───────────────────────  TX
   GND ────────────────────────  GND
```

보드에 적힌 TX/RX가 "이 보드 기준"인지 "상대 기준"인지 헷갈리기 쉽다. 멀티미터로 idle 전압을 재면 TX 선이 high인 쪽을 찾을 수 있다. 14장에서 이 측정을 다룬다.

### 공통 접지가 필수다

TTL UART는 전압이 접지를 기준으로 하므로 **공통 접지가 필수**다. 접지가 없으면 기준이 떠서 쓰레기 값이 나오거나 핀이 상한다. 절연 어댑터를 쓰면 접지를 공유하지 않아도 된다. 차량·산업 장비처럼 접지 전위가 다른 환경에서는 절연이 특히 중요하다.

### 흐름 제어는 대부분 `none`

- 하드웨어 흐름 제어는 RTS/CTS 선을 추가로 연결한다. 상대가 "잠깐 보내지 마"라고 알려 주는 방식이다.
- 소프트웨어 흐름 제어(XON/XOFF)는 `0x11`/`0x13`을 데이터 안에 섞는다. 바이너리 프로토콜에는 부적합하다. payload에 같은 값이 들어가면 흐름 제어 문자로 오인되기 때문이다.
- USB-UART 어댑터 중에는 RTS/CTS가 나오지 않는 것이 많다. ESP32처럼 흐름 제어를 켜는 장치는 어댑터의 핀 노출을 확인한다.

### 케이블 길이

케이블 길이는 TTL에서 짧게(수십 cm~수 m, 보율과 환경에 따라 다름), RS-232는 15m 안팎, RS-485는 낮은 속도에서 1km 이상도 가능하다. 모두 경험칙이며 속도·노이즈·접지에 좌우된다. "RS-485니까 1km"가 아니라 "낮은 속도와 좋은 설치 조건에서 1km"라고 이해해야 한다.

## 2.5 USB-UART 어댑터와 COM 포트

PC에는 UART가 직접 나오지 않는다. USB를 UART로 바꿔 주는 어댑터를 쓴다.

### 대표 칩

| 칩 | 특징 |
|---|---|
| CH340 | 저렴, 드라이버 필요, 클론 주의 |
| CP2102/CP2104 | Silicon Labs |
| FT232 | FTDI, 안정적, 가품 주의 |
| PL2303 | 오래됨, 클론 드라이버 문제 |

ELM327 어댑터 중에는 CH340을 쓰는 저가 제품이 많다. 실차 기록에서도 CH340 기반 어댑터가 `COM5`/`COM6`으로 잡혔다. CH340 자체는 나쁘지 않지만, 드라이버 버전·USB 케이블·허브·노트북 전원에 따라 장치가 사라질 수 있다. **통신이 끊길 때 앱 로그만 보지 말고 Windows 장치 관리자와 이벤트 로그를 함께 본다.**

### 운영체제별 포트 이름

- Windows: `COM3` 같은 이름
- Linux: `/dev/ttyUSB0`(USB-UART 브리지) 또는 `/dev/ttyACM0`(CDC-ACM)
- macOS: `/dev/cu.usbserial-*`(USB-UART 브리지) 또는 `/dev/cu.usbmodem*`(CDC-ACM)

### 어댑터를 쓸 때의 함정

- 어댑터의 전압 점퍼(3.3V/5V)는 보통 **TX 신호 레벨**을 바꾸지만, 점퍼가 VCC 출력만 바꾸고 TX는 고정인 제품도 있다. 연결 전에 TX idle 전압을 멀티미터로 확인한다.
- VCC 핀은 출력인 경우가 많고 전류가 작다. 모터·릴레이는 어댑터 전원으로 돌리지 않는다.
- USB 케이블 중에는 전원만 연결된 **충전 전용 케이블**이 있다. 장치가 인식되지 않으면 케이블부터 바꿔 본다. 데이터 선이 없는 케이블은 아무리 드라이버를 설치해도 포트가 나타나지 않는다.
- Arduino/ESP32 보드는 포트를 열 때 DTR/RTS 토글로 리셋될 수 있다. 첫 줄이 사라지거나 부트로더에 들어가면 이 동작을 의심한다.
- Windows는 같은 COM 포트를 두 프로그램이 동시에 열 수 없다. 시리얼 모니터를 켜 둔 채 스크립트를 실행하면 `Access is denied`가 난다. 이 오류를 보면 코드보다 **포트를 잡고 있는 다른 프로그램**을 먼저 확인한다.

## 2.6 설정 항목

pyserial 기준으로 다음이 모두 맞아야 한다.

| 항목 | 보통 값 | 틀리면 |
|---|---|---|
| 포트 | COM5, /dev/ttyUSB0 | 열리지 않거나 엉뚱한 장치 |
| 보율 | 115200 | 쓰레기 문자, 프레임 오류 |
| 데이터 비트 | 8 | 문자 깨짐 |
| 패리티 | N | 프레임 오류 |
| stop 비트 | 1 | 프레임 오류 |
| 흐름 제어 | none | 송신 정지, 데이터 유실 |
| 타임아웃 | 0.1~1초 | 영원히 블록, 또는 너무 일찍 포기 |
| 줄 끝 | ELM327은 `\r`, 일반 텍스트는 `\n`/`\r\n` | 명령이 안 먹거나 빈 명령이 감 |

이 표는 "설정 하나만 틀려도 조용히 깨진다"는 말의 구체적인 모습이다. 특히 보율과 8N1은 상대 매뉴얼을 그대로 따라야 한다. "아마 115200이겠지"로 시작하지 말고 문서를 확인한다.

ELM327은 여기에 **프로토콜 설정**이 하나 더 있다. 시리얼 보율이 맞아도 `ATSP`가 차량 프로토콜과 다르면 `UNABLE TO CONNECT`나 `NO DATA`가 난다. 보통은 `ATSP0`(자동)로 시작하고, `ATDPN`으로 실제 선택된 프로토콜을 확인한다. 쏘렌토에서는 `A6`(ISO 15765-4 CAN 11비트 500k)이 나왔다(실차 기록).

## 2.7 흔한 증상과 원인

| 증상 | 먼저 볼 것 |
|---|---|
| 아무것도 안 옴 | TX/RX 반대, 접지 누락, 포트 오선택, 충전 전용 케이블 |
| 깨진 문자(`�`, `ÿ`) | 보율 불일치, 8N1 불일치, 클록 설정 오류 |
| 가끔씩만 깨짐 | 접지 불량, 노이즈, 케이블 길이, 전원 불안정 |
| 첫 바이트만 사라짐 | 포트 열 때 보드 리셋, 상대가 초기화 중 |
| 한쪽만 보내고 못 받음 | TX/RX 교차 오류, 흐름 제어, 상대가 반이중 |
| 포트가 사라짐 | USB 전원/케이블, 드라이버, 커넥터 접촉 |
| `Access is denied` | 다른 프로그램이 포트를 잡고 있음 |
| ELM327 `NO DATA` | 시동 OFF, 프로토콜 불일치, PID 미지원, 헤더/필터, `ATST` |
| ELM327 `?` | 명령 오타, 공백, 클론 미지원 명령 |
| ELM327 `STOPPED` | 프롬프트 전에 다음 명령을 보냄 |
| ELM327 `BUFFER FULL` | 보율이 낮거나 소비가 느림, 다중 프레임 과다 |
| ELM327 `UNABLE TO CONNECT` | OBD 포트 체결, 시동, 차량 프로토콜 |
| ELM327 `LV RESET` | 배터리 전압 강하, 크랭킹, USB 전원 |

증상별로 "코드를 고칠 것"이 거의 없다는 점에 주목하자. UART 문제의 대부분은 전기·배선·설정에서 나온다.

## 2.8 UART와 다른 버스

- **UART**: 비동기, 점대점, 주소 없음, 선 2개(TX/RX) + 접지. 케이블로 나가는 통신, 디버그 콘솔, GPS, 모뎀, RS-485 변환에 적합하다.
- **USART**: 동기 모드(클록 선)도 지원하는 UART 변형이다. 보통은 비동기 UART로 쓴다.
- **I2C**: 동기, 2선, 주소 있음, 보드 안 센서·레지스터. 6장에서 다룬다.
- **SPI**: 동기, 4선, CS로 선택, 고속, 보드 안 플래시·디스플레이. 6장에서 다룬다.
- **CAN**: 차동, 다중 마스터, 중재, 차량·산업. 7장에서 다룬다.

UART에는 주소 개념이 없다. 여러 장치를 한 선에 묶으려면 RS-485 같은 물리 계층과 Modbus 같은 주소 지정 프로토콜이 필요하다. 12장에서 Modbus를 다룬다.

## 2.9 ELM327: UART 위에 올라간 OBD 어댑터

ELM327은 OBD-II 포트와 PC를 이어 주는 작은 인터프리터다. 차량 쪽에서는 여러 OBD 프로토콜(CAN, KWP, J1850 등)을 해석하고, PC 쪽에서는 **평범한 UART/RS-232 시리얼**로 말한다. 그래서 ELM327을 이해하는 가장 빠른 길은 "UART로 AT 명령을 주고받는 장치"로 보는 것이다.

```text
[PC] ── USB ── [USB-UART 칩] ── UART TX/RX ── [ELM327 MCU] ── CAN 트랜시버 ── [차량 OBD 포트]
      COM5/COM6               38400 또는 9600/115200 8N1              CAN_H/CAN_L
```

시리얼 설정은 대개 다음과 같다.

| 항목 | 값 | 비고 |
|---|---|---|
| 보율 | 38400(많음), 9600, 115200 | 제품·클론마다 다르다. `ATI`가 응답하는 보율을 찾는다 |
| 데이터/패리티/stop | 8N1 | 거의 항상 8N1 |
| 흐름 제어 | none | RTS/CTS를 쓰는 제품은 드물다 |
| 줄 끝 | `\r`(CR) | ELM327은 CR로 명령을 끝낸다. `\r\n`을 보내면 빈 명령이 하나 더 갈 수 있다 |
| 프롬프트 | `>` | 응답이 끝났다는 표시. 다음 명령은 프롬프트를 본 뒤 보낸다 |

### AT 명령

ELM327은 Hayes 모뎀과 비슷한 `AT` 명령을 쓴다. 자주 쓰는 것만 추려 보면 다음과 같다.

| 명령 | 뜻 | 비고 |
|---|---|---|
| `ATZ` | 전체 리셋 | 첫 응답이 `ELM327 v...`로 온다. 늦게 오면 `STOPPED`가 먼저 올 수 있다 |
| `ATI` | 버전 출력 | 클론이 `v1.5`를 보고하는 경우가 있다. v1.5는 실제 ELM Electronics 버전이 아니다 |
| `ATE0` / `ATE1` | 에코 끄기/켜기 | 스크립트에서는 끈다 |
| `ATL0` / `ATL1` | LF 끄기/켜기 | 응답을 `\r`만으로 끝내 간단해진다 |
| `ATS0` / `ATS1` | 공백 끄기/켜기 | `ATS0`이면 `410C1AF8`처럼 붙어 온다. 파서가 두 형식을 처리해야 한다 |
| `ATSP0` | 프로토콜 자동 검색 | 차량에 맞는 프로토콜을 찾는다 |
| `ATSP6` | ISO 15765-4 CAN 11비트 500k 고정 | 쏘렌토에서 확인된 설정 |
| `ATDPN` | 현재 프로토콜 번호 | `A6`이면 자동 검색 후 프로토콜 6 |
| `ATRV` | 배터리 전압 읽기 | 대략 12V 이상인지 확인 |
| `ATH0` / `ATH1` | 헤더 숨김/표시 | `ATH1`이면 `7E8 04 41 0C ...`처럼 CAN ID와 PCI가 보인다 |
| `ATSH7E0` | 요청 헤더 설정 | 특정 ECU에 물리 주소로 보낼 때 |
| `ATCRA7E8` | 수신 주소 필터 | 헤더를 바꾼 뒤 응답을 받을 때 |
| `ATAR` | 수신 필터 자동으로 | 클론에서 `ATCRA` 인자 없이 보내면 `?`가 오는 경우가 있다 |
| `ATST hh` | 응답 대기 시간 | hh × 4ms. 차량·ECU에 따라 조정 |
| `ATFCSH`, `ATFCSD`, `ATFCSM` | ISO-TP 흐름 제어 수동 설정 | 표준 밖 주소로 다중 프레임을 받을 때 |

명령은 대소문자를 가리지 않지만, 스크립트에서는 대문자로 통일하는 편이 읽기 좋다. `AT SH 7E0`처럼 공백을 넣어도 되고 `ATSH7E0`처럼 붙여도 된다. 제품에 따라 공백 처리나 긴 명령 지원이 조금씩 다르므로, 클론에서는 짧은 형식을 먼저 시도한다.

### 첫 대화

```text
PC → ATZ\r
ELM327 → ATZ\r\n\r\nELM327 v1.5\r\n\r\n>   ← ATL1(기본)이라 CR 뒤에 LF가 붙는다

PC → ATE0\r
ELM327 → OK\r\n\r\n>

PC → ATL0\r
ELM327 → OK\r\r>                       ← ATL0 이후에는 LF가 없다

PC → ATSP0\r
ELM327 → OK\r\r>

PC → 010C\r
ELM327 → SEARCHING...\r41 0C 1A F8\r\r>
```

- `ATL1`이 기본이라 첫 응답에는 `\n`이 붙는다. `ATL0`을 보낸 뒤부터는 `\r`만 온다. 파서는 둘 다 처리해야 한다.
- 에코가 켜져 있으면 내가 보낸 명령도 돌아온다. `ATE0`은 그 에코를 끈다.

- `SEARCHING...`은 프로토콜을 찾는 중이라는 뜻이다. 첫 요청에서만 나올 수 있다.
- 응답 `41 0C 1A F8`은 "Mode 01, PID 0C, 데이터 1A F8"이다. 9장에서 이 값을 회전수로 바꾼다.
- `>`가 오기 전에 다음 명령을 보내면 ELM327이 현재 작업을 중단하고 `STOPPED`를 출력할 수 있다. **프롬프트를 기다리는 것이 프로토콜의 일부**다.
- `ATSP0`는 모든 프로토콜을 순서대로 시도하므로 몇 초 걸릴 수 있다. 이 명령만 타임아웃을 길게 잡는다.

### 응답이 이상할 때

| 응답 | 뜻 | 확인 |
|---|---|---|
| `SEARCHING...` | 프로토콜 검색 중 | 잠시 기다린다. 첫 요청에서 흔하다 |
| `NO DATA` | 정해진 시간 안에 차량 응답 없음 | 시동, 프로토콜, PID 지원, 헤더/필터, `ATST` 확인 |
| `?` | 명령을 이해하지 못함 | 오타, 공백, 클론이 지원하지 않는 명령 |
| `STOPPED` | 명령 수행 중 시리얼 입력이 들어와 중단 | 프롬프트를 기다리지 않고 보냈는지 확인 |
| `BUFFER FULL` | ELM327 내부 버퍼(512바이트)가 참 | 보율을 높이고, 헤더/공백을 끄고, 필터를 좁힌다 |
| `UNABLE TO CONNECT` | 모든 프로토콜 시도 실패 | 시동이 OFF인지, OBD 포트 체결, 차량 프로토콜 확인 |
| `CAN ERROR` | CAN 초기화/송수신 문제 | 배선, 비트레이트, 6/14번 핀, 종단 |
| `LV RESET` | 전압 강하로 어댑터 리셋 | 배터리 전압, 크랭킹, USB 전원 |

`NO DATA`는 "차가 고장났다"는 뜻이 아니다. ELM327이 정한 시간 안에 응답이 없었다는 뜻일 뿐이다. 시동이 꺼져 있으면 응답하지 않는 ECU가 많고, 어떤 PID는 엔진이 돌아야만 응답한다. 실차 기록에서도 엔진이 돌 때만 응답하는 DID가 있었다.

### 클론과 USB 함정

ELM327은 원래 Elm Electronics가 만들었지만, v1.4 펌웨어가 복제되면서 저가 클론이 널리 퍼졌다. 클론은 존재하지 않는 `v1.5`를 보고하기도 하고, 일부 AT 명령의 인자 처리나 다중 프레임 버퍼링이 원본과 다르다. 실차 기록에서 확인된 것들은 다음과 같다.

- `ATCRA`를 인자 없이 보내면 `?`가 오는 클론이 있다. `ATAR`로 필터를 푼다.
- 7E0~7E7 밖의 주소로 요청할 때는 `ATCRA <응답 주소>`, `ATFCSH <요청 주소>`, `ATFCSD 30 00 00`, `ATFCSM 1`을 함께 설정해야 다중 프레임 응답이 온다.
- 긴 다중 프레임 응답에서 `BUFFER FULL`이 나고, 다음 응답에 이전 프레임이 섞이는 경우가 있다. 요청 전에 입력 버퍼를 비우고, `BUFFER FULL`이 낀 응답은 버린다.
- `ATZ` 응답이 `STOPPED`면 리셋이 실행되지 않았을 수 있다. 한 번 더 `\r`을 보내거나 다시 `ATZ`한다.

USB 쪽도 함정이 있다. CH340 계열 어댑터는 저렴하지만 드라이버·케이블·전원에 민감하다. 실차 기록에서는 주행 중 USB 장치가 버스에서 누락되어 통신이 끊긴 사례가 있었고, 재연결 후 COM 번호가 `COM5`에서 `COM6`으로 바뀌었다. Windows 이벤트 로그의 `USB\VID_1A86&PID_7523` 같은 항목이 단서가 된다. **포트가 사라지면 코드보다 케이블·허브·전원·드라이버를 먼저 본다.**

## 2.10 최소 파이썬 예제(uv)

먼저 프로젝트를 만든다.

```bash
uv init uart-demo
cd uart-demo
uv add pyserial
```

다음은 포트를 열고 `ping`을 보낸 뒤 한 줄을 읽는 예제다.

```python
import serial

PORT = "COM5"  # Linux: "/dev/ttyUSB0" 또는 "/dev/ttyACM0", macOS: "/dev/cu.usbserial-..." 또는 "/dev/cu.usbmodem..."

with serial.Serial(PORT, baudrate=115200, bytesize=8, parity="N",
                   stopbits=1, timeout=1) as ser:
    ser.reset_input_buffer()
    ser.write(b"ping\r\n")
    line = ser.readline()
    print(repr(line))
```

- `timeout=1`은 읽기 최대 대기 시간이다. `readline()`은 개행을 만나거나 타임아웃이 되면 지금까지 받은 것을 돌려준다.
- 쓰기 직후 바로 읽지 말고 상대의 처리 시간을 기다린다. 필요하면 `time.sleep()`보다 프로토콜 타임아웃을 쓴다. 고정 `sleep`은 빠른 장치에서도 똑같이 기다리게 만든다.
- 바이너리 프로토콜이면 `readline()` 대신 `read(1)`/`read(n)`과 직접 만든 파서를 쓴다. `readline()`은 개행이 payload에 우연히 들어갈 수 있어 바이너리에 부적합하다.
- `reset_input_buffer()`는 포트를 연 직후 이전에 쌓인 데이터를 버린다. 보드가 리셋되며 남긴 부트 메시지가 첫 응답에 섞이는 것을 줄여 준다.

### 실행

```bash
uv run python uart_demo.py
```

파일 이름은 예시다. `uv run`은 프로젝트 가상환경에서 실행하므로 `pyserial`이 설치된 인터프리터를 따로 찾을 필요가 없다.

### ELM327에 명령 보내기

ELM327은 `\r`로 끝나는 명령을 받고, `\r`로 끝나는 줄과 프롬프트 `>`로 응답한다. pyserial의 `readline()`은 `\n`을 찾으므로 ELM327에는 잘 맞지 않는다. **프롬프트 `>`를 만날 때까지 읽는** 작은 래퍼를 만든다.

```python
import time
import serial


class Elm327:
    def __init__(self, port: str, baudrate: int = 38400, timeout: float = 1.0):
        self.ser = serial.Serial(port, baudrate, timeout=0.1)
        self.timeout = timeout

    def close(self) -> None:
        self.ser.close()

    def command(self, cmd: str, timeout: float | None = None) -> list[str]:
        """AT 명령 또는 OBD 요청을 보내고, 프롬프트 '>'까지 읽어 줄 목록으로 돌려준다."""
        timeout = self.timeout if timeout is None else timeout
        self.ser.reset_input_buffer()
        self.ser.write((cmd + "\r").encode("ascii"))
        self.ser.flush()

        buf = bytearray()
        deadline = time.monotonic() + timeout
        while time.monotonic() < deadline:
            chunk = self.ser.read(1)
            if not chunk:
                continue
            buf.extend(chunk)
            if chunk == b">":
                break
        else:
            raise TimeoutError(f"{cmd!r} 응답에 프롬프트가 없습니다: {buf!r}")

        text = buf.decode("ascii", errors="replace").replace("\r", "\n")
        lines = []
        for line in text.split("\n"):
            line = line.strip()
            if not line or line == ">" or line == cmd:  # 에코·프롬프트·빈 줄 제거
                continue
            lines.append(line)
        return lines


elm = Elm327("COM5", baudrate=38400)  # Linux: /dev/ttyUSB0, macOS: /dev/cu.usbserial-...
try:
    print(elm.command("ATZ", timeout=3))       # ['ELM327 v1.5'] 같은 버전 문자열
    print(elm.command("ATE0"))                 # ['OK']
    print(elm.command("ATL0"))
    print(elm.command("ATSP0", timeout=10))    # 프로토콜 자동 검색은 오래 걸릴 수 있다
    print(elm.command("ATDPN"))                # 예: ['A6']
    print(elm.command("010C"))                 # 예: ['41 0C 1A F8']
finally:
    elm.close()
```

- `ATSP0`는 모든 프로토콜을 시도하므로 타임아웃을 10초 정도로 길게 준다.
- `read(1)` 루프는 바이트가 올 때마다 반환된다. `timeout=0.1`은 "0.1초 안에 바이트가 없으면 빈 값을 돌려준다"는 뜻이고, 전체 명령 타임아웃은 `deadline`으로 따로 잰다.
- `SEARCHING...`이 첫 응답에 섞이면 `lines`에 함께 들어온다. 파서에서 무시하거나 상태 메시지로 처리한다.
- 클론의 보율을 모르면 38400, 9600, 115200 순으로 `ATI`를 시도한다. 응답이 깨지면 보율이 맞지 않는 것이다.
- `ATZ` 직후에는 어댑터가 리셋되므로 1~2초 기다리거나 프롬프트를 기다린다.

이 코드는 ELM327이 없어도 `serial.serial_for_url("loop://")`로 일부를 시험할 수 있다. 다만 실제 ELM327의 `\r`·프롬프트 동작은 가짜 시리얼과 다를 수 있으므로, 9장에서 실제 어댑터 응답을 녹화한 로그로 리플레이 테스트를 만든다.

## 2.11 루프백으로 어댑터만 시험하기

코드를 쓰기 전에 어댑터와 드라이버가 살아 있는지 확인하고 싶다면 TX와 RX를 점퍼로 직접 연결한다.

```python
import serial

PORT = "COM5"

with serial.Serial(PORT, 115200, timeout=1) as ser:
    ser.write(b"loopback")
    ser.flush()
    print(ser.read(8))   # b"loopback"이 나와야 한다
```

- 어댑터 자체가 살아 있는지, 드라이버가 붙었는지, 보율이 맞는지를 한 번에 확인한다.
- 여기서 실패하면 보드나 프로토콜을 의심하기 전에 어댑터·케이블·드라이버를 먼저 본다.
- 두 개의 USB-UART를 TX-RX/GND로 교차 연결하면 양방향 시험을 할 수 있다.

## 흔한 실수

| 실수 | 결과 | 확인 |
|---|---|---|
| TX끼리, RX끼리 연결 | 아무것도 안 옴 | TX→RX로 교차 |
| 공통 접지 누락 | 쓰레기 값, 간헐 오류 | GND 연속성 |
| 보율만 맞추고 8N1을 무시 | 프레임 오류, 깨진 문자 | 데이터/패리티/stop 비트 |
| RS-232를 TTL에 직결 | 장치 손상 | MAX3232 등 트랜시버 |
| 5V 신호를 3.3V 핀에 직결 | 핀 손상, 발열 | 레벨 시프터/분압, 5V tolerant 확인 |
| 충전 전용 USB 케이블 | 포트가 안 보임 | 데이터 케이블로 교체 |
| 시리얼 모니터를 켜 둔 채 스크립트 실행 | `Access is denied` | 포트 점유 프로그램 종료 |
| `read()` 반환 길이를 확인하지 않음 | 일부만 받고 파싱 실패 | 반환값과 타임아웃 확인 |
| `readline()`으로 바이너리 읽기 | payload의 개행에서 끊김 | `read(n)` + 파서 |
| `write()` 후 상대가 받았다고 단정 | 간헐 실패 | `flush()`, 처리 시간, 응답 대기 |
| ELM327에 `\n` 또는 `\r\n`으로 명령 | 빈 명령, `?`, 응답 어긋남 | `\r`로 끝내고 프롬프트 `>`를 기다린다 |
| 프롬프트 전에 다음 명령 전송 | `STOPPED`, 응답 섞임 | `>`를 본 뒤 보낸다 |
| ELM327 보율을 115200으로 단정 | 깨진 문자, 응답 없음 | 38400/9600/115200을 시도하고 `ATI`로 확인 |
| `NO DATA`를 코드 버그로 판단 | 엉뚱한 수정 | 시동·프로토콜·PID·필터를 먼저 확인 |

## 장 요약

- UART는 클록 선 없이 약속된 보율로 비트를 주고받는 비동기 점대점 통신이다.
- 8N1은 데이터 8비트, 패리티 없음, stop 1비트다. 한 바이트에 10비트를 쓴다.
- 보율과 8N1이 양쪽에서 같아야 한다. 클록 오차가 크면 프레임 오류가 늘어난다.
- TTL·RS-232·RS-485는 전기적으로 완전히 다르다. 직결하지 말고 트랜시버·레벨 시프터를 쓴다.
- TX→RX로 교차하고, 공통 접지를 연결한다. 흐름 제어는 대부분 `none`이다.
- USB-UART 어댑터의 전압 점퍼, 충전 전용 케이블, 포트 점유를 확인한다.
- `read()`는 원하는 만큼 오지 않을 수 있다. 바이너리는 `read(n)`과 직접 만든 파서로 읽는다.
- UART에는 주소가 없다. 여러 장치를 묶으려면 RS-485와 Modbus 같은 상위 계층이 필요하다.
- ELM327은 UART 위에서 AT 명령과 OBD 요청을 받는다. 명령은 `\r`로 끝내고 프롬프트 `>`를 기다린다.
- ELM327의 보율은 38400/9600/115200 후보를 시도하고, `ATSP0` 뒤 `ATDPN`으로 프로토콜을 확인한다.
- `NO DATA`, `?`, `STOPPED`, `BUFFER FULL`, `UNABLE TO CONNECT`는 서로 다른 문제다. 응답 문자열을 구분해 처리한다.

다음 장에서는 UART로 들어온 바이트 더미에서 **메시지의 경계**를 찾아내는 방법을 다룬다. ELM327의 줄 응답과 ISO-TP 다중 프레임이 좋은 실습 대상이다. 이 책에서 가장 중요한 장이다.

## 정답과 해설

### 1.

1. `38400 / 10 = 3840B/s`
2. `100 / 3840 = 0.02604s ≈ 26.0ms`
3. `9600 / 10 = 960B/s`, `100 / 960 ≈ 104.2ms`

### 2.

1. MCU TX → 어댑터 RX, MCU RX → 어댑터 TX. 이름이 같은 것끼리 연결하지 않는다.
2. 두 장치의 전압 기준(0V)을 맞추기 위해서다. 접지가 없으면 논리 레벨이 떠서 오작동하거나 손상될 수 있다.
3. RS-232는 ±수 V의 큰 전압을 쓰므로 MCU 핀이 손상된다. MAX3232 같은 트랜시버로 레벨을 바꾼다.

### 3.

1. 요청에 대한 응답이 없다. PID 미지원, 시동 상태, 타임아웃, 필터를 확인한다.
2. 명령을 이해하지 못했다. 오타이거나 클론이 지원하지 않는 AT 명령이다.
3. 명령이 중단됐다. `ATZ`가 제대로 실행되지 않았을 수 있으니 다시 보낸다.
4. 어댑터 버퍼가 찼다. 보율·출력 설정·수신 필터를 조정하고, 응답을 읽는 속도를 높인다.

### 4.

1. 시리얼은 바이트 스트림이라 `read(n)`이 항상 n바이트를 기다리지 않는다. 타임아웃 안에 온 만큼만 돌려준다.
2. `deadline`을 정하고, 받은 바이트 수가 10이 될 때까지 `read(남은 수)`를 반복한다. 타임아웃이면 부분 데이터를 버리거나 오류로 처리한다.
3. 개행 문자 같은 **구분자**가 반드시 와야 한다. 바이너리 데이터에는 `readline()`을 쓰지 않는다.

### 5.

start 1 + data 8 + parity 1 + stop 1 = 11비트. `38400 / 11 ≈ 3490.9B/s`.
