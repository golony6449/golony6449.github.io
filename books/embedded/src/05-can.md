# 5장 CAN: 여러 노드가 말하는 버스

## 이 장에서

CAN(Controller Area Network)은 차량과 산업 현장에서 쓰는 **차동 신호 기반의 다중 마스터 버스**다. UART처럼 두 장치가 점대점으로 말하는 방식이 아니라, 여러 노드가 한 쌍의 선을 공유하며 **ID 우선순위로 중재**하고 하드웨어가 오류를 검출한다.

웹 개발자에게 CAN은 "브로커가 없는 pub/sub"처럼 보일 수 있다. 여러 노드가 같은 버스에 메시지를 던지고, 관심 있는 노드가 ID로 걸러 받는다. 하지만 결정적인 차이가 있다. 웹의 메시지 브로커는 메시지를 저장하고 재전달하지만, CAN은 저장하지 않는다. 버스가 바쁘면 우선순위가 낮은 메시지는 밀리고, 수신 노드가 없으면 송신 자체가 실패한다. **"보냈다"와 "받았다"가 웹과 전혀 다른 의미**를 갖는다.

이 장은 CAN의 일반 원리만 다룬다. 차량 진단(OBD-II·UDS·ELM327)의 실무는 이 책에서 다루지 않는다.

## 5.1 CAN이 푸는 문제

- 여러 ECU가 같은 버스에서 말한다. 노드를 추가해도 배선이 크게 늘지 않는다.
- 충돌을 피하는 대신 **중재**한다. 우선순위가 높은 메시지가 먼저 나가고, 진 노드는 자동으로 물러난다.
- 잡음에 강한 차동 신호를 쓰고, CRC·ACK·비트 스터핑·오류 카운터로 고장을 감지한다.
- 메시지는 보통 **ID = 내용(기능)**이다. "누가 보냈는지"보다 "무엇을 뜻하는지"가 중요하다. 같은 ID를 여러 노드가 받는다(브로드캐스트).

이 네 가지가 CAN의 설계 철학을 요약한다. 특히 "ID = 내용"은 웹의 URL과 다르다. CAN ID는 목적지 주소가 아니라 메시지의 종류를 나타내는 경우가 많다.

## 5.2 물리 계층

### 차동 신호

CAN은 두 선 **CAN_H / CAN_L**의 전압 차이로 비트를 표현한다.

- **recessive(1)**: 두 선이 약 2.5V, 차동 전압 ≈ 0V.
- **dominant(0)**: CAN_H ≈ 3.5V, CAN_L ≈ 1.5V, 차동 전압 ≈ 2V.

```text
recessive (1)     dominant (0)
CAN_H ── 2.5V     CAN_H ── 3.5V
CAN_L ── 2.5V     CAN_L ── 1.5V
차동 ≈ 0V          차동 ≈ 2V
```

버스는 **wired-AND**처럼 동작한다. 하나라도 dominant를 보내면 버스 전체가 dominant가 된다. 이것이 중재의 기반이다. 여러 노드가 동시에 말해도, dominant를 보낸 쪽이 이기고 recessive를 보낸 쪽은 물러난다.

트랜시버(예: TJA1050, MCP2551, SN65HVD230)가 MCU의 논리 신호를 차동 신호로 바꾼다. MCU의 CAN 컨트롤러와 트랜시버는 별개다. 컨트롤러는 프레임을 만들고, 트랜시버는 전기 신호를 만든다.

3.3V MCU에 5V 트랜시버를 붙이면 RXD가 5V로 올 수 있다. 3.3V용 트랜시버(SN65HVD230 등)를 쓰거나 레벨을 맞춘다.

### 종단 저항

버스 양 끝에 **120Ω**을 각각 둔다. 두 개가 병렬로 보여 전원을 끈 상태에서 CAN_H-CAN_L 저항이 약 **60Ω**으로 측정된다.

```text
CAN_H ──┬──────────────────────────┬──
        │                          │
       120Ω                       120Ω
        │                          │
CAN_L ──┴──────────────────────────┴──
       버스 끝                     버스 끝
```

종단이 없거나 하나만 있으면 반사가 생겨 통신 거리와 안정성이 떨어진다. 60Ω이 아니면 배선부터 의심한다. 멀티미터로 전원을 끄고 CAN_H와 CAN_L 사이를 재는 것이 가장 빠른 확인이다.

스텁(노드까지의 짧은 분기)은 짧게 유지한다. 1Mbps에서는 0.3m 안팎이 권장된다(경험칙, 확인 필요). 트위스트 페어를 쓰고, 접지는 신호 기준과 차폐를 위해 필요하다. 절연 트랜시버를 쓰면 접지 루프를 끊을 수 있다.

### 비트레이트와 거리

| 비트레이트 | 대략 최대 버스 길이 |
|---|---|
| 1 Mbps | 40m |
| 500 kbps | 100m |
| 250 kbps | 250m |
| 125 kbps | 500m |
| 50 kbps | 1000m |

위 값은 경험칙이다. 트랜시버·케이블·스텁·노이즈에 따라 달라진다. 속도를 높일수록 거리가 급격히 줄어든다.

차량은 500kbps(파워트레인), 250kbps, 125kbps(바디)가 흔하다. 같은 버스의 모든 노드는 **같은 비트레이트와 비트 타이밍**을 써야 한다.

비트 타이밍은 동기화 구간 + 전파 구간 + phase seg1/seg2로 나뉘고, 샘플 포인트는 보통 비트의 75~87.5% 지점에 둔다. MCU의 비트 타이밍 레지스터를 계산할 때 이 값을 맞춘다. 비트레이트만 같고 샘플 포인트가 다르면 먼 거리에서 간헐 오류가 날 수 있다.

## 5.3 클래식 CAN 프레임

표준(11비트 ID) 프레임의 구조는 다음과 같다.

| 필드 | 길이 | 내용 |
|---|---|---|
| SOF(Start of Frame) | 1비트 | dominant, 프레임 시작 |
| 중재 필드 | 12비트 | 11비트 ID + RTR(remote transmission request) |
| 제어 필드 | 6비트 | IDE, r0, DLC(Data Length Code, 4비트) |
| 데이터 | 0~8바이트 | 페이로드 |
| CRC | 16비트 | 15비트 CRC + delimiter |
| ACK | 2비트 | ACK slot + delimiter |
| EOF(End of Frame) | 7비트 | recessive, 프레임 끝 |
| IFS(Inter-Frame Space) | 3비트 | 프레임 간 간격 |

```text
| SOF | 중재(11비트 ID + RTR) | 제어 | 데이터(0~8) | CRC | ACK | EOF | IFS |
  1bit        12bit              6bit     0~64bit      16bit  2bit  7bit  3bit
```

- 확장 프레임은 29비트 ID를 쓴다. 기본 11비트 뒤에 SRR, IDE, 18비트 확장 ID, RTR이 붙는다.
- DLC는 데이터 길이를 0~8로 인코딩한다. 9 이상은 클래식 CAN에서 8로 취급된다.
- **비트 스터핑**: 같은 레벨이 5번 연속되면 반대 비트를 하나 끼워 넣는다. 수신측은 이를 제거한다. 스터핑 규칙 위반은 오류다.
- ACK 슬롯은 수신 노드가 dominant로 채워 "받았다"를 알린다. **버스에 수신 노드가 없으면 송신 노드는 ACK 오류를 낸다.** 어댑터 하나만 연결해 시험할 때 자주 겪는 문제다.
- RTR(remote frame)은 데이터 없이 요청만 보내는 클래식 CAN 기능이다. 실제로는 거의 쓰지 않고, CAN FD에서는 지원하지 않는다.

비트 스터핑은 "프레임에 규칙적으로 반대 비트를 섞는" 방식이라 처음에는 낭비처럼 보인다. 하지만 수신기가 송신기의 클록에 계속 동기화할 수 있게 해 주는 장치다. CAN이 클록 선 없이도 비교적 긴 프레임을 안정적으로 받는 이유 중 하나다.

## 5.4 ID와 중재

- ID는 작을수록 우선순위가 높다. 중재 필드를 보낼 때 dominant(0)가 recessive(1)를 이기므로, `0x100`이 `0x200`과의 중재에서 이기고 먼저 나간다.

```text
0x100 = 001 0000 0000
0x200 = 010 0000 0000
         ↑
         첫 번째로 다른 비트에서 0x100이 0(dominant),
         0x200이 1(recessive)이므로 0x100이 이긴다
```

- 중재는 **비파괴적**이다. 진 노드는 다음 기회에 다시 시도하면 되고, 버스에는 이긴 프레임만 남는다.
- 수신 노드는 하드웨어 수용 필터(acceptance filter)로 필요한 ID만 받는다. 필터를 잘못 설정하면 "메시지가 안 온다"고 착각한다.
- ID는 목적지 주소가 아닐 수 있다. 차량에서는 제조사마다 ID-신호 매핑이 다르고, J1939/CANopen은 ID 안에 기능/노드 정보를 담는다.
- 같은 ID를 여러 노드가 보내면 중재로 구분되지 않아 데이터가 충돌할 수 있다. ID는 고유하게 관리한다.

웹의 REST라면 `GET /temperature`처럼 경로가 의미를 담는다. CAN에서는 `0x123`이라는 ID가 "온도"를 뜻할 수 있지만, 그 매핑은 DBC 파일이나 제조사 문서에 있다. **버스 위의 ID만 보고 의미를 알 수 없다**는 점이 중요하다.

## 5.5 오류 처리와 상태

CAN은 오류를 **감지하고 스스로 회복**하려는 프로토콜이다.

- 오류 종류: 비트 오류, 스터핑 오류, CRC 오류, form 오류, ACK 오류.
- 모든 노드는 송신 오류 카운터(TEC)와 수신 오류 카운터(REC)를 유지한다.
- **Error Active**: TEC/REC ≤ 127. 오류를 감지하면 active error frame(dominant)을 보낸다.
- **Error Passive**: TEC 또는 REC > 127. passive error frame(recessive)을 보내고, 버스에 덜 영향을 준다.
- **Bus-Off**: TEC > 255. 노드는 버스에서 스스로 빠진다. 128번의 11비트 recessive를 본 뒤 복구를 시도한다.

```text
Error Active  ──(오류 누적)──→  Error Passive  ──(TEC > 255)──→  Bus-Off
   TEC/REC ≤ 127                  TEC/REC > 127                  버스 이탈
```

- 오류가 나면 프레임은 자동 재전송된다. 이것이 편리하지만, 고장 노드가 계속 오류를 내면 버스 전체의 지연을 키울 수 있다.
- 오류 프레임과 카운터는 소프트웨어가 직접 다루기보다 컨트롤러가 처리한다. 애플리케이션은 상태 전이(특히 bus-off)와 복구 정책을 봐야 한다.

"CAN은 오류가 나도 자동으로 다시 보내 준다"는 말은 절반만 맞다. 자동 재전송은 일시적인 잡음에는 강하지만, **고장 노드가 버스를 마비시키는 문제**를 없애지는 않는다. bus-off 상태를 애플리케이션이 감시하고, 필요하면 노드를 격리하거나 복구해야 한다.

## 5.6 CAN FD

- 페이로드를 **최대 64바이트**까지 늘리고, 데이터 구간만 더 빠른 비트레이트로 전환한다(BRS = Bit Rate Switch).
- ISO 11898-1:2015 기준 데이터 구간 최대 5Mbps. 실제로는 2Mbps 구성이 흔하다(확인 필요).
- FDF(FD Format) 비트로 FD 프레임임을 표시하고, CRC는 17/21비트로 강화된다. RTR(remote frame)은 없다.
- 클래식 CAN 컨트롤러는 FD 프레임을 오류로 본다. **같은 버스에 클래식 노드와 FD 노드를 섞으면 문제가 된다.** 모든 노드와 트랜시버가 FD를 지원해야 한다.
- 비ISO(Bosch 1.0)와 ISO 버전은 CRC 계산과 스터프 비트 규칙이 달라 호환되지 않는다. 장비 스펙을 확인한다.
- FD는 데이터 구간이 빨라지므로 트랜시버 지연, 스텁, 종단, 케이블 품질의 영향을 더 크게 받는다.

CAN FD는 "같은 CAN"처럼 보이지만, 버스에 한 대의 클래식 노드만 섞여도 전체가 깨질 수 있다. 장비를 고를 때 "FD 지원"이라는 표기만 보지 말고, **버스의 모든 노드와 트랜시버가 같은 버전을 지원하는지** 확인해야 한다.

## 5.7 ISO-TP (ISO 15765-2)

클래식 CAN은 한 프레임에 8바이트까지만 담는다. 더 긴 진단 메시지는 ISO-TP로 나눈다.

- **SF(Single Frame)**: 7바이트 이하(클래식)를 한 번에. PCI(Protocol Control Information, 데이터 앞부분; SF/CF 1바이트, FF 2바이트, FC 3바이트) 상위 니블 0.
- **FF(First Frame)**: 첫 프레임. PCI 상위 니블 1, 12비트 전체 길이.
- **CF(Consecutive Frame)**: 이어지는 프레임. PCI 상위 니블 2, 4비트 시퀀스(1~15 순환).
- **FC(Flow Control)**: 수신측이 보내는 흐름 제어. 상태(CTS/WAIT/OVERFLOW), 블록 크기, STmin(프레임 간 최소 시간)을 담는다.
- 수신은 FF → FC(CTS) → CF... 순서로 진행된다. WAIT는 "잠시 기다려", OVERFLOW는 "그만 보내"다.

```text
FF:  10 0A 01 02 03 04 05 06     ← 전체 10바이트, 첫 6바이트
FC:  30 00 00 ...                ← CTS, block size 0, STmin 0
CF:  21 ...                      ← 시퀀스 1
```

- 클래식에서는 8바이트에 맞추기 위해 남는 바이트를 패딩한다. 패딩 값은 `0x00`, `0xAA`, `0xCC` 등 구현마다 다르다.
- 주소 지정은 normal(11비트 ID), extended(첫 데이터 바이트에 주소), mixed 등이 있다. 진단은 보통 normal + 물리 주소를 쓴다.
- 타이밍 파라미터(N_Bs, N_Cr, STmin)가 맞지 않으면 "응답이 일부만 온다" 또는 "타임아웃"이 난다.
- CAN FD에서는 ISO-TP도 확장되어 64바이트 프레임과 escape 길이를 쓸 수 있다.

ISO-TP는 CAN 위에 올라가는 작은 전송 계층이다. 웹의 TCP가 IP 위에서 바이트 스트림을 나누고 재조립하는 것과 역할이 비슷하다. 다만 여기서는 **프레임 간 타이밍**이 프로토콜의 일부라서, STmin을 어기면 상대가 응답을 중단할 수 있다.

## 5.8 상위 프로토콜 지도

| 프로토콜 | 기반 | 용도 |
|---|---|---|
| OBD-II | ISO-TP, 11비트 500k 또는 29비트 250k 등(차종별 확인 필요) | 법규 배출가스 진단, 공개 PID |
| UDS (ISO 14229) | ISO-TP | 제조사 진단, DID 읽기 (차량에서는 쓰기·루틴·보안 접근 금지) |
| KWP2000 | ISO-TP 계열 | 구형 진단 |
| J1939 | 29비트 CAN | 트럭·버스·건설기계, PGN(Parameter Group Number), 소스 주소, 전송 프로토콜 |
| CANopen | 11비트 CAN | 산업 자동화, NMT(Network Management)/SDO(Service Data Object)/PDO(Process Data Object), CiA 301 |
| DeviceNet | 11비트 CAN | 산업 네트워크, CIP(Common Industrial Protocol) |
| NMEA 2000 | 29비트 CAN, 250k | 선박 전자장비 |

차량 진단의 실제 주소·서비스 코드·ELM327 명령은 이 책에서 다루지 않는다. 여기서는 "CAN 위에 이런 프로토콜이 올라간다"는 지도만 기억하자.

## 5.9 도구와 실무

### Linux SocketCAN

Linux에서는 SocketCAN이 표준이다.

```bash
sudo ip link set can0 type can bitrate 500000
sudo ip link set up can0
candump -ta can0                 # 절대 시각과 함께 수신
candump -e can0                  # 오류 프레임 포함
cansend can0 123#DEADBEEF
cangen can0
canbusload can0@500000
```

`python-can`은 `interface="socketcan"`으로 붙는다. 수신 예는 8장에서 다룬다.

`candump`의 출력은 대략 다음과 같은 형식이다(버전에 따라 조금 다르다).

```text
  can0  100   [8]  01 02 03 04 05 06 07 08
```

### Windows

PCAN, Kvaser, Vector, CANable(slcan), USB2CAN 등 어댑터별 드라이버/인터페이스를 쓴다. `python-can`의 `interface` 값을 장비에 맞춘다.

ELM327은 OBD-II 읽기에는 편하지만 임의의 고속 CAN 트래픽 분석에는 부적합하다. 클론마다 동작이 다르다. 이 책은 차량 진단을 다루지 않으므로 ELM327 사용법은 설명하지 않는다.

### 로직 분석기/오실로스코프

CAN_H/CAN_L 파형, 종단, 비트 타이밍을 볼 때 쓴다. CAN 디코더가 있는 장비가 편하다. 8장에서 샘플 레이트와 프로브 사용법을 다룬다.

### 시험할 때의 함정

- **활성 노드 2개 이상**을 연결한다. 하나만 있으면 ACK가 없어 송신이 실패한다.
- 이미 다른 활성 노드가 있는 버스를 관찰만 할 때는 listen-only를, 자동 재전송을 막고 싶을 때는 one-shot을 쓴다.
- 노드 하나로 송신을 시험하려면 컨트롤러의 loopback/self-test 모드를 쓴다.
- 버스에 처음 붙을 때는 비트레이트를 모를 수 있다. 후보(125/250/500/1M)를 바꿔 가며 조용한 버스를 찾거나, 자동 비트레이트 감지 기능이 있는 어댑터를 쓴다.
- 차량에서는 **읽기 전용** 원칙을 지킨다. 쓰기·위험 서비스와 고장코드 삭제는 하지 않는다.

## 5.10 흔한 실수

| 증상 | 원인 후보 |
|---|---|
| 아무 프레임도 안 보임 | 비트레이트 불일치, CAN_H/L 반대, 종단 없음, 트랜시버 전원 없음 |
| 송신만 실패(ACK 오류) | 수신 노드 없음, 한 노드만 연결, 종단/배선 문제 |
| 간헐적 오류 | 종단 하나만 있음, 스텁이 긴 것, 접지/차폐 불량, 3.3V/5V 트랜시버 혼용 |
| bus-off 반복 | 비트레이트/샘플 포인트 불일치, 배선 노이즈, 고장 노드 |
| FD 프레임에서 오류 | 클래식 노드/트랜시버 혼재, FD 미지원 |
| 긴 진단 응답이 끊김 | ISO-TP 흐름 제어/STmin/타이밍 문제, 패딩 불일치 |

## 5.11 체크리스트

- [ ] CAN_H/CAN_L을 바꿔 연결하지 않았는가
- [ ] 양 끝 120Ω, 전원 끈 상태에서 약 60Ω인가
- [ ] 모든 노드가 같은 비트레이트·비트 타이밍인가
- [ ] 트랜시버 전원과 논리 레벨(3.3V/5V)이 맞는가
- [ ] 수신 노드가 최소 하나 있는가(ACK)
- [ ] 수용 필터가 원하는 ID를 통과시키는가
- [ ] FD/클래식 혼재가 없는가
- [ ] ISO-TP라면 흐름 제어와 타이밍을 맞췄는가
- [ ] 차량에서는 읽기 전용인가

## 장 요약

- CAN은 차동 신호를 쓰는 다중 마스터 버스다. ID가 작을수록 우선순위가 높고, 중재는 비파괴적이다.
- 양 끝 120Ω 종단이 필수이며, 전원을 끈 상태에서 약 60Ω이 나와야 한다.
- 같은 버스의 모든 노드는 같은 비트레이트와 비트 타이밍을 써야 한다.
- ACK는 수신 노드가 채운다. 수신 노드가 없으면 송신은 ACK 오류로 실패한다.
- 오류 카운터에 따라 Error Active → Error Passive → Bus-Off로 전이한다. 애플리케이션은 bus-off 복구를 설계해야 한다.
- CAN FD는 64바이트와 빠른 데이터 구간을 제공하지만, 클래식 노드와 섞으면 안 된다.
- 긴 메시지는 ISO-TP로 나눈다. 흐름 제어와 STmin 타이밍이 맞아야 한다.
- 차량 진단의 실무는 이 책에서 다루지 않는다. 차량에서는 읽기 전용 원칙을 지킨다.

다음 장에서는 CAN 같은 개별 버스에서 한 걸음 물러나, 장치를 네트워크와 클라우드에 연결하는 IoT 프로토콜 지도를 그린다.
