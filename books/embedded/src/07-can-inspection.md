# 7장 CAN 버스 점검과 PC로 듣기

## 이 장에서

6장에서 차 안의 CAN 망 구조를 그렸다. 이 장에서는 손을 움직인다. 두 가지를 한다.

1. **버스가 살아 있는지 확인한다.** 멀티미터 하나로 종단 저항, 전압, 단락을 재고, 오실로스코프가 있으면 파형을 본다. 정비 현장에서 "통신 불가" 고장을 찾을 때 쓰는 순서 그대로다.
2. **PC로 버스를 듣는다.** USB-CAN 어댑터를 수신 전용으로 붙이고, 흐르는 프레임을 ID별로 정리해 본다.

웹으로 치면 1은 "케이블이 꽂혀 있고 링크 불이 들어오는가", 2는 "패킷 캡처(tcpdump·Wireshark)"다. 패킷 캡처를 하기 전에 링크부터 확인하는 것과 같은 순서다.

**안전 원칙**: 이 장의 모든 작업은 **측정과 수신만** 한다. 차량 버스에 프레임을 보내지 않는다. 차가 움직이는 동안에는 배선을 만지지 않는다.

## 7.1 준비물

| 도구 | 용도 | 비고 |
|---|---|---|
| 멀티미터 | 저항·전압·통전 | 10장의 기본 사용법 참고 |
| OBD-II 분기 케이블 또는 백프로브 핀 | 진단 단자 6·14번에 안전하게 접촉 | 단자 핀을 벌리지 않게 |
| 오실로스코프 | 파형 확인 | 선택. 2채널이면 CAN-H·CAN-L을 같이 본다 |
| USB-CAN 어댑터 | PC로 수신 | 수신 전용(listen-only) 모드를 지원해야 한다 |
| 배선도 | 버스 종류·종단 위치 | 정비 매뉴얼 |

6장에서 본 것처럼 진단 단자의 6번이 CAN-H, 14번이 CAN-L이다. 이 장의 측정은 진단 단자가 고속 CAN에 연결된 경우를 기준으로 한다.

## 7.2 종단 저항 재기 (시동 끔)

시동을 끄고 멀티미터를 저항 모드로 두고 6번과 14번 사이를 잰다. 고속 CAN은 양 끝에 120Ω이 하나씩 병렬로 있으므로 약 **60Ω**이 정상이다(5.2절).

| 측정값 | 뜻 |
|---|---|
| 약 60Ω (예: 58~65Ω) | 정상: 종단 두 개가 모두 있다 |
| 약 120Ω | 종단 하나가 빠졌다: 끝 쪽 제어기 커넥터가 빠졌거나, 그 안의 저항·배선이 끊겼다 |
| 약 40Ω | 종단이 하나 더 있다: 세 개가 병렬(120 ÷ 3) |
| 0Ω에 가까움 | CAN-H와 CAN-L이 서로 단락 |
| 무한대(OL) | 두 종단이 모두 없거나, 재는 지점이 버스와 끊겼다 |

정비 현장에서 쓰는 확인법도 있다. 종단 저항이 들어 있다고 알려진 제어기(예: ECM)의 커넥터를 뽑고 다시 재면 약 120Ω이 나와야 한다. 남은 하나가 살아 있다는 뜻이다. **커넥터를 뽑는 작업은 배터리·시동 상태와 제조사 절차를 지켜서** 한다. 이 책에서는 권하지 않고, 원리만 소개한다.

주의할 점이 두 가지 있다.

- 시동을 꺼도 문을 열거나 키를 가까이 두면 일부 제어기가 깨어나 통신한다. 통신 중에는 저항 값이 흔들린다. 제어기가 잠들 때까지 기다린 뒤 잰다(차마다 수십 초~수 분, 확인 필요).
- 저속 CAN(B-CAN 등)은 이 표가 맞지 않는다(6.3절).

## 7.3 전압 재기 (시동 켬)

시동(또는 ON)을 켜고 멀티미터를 직류 전압 모드로 둔다. 검은 리드는 차체 접지(4번 핀이나 좋은 접지점), 빨간 리드는 6번, 그다음 14번에 댄다.

| 측정 | 정상 범위(대표값) |
|---|---|
| CAN-H(6번) | 약 2.6~2.8V |
| CAN-L(14번) | 약 2.2~2.4V |

왜 3.5V나 1.5V가 아니고 2.5V 근처가 나올까? 멀티미터는 빠르게 바뀌는 전압의 **평균**을 보여 주기 때문이다. CAN-H는 대부분의 시간을 2.5V(recessive)에 있다가 dominant 비트에서 잠깐 3.5V로 올라가므로 평균이 2.5V보다 조금 높다. CAN-L은 반대로 조금 낮다. 그래서 "H는 2.5V보다 약간 위, L은 약간 아래"면 버스가 움직이고 있다는 신호다.

| 이상한 값 | 의심할 것 |
|---|---|
| 둘 다 정확히 2.5V, 전혀 안 움직임 | 버스에 아무도 말하지 않음(제어기 꺼짐, 버스 휴면) |
| 둘 다 0V 근처 | 접지 단락, 트랜시버 전원 없음 |
| 한쪽이 12V 근처 | 배터리 전원과 단락 |
| H와 L이 같은 값으로 붙어 움직임 | H-L 단락 |

## 7.4 단락 찾기 (시동 끔)

멀티미터를 통전(삐 소리) 모드로 두고, 한 리드는 차체 접지, 다른 리드는 6번, 그다음 14번에 댄다. **소리가 나면 안 된다.** 소리가 나면 그 선이 어딘가에서 접지와 붙었다.

CAN 선 하나가 접지와 단락되면 대부분의 경우 버스 전체가 통신을 못 한다. 다음 단계는 배선도를 보며 커넥터를 하나씩 분리해 단락이 사라지는 구간을 좁히는 것이다. 이것은 정비 작업이므로 이 책에서는 다루지 않는다.

## 7.5 오실로스코프로 파형 보기

멀티미터는 평균만 보여 준다. 오실로스코프는 비트 하나하나를 보여 준다.

- 프로브 접지는 차체 접지에, 채널 1은 CAN-H, 채널 2는 CAN-L에 댄다.
- 시동을 걸어 모든 제어기가 통신하게 한다.
- 정상 파형: CAN-H는 2.5V를 기준으로 3.5V까지 올라가는 펄스, CAN-L은 2.5V를 기준으로 1.5V까지 내려가는 펄스. 두 파형이 **거울처럼 대칭**이다.

```text
3.5V ─   ┌─┐ ┌───┐   ┌─┐        CAN-H
2.5V ────┘ └─┘   └───┘ └──────  (recessive는 2.5V)
2.5V ────┐ ┌─┐   ┌───┐ ┌──────  (recessive는 2.5V)
1.5V ─   └─┘ └───┘   └─┘        CAN-L
```

- 수학 채널로 CAN-H − CAN-L을 그리면 0V와 2V 사이를 오가는 깨끗한 디지털 파형이 된다(5.2절의 차동 전압).
- CAN-H나 CAN-L이 접지와 단락되면 파형이 0V 근처에서 무너진다. 통신이 멈춘 버스의 전형적인 모습이다.
- 디코더 기능이 있는 스코프는 파형을 프레임(ID·데이터)으로 풀어 보여 준다. 샘플 레이트와 프로브 설정은 10.5절·10.6절을 참고한다.

## 7.6 PC로 듣기: USB-CAN 어댑터

버스가 살아 있는 것을 확인했으면, 이제 프레임을 듣는다.

### 어댑터 고르기

| 종류 | PC 쪽 인터페이스 | 비고 |
|---|---|---|
| CANable(candleLight 펌웨어) | gs_usb | 리눅스 SocketCAN에 바로 붙는다 |
| CANable(slcan 펌웨어), USB2CAN 계열 | slcan(가상 직렬) | `python-can`의 `slcan` |
| PCAN-USB, Kvaser, Vector | 제조사 드라이버 | 안정적이고 비싸다 |
| 저가 직렬형(예: CH340 칩의 USB-CAN 분석기) | 가상 직렬 + 전용 이진 프레임 | 싸고 단순하다. 프로토콜 문서를 확인 |

ELM327 같은 OBD 진단 어댑터는 진단 요청·응답에는 편하지만, 버스에 흐르는 모든 프레임을 빠짐없이 듣는 데에는 맞지 않는다(5.9절).

### 동작 모드: 수신 전용이 기본이다

CAN 컨트롤러에는 보통 세 가지 모드가 있다.

| 모드 | 버스에 하는 일 | 쓰는 때 |
|---|---|---|
| 침묵(listen-only, silent) | 아무것도 내보내지 않는다. ACK 비트도 넣지 않는다 | **차량에 처음 붙일 때 항상** |
| 루프백(+침묵) | 보낸 프레임을 내부에서 자기에게 되돌린다. 버스에는 안 나간다 | 차 없이 어댑터·프로그램 자체 시험 |
| 일반(normal) | 수신한 프레임에 ACK 비트를 넣고, 오류를 감지하면 오류 프레임을 낸다. 송신도 한다 | 시험대(책상 위 버스) |

일반 모드는 **보내지 않아도** 버스에 영향을 준다. 남의 프레임에 ACK 비트를 넣고, 비트레이트가 틀리면 오류 프레임을 연달아 내서 버스를 방해할 수 있다. 차량 버스에는 침묵 모드로 붙인다.

### 비트레이트 맞추기

같은 버스의 모든 노드는 같은 비트레이트를 쓴다(5.2절). 차량 고속 CAN은 500kbps가 가장 흔하다. 모르면 침묵 모드로 500k → 250k → 125k → 1M 순서로 바꿔 가며, 프레임이 깨끗하게 들어오는 값을 찾는다. 침묵 모드라면 틀린 값으로 들어도 버스를 방해하지 않는다.

### 차 없이 먼저 해 보는 루프백 시험

어댑터를 산 날 차에 가져가기 전에, 책상에서 루프백으로 어댑터와 프로그램을 확인한다.

1. 어댑터를 루프백+침묵 모드로 설정한다.
2. 시험 프레임(예: ID `0x123`, 데이터 `DE AD BE EF 00`)을 보낸다.
3. 같은 바이트가 그대로 돌아오는지 확인한다.

돌아오면 PC → USB → 어댑터 안의 CAN 컨트롤러 → PC 경로가 모두 정상이다. 남은 것은 버스 쪽 배선뿐이다. 10.7절의 "레이어별 시험"과 같은 생각이다.

### 예: 직렬형 어댑터의 이진 프레임 파싱

저가 직렬형 어댑터 중에는 USB 가상 직렬(예: 2Mbps) 위에 이런 모양의 이진 프레임을 쓰는 것이 있다(어떤 USB-CAN 분석기의 예, 장치마다 다르니 문서를 확인).

```text
AA  <종류>  <ID 2바이트, 리틀 엔디언>  <데이터 0~8바이트>  55
     └ 상위 2비트 11 = 데이터 프레임, 비트5 = 확장 ID, 비트4 = 원격 프레임, 하위 4비트 = DLC
```

`AA C5 23 01 DE AD BE EF 00 55`는 표준 ID `0x123`, 데이터 5바이트 `DE AD BE EF 00`이다. 3장의 상태 기계 파서와 같은 방식으로 읽는다. 시작 바이트를 찾고, 종류 바이트로 길이를 정하고, 끝 바이트가 `55`가 아니면 한 바이트 버리고 다시 동기를 잡는다.

```python
def feed(buf: bytearray) -> list[tuple[int, bytes]]:
    """버퍼에서 완성된 프레임을 꺼낸다. 남은 조각은 buf에 남는다."""
    frames = []
    while buf:
        if buf[0] != 0xAA:
            del buf[0]                      # 동기 잃음: 다음 AA까지 버린다
            continue
        if len(buf) < 2:
            break                           # 종류 바이트를 기다린다
        kind = buf[1]
        if kind & 0xC0 != 0xC0 or kind & 0x0F > 8:
            del buf[0]
            continue
        id_len = 4 if kind & 0x20 else 2
        size = 2 + id_len + (kind & 0x0F) + 1
        if len(buf) < size:
            break                           # 나머지 바이트를 기다린다
        if buf[size - 1] != 0x55:
            del buf[0]
            continue
        can_id = int.from_bytes(buf[2:2 + id_len], "little")
        frames.append((can_id, bytes(buf[2 + id_len:size - 1])))
        del buf[:size]
    return frames
```

이 파서는 3.8절처럼 **1바이트씩 나눠 넣기**, **잡음 바이트 섞기**로 시험한다. 직렬 읽기는 언제든 프레임 중간에서 끊길 수 있다.

### 무엇을 화면에 띄울까

프레임을 한 줄씩 흘려 보내면 읽을 수 없다. ID별로 모아 한 줄씩 보여 주는 표가 실용적이다.

```text
  ID     DLC  데이터                    개수     Hz   경과
  316      8  05 20 1A 0F 00 3C 00 7F   12034   100.0  0.0s
  329      8  40 8B 7F 0A 11 2F 00 00    6012    50.0  0.0s
  545      8  D8 00 00 00 00 00 00 00     601     5.0  0.1s
```

- **Hz**: 같은 ID가 들어오는 주기. 상시 메시지는 주기가 일정하다.
- **바뀐 바이트 강조**: 최근 1초 안에 바뀐 바이트에 색을 칠한다. 가속 페달을 밟을 때 바뀌는 바이트를 찾는 식으로 의미를 추측한다.
- **원본 기록**: 화면과 별개로 받은 프레임을 **단조 시각과 원본 바이트 그대로** 파일에 남긴다(10.9절). 해석은 나중에 다시 할 수 있지만, 놓친 원본은 다시 얻을 수 없다.

위 표의 ID와 값은 형식을 보여 주는 예시다. 실제 차의 ID와 의미는 차종마다 다르고, 이 책의 범위 밖이다.

## 7.7 들은 것으로 구조 판단하기

6.5절의 질문, "진단 단자가 C-CAN에 바로 붙었나, 게이트웨이 뒤에 있나"는 침묵 모드로 들어 보면 답이 나온다.

| 시동 켬 상태에서 들은 것 | 판단 |
|---|---|
| 진단 요청 없이도 ID 수십 개가 일정한 주기로 흐른다 | (가) 진단 단자가 C-CAN에 바로 연결 |
| 아무것도 안 흐르다가, 진단기로 요청하면 그 응답만 보인다 | (나) 게이트웨이 뒤 |
| 아무것도 안 들린다 | 비트레이트 불일치, CAN-H/L 반대, 다른 핀에 다른 버스가 있을 수 있음 |
| 오류가 계속 난다 | 비트레이트 불일치. 침묵 모드인지 다시 확인 |

(나)라면 진단 단자에서는 상시 메시지를 들을 수 없다. 다른 지점에서 버스에 접근해야 하는데, 이것은 배선 작업이고 차종별 정보가 필요하므로 이 책에서는 다루지 않는다.

## 7.8 흔한 실수

| 증상 | 원인 후보 |
|---|---|
| 저항이 60Ω과 120Ω 사이를 오간다 | 제어기가 깨어 통신 중. 잠들 때까지 기다린다 |
| 전압이 정확히 2.5V로 고정 | 버스 휴면 또는 시동 꺼짐 |
| 어댑터를 꽂자 계기판 경고등이 켜졌다 | 일반 모드로 붙였거나 비트레이트가 틀렸다. 즉시 뽑고 침묵 모드로 |
| 루프백은 되는데 차에서는 아무것도 안 들림 | 게이트웨이 뒤 구조, 비트레이트, 핀 확인 |
| 프레임이 가끔 깨진다 | 직렬 파서가 부분 수신을 처리하지 못함(3.6절) |
| 같은 COM 번호인데 다른 장치가 열린다 | USB 장치를 다시 꽂으면 번호가 바뀐다. 장치를 확인하고 연다 |

- [ ] 시동 켬 상태에서 CAN-H가 2.5V보다 약간 높고 CAN-L이 약간 낮은가
- [ ] 6·14번이 접지와 단락되지 않았는가
- [ ] 어댑터를 루프백으로 먼저 시험했는가
- [ ] 차량에는 침묵(listen-only) 모드로 붙였는가
- [ ] 비트레이트를 맞췄는가
- [ ] 원본 프레임을 단조 시각과 함께 기록하는가

## 장 요약

- 버스 점검은 저항(시동 끔, 약 60Ω) → 전압(시동 켬, H는 2.5V보다 약간 위·L은 약간 아래) → 단락(통전 없음) → 파형 순서로 한다.
- 멀티미터는 평균을, 오실로스코프는 비트를 보여 준다. 정상 파형은 CAN-H와 CAN-L이 2.5V를 중심으로 거울처럼 움직인다.
- PC로 들을 때는 침묵 모드가 기본이다. 일반 모드는 보내지 않아도 ACK·오류 프레임으로 버스에 영향을 준다.
- 어댑터는 차에 가져가기 전에 루프백으로 시험한다.
- 직렬형 어댑터의 이진 프레임은 3장의 상태 기계 파서로 읽고, 원본을 단조 시각과 함께 남긴다.
- 진단 단자에서 상시 메시지가 들리는지로 게이트웨이 구조를 판단한다.

다음 장에서는 CAN 같은 차량·장비 안의 버스에서 한 걸음 물러나, 장치를 네트워크와 클라우드에 연결하는 IoT 프로토콜 지도를 그린다.
