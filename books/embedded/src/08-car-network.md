# 8장 자동차는 거대한 CAN 네트워크다

## 이 장에서

7장에서는 CAN 한 개의 버스를 보았다. 실제 자동차는 CAN 하나로 끝나지 않는다. 엔진·변속기·브레이크·계기판·도어·공조·멀티미디어가 각자의 네트워크에 붙어 있고, 그 사이를 **게이트웨이**가 잇는다. OBD-II 포트는 이 네트워크로 들어가는 진단 창구다.

웹 개발자에게 이 구조는 마이크로서비스 아키텍처와 닮았다. 서비스마다 경계가 있고, API 게이트웨이가 라우팅하며, 모든 서비스가 같은 데이터베이스를 직접 보지는 않는다. 차량도 비슷하다. 파워트레인 CAN과 바디 CAN은 목적과 속도가 다르고, 게이트웨이가 진단 요청을 필요한 버스로 넘긴다. **OBD 포트에 꽂았다고 차량 전체 트래픽이 다 보이는 것은 아니다.**

이 장에서 다루는 것:

- 차량에 여러 CAN 버스가 있는 이유
- 파워트레인·바디·샤시·인포테인먼트 버스와 LIN·FlexRay·Automotive Ethernet
- 게이트웨이의 역할과 진단 라우팅
- OBD-II 16핀 커넥터의 핀 배치
- OBD-II가 지원하는 5가지 신호 프로토콜
- 쏘렌토 UM 2019 2.2 디젤에서 확인된 주소와 버스
- 기능 주소와 물리 주소, 응답 주소 +8의 규칙
- OBD 포트로 무엇을 볼 수 있고 무엇을 볼 수 없는지
- CAN FD·CAN XL·차량 이더넷이 다음 세대에 맡는 역할

## 8.1 자동차가 네트워크가 된 이유

초기 자동차는 스위치와 램프를 직접 배선했다. 기능이 늘수록 전선이 기하급수적으로 늘어났다. CAN은 이 문제를 **버스 하나에 여러 ECU를 묶고, 센서 값을 공유**하는 방식으로 풀었다.

- ECU 수: 현대차 한 대에 70개 이상의 ECU가 있을 수 있다.
- 배선 중량: 점대점 배선을 버스로 바꾸면 전선과 커넥터가 줄어든다.
- 센서 공유: 휠 속도 하나를 ABS·ESC·계기판·ADAS가 함께 쓴다.
- 진단: 버스에 붙으면 여러 ECU의 상태를 한 포트에서 읽을 수 있다.

CAN은 원래 배출가스 규제와 진단 편의를 위해 차량에 들어왔지만, 지금은 차체·안전·편의 기능까지 퍼졌다. 그 결과 **버스마다 요구가 달라졌다.** 엔진 제어는 빠르고 결정적이어야 하고, 도어 램프는 느려도 된다. 그래서 차량은 하나의 거대한 버스가 아니라 **여러 개의 버스**로 나뉜다.

## 8.2 차량 안의 여러 버스

| 버스 | 전형적인 속도 | 하는 일 | 특징 |
|---|---|---|---|
| 파워트레인 CAN | 500kbps | 엔진·변속기·ABS/ESC·조향 | 빠르고 결정적. 진단 PID의 핵심 |
| 샤시 CAN | 500kbps 또는 250kbps | 브레이크·조향·서스펜션 | 안전 관련, 지연에 민감 |
| 바디 CAN | 125kbps 또는 100kbps | 도어·램프·와이퍼·시트·공조 | 느리지만 노드가 많다 |
| 인포테인먼트 CAN | 500kbps 또는 125kbps | 오디오·내비·디스플레이 | 사용자 조작, 업데이트 |
| 진단 CAN | 파워트레인과 공유하는 경우가 많다 | OBD-II·UDS 요청 | 게이트웨이를 통해 다른 버스로 라우팅 |
| LIN | 최대 20kbps | 도어 모듈·미러·공조 액추에이터 | 단일 선, 1 master + 최대 15 slave |
| FlexRay | 최대 10Mbps | 고성능 샤시·ADAS | CAN보다 빠르고 이중화 가능 |
| Automotive Ethernet | 100Mbps~ | 카메라·레이다·OTA·백본 | 대용량, 점대점 스위치 |

이 표는 **일반적인 분류**다. 차종마다 버스 이름과 속도, ECU 배치는 다르다. 같은 "바디 CAN"이라도 회사마다 부르는 이름이 다르고, 한 버스에 파워트레인과 바디 ECU가 섞이는 차도 있다.

중요한 것은 **버스마다 속도와 우선순위가 다르고, 서로 직접 연결되지 않는다**는 점이다. 파워트레인 CAN의 프레임이 바디 CAN으로 자동으로 흘러가지 않는다. 게이트웨이가 필요하다.

## 8.3 게이트웨이: 버스 사이의 라우터

게이트웨이는 여러 CAN 버스를 연결하고, 프레임을 **라우팅·필터링·변환**한다. 웹의 API 게이트웨이와 비슷하다.

- 진단 요청을 해당 ECU가 있는 버스로 넘긴다.
- 모든 프레임을 그대로 전달하지 않고, 필요한 것만 통과시킨다.
- 버스 간 속도 차이를 흡수한다.
- 일부 게이트웨이는 보안·인증·세션 관리를 한다.

OBD-II 포트는 보통 파워트레인 CAN에 직접 붙어 있거나, 게이트웨이를 통해 여러 버스로 이어진다. 어느 쪽인지는 차종마다 다르다.

### 쏘렌토에서 관찰된 것

실차 탐색에서 OBD-II 포트로 `7E0`(엔진), `7E1`(변속기)뿐 아니라 `7A0`(BCM), `7C6`(계기판), `7D1`(ESC) 같은 주소에도 `22`(ReadDataByIdentifier) 요청이 닿았다. 응답 주소는 요청 +8이었다.

```text
요청 7E0 → 응답 7E8   엔진
요청 7E1 → 응답 7E9   변속기
요청 7A0 → 응답 7A8   BCM
요청 7C6 → 응답 7CE   계기판
요청 7D1 → 응답 7D9   ESC
```

이것은 **OBD 포트가 게이트웨이를 통해 다른 버스의 ECU에도 요청을 전달한다**는 간접 증거다. 다만 제조사 문서로 확인한 것은 아니므로 `추정`이다. OBD 포트에 물리적으로 파워트레인 CAN만 연결되어 있고, 게이트웨이가 진단 요청을 라우팅하는 구조일 가능성이 높다.

반대로, OBD 포트에서 다른 버스의 **일반 트래픽**이 다 보인다고 가정하면 안 된다. 게이트웨이는 진단 요청만 통과시키거나, 특정 ID만 포워딩할 수 있다. 차량 전체를 스니핑하려면 각 버스에 직접 접근해야 한다.

## 8.4 OBD-II 16핀 커넥터

OBD-II는 SAE J1962 16핀 커넥터를 쓴다. 12V 차량은 Type A, 24V 차량은 Type B다. 커넥터는 핸들(스티어링 휠)에서 0.61m(2ft) 이내에 있어야 한다(제조사 예외 있음).

| 핀 | 용도 | 비고 |
|---|---|---|
| 1 | 제조사 재량 | GM GMLAN, Audi/VW 점화 신호 등 |
| 2 | SAE J1850 Bus+ | PWM/VPW |
| 3 | 제조사 재량 | Ethernet TX+, Chrysler CCD+ 등 |
| 4 | 차체 접지(chassis ground) | 전원 접지 |
| 5 | 신호 접지(signal ground) | 신호 기준 |
| 6 | CAN_H | ISO 15765-4, SAE J2284 |
| 7 | K-line | ISO 9141-2, ISO 14230-4 |
| 8 | 제조사 재량 | Ethernet 활성화, BMW K-line 등 |
| 9 | 제조사 재량 | RPM 신호, ALDL 등 |
| 10 | SAE J1850 Bus− | PWM만 |
| 11 | 제조사 재량 | Ethernet TX−, Chrysler CCD− 등 |
| 12 | 제조사 재량 | Ethernet RX+ 등 |
| 13 | 제조사 재량 | Ethernet RX−, Ford FEPS 등 |
| 14 | CAN_L | ISO 15765-4, SAE J2284 |
| 15 | L-line | ISO 9141-2, ISO 14230-4 (선택) |
| 16 | 배터리 +12V (Type A) / +24V (Type B) | 어댑터 전원 |

- **4번과 5번을 모두 접지로 본다.** 차체 접지와 신호 접지는 차량 안에서 한 점에서 만나는 경우가 많지만, 전위차가 생길 수 있다.
- 6·14번이 CAN이다. 7·15번은 구형 K-line/L-line이다. 2·10번은 J1850이다.
- 나머지 핀은 제조사 재량이다. "OBD 포트의 3번 핀이 I2C일 것"처럼 추측하고 프로빙하면 안 된다.
- 16번은 배터리 전원이다. 어댑터가 차량 배터리로 동작하므로, 장시간 꽂아 두면 방전에 영향을 줄 수 있다.

### 전원과 접지

OBD-II 포트의 16번 핀은 차량 배터리와 연결된다. 어댑터에 퓨즈가 없는 제품도 있으므로, USB 전원과 차량 전원이 동시에 들어오는 구성은 주의한다. 노트북을 충전기에 꽂은 채 차량에 연결하면 접지 루프가 생길 수 있다. 절연 USB 어댑터나 절연 CAN 트랜시버가 도움이 된다.

## 8.5 OBD-II가 지원하는 5가지 신호 프로토콜

OBD-II는 하나의 프로토콜만 쓰는 것이 아니다. 차량 연식과 제조사에 따라 다음 중 하나를 쓴다.

| 프로토콜 | 속도 | 핀 | 특징 |
|---|---|---|---|
| SAE J1850 PWM | 41.6kbps | 2, 10 | Ford 계열, 12바이트 메시지 |
| SAE J1850 VPW | 10.4kbps | 2 | GM 계열, idle low |
| ISO 9141-2 | 10.4kbps | 7, 15(선택) | K-line, UART 유사 |
| ISO 14230-4 KWP2000 | 1.2~10.4kbps | 7, 15(선택) | K-line, 5baud/fast init |
| ISO 15765-4 CAN | 250/500kbps | 6, 14 | 11비트/29비트, 현재의 표준 |

ELM327은 이 다섯 가지를 자동으로 찾는다. 프로토콜 번호는 다음과 같다.

| 번호 | 프로토콜 |
|---|---|
| 0 | 자동 |
| 1 | SAE J1850 PWM |
| 2 | SAE J1850 VPW |
| 3 | ISO 9141-2 |
| 4 | ISO 14230-4 KWP (5baud) |
| 5 | ISO 14230-4 KWP (fast) |
| 6 | ISO 15765-4 CAN 11비트 500k |
| 7 | ISO 15765-4 CAN 29비트 500k |
| 8 | ISO 15765-4 CAN 11비트 250k |
| 9 | ISO 15765-4 CAN 29비트 250k |
| A | SAE J1939 29비트 250k |
| B | User1 CAN 11비트 |
| C | User2 CAN 11비트 |

쏘렌토에서는 `ATSP0` 자동 검색 뒤 `ATDPN`이 `A6`으로 나왔다. `A`는 "자동 검색", `6`은 ISO 15765-4 CAN 11비트 500k다.

프로토콜을 모를 때는 `ATSP0`로 시작한다. 자동 검색이 끝나면 `ATDPN`으로 실제 선택된 번호를 확인한다. `ATSP6`처럼 고정하면 검색 시간을 줄일 수 있지만, 다른 차량에 꽂으면 통신이 안 된다.

## 8.6 쏘렌토 UM 2019 2.2 디젤의 실제 주소

다음은 실차에서 확인된 정보다. **이 차 한 대의 기록**이며, 모든 쏘렌토에 그대로 적용되지 않는다.

| 요청 주소 | 응답 주소 | 제어기 | 근거 |
|---|---|---|---|
| 7DF | 7E8~7EF | 기능 주소(모든 OBD ECU) | ISO 15765-4 |
| 7E0 | 7E8 | 엔진(ECM) | Mode 09 이름 `ECM-EngineControl` |
| 7E1 | 7E9 | 변속기(TCM) | Mode 09 이름 `TCM-TransmisCtrl` |
| 7A0 | 7A8 | BCM | `22 F187` 부품번호 954A0 |
| 7A1 / 7A2 | 7A9 / 7AA | 운전석 / 조수석 도어 | 부품번호 93570 / 93575 |
| 7A3 | 7AB | 시트 메모리(추정) | 부품번호 95450, 문헌 기반 |
| 7C4 | 7CC | 차로 유지 카메라(LKAS) | `22 F100` 응답 `UM2 LKAS` |
| 7C6 | 7CE | 계기판 | `22 F187` 응답 `721` |
| 737 / 7D0 | 73F / 7D8 | 스마트 크루즈 레이더(SCC) | `22 F100` 응답 `UM SCC` |
| 7D1 | 7D9 | ESC/ABS | `22 F100` 응답 `UM ESC` |
| 7D5 | 7DD | 전자식 주차 브레이크(EPB) | `22 F100` 응답 `UM EPB` |
| 770 / 771 | 778 / 779 | 정션박스 | 부품번호 91961 / 91950 |
| 777 | 77F | 전동 테일게이트 | 부품번호 81870 |

- 응답 주소가 7FF를 넘으면 ELM327의 수신 필터로 받기 어렵다. 요청은 7F7까지만 하는 편이 안전하다.
- 7E2~7E7은 이 차에서 응답이 없었다. 모든 OBD 차량이 8개 ECU를 다 쓰는 것은 아니다.
- 에어컨(7B3)은 응답이 없었고, 7D2는 에어백 추정이지만 기본 세션에서 `7F 22 7F`가 왔다.
- `22 F187`(부품번호)과 `22 F100`(짧은 버전 문자열)은 제조사 고유 DID다. 표준 OBD PID가 아니다.
- `22 F190`은 VIN으로 알려져 있지만, 개인정보이므로 이 책에서는 읽지도, 기록하지도 않는다.

이 주소들은 **진단 요청을 보낼 때** 쓴다. 일반 CAN 트래픽을 스니핑할 때 보이는 ID와는 다르다. OBD-II의 7E0~7E7/7E8~7EF는 진단용 주소 체계이고, 차량의 일반 메시지는 다른 ID를 쓴다.

## 8.7 기능 주소와 물리 주소

OBD-II에서 요청 주소는 두 가지다.

- **기능 주소(functional)**: `7DF`. "이 요청을 들을 수 있는 모든 ECU"에게 보낸다. 여러 ECU가 응답할 수 있다.
- **물리 주소(physical)**: `7E0`~`7E7`. 특정 ECU 하나에 보낸다. 응답은 `7E8`~`7EF`로 돌아온다.

```text
기능 주소:
  tester ── 7DF (02 01 0C ...) ──┬── ECU1 → 7E8 (04 41 0C ...)
                                  ├── ECU2 → 7E9 (...)
                                  └── ECU3 → 7EA (...)

물리 주소:
  tester ── 7E0 (22 F1 87 ...) ────── ECU1 → 7E8 (62 F1 87 ...)
```

- 기능 주소로 보내면 여러 응답이 섞인다. 응답 ID를 보고 ECU를 구분해야 한다.
- 물리 주소로 보내면 응답이 하나라 파싱이 쉽다. 대신 주소를 알아야 한다.
- 다중 프레임 응답은 기능 주소가 아니라 **물리 주소**로 이어가야 한다. ISO 15765-4가 그렇게 정한다.
- ELM327에서 `ATH0`이면 헤더가 숨겨져 여러 ECU 응답을 구분할 수 없다. 기능 주소로 여러 ECU에 물을 때는 `ATH1`을 켠다.

## 8.8 쏘렌토 네트워크 구조(추정)

실차에서 확인된 것과 일반적인 차량 구조를 합치면 다음과 같이 그릴 수 있다. 점선은 추정이다.

```text
                        ┌────────────────────┐
                        │      OBD-II 포트    │
                        │  6/14 CAN, 16 +12V  │
                        └─────────┬──────────┘
                                  │ ISO 15765-4 11bit 500k
                        ┌─────────▼──────────┐
                        │      게이트웨이      │
                        │  진단 요청 라우팅    │
                        └───┬──────────┬─────┘
                            │          │
              ┌─────────────▼──┐   ┌───▼─────────────┐
              │ 파워트레인 CAN  │   │   바디 CAN       │
              │ 500kbps        │   │   125kbps 추정   │
              ├────────────────┤   ├─────────────────┤
              │ 7E0 엔진        │   │ 7A0 BCM         │
              │ 7E1 변속기      │   │ 7A1/7A2 도어     │
              │ 7D1 ESC         │   │ 7C6 계기판       │
              │ 7D5 EPB         │   │ 770/771 정션박스 │
              │ 7C4 LKAS        │   │ 777 테일게이트   │
              │ 737/7D0 SCC     │   │ ...             │
              └────────────────┘   └─────────────────┘
```

- 파워트레인 CAN의 500kbps와 7E0/7E1은 실차에서 확인됐다.
- 바디 CAN의 125kbps와 게이트웨이의 정확한 위치는 **추정**이다. 제조사 문서로 확인하지 않았다.
- 계기판(7C6)은 파워트레인 CAN에 있을 수도, 별도 버스에 있을 수도 있다. OBD 포트에서 응답이 왔다는 사실만 확인됐다.
- 실제 차량에는 이 외에도 에어백·TPMS·멀티미디어·ADAS 버스가 있을 수 있다.

이 그림의 목적은 "OBD 포트 하나로 차 전체를 본다"는 오해를 깨는 것이다. OBD 포트는 **진단 창구**이고, 그 뒤에는 게이트웨이와 여러 버스가 있다.

## 8.9 OBD 포트로 무엇을 볼 수 있나

OBD-II 포트로 할 수 있는 일:

- 표준 Mode 01 PID 읽기(회전수, 차속, 냉각수 온도 등)
- Mode 03/07/0A DTC 읽기
- Mode 09 VIN·Calibration ID 읽기
- 제조사 고유 `22` DID 읽기(차량에 따라)
- UDS `19` DTC 읽기, `22` DID 읽기(차량에 따라)

OBD-II 포트로 **볼 수 없는 것**:

- 다른 버스의 일반 CAN 트래픽 전체
- ECU 내부 메모리·I2C/SPI 버스
- 게이트웨이가 라우팅하지 않는 제조사 진단 요청
- 주행 중 안전 관련 액추에이터의 실시간 내부 상태

OBD 포트는 "차량 전체의 와이어탭"이 아니다. 웹으로 비유하면, API 게이트웨이의 공개 엔드포인트에 접속한 것이지, 모든 마이크로서비스의 내부 로그를 보는 것이 아니다.

이 장의 구조는 승용차의 OBD-II 기준이다. 트럭·버스·건설기계는 같은 CAN을 쓰지만 OBD-II 대신 J1939를 쓴다. 29비트 ID, PGN/SPN, 소스 주소, DM1은 33장에서 다룬다.

## 8.10 버스 관찰 입문: 수동 스니핑, DBC, cantools

지금까지는 진단 요청을 보내고 응답을 받았다. 이 절에서는 **보내지 않고 듣기만 하는** 관찰을 다룬다. 차량 버스에는 진단 요청과 무관한 프레임도 계속 흐르므로, 원시 프레임을 기록하면 차량의 동작을 이해하는 단서가 된다. 단, OBD 포트는 차 전체의 와이어탭이 아니다. 게이트웨이가 라우팅하는 진단 트래픽만 보일 수 있다.

### 먼저 읽기 전용으로 시작한다

- **차량을 움직이지 않는다.** 정차·주차 상태에서만 기록한다.
- **프레임을 보내지 않는다.** `candump`·`python-can` 수신만 쓴다. `cansend`, `cangen`, UDS 쓰기·리셋은 보내지 않는다.
- **listen-only를 우선한다.** CAN 컨트롤러가 ACK조차 보내지 않도록 설정하면 버스에 영향을 주지 않는다.
- **내 차 또는 서면 허가를 받은 차만** 대상으로 한다. 11장의 법·윤리 규칙이 그대로 적용된다.
- VIN·GPS·주행 경로가 로그에 섞이지 않게 한다. 원본 로그는 공개하지 않는다.

Linux SocketCAN에서는 인터페이스를 listen-only로 올린다.

```bash
sudo ip link set can0 type can bitrate 500000 listen-only on
sudo ip link set up can0
ip -details link show can0        # listen-only on 확인
```

```bash
candump -tz can0                  # 사람이 읽는 형식, 타임스탬프 포함
candump -L can0 > capture.log     # 재생 가능한 로그 형식
```

- `-tz`는 사람이 읽기 좋은 형식, `-L`은 `canplayer`로 재생할 수 있는 형식이다.
- 비트레이트는 차량 버스에 맞춘다. 쏘렌토의 OBD CAN은 11비트 500kbps다(실차 확인). 다른 버스는 125kbps일 수 있다.
- listen-only를 지원하지 않는 어댑터도 있다. 이때는 수신만 하더라도 컨트롤러가 ACK를 보낼 수 있으므로, 버스에 영향을 줄 수 있는지 먼저 확인한다.
- 벤치에서 노드 두 개만 연결했는데 한쪽이 listen-only면 ACK가 없어 송신이 실패할 수 있다. 이때는 정상 모드의 두 번째 노드를 둔다.

Python으로 같은 일을 한다.

```python
import can

bus = can.Bus(interface="socketcan", channel="can0", receive_own_messages=False)
try:
    while True:
        msg = bus.recv(timeout=1.0)
        if msg is None:
            continue
        print(f"{msg.timestamp:.6f} {msg.arbitration_id:03X} "
              f"{msg.dlc} {msg.data.hex(' ')}")
except KeyboardInterrupt:
    pass
finally:
    bus.shutdown()
```

- `arbitration_id`는 11비트 표준 ID와 29비트 확장 ID를 모두 담는다. `msg.is_extended_id`로 구분한다.
- `msg.dlc`는 데이터 길이다. 클래식 CAN은 8 이하, CAN FD는 64까지다.
- 원시 로그에는 **시각·ID·DLC·바이트**를 남긴다. 해석한 값만 남기면 나중에 DBC가 틀렸을 때 복구할 수 없다.

### DBC: 바이트를 신호로 바꾸는 지도

원시 프레임은 `ID + 바이트`일 뿐이다. DBC 파일은 "이 ID의 이 비트 구간은 이 신호이고, 배율·오프셋·단위는 이렇다"를 적은 텍스트 파일이다. CAN 데이터베이스라고도 부른다.

```text
BO_ 291 ExampleFrame: 8 ECU1
 SG_ VehicleSpeed : 0|8@1+ (1,0) [0|255] "km/h" ECU2
 SG_ CoolantTemp : 8|8@1+ (1,-40) [-40|215] "degC" ECU2
```

- `BO_ 291`은 메시지 ID 291(10진수)이다. 16진수 `0x123`에 해당한다.
- `ExampleFrame: 8`은 메시지 이름과 DLC 8이다. `ECU1`은 송신자다.
- `SG_`는 신호다. `VehicleSpeed`는 시작 비트 0, 길이 8, 바이트 순서 `@1`(Intel little-endian), 부호 `+`(unsigned), 배율 1, 오프셋 0, 범위 0~255, 단위 km/h, 수신자 ECU2라는 뜻이다.
- `CoolantTemp`는 시작 비트 8, 길이 8, 배율 1, 오프셋 −40이다. 원시 값 0이면 −40°C다.
- 실제 DBC에는 다중화(multiplex) 신호, 값 테이블, 확장 ID 표기 등이 더 있다. 파일마다 문법과 관례가 다르므로, 처음에는 `cantools`로 읽어 구조를 확인한다.

위 파일을 `example.dbc`로 저장하고 `cantools`로 디코딩한다.

```bash
uv add cantools python-can
```

```python
import can
import cantools

db = cantools.database.load_file("example.dbc")
bus = can.Bus(interface="socketcan", channel="can0", receive_own_messages=False)

try:
    while True:
        msg = bus.recv(timeout=1.0)
        if msg is None:
            continue
        try:
            values = db.decode_message(msg.arbitration_id, msg.data)
        except KeyError:
            continue          # DBC에 없는 ID는 건너뛴다
        print(msg.timestamp, values)
finally:
    bus.shutdown()
```

- `decode_message()`는 신호 이름과 값을 dict로 돌려준다. 배율·오프셋·부호를 적용한 뒤의 값이다.
- DBC에 없는 ID는 `KeyError`가 난다. 예외를 삼키지 말고 "디코딩하지 않은 ID"로 따로 세면, DBC에 빠진 메시지를 발견할 수 있다.
- 디코딩된 값이 그럴듯해 보여도 **DBC가 틀리면 조용히 틀린다.** 엔진 회전수를 실제 계기판과 비교하거나, 시동을 걸고 끄면서 값이 변하는지 확인한다. 물리적으로 말이 되는 범위인지도 본다.
- 공개 DBC는 차량·연식·옵션마다 다르다. 라이선스와 적용 범위를 확인하고, 남의 차량 DBC를 그대로 내 차에 맞다고 가정하지 않는다.
- DBC는 "표준"이 아니라 **해석 규칙**이다. 같은 ID라도 다른 DBC에서는 다른 신호일 수 있다. 원시 로그와 DBC 버전을 함께 보관한다.

### OBD 포트에서 어디까지 보이나

- OBD 포트에는 게이트웨이가 진단 요청과 응답을 라우팅한다. 파워트레인·바디 버스의 모든 일반 프레임이 그대로 보인다고 가정하지 않는다.
- `7DF`/`7E0~7E7`/`7E8~7EF`는 진단용 주소다. 일반 차량 프레임은 다른 ID를 쓴다. 8.9절의 "볼 수 없는 것" 목록을 다시 보라.
- 더 많은 프레임을 보려면 해당 버스에 직접 접근해야 하지만, 배선·종단·안전 문제가 커진다. 이 책의 범위는 **OBD 포트에서 읽을 수 있는 것**까지다.
- 기록한 로그를 재생할 때도 송신하지 않는다. `canplayer`는 기본적으로 로그를 재전송하므로, 분석만 하려면 수신 전용 뷰어나 오프라인 디코딩을 쓴다.

### 역공학의 경계

버스 관찰은 "차가 어떻게 동작하는가"를 이해하는 강력한 도구지만, 곧바로 "차를 어떻게 제어할까"로 넘어가기 쉽다. 이 책은 그 선을 넘지 않는다.

- **내 차 또는 허가받은 차**의 진단·연구 목적 읽기만 한다.
- **주행 중 조작하지 않는다.** 기록은 정차 상태에서 시작하고, 주행 중에는 조수석·기록 장치만 쓴다.
- **안전·배출가스·도난 방지 장치를 우회하지 않는다.** 11장에서 설명한 법적·윤리적 문제가 된다.
- **타인의 차량·VIN·위치를 공개하지 않는다.** 로그 공유 전에 식별 정보를 지운다.
- **취약점을 찾았다면 책임 있게 공개한다.** 제조사·관계 기관에 먼저 알리고, 악용 가능한 세부는 공개하지 않는다.

DBC와 cantools는 "읽은 바이트를 이해하는" 도구이지, "차를 바꾸는" 도구가 아니다. 11장의 안전 계약을 먼저 읽고, 이 절의 실습은 정차 상태의 수동 관찰로 제한한다.

## 8.11 CAN FD·CAN XL·차량 이더넷

7장에서 CAN FD의 기본을 보았다. 이 절은 "다음 세대 네트워크가 왜 필요한가"와 "지금 읽는 차량이 어느 세대인지"를 구분하는 데 초점을 둔다. 2019년 쏘렌토 UM 2.2 디젤의 OBD 포트에서 확인된 것은 **클래식 CAN 11비트 500kbps**다(실차 기록). 이 차의 내부 백본이 차량 이더넷인지, CAN FD를 쓰는지는 확인하지 못했다. 확인되지 않은 차종별 사실은 쓰지 않는다.

### 왜 다음 세대가 필요한가

- 카메라·레이다·라이다·OTA 업데이트처럼 큰 데이터를 주고받는 기능이 늘었다.
- 클래식 CAN은 한 프레임에 8바이트, 최대 1Mbps다. 여러 ECU가 같은 버스를 공유하면 대역폭과 지연이 빠듯해진다.
- 그래서 **데이터 구간만 빠르게 보내는 CAN FD**, **더 큰 프레임과 백본을 겨냥한 CAN XL**, **스위치 기반 차량 이더넷**이 함께 쓰인다. 하나가 다른 하나를 완전히 대체하는 것이 아니라, 목적별로 층을 나눈다.

### CAN FD

| 항목 | 클래식 CAN | CAN FD |
|---|---|---|
| 페이로드 | 최대 8바이트 | 최대 64바이트 |
| 중재 구간 | 최대 1Mbps | 최대 1Mbps(클래식과 호환) |
| 데이터 구간 | 중재와 같은 속도 | BRS로 더 빠르게(보통 2~5Mbps, SIC 트랜시버로 8Mbps) |
| CRC | 15비트 | 17비트(≤16바이트), 21비트(>16바이트) |
| RTR(remote frame) | 지원 | 지원하지 않음 |
| 프레임 형식 | 클래식 | FDF 비트로 구분, BRS/ESI 추가 |

- FD 프레임은 **FDF(FD Format)** 로 구분하고, **BRS(Bit Rate Switch)** 로 데이터 구간의 속도를 바꾼다. **ESI(Error State Indicator)** 는 송신 노드의 오류 상태를 알린다.
- 중재 구간은 클래식과 같은 속도로 유지해야 같은 버스의 클래식 노드가 프레임 시작을 이해할 수 있다.
- 클래식 컨트롤러는 FD 프레임을 오류로 본다. **한 버스에 클래식 노드와 FD 노드를 섞으면 안 된다.** 모든 노드와 트랜시버가 FD를 지원해야 한다.
- ISO 11898-1:2015 FD와 Bosch 1.0 비ISO FD는 CRC·스터핑 규칙이 달라 호환되지 않는다. 장비 스펙을 확인한다.
- 2019 쏘렌토처럼 클래식 CAN 차량은 기존 ELM327로 읽을 수 있지만, FD 차량은 FD 지원 어댑터가 필요할 수 있다. "CAN FD 지원" 표기만 보지 말고, 중재/데이터 비트레이트와 트랜시버 조합을 확인한다.

### CAN XL

- CAN XL은 ISO 11898-1:2024에 포함된 **세 번째 CAN 데이터링크 세대**다. 데이터 필드는 **1~2048바이트**까지 가능하다.
- CAN ID를 **11비트 우선순위 ID** 와 **32비트 수용 필드(AF)** 로 분리한다. 클래식 CAN처럼 ID 하나가 중재와 주소를 겸하지 않는다.
- CRC를 두 개 쓴다. 제어 필드의 **13비트 PCRC** 와 프레임 전체를 보호하는 **32비트 FCRC** 다.
- CAN SIC XL 트랜시버와 PWM 인코딩을 쓰면 **20Mbps 이상**도 가능하다(CiA). 다만 이는 물리 네트워크 설계에 달려 있다.
- 백본·서브백본과 TCP/IP 연동을 겨냥한다. CAN XL 자체가 IP를 대체하는 것이 아니라, IP 패킷을 실을 수 있게 설계된 것이다.
- CAN XL과 CAN FD, 클래식 CAN은 같은 데이터링크 계열이지만 프레임 형식과 트랜시버 요구가 다르다. 혼용 여부는 차량 설계 문서를 확인해야 한다(확인 필요).

### 차량 이더넷

- **100BASE-T1**(IEEE 802.3bw)은 한 쌍의 꼬임선으로 100Mbps를 보내는 차량용 이더넷이다. **1000BASE-T1**(IEEE 802.3bp)은 1Gbps, **10BASE-T1S**(IEEE 802.3cg)는 10Mbps급의 짧은 버스형 연결을 겨냥한다.
- 차량 이더넷은 보통 **스위치**로 점대점 링크를 연결한다. CAN처럼 한 쌍의 선을 모든 노드가 공유하는 버스가 아니다. 링크별 전이중 통신이 가능하고, VLAN·QoS·진단 라우팅을 쓸 수 있다.
- 대표적인 상위 프로토콜은 다음과 같다.
  - **SOME/IP**: AUTOSAR가 정의한 서비스 지향 미들웨어다. 원격 프로시저 호출, 이벤트 알림, 직렬화 형식을 제공하고 UDP/TCP 위에서 동작한다.
  - **DoIP(Diagnostics over IP)**: ISO 13400-2로 표준화된 IP 기반 진단이다. TCP/UDP 13400 포트를 사용하며, 차량 이더넷에 붙은 ECU와 진단 도구가 IP로 통신한다.
- OBD-II 포트가 항상 DoIP를 노출하는 것은 아니다. 차량마다 진단 게이트웨이가 CAN과 이더넷을 어떻게 나누는지 다르다. OBD 포트에 이더넷 핀이 있다고 가정하거나, 모르는 핀에 프로빙하지 않는다.

### 독자에게 무엇이 달라지나

| 네트워크 | 주로 보는 도구 | 이 책에서의 다룸 |
|---|---|---|
| 클래식 CAN 500kbps | ELM327, SocketCAN, USB-CAN | 7~10장, 16~23장 |
| CAN FD | FD 지원 USB-CAN/인터페이스 | 36장(개념·가상 버스) |
| CAN XL | CAN XL 지원 인터페이스·계측기 | 36.8절(개념만) |
| LIN | LIN 트랜시버·분석기 | 37장(개념·PC 계산) |
| 차량 이더넷/DoIP/SOME/IP | 이더넷 인터페이스, DoIP 진단 도구 | 38장(개념·루프백) |

- 독자가 가진 ELM327 클론은 CAN FD·CAN XL·DoIP를 지원하지 않는 경우가 많다. 차량이 이 세대라면 `UNABLE TO CONNECT`·`NO DATA`가 나도 차량 고장으로 단정하지 말고 어댑터 지원 범위를 확인한다.
- CAN FD는 36장에서 가상 버스로, LIN은 37장에서 PC 계산으로, DoIP·SOME/IP는 38장에서 루프백으로 실습한다. CAN XL과 실차 FD·DoIP·이더넷 진단은 범위 밖이다. 실제 차량에서 쓰려면 해당 차량의 진단 문서와 지원 장비를 먼저 확인한다.
- 대역폭이 커질수록 공격 표면도 커진다. 게이트웨이·도메인 분리, 인증, 보안 이벤트 로그가 함께 설계된다. 11장의 읽기 전용·최소 권한 원칙은 여기서도 그대로다.

## 8.12 흔한 실수

| 실수 | 결과 | 확인 |
|---|---|---|
| OBD 포트에 차 전체 트래픽이 보인다고 가정 | 원하는 신호가 안 보임 | 버스별 접근, 게이트웨이 구조 확인 |
| 7DF 응답을 하나로 가정 | 여러 ECU 응답이 섞임 | `ATH1`, 응답 ID별 분리 |
| 응답 주소를 요청 주소로 착각 | 7E8 대신 7E0을 필터링 | 요청 +8 규칙 |
| 차량 CAN에 120Ω 추가 | 종단 값 변화, 통신 불안 | 차량에는 추가하지 않는다 |
| OBD 핀을 I2C/SPI로 프로빙 | ECU 손상 위험 | 6/14는 CAN, 나머지는 제조사 재량 |
| OBD 포트 전원을 상시 사용 | 배터리 방전 | 장시간 사용 후 분리, 퓨즈 확인 |
| 게이트웨이 라우팅을 제조사 문서로 확인하지 않음 | 추정을 사실로 오해 | `추정` 표시를 유지 |

## 8.13 체크리스트

- [ ] 차량의 OBD-II 포트 위치와 핀 배치를 확인했는가
- [ ] 6/14번이 CAN인지, 7/15번 K-line인지 확인했는가
- [ ] 4/5번 접지와 16번 전원을 확인했는가
- [ ] `ATSP0`로 프로토콜을 찾고 `ATDPN`을 기록했는가
- [ ] 기능 주소(7DF)와 물리 주소(7E0~7E7)를 구분했는가
- [ ] 응답 주소가 요청 +8인지 확인했는가
- [ ] 차량 CAN에 120Ω을 추가하지 않았는가
- [ ] OBD 포트가 차 전체 트래픽을 보여 준다고 가정하지 않았는가
- [ ] 게이트웨이 라우팅에 대한 추정을 사실로 쓰지 않았는가
- [ ] 스니핑은 listen-only·수신 전용으로 했는가
- [ ] 원시 로그에 시각·ID·DLC·바이트를 남겼는가
- [ ] DBC 파일의 출처·버전·라이선스를 확인했는가
- [ ] 로그에서 VIN·GPS·경로를 제거했는가
- [ ] 차량이 클래식 CAN/FD/XL/이더넷 중 무엇인지 어댑터·차량 문서로 확인했는가
- [ ] 모르는 OBD 핀이나 이더넷 핀을 프로빙하지 않았는가

## 장 요약

- 자동차는 여러 CAN 버스와 LIN·FlexRay·Automotive Ethernet이 게이트웨이로 연결된 네트워크다.
- 파워트레인 CAN은 빠르고(보통 500kbps), 바디 CAN은 느리다(보통 125kbps). 버스마다 목적과 우선순위가 다르다.
- OBD-II 포트는 16핀 J1962 커넥터다. 6/14번 CAN, 4/5번 접지, 16번 +12V, 7/15번 K-line, 나머지는 제조사 재량이다.
- OBD-II는 J1850 PWM/VPW, ISO 9141-2, ISO 14230-4, ISO 15765-4 CAN을 지원한다. 쏘렌토는 11비트 500kbps CAN이다.
- 기능 주소 7DF는 여러 ECU에 브로드캐스트하고, 물리 주소 7E0~7E7은 특정 ECU에 보낸다. 응답은 7E8~7EF다.
- 쏘렌토에서 엔진 7E0, 변속기 7E1, BCM 7A0, 계기판 7C6, ESC 7D1 등이 응답했다. 이는 이 차 한 대의 기록이다.
- OBD 포트는 진단 창구이지 차량 전체의 와이어탭이 아니다. 게이트웨이가 라우팅하지 않는 트래픽은 보이지 않는다.
- 버스 관찰은 listen-only·수신 전용으로 시작한다. 원시 로그에는 시각·ID·DLC·바이트를 남긴다.
- DBC는 ID와 비트 구간을 신호로 해석하는 규칙이다. cantools로 디코딩하되, DBC가 틀리면 값도 조용히 틀린다.
- CAN FD는 64바이트와 빠른 데이터 구간을, CAN XL은 2048바이트와 20Mbps급 데이터 구간을 겨냥한다. 클래식 CAN과 프레임·트랜시버 요구가 다르다.
- 차량 이더넷은 스위치 기반이며 SOME/IP·DoIP 같은 IP 기반 프로토콜이 올라간다. OBD 포트가 항상 이더넷 진단을 노출하지는 않는다.
- 2019 쏘렌토에서 확인된 것은 클래식 CAN 500kbps다. CAN FD·CAN XL·DoIP 차량 여부는 차량·어댑터 문서로 확인한다.
- 스니핑·역공학은 내 차 또는 허가받은 차의 정차 상태로 제한하고, VIN·위치를 지우며, 안전·배출가스 장치를 우회하지 않는다.
- 게이트웨이는 라우팅·필터링의 경계다. 도메인 분리와 진단 접근 통제를 보안 관점에서 다시 보려면 32.3절과 32.7절을 본다.

다음 장에서는 OBD-II 포트로 실제 쏘렌토의 PID를 읽고, 값을 계산하고, 파이썬 대시보드로 표시한다.

## 정답과 해설

### 1.

1. CAN-H
2. CAN-L
3. 배터리 +12V(type A)
4. 4번 chassis ground, 5번 signal ground. 둘 다 접지지만 차량에 따라 내부 연결이 다를 수 있으므로 도통을 확인한다.

### 2.

1. 엔진 `7E8`, 변속기 `7E9`. 요청 7E0/7E1의 응답은 각각 +8이다.
2. `7E0`(엔진의 물리 주소). 응답은 `7E8`로 온다.
3. OBD-II의 진단 주소 체계에서 물리 요청 7E0~7E7에 대해 응답 7E8~7EF를 쓰도록 정해져 있기 때문이다. 요청 주소와 응답 주소를 혼동하지 않는다.

### 3.

1. OBD 포트는 게이트웨이를 통해 진단 트래픽만 라우팅한다. BCM이 진단 요청에 응답한 것과 바디 CAN의 일반 프레임이 보이는 것은 별개다.
2. "포트 하나로 차 전체를 본다"고 오판해, 원하는 신호가 안 보일 때 코드나 도구만 의심하게 된다. 실제로는 다른 버스에 있는 트래픽일 수 있다.
3. 차량의 버스 구조와 게이트웨이 라우팅 문서를 확인한다. 해당 버스에 직접 접근하려면 배선·종단·안전 문제를 별도로 검토해야 하며, 이 책의 범위 밖이다.

### 4.

1. 버스에 ACK나 프레임을 보내지 않고 수신만 해서, 관찰이 차량 통신에 영향을 주지 않게 한다.
2. 시각, CAN ID, DLC, 데이터 바이트가 들어간다. `-L`은 재생 가능한 로그 형식이다.
3. 값이 그럴듯하지만 실제와 다른 채로 조용히 디코딩된다. 원시 바이트와 물리적 거동(계기판, rpm 변화)을 대조해야 한다.

### 5.

1. 아니다. 소유자의 허가가 필요하고, 공용 주차장에서 타인 차량을 관찰하는 것은 법·윤리 문제가 될 수 있다.
2. 소유자의 서면 허가, 정차 상태, 읽기 전용, 개인정보 제거, 안전·배출가스 장치를 건드리지 않는다는 합의를 확인한다.
3. VIN·번호판·GPS·주행 경로를 제거하고, 원본 접근을 제한한다. 취약점이 있으면 책임 있게 공개한다.
