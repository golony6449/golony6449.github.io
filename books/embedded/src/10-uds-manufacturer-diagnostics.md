# 10장 UDS와 제조사 진단

## 이 장에서

9장의 OBD-II Mode 01은 공개된 PID만 읽는다. 회전수·차속·냉각수 온도는 읽을 수 있지만, 변속기 오일 온도·기어 단수·DPF 매연량·계기판 주행거리는 표준 PID에 없다. 이 데이터는 제조사 고유 영역에 있고, 보통 **UDS(Unified Diagnostic Services, ISO 14229)** 의 `0x22 ReadDataByIdentifier`로 읽는다.

웹 개발자에게 UDS는 **공개 API 바깥의 사내 API**에 가깝다. 서비스 코드·세션·NRC는 ISO 14229가 정하지만, 어떤 DID가 어떤 값을 주는지는 문서 밖에 있고 제조사마다 다르다. 9장에서 본 "공개 API와 사내 API" 비유가 여기서 본격적으로 나온다.

이 장은 UDS의 전체 문법을 가르치는 것이 목적이 아니다. **읽기 전용 진단**에 필요한 만큼만 다룬다. 서비스 코드, 긍정/부정 응답, DID, 세션, NRC를 이해하고, 쏘렌토에서 확인된 제조사 데이터를 해석한다. 쓰기·루틴·보안 접근·플래싱은 왜 위험한지 설명하되, 실제로 보내지 않는다.

이 장에서 다루는 것:

- UDS 요청/응답 형식과 긍정/부정 응답
- 읽기 서비스와 쓰기·위험 서비스의 구분
- `0x22 ReadDataByIdentifier`와 DID
- 부정 응답 코드(NRC)
- 세션(`0x10`)과 `0x3E TesterPresent`
- DTC 읽기(`0x19`)와 삭제(`0x14`)의 차이
- 쏘렌토의 계기판·변속기·ESC·DPF 데이터
- ELM327로 `0x22`를 읽는 명령과 파이썬 코드
- DPF 데이터를 해석할 때의 한계

## 10.1 OBD-II와 UDS의 관계

OBD-II와 UDS는 경쟁 관계가 아니라 층이 다르다.

```text
OBD-II Mode 01/03/09     ← 배출가스 규제 중심의 공개 서비스
UDS 0x22/0x19/0x10 ...   ← 제조사 진단, 모든 ECU, 더 많은 데이터
ISO-TP (ISO 15765-2)     ← 8바이트보다 긴 메시지 전송
CAN (ISO 11898)          ← 물리/데이터 링크
```

- OBD-II는 법규가 요구하는 배출가스 관련 데이터와 DTC를 공개한다.
- UDS는 제조사가 정한 DID·루틴·보안 접근을 포함해 더 넓은 진단을 한다.
- 둘 다 CAN 위에서 ISO-TP로 오간다.
- 같은 `7E0` ECU라도 OBD-II 요청(`01 0C`)과 UDS 요청(`22 F1 87`)을 모두 받을 수 있다.
- UDS는 CAN뿐 아니라 LIN, Ethernet, FlexRay 위에서도 쓸 수 있다. 차량에서는 DoCAN(ISO 15765)이 흔하다.

OBD-II가 "공개 API"라면 UDS는 "제조사 내부 API"에 가깝다. 물론 `0x22`처럼 공개된 서비스도 있지만, DID의 의미는 제조사마다 다르다.

상용차·건설기계는 이 구조 대신 J1939를 쓴다. 진단도 UDS `0x19` 대신 DM1(PGN 65226)의 SPN/FMI를 읽는다. 같은 "고장 코드"라도 형식과 전달 방식이 다르므로, 27장에서 따로 다룬다.

## 10.2 UDS 메시지 형식

UDS 요청의 첫 바이트는 서비스 ID(SID)다. 긍정 응답의 첫 바이트는 보통 **SID + 0x40**이다.

```text
요청:  22 F1 87
응답:  62 F1 87 39 35 34 41 30 ...   ← 0x22 + 0x40 = 0x62

요청:  10 03
응답:  50 03 ...

요청:  19 02 FF
응답:  59 02 ...
```

부정 응답은 항상 `7F <요청 SID> <NRC>` 세 바이트로 시작한다.

```text
요청:  22 F1 87
응답:  7F 22 31        ← 0x22 서비스, NRC 0x31(requestOutOfRange)
```

- `7F`는 부정 응답 표시다.
- 두 번째 바이트는 실패한 요청의 SID다.
- 세 번째 바이트는 이유(NRC)다.
- 긍정 응답의 데이터 형식은 서비스마다 다르다. `0x22`는 `62 <DID hi> <DID lo> <data...>`다.

## 10.3 서비스 분류: 읽기, 삭제, 쓰기, 위험

UDS 서비스를 "읽기"와 "쓰기"로만 나누면 위험하다. 삭제·리셋·루틴·보안 접근은 읽기가 아니지만, 쓰기와도 다르다. 이 책의 기준은 다음과 같다.

| 분류 | 서비스 | 이 책에서 |
|---|---|---|
| 읽기 | `0x22` ReadDataByIdentifier, `0x19` ReadDTCInformation, `0x3E` TesterPresent | 허용. 정차 상태에서 |
| 읽기(주의) | `0x23` ReadMemoryByAddress | 권장하지 않음. 메모리 노출·오작동 위험 |
| 삭제 | `0x14` ClearDiagnosticInformation, OBD Mode 04 | 보내지 않음 |
| 쓰기/작동 | `0x2E` WriteDataByIdentifier, `0x2F` InputOutputControlByIdentifier, `0x31` RoutineControl | 보내지 않음 |
| 위험 | `0x10` DiagnosticSessionControl(프로그래밍 세션), `0x11` ECUReset, `0x27` SecurityAccess, `0x34`~`0x37` 다운로드/전송, `0x3D` WriteMemoryByAddress | 보내지 않음 |

`0x10`은 "세션 전환"이라 읽기처럼 보일 수 있지만, 프로그래밍 세션은 쓰기·플래싱의 문을 여는 단계다. `0x27`은 보안 접근이고, `0x2F`는 액추에이터를 직접 구동할 수 있다. `0x31`은 DPF 강제 재생 같은 루틴을 실행할 수 있다. **읽기 전용 원칙은 이 서비스들을 보내지 않는 것까지 포함한다.**

## 10.4 부정 응답 코드(NRC)

자주 만나는 NRC만 정리한다.

| NRC | 이름 | 뜻 | 대응 |
|---|---|---|---|
| 0x10 | generalReject | 일반 거부 | 요청 형식 확인 |
| 0x11 | serviceNotSupported | 서비스 미지원 | 다른 서비스 시도(예: 0x22 대신 0x21) |
| 0x12 | subFunctionNotSupported | 하위 기능 미지원 | 하위 기능 값 확인 |
| 0x13 | incorrectMessageLengthOrInvalidFormat | 길이·형식 오류 | 요청 바이트 수 확인 |
| 0x21 | busyRepeatRequest | 바쁨, 다시 요청 | 잠시 후 재시도 |
| 0x22 | conditionsNotCorrect | 조건 불충족 | 엔진 상태·세션·온도 확인 |
| 0x24 | requestSequenceError | 순서 오류 | 선행 서비스 확인 |
| 0x31 | requestOutOfRange | 범위 밖 | DID/PID가 없음. 재시도 무의미 |
| 0x33 | securityAccessDenied | 보안 접근 거부 | 보안 접근하지 않는다 |
| 0x35 | invalidKey | 키 오류 | 보안 접근하지 않는다 |
| 0x36 | exceedNumberOfAttempts | 시도 횟수 초과 | 더 시도하지 않는다 |
| 0x37 | requiredTimeDelayNotExpired | 대기 시간 미경과 | 기다린다 |
| 0x78 | requestCorrectlyReceived-ResponsePending | 응답 대기 | 기다린다. 재요청 금지 |
| 0x7E | subFunctionNotSupportedInActiveSession | 현재 세션에서 하위 기능 미지원 | 세션 전환하지 않는다 |
| 0x7F | serviceNotSupportedInActiveSession | 현재 세션에서 서비스 미지원 | 세션 전환하지 않는다 |

`0x31`은 "그 DID가 없다"는 뜻이므로 같은 요청을 반복해도 결과가 같다. `0x78`은 "곧 응답한다"는 뜻이므로 기다린다. `0x7F`는 "기본 세션에서는 안 된다"는 뜻인데, **세션을 바꾸면 위험한 서비스가 열릴 수 있으므로 이 책에서는 포기한다.**

## 10.5 0x22 ReadDataByIdentifier

`0x22`는 DID(Data Identifier)로 데이터를 읽는다. DID는 2바이트다.

```text
요청:  22 F1 87
응답:  62 F1 87 <data...>
```

- `F1xx` 대역은 식별 정보(부품번호, 버전, VIN 등)에 많이 쓰인다.
- `B0xx`, `01xx`, `EDxx` 같은 대역은 제조사가 자유롭게 쓴다.
- 같은 DID 번호라도 **ECU가 다르면 의미가 다르다.** `B002`는 계기판(7C6)에서는 주행거리지만, 다른 ECU에서는 전혀 다른 값일 수 있다.
- 응답 데이터의 **바이트 오프셋**은 DID 문서에 있다. "DID 뒤 데이터의 0번째 바이트"를 기준으로 센다.
- 여러 DID를 한 요청에 넣을 수도 있다(`22 F1 87 F1 90`). 응답은 DID별로 이어지지만, 구현에 따라 지원이 다르다. 초보자는 하나씩 읽는다.

### ELM327로 읽기

```text
>ATH1
OK
>ATSH7E0
OK
>22F187
7E8 10 14 62 F1 87 39 35 34
7E8 21 41 30 30 30 30 30 30
7E8 22 30 30 30 30 30 30 30
```

- `ATSH7E0`은 이후 요청의 헤더를 엔진 ECU로 바꾼다.
- `ATH1`이면 CAN ID와 ISO-TP PCI가 보인다. `ATH0`이면 ELM327이 조립한 데이터만 보인다.
- 긴 응답은 `10 14`(FF) → `21`(CF1) → `22`(CF2)로 온다.
- `62 F1 87` 뒤 데이터가 부품번호다. 위 예시는 테스트용 가짜 문자열이다.
- 표준 주소로 돌아가려면 `ATSH7DF` 또는 `ATAR`을 쓴다.
- 위 로그는 `ATH1`로 원시 프레임을 본 예시다. 아래 `read_did()`는 `ATH0` 기준이므로, 코드로 읽을 때는 `ATH0`을 보낸 뒤 호출한다.
- 7E0~7E7 밖의 주소로 요청할 때는 `ATCRA <응답 주소>`, `ATFCSH <요청 주소>`, `ATFCSD 30 00 00`, `ATFCSM 1`이 필요할 수 있다. 클론에 따라 인자 없는 `ATCRA`가 `?`를 돌려주므로 `ATAR`로 필터를 푼다.

### 파이썬으로 읽기

9장의 `Elm327` 클래스에 다음 함수를 붙인다.

```python
def read_did(elm: "Elm327", did: int, timeout: float = 2.0):
    """0x22로 DID를 읽고 (데이터, NRC)를 돌려준다. 성공하면 NRC는 None.

    ATH0(헤더 숨김) + CAF1(자동 포맷) 기준이다. ATH1이면 CAN ID와 PCI가
    섞이므로 이 함수를 쓰지 말고 ISO-TP를 직접 조립한다.
    """
    lines = elm.command(f"22{did:04X}", timeout=timeout)

    tokens: list[int] = []
    for line in lines:
        if ":" in line:                 # ELM327의 '0:', '1:' 조립 줄
            line = line.split(":", 1)[1]
        for part in line.split():
            try:
                tokens.append(int(part, 16))
            except ValueError:
                pass                    # SEARCHING..., NO DATA 등

    if any(token > 0xFF for token in tokens):
        raise ValueError("ATH1 응답이 섞였습니다. ATH0으로 헤더를 끄세요.")

    for i in range(len(tokens) - 2):
        if tokens[i] == 0x62 and (tokens[i + 1] << 8 | tokens[i + 2]) == did:
            return bytes(tokens[i + 3:]), None
        if tokens[i] == 0x7F and tokens[i + 1] == 0x22:
            return None, tokens[i + 2]
    return None, None
```

- `62`와 DID를 확인해 다른 응답과 섞이지 않게 한다.
- `7F 22 xx`면 NRC를 돌려준다.
- `SEARCHING...`, `NO DATA`, `?` 같은 문자열은 16진수 변환에서 걸러진다.
- 이 함수는 `ATH0`(헤더 숨김) 기준이다. `ATH1`이면 CAN ID와 PCI가 섞여 `bytes()` 변환도 실패하므로, `ATH0`으로 바꾼 뒤 호출한다. `ATH1` 원시 프레임은 3장의 ISO-TP 조립 코드로 처리한다.
- 긴 응답에서 ELM327이 `0:`/`1:`로 조립해 주면 `:` 뒤만 이어 붙인다.

## 10.6 세션과 TesterPresent

UDS ECU는 세션을 가진다.

- **기본 세션(default)**: 시동 후 기본. 읽기 서비스 일부만 허용.
- **프로그래밍 세션**: 플래싱·쓰기를 위한 세션. `0x10 02`.
- **확장 세션**: 제조사 진단을 위한 세션. `0x10 03`.

`0x10`으로 세션을 바꾸면 더 많은 서비스가 열린다. 그것이 **쓰기·플래싱의 문**이다. 이 책에서는 세션을 바꾸지 않는다. `0x7F 22 7F`(현재 세션에서 미지원)를 받아도 "세션을 바꿔서 다시 시도"하지 않는다.

`0x3E TesterPresent`는 "테스터가 연결되어 있다"고 알려 세션 유지 시간을 늘린다. 그 자체는 상태를 바꾸지 않지만, 세션을 유지하려는 목적이면 쓰지 않는다. 한 번 읽고 끝내는 작업에는 필요 없다.

```text
>3E00
7E 00        ← TesterPresent 긍정 응답(에코 형태)
```

- `0x3E`는 읽기 목록에 넣을 수 있지만, 이 책의 실습에서는 보내지 않아도 된다.
- 세션이 필요한 제조사 DID는 "기본 세션에서 미지원"일 수 있다. 그때는 **읽지 못하는 것으로 받아들인다.**

## 10.7 DTC 읽기(0x19)와 삭제(0x14)

UDS의 `0x19 ReadDTCInformation`은 OBD-II Mode 03보다 더 자세한 DTC 정보를 준다. 하위 기능에 따라 DTC 개수, 상태 마스크별 목록, 스냅샷, 확장 데이터를 읽는다. 하위 기능 값과 응답 형식은 ISO 14229 문서를 확인해야 한다.

`0x14 ClearDiagnosticInformation`은 DTC와 관련 데이터를 지운다. OBD-II Mode 04와 같은 위험이 있다.

- DTC를 지우면 readiness monitor가 초기화될 수 있다.
- 배출가스 검사 전에 지우면 불합격할 수 있다.
- 고장 원인을 확인하지 않고 지우면 재발까지 시간이 걸린다.
- Permanent DTC는 쉽게 지워지지 않는다.
- **이 책에서는 `0x14`를 보내지 않는다.** DTC를 읽는 `0x19`만 다룬다.

| 7E0 | ED03 | 41..44 | 마지막 재생 주행거리 | 32비트 / 1000 km | 문헌 기반 |
| 7E0 | ED03 | 45..48 | 재생 후 거리 | 32비트 / 1000 km | 문헌 기반 |
| 7E0 | ED03 | 49..52 | ECU 주행거리 | 32비트 / 1000 km | 문헌 기반 |
| 7E0 | ED03 | 53 | 재생 성공 상태 | 스칼라 | 문헌 기반 |
| 7E0 | ED03 | 54 | 재생 후 연료 | A × 1.2549 L | 문헌 기반 |
| 7E0 | ED03 | 55 | 재생 횟수 | 스칼라 | 문헌 기반 |
| 7E0 | ED94 | 7 | DPF 매연량 | A × 99 / 255, 단위 gravity | 문헌 기반 |
| 7E0 | ED29 | 0..1 | DPF 누적 황 질량 | 16비트 × 0.15259, 단위 불명 | 문헌 기반 |
| 7E0 | E0F1 | 31 | DPF 차압(대체) | A × 4.3137 − 100 | 문헌, 값이 음수라 의심 |

- `실차 확인`은 계기판·엔진 rpm 등과 대조했다는 뜻이다.
- `문헌 기반`은 OBDb 공식을 실차 응답에 적용했지만, 값의 물리적 의미를 완전히 검증하지 않았다는 뜻이다.
- `단위 불명`은 OBDb 원문도 확신하지 못한 단위다. 대시보드에 단위를 붙이지 않는다.
- `E0F1`의 DPF 차압은 실차에서 음수가 나와 의심스럽다. `ED03`의 차압을 우선 본다.
- `ED94`는 쏘렌토 파일에는 없고, 같은 플랫폼의 산타페 파일에 있는 정의다. 쏘렌토 응답에 적용해 본 결과이므로 `문헌 기반`이다.
- `ED03` 41..44와 49..52가 모두 주행거리다. ECU 주행거리가 계기판보다 수백 km 많을 수 있다. 어느 쪽이 "정답"이라고 단정하지 않는다.

### 바이트 오프셋 계산

OBDb의 `bix`는 DID 뒤 데이터의 **비트 위치**다. 0번째 바이트의 MSB가 0이다.

```text
bix 288 → 288 / 8 = 36번째 바이트
bix 320 → 40번째 바이트
bix 328 → 41번째 바이트, len 32 → 41..44
```

값은 `raw × mul / div + add`로 계산한다. `sign`이면 2의 보수, `len`은 비트 수(빅 엔디언)다. OBDb의 공식은 제조사 공식 문서가 아니라 공개 데이터베이스이므로, 값이 이상하면 원문과 실차를 다시 대조한다.

### 디코더 예

```python
def u8(data: bytes, offset: int) -> int:
    return data[offset]


def u16(data: bytes, offset: int) -> int:
    return int.from_bytes(data[offset:offset + 2], "big")


def s16(data: bytes, offset: int) -> int:
    return int.from_bytes(data[offset:offset + 2], "big", signed=True)


def u24(data: bytes, offset: int) -> int:
    return int.from_bytes(data[offset:offset + 3], "big")


def u32(data: bytes, offset: int) -> int:
    return int.from_bytes(data[offset:offset + 4], "big")


def decode_transmission(data: bytes) -> dict[str, float | int]:
    return {
        "rpm": u16(data, 4) / 4,
        "speed": u8(data, 6),
        "pedal": u8(data, 8) * 100 / 255,
        "turbine": u16(data, 9) / 4,
        "output": u16(data, 11) / 4,
        "atf_temp": u8(data, 13) - 40,
        "slip": u16(data, 16) / 4 - 512,
        "lever": u8(data, 20),
        "gear": u8(data, 21),
        "target_gear": u8(data, 22),
    }


def decode_dpf(data: bytes) -> dict[str, float | int]:
    return {
        "diff_pressure": u8(data, 36) * 4.31373,
        "doc_temp": u8(data, 37) * 4.7098 + 99,
        "dpf_temp": u8(data, 38) * 4.7098 + 99,
        "regen_demand": u8(data, 40),
        "last_regen_km": u32(data, 41) / 1000,
        "since_regen_km": u32(data, 45) / 1000,
        "ecu_odo_km": u32(data, 49) / 1000,
        "regen_ok": u8(data, 53),
        "fuel_since_regen": u8(data, 54) * 1.2549,
        "regen_count": u8(data, 55),
    }
```

- `decode_transmission`은 `22 01A0` 응답 데이터에 적용한다.
- `decode_dpf`는 `22 ED03` 응답 데이터에 적용한다.
- 길이를 확인하지 않고 오프셋을 읽으면 `IndexError`가 난다. 실제 코드에서는 `len(data) >= 56` 같은 검사를 넣는다.
- `atf_temp`는 53~54°C 같은 값이 나오면 그럴듯하다. 215°C 같은 값이 나오면 오프셋이나 공식을 의심한다.
- `diff_pressure`의 단위는 모른다. "4.3" 같은 값을 kPa로 단정하지 않는다.

## 10.9 DPF 데이터를 읽을 때

DPF(Diesel Particulate Filter)는 디젤 배기가스의 그을음을 걸러 내는 필터다. 그을음이 쌓이면 배압이 올라가고, ECU가 **재생(regeneration)** 을 해서 그을음을 태운다.

- 자연 재생(passive): 주행 중 배기가스 온도로 자연히 연소.
- 능동 재생(active): ECU가 연료를 추가로 분사해 배기가스 온도를 높임.
- 강제 재생(forced): 정비 도구로 루틴을 실행. 높은 온도와 안전 조건이 필요.

실차 데이터에서 볼 수 있는 것:

- DPF 차압(`ED03` 36): 필터가 막힐수록 올라가는 경향.
- DPF 전단 온도(`ED03` 38): 재생 중에는 수백 °C까지 올라간다.
- 재생 요구 카운터(`ED03` 40): 그을음이 쌓여 재생이 필요하다고 판단한 횟수.
- 마지막 재생 주행거리(`ED03` 41..44), 재생 후 거리(`45..48`).
- 재생 횟수(`ED03` 55), 재생 성공 상태(`53`).
- 매연량(`ED94` 7): OBDb 정의는 `A × 99 / 255`, 단위는 `gravity`로 되어 있다.

**하지 말 것:**

- `0x31 RoutineControl`로 강제 재생을 실행하지 않는다. 배기가스 온도가 매우 높아지고, 차량 주변 가연물·밀폐 공간·엔진 상태에 따라 화재·손상 위험이 있다.
- DPF 경고등이 켜진 상태에서 임의로 데이터만 보고 "괜찮다"고 판단하지 않는다. 제조사 정비 절차를 따른다.
- DPF를 물리적으로 제거하거나 재생 기능을 무력화하지 않는다. 배출가스 규제 위반이고, 국내 법령·보증에도 문제가 될 수 있다.

**할 수 있는 것:**

- 정차 상태에서 차압·온도·재생 카운터를 **읽기만** 한다.
- 같은 주행 조건에서 값의 추세를 기록한다. 예: 시동 직후 vs 20분 주행 후.
- 값이 비정상적으로 보이면 정비사에게 데이터를 보여 준다. 진단은 정비사의 몫이다.

## 10.10 흔한 실수

| 실수 | 결과 | 확인 |
|---|---|---|
| DID 번호만 보고 의미를 단정 | 다른 ECU의 같은 DID를 잘못 해석 | ECU 주소와 DID를 함께 본다 |
| 바이트 오프셋을 1부터 셈 | 모든 값이 한 바이트씩 밀림 | DID 뒤 데이터의 0번째부터 |
| `7F 22 31`을 재시도 | 같은 결과 | 그 DID가 없다. 다른 DID 시도 |
| `7F 22 78`을 실패로 판단 | 불필요한 재요청 | 기다린다 |
| `0x10`으로 세션 전환 | 쓰기·플래싱의 문이 열림 | 세션을 바꾸지 않는다 |
| `0x2F`/`0x31`을 "읽기"로 착각 | 액추에이터 구동·루틴 실행 | 읽기 서비스만 보낸다 |
| `0x14`로 DTC 삭제 | readiness 초기화, 검사 불합격 | DTC는 읽기만 |
| OBDb 공식을 제조사 공식으로 착각 | 틀린 단위·오프셋을 확정 | `문헌 기반` 표시 유지 |
| DPF 차압을 kPa로 단정 | 단위 오류 | 단위 불명으로 둔다 |
| 강제 재생 루틴 실행 | 고온·화재·필터 손상 | 정비사에게 맡긴다 |

## 10.11 체크리스트

- [ ] ECU 주소와 DID를 함께 기록했는가
- [ ] 요청 SID와 긍정 응답 SID(+0x40)를 확인했는가
- [ ] `7F <SID> <NRC>`를 해석했는가
- [ ] 데이터 오프셋을 0부터 셌는가
- [ ] 공식의 `mul/div/add/sign`을 확인했는가
- [ ] 단위가 `unknown`/`gravity`인 값을 단정하지 않았는가
- [ ] 세션을 바꾸지 않았는가
- [ ] `0x2E`, `0x2F`, `0x31`, `0x27`, `0x14`를 보내지 않았는가
- [ ] DPF 데이터를 읽기만 했는가
- [ ] VIN을 저장·공개하지 않았는가

## 장 요약

- UDS는 OBD-II 위에 제조사 진단을 얹는 표준이다. CAN 위에서는 ISO-TP로 오간다.
- 요청은 `SID`, 긍정 응답은 `SID + 0x40`, 부정 응답은 `7F SID NRC`다.
- `0x22`는 DID로 데이터를 읽는다. 같은 DID라도 ECU마다 의미가 다르다.
- NRC `0x31`은 DID 없음, `0x78`은 응답 대기, `0x7F`는 현재 세션 미지원이다.
- `0x10` 세션 전환, `0x2E` 쓰기, `0x2F` IO 제어, `0x31` 루틴, `0x27` 보안 접근, `0x14` 삭제는 이 책에서 보내지 않는다.
- 쏘렌토에서는 계기판 주행거리, 변속기 rpm·ATF 온도·기어, ESC 바퀴 속도·조향각, DPF 차압·온도·재생 카운터를 읽을 수 있었다.
- 제조사 DID 공식은 OBDb 같은 공개 데이터베이스와 실차 응답을 대조한 것이다. 제조사 공식 문서가 아니므로 `문헌 기반` 표시를 유지한다.
- DPF 강제 재생은 정비 절차다. 읽기만 하고 실행하지 않는다.
- `0x27` SecurityAccess와 `0x29` Authentication의 차이, 진단 접근 통제는 26.7절에서 다룬다. 이 책은 실차에서 두 서비스를 보내지 않는다.

다음 장에서는 지금까지 배운 읽기 기술을 안전하게 쓰기 위한 규칙을 정리한다. 주행 중 조작, 쓰기 명령, 배터리, 보증, 개인정보, 법규가 주제다.

## 정답과 해설

### 1.

1. `62`는 `0x22`의 긍정 응답, `F1 87`은 DID, 뒤는 데이터다. 부품번호나 식별 문자열의 일부다.
2. `7F` 부정 응답, `22` 요청 서비스, `31` requestOutOfRange. 그 DID가 없거나 범위 밖이다. 같은 요청을 반복해도 결과가 같다.
3. `7F 22 78`은 responsePending이다. ECU가 곧 응답하겠다는 뜻이므로 재요청하지 말고 기다린다.

### 2.

1. `0x20 = 32`이고 `32 × 4.31373 = 138.03936`. 계산은 되지만 단위가 unknown이므로 "무엇의 138.0인지" 말할 수 없다.
2. 안 된다. `문헌 기반` 또는 `확인 필요`로 표시하고, 실차 대조나 제조사 문서 없이 확정하지 않는다.

### 3.

1. `0x19`는 DTC 개수·상태 마스크·스냅샷·확장 데이터 등 더 자세한 정보를 읽는다. Mode 03은 저장된 DTC 목록 중심이다.
2. DTC와 관련 데이터를 지운다. OBD Mode 04와 같은 위험이 있다.
3. 삭제는 읽기처럼 보이지만 readiness를 초기화하고 진단 근거를 없앤다. "읽기 전용" 원칙에는 삭제 금지가 포함된다.

### 4.

1. 현재 세션에서 그 서비스가 지원되지 않는다는 뜻이다.
2. 아니다. 세션을 바꾸면 쓰기·플래싱의 문이 열릴 수 있다. 이 책은 세션 전환을 하지 않는다.
3. 읽지 못하는 것으로 받아들이고 종료한다. 다른 DID나 기본 세션에서 허용된 읽기만 시도한다.

### 5.

1. 요청 `22 B0 02`(7C6), 긍정 응답 `62 B0 02 <data...>`(7CE). 응답은 요청 +8 주소로 온다.
2. 24비트 빅 엔디언 `0x02258C = 140684km`.
3. DID·바이트 오프셋·엔디언이 맞는지, 응답이 다른 ECU에서 온 것은 아닌지, 계기판 단위가 km인지 먼저 확인한다. 값이 비슷하지만 다를 수 있으므로 오차 범위와 출처를 기록한다.
