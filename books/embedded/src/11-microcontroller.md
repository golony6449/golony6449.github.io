# 11장 마이크로컨트롤러

## 이 장에서

MCU(Microcontroller Unit)는 CPU·플래시·RAM·주변장치를 한 칩에 넣은 컴퓨터다. 웹 서버처럼 OS 위에서 프로세스를 돌리는 대신, 보통은 `main()` 하나와 인터럽트로 모든 일을 한다.

웹 개발자에게 MCU는 "아주 작은 서버"처럼 보일 수 있다. 하지만 베어메탈에서는 프로세스도, 스레드도, 파일 시스템도, 가비지 컬렉터도 없다. 대신 인터럽트, 링 버퍼, 상태 기계, 워치독이 있다. 이 장은 그 구조를 잡는 방법을 다룬다. 통신 자체보다 **통신을 돌리는 그릇**에 가깝다.

이 장에서 다루는 것:

- MCU와 SBC(라즈베리파이 같은 단일 보드 컴퓨터)의 차이
- 대표 보드의 특성과 선택
- 인터럽트에서 지켜야 할 규칙
- ISR과 메인 루프 사이의 링 버퍼
- `delay()` 없는 메인 루프와 상태 기계
- 메모리 영역과 절약 습관
- GPIO·ADC·PWM·타이머
- 펌웨어 업로드와 디버깅
- RTOS를 쓸지 판단하는 기준
- 차량 ECU와 ELM327 안의 MCU가 하는 일
- UART 인터럽트 → 링 버퍼 → OBD 요청 상태 기계

## 11.1 MCU와 SBC는 다르다

| 구분 | MCU (ESP32, STM32, AVR) | SBC (Raspberry Pi 등) |
|---|---|---|
| OS | 베어메탈 또는 RTOS(Real-Time Operating System) | Linux |
| 메모리 | KB~수백 KB | GB |
| 부팅 | 즉시(ms) | 수십 초 |
| 실시간성 | 타이밍 예측 가능 | 스케줄러·SD 카드·전원에 좌우 |
| 전력 | mA, sleep 시 µA | 수백 mA~수 W |
| 저장 | 내장 플래시 | SD 카드/eMMC |
| 용도 | 센서 제어, 실시간 I/O | 게이트웨이, 영상, DB |

"라즈베리파이로 하면 되지"가 항상 답은 아니다. 전원·부팅 시간·SD 카드 손상·실시간 지연이 문제가 되는 현장에서는 MCU가 낫다. 반대로 복잡한 네트워크·DB·영상 처리는 SBC가 낫다. 둘을 나눠 MCU가 실시간 I/O를 맡고 SBC가 통신을 맡는 구성도 흔하다.

이 표는 "MCU가 더 좋다"는 뜻이 아니다. **문제에 맞는 도구를 고르라**는 뜻이다. 웹 개발자가 익숙한 Linux 환경을 억지로 MCU에 이식하려 하면 실시간성과 전력에서 손해를 본다.

차량에는 두 종류의 MCU가 있다.

- **ECU 안의 MCU**: 엔진·변속기·브레이크를 실시간으로 제어한다. ms 단위 마감이 있고, 보통 AUTOSAR/RTOS 또는 정교한 베어메탈 스케줄러 위에서 돈다. 이 펌웨어는 제조사 영역이고, 이 책에서 작성·수정하지 않는다.
- **진단 어댑터 안의 MCU**: ELM327은 OBD 프로토콜과 UART를 해석하는 작은 MCU다. 차량 제어에는 관여하지 않고, 요청을 번역해 주는 인터프리터다.

우리가 만드는 것은 보통 두 번째, 또는 그 옆의 게이트웨이 MCU다. 차량 ECU의 제어 루프를 직접 건드리는 것이 아니다. 이 구분을 잊으면 "내 코드가 ECU를 제어한다"는 착각에 빠진다. **OBD-II는 제어 인터페이스가 아니라 진단 인터페이스다.**

## 11.2 대표 보드 비교

| 보드 | MCU | 클록 | 플래시/RAM | 논리 전압 | 특징 |
|---|---|---|---|---|---|
| Arduino Uno R3 | ATmega328P (AVR) | 16 MHz | 32KB / 2KB | 5V | 입문용, 8비트, 주변장치 단순 |
| Arduino Uno R4 | Renesas RA4M1 (Cortex-M4) | 48 MHz | 256KB / 32KB | 5V | 32비트, USB-C, Uno 호환 |
| ESP32 DevKit | ESP32 (Xtensa LX6 듀얼) | 240 MHz | 4MB / 520KB (보드별) | 3.3V | Wi-Fi+BLE, IoT에 최적 |
| ESP32-S3 / C3 | LX7 듀얼 / RISC-V 싱글 | 240 / 160 MHz | 보드별 | 3.3V | USB·BLE 5·저전력 변형 |
| STM32 Nucleo / Blue Pill | Cortex-M0+/M3/M4/M7 | 보드별(예: Blue Pill F103 72 MHz, Nucleo-F401 84 MHz, Nucleo-H743 480 MHz) | 보드별 | 3.3V | HAL(Hardware Abstraction Layer)/LL(Low-Layer), SWD(Serial Wire Debug) 디버깅, 산업용 |
| Raspberry Pi Pico | RP2040 (Cortex-M0+ 듀얼) | 133 MHz | 2MB / 264KB | 3.3V | PIO(Programmable I/O), MicroPython/C SDK, 저렴 |

입문 순서는 보통 **Arduino(개념) → ESP32(통신/IoT) → STM32(전문)** 또는 Pico(파이썬 친화)다.

보드를 고를 때는 다음을 확인한다.

- Arduino Uno R3의 `int`는 16비트다. `long`을 32비트로 가정하지 말고 `stdint.h` 타입을 쓴다.
- ESP32는 3.3V 논리이고 5V tolerant가 아니다. 5V 센서를 직결하면 핀이 상한다. 레벨 시프터나 분압을 쓴다.
- STM32는 5V tolerant 핀이 일부 있지만 전체가 아니다. 데이터시트의 FT 표기를 확인한다.
- ESP32 개발 보드의 USB 5V(VIN)는 입력이지만, GPIO에 5V를 넣는 것과는 전혀 다르다.

"입문용"이라는 표기는 성능이 낮다는 뜻이 아니라 **배울 것이 적다**는 뜻이다. Arduino Uno R3는 8비트이고 메모리가 작아서, 오히려 임베디드의 제약을 몸으로 익히기에 좋다.

## 11.3 인터럽트

인터럽트(ISR)는 하드웨어 이벤트가 발생하면 메인 코드를 잠시 멈추고 실행되는 함수다. 시리얼 수신, 타이머, GPIO 변화, ADC 완료 등에 쓴다.

웹의 이벤트 리스너와 비슷하게 생각할 수 있지만, 결정적인 차이가 있다. 웹의 콜백은 이벤트 루프가 처리할 준비가 되었을 때 실행되지만, ISR은 **지금 실행 중인 코드를 즉시 중단**한다. 그래서 ISR은 짧아야 하고, 공유 데이터의 원자성을 직접 생각해야 한다.

### 원칙

- **짧게.** ISR 안에서 `delay()`, 긴 루프, `printf`, `malloc`, 파일 I/O, 네트워크를 하지 않는다.
- **공유 변수는 `volatile`.** 컴파일러가 매번 메모리에서 읽게 한다. 하지만 `volatile`은 **원자성을 보장하지 않는다.**
- **원자성.** 8비트 AVR에서 16비트 변수를 읽는 동안 ISR이 쓰면 반쪽 값이 나올 수 있다. 인터럽트를 잠시 끄거나, 8비트 변수/더블 버퍼/시퀀스 카운터를 쓴다. Cortex-M의 정렬된 32비트 접근은 원자적이다.
- **ISR에서는 큐/링 버퍼에 넣기만** 하고, 실제 처리는 메인 루프나 태스크에서 한다.
- 디바운스·엣지 검출은 ISR에서 최소한으로 하고, 타이머로 시간을 재는 편이 안전하다.
- 우선순위와 중첩을 지원하는 MCU에서는 긴 ISR이 다른 ISR을 지연시킨다. 우선순위를 설계한다.
- `volatile` 변수 여러 개를 함께 갱신해야 한다면 락/인터럽트 차단/원자적 구조가 필요하다. ESP32 듀얼코어에서는 `volatile`만으로 부족하고 원자 연산이나 큐를 쓴다.

### ISR에서 하면 안 되는 일

| 하면 안 되는 일 | 이유 |
|---|---|
| `delay()` | 그동안 다른 인터럽트와 메인 루프가 멈춘다 |
| `printf` | 내부 버퍼·포맷팅·블로킹 가능성 |
| `malloc`/`free` | 힙 조각화, 실행 시간 예측 불가 |
| 긴 루프/파일 I/O/네트워크 | 실시간 마감을 놓친다 |
| 공유 변수 다중 갱신 | 원자성이 깨진다 |

## 11.4 링 버퍼

링 버퍼는 ISR과 메인 루프 사이에서 바이트를 넘기는 표준 구조다. 생산자 하나, 소비자 하나(SPSC)면 락 없이 동작한다.

```text
buf:  [ d0 ][ d1 ][ d2 ][    ][    ][    ][    ]
        ↑tail        ↑head
```

`head`는 생산자가 쓰는 위치, `tail`은 소비자가 읽는 위치다. 둘 다 앞으로만 움직이고, 끝에 닿으면 0으로 돌아간다. 한 칸을 비워 두어 "가득 참"과 "비었음"을 구분한다.

```c
#include <stdbool.h>
#include <stdint.h>

#define RB_SIZE 256u  // 8비트 인덱스가 한 바퀴 도는 크기

#if RB_SIZE != 256
#error "8비트 인덱스 wrap을 사용하는 예제라 RB_SIZE=256만 지원한다"
#endif

static volatile uint8_t buf[RB_SIZE];
static volatile uint8_t head, tail;  // 8비트라 AVR에서도 접근이 원자적

bool rb_push(uint8_t b) {
    uint8_t next = (uint8_t)(head + 1u);
    if (next == tail) return false;   // 가득 참
    buf[head] = b;
    head = next;
    return true;
}

bool rb_pop(uint8_t *b) {
    if (tail == head) return false;   // 비었음
    *b = buf[tail];
    tail = (uint8_t)(tail + 1u);
    return true;
}
```

- `head`/`tail`을 8비트로 두면 AVR에서도 읽기/쓰기가 원자적이고, 256에서 자연스럽게 0으로 돌아간다. 대신 **이 예제는 `RB_SIZE=256` 전용**이다. 다른 크기를 쓰려면 16비트 인덱스와 마스크, 인터럽트 차단(또는 원자 연산)이 필요하다.
- 일반적으로 크기를 2의 거듭제곱으로 두면 `% RB_SIZE` 대신 `& (RB_SIZE - 1)`로 인덱스를 감쌀 수 있다. 위 코드는 256 전용이라 8비트 wrap을 그대로 쓴다.
- 한 칸을 비워 두는 방식이라 실제 저장 가능 크기는 `RB_SIZE - 1`이다.
- 넘칠 때 정책을 정한다: 새 데이터를 버릴지, 오래된 데이터를 덮어쓸지, 오버플로 카운터를 올릴지.
- 링 버퍼 크기와 최악의 생산 속도를 계산한다. 처리 속도가 생산 속도보다 느리면 언젠가 넘친다.

링 버퍼는 "큐"라는 이름으로 웹에서도 익숙하지만, 여기서는 **ISR과 메인 루프라는 두 실행 문맥**이 공유한다는 점이 다르다. 그래서 인덱스의 폭과 원자성이 설계의 일부가 된다.

차량 OBD 로거에서는 이런 구조가 자연스럽다.

```text
UART RX ISR ──바이트──→ 링 버퍼 ──→ 메인 루프의 ELM327 줄 파서 ──→ PID 값
   (짧게)                (SPSC)              (상태 기계)
```

- ISR은 UART 데이터 레지스터에서 바이트를 읽어 링 버퍼에 넣기만 한다.
- 메인 루프는 링 버퍼에서 바이트를 꺼내 `\r`과 `>`를 찾는다.
- 파서가 한 줄을 완성하면 PID 해석, 로깅, 화면 갱신을 한다.
- 링 버퍼가 넘치면 오래된 바이트를 버릴지, 새 바이트를 버릴지 정한다. OBD 응답은 줄 중간이 잘리면 파싱이 깨지므로, **오버플로 카운터를 올리고 그 응답은 버리는** 편이 낫다.
- ELM327의 보율이 38400이면 초당 약 3,840바이트다. 256바이트 링 버퍼는 60ms마다 비워야 한다. 메인 루프가 화면 갱신 등으로 60ms 이상 멈추면 넘친다.
- ELM327 내부 버퍼(512바이트)와 MCU의 링 버퍼는 **다른 버퍼**다. 둘 다 넘칠 수 있다.

링 버퍼 크기는 "최악의 생산 속도 × 최악의 소비 지연"으로 계산한다. 평균 속도로 계산하면 간헐 오버플로를 놓친다.

## 11.5 메인 루프 구조

```c
int main(void) {
    init_clock();
    init_gpio();
    init_uart();
    init_timer();

    for (;;) {
        poll_inputs();      // 논블로킹
        update_state();     // 상태 기계
        update_outputs();
        feed_watchdog();    // 워치독 리셋
    }
}
```

### `delay()` 대신 시각 비교

`delay(1000)`은 그 1초 동안 아무 입력도 처리하지 못한다. 대신 `millis()`(또는 타이머 플래그)로 "마지막 실행 시각"을 비교해 주기를 만든다.

```c
static uint32_t last_toggle;

uint32_t now = millis();
if (now - last_toggle >= 500) {
    last_toggle = now;
    toggle_led();
}
```

`millis()`는 32비트면 약 49.7일 뒤 0으로 돌아간다. `if (now - last >= period)`처럼 **뺄셈**으로 비교하면 오버플로를 견딘다. `if (now >= last + period)`처럼 덧셈으로 비교하면 오버플로 순간에 한 번씩 오동작할 수 있다.

### 상태 기계

복잡해지면 상태 기계를 쓴다. `IDLE → MEASURE → SEND → WAIT_ACK → ERROR`처럼 상태와 전이를 명시하면 블로킹 없이 여러 일을 동시에 처리할 수 있다.

```text
IDLE
  │ 주기 도달
  ▼
MEASURE
  │
  ▼
SEND
  │
  ▼
WAIT_ACK ──(성공)──────────────────→ IDLE
  │
  └──(타임아웃/오류)──→ ERROR ─────→ IDLE
```

웹의 상태 기계(로딩/성공/오류)와 같은 사고방식이다. 다른 점은 상태 전이 사이에 `sleep`을 넣지 않고, 매 루프에서 **지금 상태에서 할 일만 조금씩** 한다는 것이다.

OBD 요청도 상태 기계로 만든다. `delay()`로 응답을 기다리면 그동안 다른 일을 못 한다.

```c
typedef enum {
    OBD_IDLE,
    OBD_SEND,
    OBD_WAIT_LINE,
    OBD_PARSE,
    OBD_ERROR
} obd_state_t;

static obd_state_t state = OBD_IDLE;
static uint32_t last_tx_ms;
static uint32_t last_rx_ms;

void obd_tick(uint32_t now) {
    switch (state) {
    case OBD_IDLE:
        if (now - last_tx_ms >= 1000u) {   /* 1초 주기 */
            uart_write_str("010C\r");
            last_tx_ms = now;
            last_rx_ms = now;
            state = OBD_SEND;
        }
        break;

    case OBD_SEND:
        state = OBD_WAIT_LINE;             /* 송신 완료 후 응답 대기 */
        break;

    case OBD_WAIT_LINE:
        if (line_ready()) {                /* 링 버퍼에서 \r까지 완성 */
            state = OBD_PARSE;
        } else if (now - last_rx_ms > 500u) {
            state = OBD_ERROR;             /* 타임아웃 */
        }
        break;

    case OBD_PARSE:
        if (parse_rpm_line()) {
            state = OBD_IDLE;
        } else {
            state = OBD_ERROR;
        }
        break;

    case OBD_ERROR:
        log_error();
        state = OBD_IDLE;                  /* 다음 주기에 재시도 */
        break;
    }
}
```

- `uart_write_str()`는 블로킹이거나 DMA/링 버퍼에 넣는 방식이다. 블로킹이면 8바이트를 보내는 짧은 시간만 기다린다.
- `line_ready()`는 링 버퍼에 `\r`이 있는지 확인한다. `>` 프롬프트도 상태로 처리한다.
- 타임아웃은 "최악의 정상 응답"보다 길게 잡는다. ELM327 클론의 `NO DATA`가 0.2초 안팎이면 0.5초는 여유가 있다. 차량·PID에 따라 조정한다.
- 오류가 나도 상태를 `OBD_IDLE`로 돌려 다음 주기에 다시 시도한다. 오류 상태에 갇히지 않는다.
- `SEARCHING...`, `NO DATA`, `?`, `STOPPED`는 `parse_rpm_line()`에서 실패로 처리하고, 필요하면 별도 오류 코드로 남긴다.
- 이 상태 기계는 한 번에 한 요청만 보낸다. 다중 PID·다중 ECU로 확장하려면 요청 큐와 응답 매칭이 필요하다.

이 구조는 7장의 파이썬 스레드와 같은 역할을 한다. 파이썬에서는 스레드가 "응답을 기다리는 동안 다른 일을 한다"를 쉽게 만들지만, MCU에서는 상태 기계가 그 역할을 한다.

### 워치독

워치독은 메인 루프가 살아 있을 때만 리셋한다. ISR에서 리셋하면 메인 루프가 죽어도 살아 있는 것으로 보인다. 워치독은 "코드가 멈췄을 때 기계를 안전하게 재시작하는 장치"이므로, 리셋 지점을 잘못 두면 의미가 없어진다.

### RTOS를 쓰면

RTOS를 쓰면 태스크·큐·뮤텍스로 나눈다. 태스크 스택 크기를 실제 사용량보다 넉넉히 잡고, 우선순위 역전을 고려한다.

`while (!flag) {}` 같은 바쁜 대기는 전력을 낭비하고 다른 일을 막는다. sleep/interrupt/이벤트를 쓴다.

## 11.6 메모리

| 영역 | 내용 | 특징 |
|---|---|---|
| Flash | 프로그램, 상수 | 쓰기 횟수 제한, 바이트 단위 쓰기 어려움 |
| SRAM | 변수, 스택, 힙 | 전원이 끊기면 사라짐, 수 KB~수백 KB |
| EEPROM/NVS(Non-Volatile Storage) | 설정, 보정값 | 쓰기 횟수 제한(수만~수십만 회), 느림 |
| 외부 플래시/SD | 로그, 펌웨어 | 속도·수명·마모 고려 |

- 동적 할당(`malloc`/`new`)은 조각화와 실패를 부른다. 가능하면 정적 버퍼와 풀을 쓴다. 특히 AVR에서 `String`은 힙 조각화의 주범이다.
- 큰 배열을 지역 변수로 두면 스택이 넘친다. 전역/정적으로 옮기거나 힙 대신 풀을 쓴다.
- 스택 오버플로는 예외가 아니라 조용한 손상이다. 스택 하이워터마크를 측정하고, RTOS 태스크 스택을 넉넉히 잡는다.
- `const` 데이터는 보통 플래시에 간다. AVR에서 큰 상수 테이블은 `PROGMEM`과 `pgm_read_*`가 필요하다.
- 구조체는 정렬/padding 때문에 크기가 예상과 다르다. 바이너리 프로토콜에 구조체를 그대로 쓰지 말고 필드별로 직렬화한다.
- 부동소수점은 MCU에 따라 느리거나 없다. 정수 스케일(0.1 단위 등)로 계산하면 빠르고 재현 가능하다.
- 최적화(`-Os`)와 `size`/맵 파일로 실제 사용량을 확인한다. "컴파일된다"와 "들어간다"는 다르다.

### 메모리 절약의 우선순위

1. 큰 배열과 문자열을 줄인다.
2. 동적 할당을 정적 버퍼로 바꾼다.
3. 로그와 버퍼의 최대 크기를 정한다.
4. 정수 스케일로 부동소수점을 피한다.
5. 그래도 부족하면 플래시/외부 메모리를 고려한다.

"일단 동작하게 만들고 나중에 최적화"는 MCU에서 위험하다. 메모리가 부족하면 기능을 빼야 할 수도 있으므로, 초기부터 예산을 잡는 편이 좋다.

차량 게이트웨이의 메모리 예산은 대략 이렇게 잡는다.

```text
UART 링 버퍼        256~1024 B
ELM327 줄 버퍼      128~512 B
PID 값 테이블       100~500 B
JSON 페이로드       256~1024 B
MQTT/TLS 스택       20~60 KB (구현에 따라 크게 다름)
오프라인 큐         4~64 KB (SD/플래시면 더 큼)
```

- TLS를 쓰는 Wi-Fi MCU는 RAM이 100KB 미만이면 빠듯할 수 있다. ESP32는 여유가 있지만, BLE+Wi-Fi+TLS를 동시에 쓰면 줄어든다.
- JSON 문자열을 `sprintf`로 계속 만들면 버퍼 오버플로 위험이 있다. 고정 크기 버퍼와 길이 검사를 쓴다.
- 로그를 플래시에 쓰면 마모와 쓰기 지연을 고려한다. 순환 버퍼와 배치 쓰기를 쓴다.
- ELM327을 쓰는 구성에서는 ELM327의 512바이트 버퍼도 예산에 포함한다. MCU가 느리면 ELM327 쪽이 먼저 넘친다.

## 11.7 GPIO와 주변장치

- 입력: 풀업/풀다운을 명시한다. 플로팅 입력은 노이즈를 그대로 받는다. 버튼은 디바운스한다.
- 출력: 핀당 전류 한도가 작다(보통 수 mA~20mA, 절대 최대는 데이터시트 확인). LED는 저항을 직렬로 넣는다. 모터·릴레이는 트랜지스터/MOSFET/드라이버를 쓴다. 유도성 부하는 플라이백 다이오드를 둔다.
- 오픈 드레인 출력은 풀업이 필요하고, 여러 장치가 선을 공유할 때 쓴다(I2C).
- 5V tolerant 여부, 핀의 대체 기능(UART/I2C/SPI/PWM), 부팅 시 기본 상태(strapping pin)를 확인한다. ESP32의 일부 핀은 부팅 모드에 영향을 준다.
- ADC(Analog-to-Digital Converter): 해상도(10/12/16비트), 기준 전압, 입력 범위, 샘플링 시간, 입력 임피던스를 본다. ESP32 ADC는 선형성이 좋지 않아 보정이 필요할 수 있다.
- PWM(Pulse Width Modulation): 주파수와 분해능은 트레이드오프다. LED는 수백 Hz~수 kHz, 모터는 가청 소음을 피하려 20kHz 안팎, 서보는 50Hz가 흔하다.
- 타이머/DMA(Direct Memory Access): 정확한 주기, 긴 버퍼 전송, CPU 부하 감소에 쓴다. DMA 버퍼가 끝나기 전에 재사용하지 않는다.

## 11.8 클록과 전원

- 클록은 크리스탈/PLL/내부 RC에서 나온다. UART 보율, 타이머, ADC 샘플링이 모두 클록에 의존한다. 클록이 틀리면 통신도 틀어진다.
- 내부 RC는 온도·전압에 따라 오차가 커서 고속 시리얼에 부적합할 수 있다. 정확한 통신에는 크리스탈을 쓴다.
- 전원은 LDO/DC-DC, 디커플링 커패시터, 브라운아웃 검출로 보호한다. 전압이 순간 떨어지면 리셋·오동작이 난다.
- USB로 전원을 공급하면서 외부 전원도 연결하면 역전류가 흐를 수 있다. 보드의 전원 선택 점퍼/다이오드를 확인한다.
- 절전: sleep 모드마다 유지되는 것과 꺼지는 것이 다르다. 깨어날 때 재초기화 시간과 전류를 계산한다.
- 배터리 기기는 평균 전류가 중요하다. 송신 순간 전류, sleep 전류, LDO 누설을 모두 더한다.

### 전원 예산 예

```text
평균 전류 = (동작 전류 × 동작 시간 + sleep 전류 × sleep 시간) / 전체 주기
```

송신 순간 전류가 크면 평균이 작아도 배터리 전압이 순간적으로 떨어질 수 있다. 커패시터와 전원 설계를 함께 본다.

차량 게이트웨이의 전원 예산은 더 까다롭다.

- 차량 배터리는 12V지만, 크랭킹 순간에는 6~8V까지 떨어질 수 있다. 3.3V 레귤레이터의 입력 범위와 브라운아웃을 확인한다.
- 시동 OFF에서 게이트웨이가 계속 동작하면 배터리가 소모된다. sleep 전류를 계산하고, 필요하면 ignition 신호로 켜고 끈다.
- USB 전원과 차량 전원을 동시에 연결하면 역전류·접지 루프가 생길 수 있다. 전원 선택 회로·다이오드·절연을 확인한다.
- CAN 트랜시버의 standby 핀을 잘못 두면 버스 트래픽을 못 받거나 전력을 낭비한다.
- OBD 포트의 16번 핀은 퓨즈가 없을 수 있다. 외부 퓨즈를 넣는다.
- 크랭킹 중에는 어댑터·게이트웨이가 리셋될 수 있다. 로그에 리셋 원인과 시각을 남긴다.

7장의 실차 기록에서도 크랭킹 때 USB가 끊긴 사례가 있었다. 전원 문제는 코드로 해결되지 않는다. **전원·접지·퓨즈·절연을 먼저 설계한다.**

## 11.9 펌웨어 업로드와 디버깅

- 업로드 경로: 부트로더(Arduino/AVR), USB DFU, SWD/JTAG(ST-Link), UART/USB(esptool), OTA.
- 부트로더는 전원이 끊겨도 다시 올릴 수 있는 마지막 수단이다. 부트로더를 지우는 설정을 피한다.
- 업로드 후 검증(체크섬/서명)과 롤백을 설계한다. OTA는 A/B 파티션이 안전하다.
- SWD/JTAG는 브레이크포인트, 변수 관찰, 레지스터 확인이 가능해 시리얼 로그보다 강력하다. STM32는 ST-Link가 저렴하다.
- ESP32는 부팅 모드(strapping)와 다운로드 모드에 들어가는 핀 조합이 있다. 업로드가 안 되면 BOOT 버튼을 누른 채 리셋한다.
- Arduino/ESP32 보드는 포트를 열 때 DTR/RTS로 리셋된다. 첫 출력이 사라지면 이 동작을 의심한다.
- 릴리스 펌웨어에는 버전, 빌드 시각, 커밋 해시, 리셋 원인을 남긴다.

## 11.10 RTOS를 쓸까

- 베어메탈 + 상태 기계로 충분한 일이 많다. 타이밍이 단순하고 코드가 작다.
- 여러 주기 작업, 통신 스택, 긴 지연, 우선순위가 섞이면 FreeRTOS 같은 RTOS가 낫다.
- RTOS를 쓰면 태스크 스택, 우선순위, 큐 깊이, 뮤텍스, 우선순위 역전, 틱 오버헤드를 설계해야 한다.
- ISR에서는 RTOS API의 `FromISR` 변형만 쓴다. 일반 API를 ISR에서 부르면 깨진다.
- 태스크가 많다고 좋은 게 아니다. 태스크마다 스택과 컨텍스트 스위치 비용이 든다.

RTOS는 "OS가 없어서 불편할 때" 쓰는 도구이지, "있으면 좋아 보여서" 쓰는 도구가 아니다. 상태 기계로 충분한 일을 RTOS로 나누면 디버깅만 어려워질 수 있다.

## 11.11 원칙 요약

- `delay()` 대신 상태 기계와 시각 비교.
- ISR은 짧게, 공유 데이터는 원자성까지 생각.
- 동적 할당은 줄이고, 버퍼 크기를 계산.
- 전원·접지·레벨을 코드보다 먼저 확인.
- 데이터시트의 absolute maximum과 recommended operating conditions를 구분.
- 하드웨어 접근을 인터페이스로 분리해 PC에서 테스트.
- 워치독과 안전 상태를 처음부터 넣는다.

| 실수 | 결과 | 확인 |

| 큰 지역 배열 | 스택 오버플로, 조용한 손상 | 전역/정적, 스택 측정 |

| 모터를 GPIO로 직결 | 리셋, 손상 | 트랜지스터/MOSFET/드라이버, 플라이백 다이오드 |
| DMA 버퍼 조기 재사용 | 데이터 손상 | 전송 완료 확인 |
| 부트로더를 지움 | 복구 불가 | 지우기 설정 피함 |
| OBD 응답을 `delay()`로 기다림 | 다른 입력·통신 정지 | 상태 기계와 타임아웃 |
| UART 링 버퍼 크기를 평균 속도로 계산 | 간헐 오버플로, 줄 잘림 | 최악 속도 × 최악 지연 |

| 차량 12V를 3.3V 보드에 직결 | 서지·과열·손상 | 레귤레이터·퓨즈·절연 |
| 크랭킹 중 로깅 지속 | 어댑터 리셋, 로그 끊김 | 전원 안정화, 재연결 처리 |
| OBD를 제어 인터페이스로 착각 | 위험한 쓰기 시도 | 진단은 읽기 전용 |

## 장 요약

- MCU는 베어메탈/RTOS에서 `main()`과 인터럽트로 동작한다. SBC와 역할이 다르다.
- 보드를 고를 때 전압·메모리·통신·디버깅·생태계를 함께 본다.
- ISR은 짧게, 공유 변수는 `volatile`과 원자성을 함께 생각한다.
- ISR과 메인 루프 사이는 링 버퍼로 잇는다. 크기와 오버플로 정책을 정한다.
- `delay()` 대신 시각 비교와 상태 기계를 쓴다. 워치독은 메인 루프에서 리셋한다.
- 메모리 영역을 이해하고 동적 할당·큰 배열·`String`을 줄인다.
- GPIO·ADC·PWM·DMA는 데이터시트의 전압·전류·타이밍을 확인한다.
- 클록과 전원이 통신과 실시간성의 기반이다.
- 업로드 경로와 디버깅 도구(SWD/JTAG, 부트로더)를 미리 파악한다.
- RTOS는 필요할 때만 쓰고, 태스크 스택과 우선순위를 설계한다.
- 차량 ECU의 MCU와 진단 어댑터의 MCU는 역할이 다르다. OBD-II는 제어가 아니라 진단 인터페이스다.
- UART ISR → 링 버퍼 → 메인 루프 상태 기계가 차량 OBD 로거의 기본 구조다. `delay()`로 응답을 기다리지 않는다.
- 차량 전원은 크랭킹·서지·배터리 방전을 전제로 퓨즈·레귤레이터·절연을 설계한다.
