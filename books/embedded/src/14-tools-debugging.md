# 14장 도구와 디버깅

## 이 장에서

임베디드 디버깅은 "코드를 읽는 일"보다 **계층을 하나씩 확인하는 일**에 가깝다. 전원·접지·배선·설정이 틀린 상태에서 코드를 고치면 시간만 버린다.

웹 개발자에게 디버깅은 DevTools, 로그, 스택 트레이스, 브레이크포인트다. 임베디드에도 비슷한 도구가 있지만 결정적인 차이가 있다. **로그를 볼 수 없는 현장이 많고, 스택 트레이스가 거의 없으며, 버그가 전기 신호에 숨어 있다.** 그래서 멀티미터와 로직 분석기가 DevTools만큼 중요해진다.

이 장에서 다루는 것:

- 디버깅 순서(전원 → 접지 → 배선 → 레벨 → 설정 → 프레이밍 → 의미 → 타이밍)
- 시리얼 모니터와 pyserial
- ELM327 점검과 OBD-II 요청
- python-can과 SocketCAN
- 로직 분석기, 멀티미터, 오실로스코프
- 루프백과 계층별 시험
- 절연과 안전
- 로깅 습관
- 차량 OBD 버스에서의 실제 측정

## 14.1 디버깅 순서

```text
1. 전원   전압, 극성, 전류, 브라운아웃
2. 접지   공통 접지, 접지 루프, 절연
3. 배선   TX/RX, A/B, CAN_H/L, CS, 커넥터, 냉납
4. 레벨   3.3V/5V, RS-232/RS-485/TTL, 종단
5. 설정   보율, 8N1, I2C 주소, SPI 모드, CAN 비트레이트
6. 프레이밍 경계, 길이, 체크섬, 엔디언
7. 의미   명령 코드, 레지스터, 스케일
8. 타이밍 타임아웃, 샘플링, 워치독
```

- 한 계층을 확인하기 전에 다음 계층을 의심하지 않는다.
- "코드는 안 바꿨는데 된다/안 된다"는 하드웨어 계층의 신호다.

이 순서는 1장과 13장에서도 나왔다. 이 장에서는 각 계층을 **어떤 도구로** 확인하는지가 핵심이다.

차량 OBD 문제라면 각 계층의 도구가 더 구체적이다.

| 계층 | 차량에서 확인할 것 | 도구 |
|---|---|---|
| 전원 | OBD 16번 핀 12V, 4/5번 접지 | 멀티미터 |
| 접지 | 차체-노트북 접지 전위차, USB 절연 | 멀티미터, 절연 USB |
| 배선 | 6/14번 CAN_H/L, 커넥터 체결 | 멀티미터, 로직 분석기 |
| 레벨 | CAN dominant/recessive, 종단 | 오실로스코프, 멀티미터 |
| 설정 | 보율, `ATSP0`/`ATDPN`, 8N1 | ELM327, 시리얼 모니터 |
| 프레이밍 | `\r`, `>`, ISO-TP | ELM327 로그, 파서 |
| 의미 | PID/DID, 바이트 오프셋 | 9~10장 표, 코드 |
| 타이밍 | `NO DATA`, `0x78`, `BUFFER FULL` | 로그, 타임아웃 설정 |

## 14.2 시리얼 모니터

- Arduino IDE 시리얼 모니터, VS Code Serial Monitor, PuTTY, Tera Term, `screen`, `minicom`, `tio` 등.
- 확인할 것: 포트, 보율, 데이터/패리티/stop, 줄바꿈(CR/LF/CRLF), 로컬 에코, 인코딩.
- 시리얼 모니터가 포트를 잡고 있으면 스크립트가 못 연다. Windows는 특히 배타적이다.
- 바이너리 데이터를 텍스트 모니터로 보면 깨져 보이는 게 정상이다. hex 모드를 쓴다.
- Arduino/ESP32는 포트를 열 때 DTR/RTS로 리셋될 수 있다. 첫 줄이 사라지면 1~2초 기다리거나 리셋을 끈다.

줄바꿈 설정은 의외로 자주 문제를 만든다. 장치가 `\r\n`을 기다리는데 모니터가 `\n`만 보내면 명령이 먹지 않는다. "보레이트는 맞는데 명령이 안 먹는다"면 CR/LF를 확인한다.

## 14.3 pyserial

먼저 프로젝트를 만든다.

```bash
uv init serial-tools
cd serial-tools
uv add pyserial
```

### 포트 목록과 기본 읽기/쓰기

```python
import serial
from serial.tools import list_ports

for p in list_ports.comports():
    print(p.device, "|", p.description, "|", p.hwid)

PORT = "COM5"  # Linux: /dev/ttyUSB0, macOS: /dev/cu.usbserial-...

with serial.Serial(PORT, baudrate=115200, bytesize=8, parity="N",
                   stopbits=1, timeout=0.2) as ser:
    ser.reset_input_buffer()
    ser.write(b"ping\r\n")
    ser.flush()                       # 쓰기 완료를 기다린다(상대 수신 보장은 아님)
    data = ser.read(64)               # 타임아웃까지 최대 64바이트
    print(data.hex(" "), repr(data))
```

- `timeout=0`은 논블로킹, `timeout=None`은 무한 대기다. 대부분 0.1~1초가 적당하다.
- `read(n)`은 n바이트를 "최대" 돌려준다. 반환 길이를 항상 확인한다.
- `readline()`은 텍스트에만 쓴다. 바이너리에서는 `read(1)` + 직접 파서를 쓴다.
- `reset_input_buffer()`는 이전에 쌓인 쓰레기 데이터를 버린다. 요청 전에 한 번 호출하면 늦게 온 응답이 섞이는 문제를 줄일 수 있다.
- `flush()`는 OS/드라이버의 쓰기 버퍼 전송이 끝날 때까지 기다린다(데이터를 버리는 함수가 아니다). USB-UART 내부 버퍼와 상대의 처리 완료는 보장하지 않는다.
- 예외: `serial.SerialException`(포트 열기/장치 사라짐), `serial.SerialTimeoutException`(쓰기 타임아웃).
- 포트가 사라졌다가 다시 나타나면 COM 번호가 바뀔 수 있다. 목록을 다시 확인한다.

### 루프백 시험

TX와 RX를 점퍼로 연결한다.

```python
import serial

PORT = "COM5"

with serial.Serial(PORT, 115200, timeout=1) as ser:
    ser.write(b"loopback")
    ser.flush()
    print(ser.read(8))   # b"loopback"이 나와야 한다
```

- 어댑터 자체가 살아 있는지, 드라이버가 붙었는지, 보율이 맞는지를 한 번에 확인한다.
- 두 개의 USB-UART를 TX-RX/GND로 교차 연결하면 양방향 시험을 할 수 있다.

루프백은 "코드가 아니라 어댑터를 시험하는" 도구다. 여기서 실패하면 보드와 프로토콜을 의심하기 전에 어댑터·케이블·드라이버를 먼저 본다.

### ELM327 점검

ELM327은 pyserial로 바로 확인할 수 있다. 시리얼 모니터로도 되지만, `\r`과 프롬프트 `>`를 눈으로 보려면 `miniterm`이 편하다.

```bash
python -m serial.tools.miniterm COM5 38400
```

접속한 뒤 `ATZ`, `ATE0`, `ATI`, `ATSP0`, `ATDPN`, `ATRV`, `0100`, `010C`를 차례로 입력한다. 화면에 `ELM327 v1.5`, `OK`, `A6`, `41 00 ...` 같은 응답이 보이면 시리얼·프로토콜·OBD 요청이 살아 있다는 뜻이다.

점검 순서:

```text
1. 포트가 보이는가          python -m serial.tools.list_ports -v
2. 보율이 맞는가            ATI 응답이 깨지지 않는가
3. 어댑터가 리셋되는가      ATZ → 버전 문자열
4. 프로토콜을 찾는가        ATSP0 → ATDPN
5. 배터리 전압이 오는가     ATRV
6. OBD 응답이 오는가        0100 → 지원 PID 마스크
7. 특정 PID가 오는가        010C → 41 0C ...
```

`ATI`가 깨지면 보율, `ATZ`가 `STOPPED`면 프롬프트 전 입력, `ATDPN`이 `A6`이 아니면 프로토콜, `0100`이 `NO DATA`면 시동·PID 지원·필터를 본다. 9장의 문제 해결 표와 같다.

## 14.4 python-can과 SocketCAN

Linux에서는 SocketCAN이 표준이다.

```bash
sudo ip link set can0 type can bitrate 500000
sudo ip link set up can0
candump -ta can0                 # 절대 시각과 함께 수신
candump -e can0                  # 오류 프레임 포함
cansend can0 123#DEADBEEF
canbusload can0@500000
```

Python 프로젝트를 만들고 `python-can`을 추가한다.

```bash
uv init can-tools
cd can-tools
uv add python-can
```

```python
import can

with can.Bus(interface="socketcan", channel="can0") as bus:
    bus.send(can.Message(
        arbitration_id=0x123,
        is_extended_id=False,
        data=[0x01, 0x02, 0x03],
    ))
    while (msg := bus.recv(timeout=1.0)) is not None:
        print(f"{msg.arbitration_id:03X} {msg.data.hex(' ')}")
```

- Windows에서는 `interface`를 장비에 맞춘다. 예: `pcan` + `PCAN_USBBUS1`, `slcan` + `COM6`, `kvaser`, `vector`.
- `bitrate`는 SocketCAN에서는 `ip link`로 설정한다. `slcan`/`pcan`처럼 드라이버가 비트레이트를 받는 인터페이스도 있다.
- 테스트에는 `interface="virtual"` 버스를 쓸 수 있다. 하드웨어 없이 송수신 로직을 검증한다.
- `bus.recv(timeout=...)`는 타임아웃이면 `None`을 돌려준다.
- `can.Notifier`로 수신 콜백을, `can.Logger`로 파일 로깅을 붙일 수 있다.
- `Message(..., check=True)`로 클래식 CAN의 8바이트 제한을 검사할 수 있다.

ELM327은 OBD-II 읽기용이지 범용 CAN 분석기로 쓰기에는 부족하다. ELM327은 OBD 요청/응답을 해석해 주지만, 버스의 모든 프레임을 원시로 보여 주지는 않는다. 반대로 USB-CAN 어댑터(SocketCAN, PCAN, CANable)는 원시 프레임을 보여 주지만, ISO-TP·OBD 해석은 직접 해야 한다.

| 목적 | 도구 |
|---|---|
| OBD-II PID·DTC·VIN 읽기 | ELM327 + pyserial |
| 제조사 UDS DID 읽기 | ELM327(헤더/필터 설정) 또는 USB-CAN |
| 원시 CAN 트래픽 로깅 | USB-CAN + SocketCAN/python-can |
| 두 노드 벤치 시험 | MCP2515/USB-CAN 2개 |
| 차량 전체 버스 스니핑 | 해당 버스에 직접 접근하는 CAN 인터페이스 |

SocketCAN으로 OBD 요청을 보내는 예는 7장에 있다. ELM327과 USB-CAN을 함께 쓰면 "ELM327로 OBD를 읽고, USB-CAN으로 버스 상태를 본다"는 식으로 역할을 나눌 수 있다. 두 도구를 같은 버스에 동시에 붙일 때는 종단과 버스 부하를 확인한다.

## 14.5 로직 분석기

- 싸구려 8채널 24MHz 클론 + sigrok/PulseView, Saleae Logic, DSLogic 등.
- 샘플 레이트는 신호 주파수의 **최소 4배, 권장 10배**다. 1Mbps CAN이면 10MS/s 이상이 필요하다. 24MHz 클론은 클래식 CAN에는 충분하지만 FD 데이터 구간에는 빠듯할 수 있다(확인 필요).
- 프로토콜 디코더(UART, I2C, SPI, CAN)를 쓰면 바이트 경계와 오류를 눈으로 볼 수 있다.
- 접지선을 반드시 연결하고, 프로브를 짧게 한다. 긴 접지선은 링잉을 만든다.
- 트리거를 걸어 두면 간헐 이벤트를 잡기 좋다. 샘플 레이트를 높이면 캡처 시간이 줄어든다.
- UART라면 TX/RX를 동시에, I2C라면 SDA/SCL을, SPI라면 CS/SCLK/MOSI/MISO를 함께 본다.

로직 분석기의 가장 큰 장점은 **"바이트가 실제로 오갔는가"를 눈으로 확인**할 수 있다는 점이다. 소프트웨어 로그가 "아무것도 안 왔다"고 말해도, 분석기에는 파형이 찍힐 수 있다. 그 반대도 마찬가지다.

차량 OBD 버스라면 다음을 본다.

- 6번(CAN_H)과 14번(CAN_L)을 동시에 프로빙한다. 접지는 차체 접지(4번)나 가까운 접지에 연결한다.
- 500kbps CAN은 비트 폭이 2µs다. 샘플 레이트는 최소 4배, 권장 10배인 5~10MS/s 이상이 필요하다. 24MHz 8채널 클론은 클래식 CAN에 충분하다.
- CAN 디코더를 켜고 500kbps로 설정한다. 파형이 보이는데 디코더가 오류를 내면 비트레이트·샘플 포인트·배선을 확인한다.
- ELM327이 `NO DATA`를 낼 때, 분석기에 요청 프레임(`7DF`)은 보이는데 응답이 없으면 ECU·프로토콜·필터 문제다. 요청조차 안 보이면 어댑터·시리얼·전원 문제다.
- 차량 버스는 이미 종단되어 있다. 분석기 프로브의 긴 접지선이 링잉을 만들 수 있으니 짧게 한다.
- 에어백·ABS 배선은 프로빙하지 않는다. OBD 포트의 6/14번만 본다.

로직 분석기는 "ELM327 로그가 거짓말을 하는지"를 확인하는 최후의 도구다. 시리얼 로그에 `NO DATA`만 보일 때, 버스에는 프레임이 오가고 있을 수 있다.

## 14.6 멀티미터와 오실로스코프

멀티미터의 기본 모드·연결 방법·CAT 등급·안전은 4.7절에서 다뤘다. 여기서는 임베디드 디버깅에서 무엇을 먼저 재는지에 집중한다.

### 멀티미터로 먼저 확인할 것

| 측정 | 기대값 |
|---|---|
| 공급 전압 | 3.3V 또는 5V ± 허용 오차 |
| UART TX idle | 3.3V 또는 5V (high) |
| CAN_H / CAN_L (recessive) | 둘 다 약 2.5V |
| CAN_H / CAN_L (dominant) | 약 3.5V / 1.5V |
| CAN 종단 저항(전원 끔) | 약 60Ω (120Ω 두 개 병렬) |
| GND 연속성 | 삐 소리, 낮은 저항 |
| OBD 16번-4/5번 | 12V 안팎(시동 OFF), 13~14V대(시동 중) |
| OBD 6번-14번 저항(차량 OFF) | 약 60Ω(차량에 종단이 있을 때) |
| OBD 6번 idle 전압 | 약 2.5V(Recessive) |

- 전류 측정은 회로를 **직렬**로 끊어 넣는다. 전압 측정 모드로 전류를 재면 단락된다.
- 도통 시험은 전원을 끄고 한다.
- 오실로스코프는 신호 무결성(링잉, 노이즈, 상승 시간)과 CAN 차동 파형을 볼 때 쓴다. UART 정도면 저가 스코프로 충분하지만, CAN FD·고속 SPI는 대역폭을 확인한다.
- 프로브 x1/x10과 접지 클립을 확인한다. 고전압·차량 전원을 다룰 때는 절연과 정격을 지킨다.

차량에서 저항을 잴 때는 **시동을 끄고, 어댑터를 빼고, 모듈이 잠들 시간을 준 뒤** 측정한다. 차량에는 배터리가 연결된 채로 여러 ECU가 살아 있어, 저항 측정값이 실제 종단값과 다르게 나올 수 있다. 저항 측정 모드로 살아 있는 회로를 찌르면 미터에 과전류가 흐를 수 있다. 확실하지 않으면 저항 대신 전압·파형으로 확인한다.

멀티미터는 "전압이 있는가"를 확인하는 도구이고, 오실로스코프는 "신호가 어떤 모양인가"를 확인하는 도구다. 전자는 싸고 빠르며, 후자는 비싸지만 신호 무결성 문제를 보여 준다. 입문 단계에서는 멀티미터와 로직 분석기의 조합이 가성비가 좋다.

## 14.7 루프백과 레이어별 시험

- **UART**: TX-RX 점퍼로 루프백. 어댑터 → 보드, 보드 → 어댑터를 각각 시험한다.
- **I2C**: 주소 스캔 → 레지스터 읽기(예: WHO_AM_I) → 설정 쓰기 → 데이터 읽기.
- **SPI**: CS/SCLK/MISO/MOSI를 로직 분석기로 확인 → 장치 ID 읽기(플래시 `0x9F`) → 쓰기/읽기 왕복.
- **CAN**: 어댑터 2개를 120Ω 종단과 함께 연결 → 한쪽에서 `cansend`, 다른 쪽에서 `candump`. 그다음 실제 노드와 연결한다.
- **ELM327**: 루프백이 아니라 `ATI` → `ATSP0` → `ATDPN` → `ATRV` → `0100` 순서로 확인한다. 시리얼·프로토콜·OBD를 한 번에 분리한다.
- **차량 OBD**: ELM327과 USB-CAN을 함께 붙여, ELM327 로그와 원시 CAN 프레임을 대조한다. 요청 `7DF`와 응답 `7E8`이 실제로 오가는지 본다.
- **Modbus**: 두 USB-RS485 어댑터로 마스터/슬레이브를 흉내 내거나, 시뮬레이터로 요청/응답을 먼저 검증한다.
- **MQTT**: 로컬 Mosquitto에 붙여 토픽/QoS/인증을 먼저 검증하고, 클라우드로 옮긴다.
- 한 번에 한 계층만 바꾼다. 두 가지를 동시에 바꾸면 원인을 분리할 수 없다.

### 레이어별 시험 순서 예

```text
1. 전원 인가 → 전압 측정
2. TX/RX 루프백 → 어댑터 확인
3. 보드 ↔ PC 통신 → 보율/8N1 확인
4. 프레임 한 개 수동 전송 → 파서 확인
5. 실제 센서/장치 연결 → 주소/설정 확인
6. 장시간 시험 → 간헐 오류 확인
```

이 순서를 지키면 "어느 계층까지는 확인했다"는 사실을 남길 수 있다. 디버깅에서 가장 비싼 것은 **이미 확인한 것을 다시 확인하는 시간**이다.

## 14.8 절연과 안전

- 차량·산업 장비는 접지 전위가 노트북과 다를 수 있다. **USB 절연기**나 절연 트랜시버를 쓴다.
- 접지 루프는 노이즈와 장치 손상의 원인이다. 신호 접지와 전원 접지를 한 점에서 만나는지 확인한다.
- 모터·릴레이·솔레노이드는 유도성 부하다. 플라이백 다이오드와 드라이버를 넣고, 첫 시험에서는 액추에이터를 분리한다.
- 전원 공급기는 전류 제한을 걸고 시작한다. 단락 시 피해를 줄인다.
- 차량에서는 퓨즈를 넣고, 주행 중 시험하지 않는다. 진단은 정차 상태에서 읽기 전용으로 한다.
- OBD 포트의 16번 핀은 배터리 전원이다. 어댑터를 오래 꽂아 두면 배터리가 소모된다.
- 노트북 충전기와 차량 전원을 동시에 연결하면 접지 루프가 생길 수 있다. USB 절연기를 쓴다.
- 에어백·ABS·고전압 배터리 배선은 프로빙하지 않는다. OBD 포트의 6/14번만 본다.
- 차량을 리프트에 올리거나 바퀴를 돌리는 시험은 하지 않는다. 이 책의 범위 밖이다.
- ESD: 보드를 만지기 전에 접지하고, 정전기에 민감한 부품을 다룰 때 주의한다.
- 계측기는 정격(CAT 등급)을 확인한다. 상용 전원을 직접 프로빙하지 않는다.

안전 규칙은 "초보자용 주의사항"이 아니라 **장비와 사람을 지키는 설계 제약**이다. 특히 차량·산업 장비는 접지 전위가 다를 수 있다는 점을 잊으면 노트북과 어댑터가 함께 상할 수 있다.

## 14.9 로깅 습관

- 양방향, 원시 hex, 단조 시각(monotonic)을 남긴다. 예: `12:34:56.789 TX 01 03 00 00 00 02 C4 0B`.
- 파싱 후 값만 남기지 않는다. 파서가 틀렸을 때 원본이 없으면 복구할 수 없다.
- 포트, 보율, 펌웨어 버전, 장치 ID를 로그 헤더에 남긴다.
- 오류 시점의 버퍼 전체와 상태 기계 상태를 남긴다.
- 장치 쪽 로그는 크기 제한과 순환 버퍼를 둔다. 플래시 마모를 고려한다.
- Python에서는 `logging` 모듈을 쓰고, 파일과 콘솔에 동시에 남긴다. `print`는 줄이 섞인다.
- 재현용으로 원시 로그를 저장하고, 같은 로그를 파서에 다시 넣는 리플레이 테스트를 만든다.

### 좋은 로그와 나쁜 로그

```text
나쁜 로그:  temperature=25.3
좋은 로그:  12:34:56.789 RX 01 03 04 00 FD 00 64 6A 28  → temp=25.3
```

좋은 로그는 원시 바이트와 해석된 값을 함께 남긴다. 나중에 파서가 틀렸다는 것을 발견하면 원시 바이트로 다시 계산할 수 있다. 이것이 리플레이 테스트의 기반이 된다.

차량 OBD 로그라면 다음 형식을 권한다.

```text
2026-10-25T14:03:12.345Z mono=12345.678 tx=010C rx="41 0C 1A F8" rpm=1726
2026-10-25T14:03:12.456Z mono=12345.789 tx=010D rx="41 0D 50" speed=80
2026-10-25T14:03:12.567Z mono=12345.900 tx=0105 rx="NO DATA" error=no_data
```

- `tx`에는 요청 hex를, `rx`에는 어댑터가 준 원시 문자열을 그대로 남긴다.
- `mono`는 단조 시각이다. 벽시계가 바뀌어도 순서를 잃지 않는다.
- `error`에는 `no_data`, `timeout`, `stopped`, `buffer_full`, `parse_error` 같은 분류를 넣는다.
- 포트·보율·프로토콜·어댑터 버전은 파일 헤더에 한 번만 적는다.
- VIN·위치·주행거리는 별도 파일이나 해시로 분리한다.
- 로그 파일은 날짜·세션별로 나누고, 크기 제한과 순환 정책을 둔다. SD 카드 로깅은 전원 차단 시 파일 손상을 고려해 주기적으로 flush한다.

### USB 끊김을 로그로 잡기

실차 기록에서는 주행 중 CH340 어댑터가 USB에서 사라졌다. 앱 로그에는 갑자기 `timeout: true`와 수 ms의 짧은 교환이 남았고, Windows 이벤트 로그에는 `USB\VID_1A86&PID_7523` 장치 누락이 있었다. 재연결 후 COM 번호가 `COM5`에서 `COM6`으로 바뀌었다.

이런 문제를 잡으려면:

- 앱 로그에 마지막 성공 시각, 마지막 수신 시각, 포트 이름을 남긴다.
- `SerialException`과 `OSError`를 구분해 기록한다.
- Windows 이벤트 로그·장치 관리자 기록과 앱 로그의 시각을 대조한다.
- COM 번호를 하드코딩하지 말고 VID/PID·설명으로 포트를 찾는다.
- 재연결 시 `ATZ`, `ATE0`, `ATSP0`을 다시 보낸다. 어댑터가 리셋됐을 수 있다.
- 크랭킹·충전기 연결·USB 허브 변경과 끊김 시각을 함께 기록한다.

## 장 요약

- 디버깅은 전원 → 접지 → 배선 → 레벨 → 설정 → 프레이밍 → 의미 → 타이밍 순서로 내려간다.
- 시리얼 모니터는 포트·보율·8N1·CR/LF·인코딩을 확인한다. 포트 점유와 DTR/RTS 리셋을 주의한다.
- pyserial의 `read(n)`은 최대 n바이트다. 반환 길이를 확인하고, `flush()`의 의미를 정확히 이해한다.
- python-can은 SocketCAN·PCAN·slcan 등 인터페이스를 장비에 맞춘다. virtual 버스로 로직을 시험할 수 있다.
- 로직 분석기는 바이트가 실제로 오갔는지 보여 준다. 샘플 레이트와 접지선이 중요하다.
- 멀티미터로 전압·도통·종단을 먼저 확인하고, 오실로스코프로 신호 무결성을 본다.
- 루프백과 계층별 시험으로 원인을 분리한다. 한 번에 한 계층만 바꾼다.
- 절연·퓨즈·전류 제한·ESD를 지킨다. 차량에서는 정차 상태의 읽기 전용, 퓨즈, USB 절연을 지킨다.
- 로그에는 원시 hex와 단조 시각을 남기고, 리플레이 테스트를 만든다.
- 차량 OBD는 ELM327로 `ATI`→`ATSP0`→`ATDPN`→`ATRV`→`0100` 순서로 점검한다.
- ELM327은 OBD 해석에, USB-CAN/SocketCAN은 원시 프레임 로깅에 맞는다. 역할을 나눈다.
- 로직 분석기로 6/14번 CAN 파형을 보고, 멀티미터로 16번 전원과 4/5번 접지를 확인한다.
- USB 끊김은 앱 로그·Windows 이벤트 로그·포트 이름을 함께 봐야 잡힌다.

다음 장에서는 차량 12V 전원 환경을 다룬다. 그다음 16장에서 지금까지 배운 도구와 디버깅 습관을 ESP32 OBD-II 웹 게이지에 모아 본다. TWAI, CAN 트랜시버, 전원·종단, Wi-Fi 웹 화면이 주제다.

## 정답과 해설

### 1.

`전원 → 접지 → 배선 → 레벨 → 설정 → 프레이밍 → 의미 → 타이밍`. 코드부터 읽지 않는다.

### 2.

1. 배터리 전압(+12V)이 있는지 확인한다. 시동 OFF/ON에 따라 달라진다.
2. CAN 버스 종단 저항이 약 60Ω인지 확인한다. 차량 버스에 추가 저항을 넣지 않는다.
3. 전원을 끄고, 회로에서 분리한 상태에서 측정한다. 저항 모드로 전원이 있는 회로를 재면 측정값이 틀리거나 손상될 수 있다.

### 3.

1. 신호 주기의 10배 이상이 안전하다. 500kbps는 비트당 2µs이므로 5MS/s 이상을 권한다. 1MS/s는 Nyquist 근처라 에지 판별이 어렵다.
2. 충분하다. 24MHz 샘플링은 500kbps 디코딩에 여유가 있다.
3. 접지선이 길면 인덕턴스와 루프가 생겨 파형이 왜곡되고, 고주파 성분을 놓친다. 접지선을 짧게 하고 신호선과 가깝게 둔다.

### 4.

1. 어댑터 버전·클론 여부 확인
2. 프로토콜 자동 검색
3. 검색된 프로토콜 번호 확인(쏘렌토는 `A6`)
4. 배터리 전압 확인
5. PID 00 지원 비트마스크로 통신과 ECU 응답 확인

### 5.

1. 마지막 성공 시각, 끊김 시각, `SerialException`, 타임아웃의 실제 길이를 본다.
2. Windows 이벤트 로그의 장치 제거(Kernel-PnP), USB VID/PID, 드라이버 오류를 본다.
3. COM 번호가 바뀔 수 있다. 포트 이름을 고정하지 말고 VID/PID·설명으로 다시 찾는다.
