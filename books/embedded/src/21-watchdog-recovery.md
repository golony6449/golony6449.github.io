# 21장 워치독과 자가 복구

## 이 장에서

20장에서 OTA로 새 펌웨어를 안전하게 배포하는 방법을 다뤘다. 하지만 새 펌웨어가 **부팅은 되는데 몇 시간 뒤에 멈추는** 문제는 OTA 롤백으로 잡기 어렵다. 자체 시험은 통과했지만, 현장에서 네트워크가 끊기거나, CAN 버스가 Bus-Off에 빠지거나, 힙이 조금씩 줄어들다가 마지막에 멈출 수 있다. 웹 서버라면 프로세스가 죽었을 때 systemd나 Kubernetes가 다시 띄워 준다. 임베디드에는 그런 운영체제가 없다. **장치가 스스로 자기를 감시하고, 멈추면 다시 시작하고, 반복해서 죽으면 안전 모드로 들어가는** 구조를 직접 만들어야 한다.

이 장의 주제는 **워치독과 자가 복구**다.

| 웹 | 임베디드 |
|---|---|
| liveness probe | 태스크 워치독(TWDT), 하트비트 |
| readiness probe | 자체 시험, "요청을 처리할 수 있는가" |
| startup probe | 부팅 유예 시간, 초기화 완료 전 워치독 지연 |
| `restartPolicy: Always` | 리셋, 워치독 타임아웃 |
| CrashLoopBackOff | 리셋 루프 카운터, 안전 모드, 백오프 |
| 코어 덤프 / 스택 트레이스 | ESP32 core dump, panic 백트레이스, 리셋 원인 |
| APM 알림 | 리셋 원인·부팅 횟수·오류 카운터 로그 |

이 장에서 다루는 것:

- 태스크 워치독(TWDT)과 인터럽트 워치독(IWDT)의 역할 차이
- `esp_task_wdt_*` API와 올바른 리셋 위치
- `esp_reset_reason()`으로 리셋 원인 읽기
- 브라운아웃 감지와 전원 문제 구분
- 리셋 루프를 막는 부팅 카운터·안전 모드 설계
- 크래시 덤프(core dump)로 원인 찾기
- Kubernetes의 헬스 체크·재시작 정책과의 대응

**안전 원칙:** 워치독과 리셋은 **차량 주행 중에 일어날 수 있다.** 리셋 자체는 안전 기능이 아니다. 리셋 후 장치가 어떤 상태로 돌아가는지, CAN 송신을 다시 시작해도 되는지, 액추에이터를 건드리지 않는지를 함께 설계해야 한다. 이 책의 차량 실습은 정차 상태의 읽기 전용이고, 리셋·Bus-Off 시험은 벤치에서만 한다.

## 21.1 "살아 있다"와 "건강하다"는 다르다

워치독은 "정해진 시간 안에 신호가 오지 않으면 MCU를 재시작"하는 장치다. 목적은 **행(hang)에서 복구**하는 것이다. 코드가 무한 루프에 빠지거나, 블로킹 호출에서 돌아오지 않거나, 스택이 깨져 흐름을 잃었을 때 기계를 다시 살린다.

하지만 "워치독을 계속 리셋했다"는 사실은 "장치가 건강하다"는 뜻이 아니다. 웹의 헬스 체크와 비교하면 차이가 선명하다.

- **liveness**: 프로세스가 살아 있는가. 실패하면 재시작한다.
- **readiness**: 요청을 처리할 수 있는가. 실패하면 트래픽에서 뺀다. 재시작하지는 않는다.
- **startup**: 초기화가 끝났는가. 끝날 때까지 liveness/readiness를 미룬다.

펌웨어에서는 이 셋을 다음처럼 나눌 수 있다.

| 웹 | 펌웨어 대응 | 실패 시 |
|---|---|---|
| liveness | TWDT 구독, 하트비트 카운터 | 리셋 |
| readiness | 자체 시험, CAN/센서/네트워크 상태 | 안전 모드, 서비스 제외, 경고 |
| startup | 부팅 유예 시간, 초기화 완료 플래그 | 워치독 시작 지연, 재시도 |

가장 흔한 실수는 **ISR이나 타이머에서 워치독을 리셋**하는 것이다. 타이머 ISR은 메인 루프가 죽어도 계속 돌 수 있으므로, 워치독은 "살아 있다"고 착각한다. 워치독은 **모든 핵심 작업이 정상적으로 완료됐을 때** 리셋해야 한다.

## 21.2 태스크 워치독(TWDT)

ESP-IDF의 Task Watchdog Timer(TWDT)는 **태스크 단위**로 감시한다. 기본적으로 각 CPU의 idle 태스크를 감시해, 어떤 태스크가 CPU를 독점해 idle이 실행되지 못하는 상황을 잡는다.

### API

| 함수 | 역할 |
|---|---|
| `esp_task_wdt_init(&config)` | 워치독 초기화. `timeout_ms`, `idle_core_mask`, `trigger_panic` |
| `esp_task_wdt_reconfigure(&config)` | 이미 초기화된 워치독의 설정 변경 |
| `esp_task_wdt_add(NULL)` | 현재 태스크를 감시 대상에 추가 |
| `esp_task_wdt_reset()` | 현재 태스크가 정상 동작 중임을 알림 |
| `esp_task_wdt_delete(NULL)` | 현재 태스크를 감시에서 제거 |
| `esp_task_wdt_add_user(name, &handle)` | 특정 코드 경로를 사용자로 등록 |
| `esp_task_wdt_reset_user(handle)` | 사용자 코드 경로의 진행을 알림 |
| `esp_task_wdt_delete_user(handle)` | 사용자 등록 해제 |
| `esp_task_wdt_print_triggered_tasks()` | 타임아웃 시 어떤 태스크가 굶었는지 출력 |

아래 ESP32 코드는 ESP-IDF 문서의 API와 대조했지만 실물에서 확인하지 않았다. **실물 확인 필요.**

```c
#include "esp_err.h"
#include "esp_task_wdt.h"

void app_main(void) {
    esp_task_wdt_config_t cfg = {
        .timeout_ms = 5000,
        .idle_core_mask = 0,       /* idle 태스크는 직접 구독하지 않는다 */
        .trigger_panic = true,     /* 타임아웃 시 패닉·리셋 */
    };

    esp_err_t err = esp_task_wdt_init(&cfg);
    if (err == ESP_ERR_INVALID_STATE) {
        /* 부팅 시 이미 초기화된 경우 */
        err = esp_task_wdt_reconfigure(&cfg);
    }
    ESP_ERROR_CHECK(err);

    ESP_ERROR_CHECK(esp_task_wdt_add(NULL));  /* 현재 태스크 감시 */

    for (;;) {
        do_can_work();
        esp_task_wdt_reset();       /* 일이 끝난 뒤에만 */
        vTaskDelay(pdMS_TO_TICKS(10));
    }
}
```

- `trigger_panic = true`면 타임아웃 시 패닉과 리셋이 일어난다. 기본 동작은 경고와 백트레이스만 남기고 계속 실행하는 것이다(설정에 따라 다름).
- ESP-IDF 설정에 따라 TWDT가 부팅 시 이미 초기화되어 있을 수 있다. 이때 `esp_task_wdt_init()`는 `ESP_ERR_INVALID_STATE`를 돌려주므로 `esp_task_wdt_reconfigure()`로 설정을 바꾼다.
- 모든 감시 대상 태스크가 각자 `esp_task_wdt_reset()`을 호출해야 한다. 한 태스크라도 굶으면 타임아웃이다.
- `esp_task_wdt_reset()`을 ISR에서 호출하지 않는다. TWDT는 태스크 문맥을 전제로 한다.
- 기본 타임아웃은 ESP-IDF Kconfig의 `CONFIG_ESP_TASK_WDT_TIMEOUT_S`로 정해지며, 일반적인 기본값은 5초다. 버전과 설정에 따라 다를 수 있으므로 `sdkconfig`를 확인한다.

### 어디서 리셋해야 하는가

워치독 리셋은 "코드가 돌고 있다"가 아니라 **"이 주기의 일이 끝났다"**는 신호여야 한다.

```text
나쁜 예: 타이머 ISR에서 1초마다 esp_task_wdt_reset()
  - 메인 루프가 멈춰도 ISR은 계속 돈다.
  - 워치독은 영원히 만족한다.

좋은 예: 수신 태스크가 프레임을 큐에 넣고, 처리 태스크가 처리 완료 후 리셋
  - 큐가 막히면 처리 태스크가 리셋하지 못한다.
  - 워치독이 "처리 경로가 막혔다"를 잡는다.
```

여러 태스크를 감시할 때는 **각 태스크가 자기 책임 범위의 완료를 보고**하게 한다. 예를 들어 CAN 수신 태스크는 "프레임을 받아 큐에 넣었다"에서, OBD 처리 태스크는 "요청·응답 사이클을 끝냈다"에서 리셋한다. 두 태스크가 서로의 리셋을 대신하지 않는다.

### 긴 작업과 워치독

플래시 지우기, OTA 쓰기, 파일 시스템 정리, 큰 TLS 핸드셰이크는 5초를 넘길 수 있다. 이때 무작정 `esp_task_wdt_reset()`을 자주 호출하면 "진행이 없다"는 사실을 숨긴다. 대신 다음을 고려한다.

- **작업을 작은 단위로 나누고, 단위가 끝날 때 리셋한다.** OTA라면 청크 하나를 쓰고 리셋한다.
- **긴 작업 전용 태스크를 두고 타임아웃을 늘린다.** `esp_task_wdt_reconfigure()`로 전체 타임아웃을 바꾸거나, OTA 태스크만 별도 사용자로 등록한다.
- **진행 카운터를 함께 본다.** 리셋은 "진행이 있었다"는 조건에서만 한다. 다운로드가 멈췄는데 타이머만 리셋하면 워치독이 무의미해진다.
- **긴 작업이 끝나면 원래 타임아웃으로 되돌린다.** 늘린 타임아웃을 방치하면 다른 행을 놓친다.

## 21.3 인터럽트 워치독(IWDT)

IWDT(Interrupt Watchdog Timer)는 **인터럽트가 너무 오래 막혀 있는지** 감시한다. TWDT가 태스크의 굶주림을 본다면, IWDT는 **인터럽트 비활성화·긴 크리티컬 섹션·긴 ISR**을 본다.

- IWDT는 Timer Group 1의 하드웨어 워치독을 쓰고, FreeRTOS tick 인터럽트가 자동으로 먹인다. 애플리케이션이 직접 먹이는 API는 없다.
- `CONFIG_ESP_INT_WDT`로 켜고, `CONFIG_ESP_INT_WDT_TIMEOUT_MS`로 타임아웃을 정한다. 일반적인 기본값은 300ms다.
- 타임아웃은 FreeRTOS tick 간격의 두 배보다 커야 한다. PSRAM을 쓰면 기본값이 늘어날 수 있다.
- 타임아웃 시 패닉 핸들러가 실행되고, `Interrupt wdt timeout on CPU0` 같은 이유가 남는다.
- OpenOCD로 디버깅할 때는 브레이크포인트에서 워치독이 멈추고, 다시 켜지지 않을 수 있다. 디버깅 중의 동작과 실물 동작을 구분한다.

IWDT가 울리는 대표적인 원인:

- `portENTER_CRITICAL()`/`portEXIT_CRITICAL()` 사이에서 오래 걸리는 작업
- 인터럽트를 끈 채로 플래시 쓰기·긴 계산·`printf`
- 높은 우선순위 ISR이 오래 실행
- 다른 ISR이 폭주해 tick 처리가 밀림

대응은 타임아웃을 늘리는 것이 아니라 **크리티컬 섹션과 ISR을 줄이는 것**이다. ISR에서는 플래그를 세우고 큐에 넣은 뒤 빠르게 빠져나온다. 17.4절의 ISR 규칙이 그대로 적용된다.

> TWDT와 IWDT는 서로를 대신하지 못한다. 태스크가 멈춘 것과 인터럽트가 막힌 것은 다른 고장이다. 둘 다 켜 두고, 리셋 원인에서 어느 쪽이 울렸는지 구분한다.

## 21.4 리셋 원인 읽기

ESP32는 `esp_reset_reason()`으로 마지막 리셋의 원인을 알려 준다. 부팅 로그에 이 값을 남기면 "가끔 멈춘다"를 "태스크 워치독이 3번 울렸다"로 바꿀 수 있다.

| 값 | 의미 |
|---|---|
| `ESP_RST_POWERON` | 전원 인가 |
| `ESP_RST_SW` | `esp_restart()`에 의한 소프트웨어 리셋 |
| `ESP_RST_PANIC` | 예외·패닉 |
| `ESP_RST_INT_WDT` | 인터럽트 워치독 |
| `ESP_RST_TASK_WDT` | 태스크 워치독 |
| `ESP_RST_WDT` | 그 밖의 워치독 |
| `ESP_RST_DEEPSLEEP` | deep sleep에서 깨어남 |
| `ESP_RST_BROWNOUT` | 브라운아웃(전원 전압 저하) |
| `ESP_RST_CPU_LOCKUP` | CPU 락업(이중 예외) |
| `ESP_RST_PWR_GLITCH` | 전원 글리치 |
| `ESP_RST_UNKNOWN` | 판별 불가 |

`ESP_RST_EXT`(외부 핀 리셋)는 ESP32에서는 해당하지 않는다. `ESP_RST_JTAG`, `ESP_RST_USB`, `ESP_RST_SDIO`, `ESP_RST_EFUSE` 같은 값도 칩·상황에 따라 나온다. 아래 코드도 문서 대조만 했으며 **실물 확인 필요**다.

```c
#include "esp_system.h"
#include "esp_log.h"

static const char *TAG = "boot";
#define FW_VERSION "1.0.0"

static const char *reset_name(esp_reset_reason_t r) {
    switch (r) {
    case ESP_RST_POWERON:   return "POWERON";
    case ESP_RST_SW:        return "SW";
    case ESP_RST_PANIC:     return "PANIC";
    case ESP_RST_INT_WDT:   return "INT_WDT";
    case ESP_RST_TASK_WDT:  return "TASK_WDT";
    case ESP_RST_WDT:       return "WDT";
    case ESP_RST_DEEPSLEEP: return "DEEPSLEEP";
    case ESP_RST_BROWNOUT:  return "BROWNOUT";
    case ESP_RST_CPU_LOCKUP:return "CPU_LOCKUP";
    case ESP_RST_PWR_GLITCH:return "PWR_GLITCH";
    default:                return "UNKNOWN";
    }
}

void log_boot_info(void) {
    esp_reset_reason_t r = esp_reset_reason();
    ESP_LOGI(TAG, "reset=%s (%d)", reset_name(r), (int)r);
    ESP_LOGI(TAG, "fw=%s build=%s", FW_VERSION, __DATE__ " " __TIME__);
}
```

- 리셋 원인은 **부팅 초기에 한 번** 읽어 NVS나 로그로 남긴다. 나중에 다른 코드가 리셋을 일으키면 값이 바뀔 수 있다.
- `ESP_RST_POWERON`은 "사용자가 전원을 뽑았다"일 수도 있고 "배터리가 떨어졌다"일 수도 있다. 브라운아웃과 구분하려면 전압 로그를 함께 본다.
- `ESP_RST_DEEPSLEEP`은 정상적인 깨어남이다. 리셋 루프로 오해하지 않도록 깨우기 원인과 함께 기록한다.
- 펌웨어 버전, 빌드 시각, 커밋 해시를 함께 남긴다. "어떤 펌웨어에서 나는 문제인가"를 구분할 수 있어야 한다.

## 21.5 브라운아웃: 전원이 흔들릴 때

브라운아웃(brownout)은 공급 전압이 순간적으로 떨어져 칩이 오동작하거나 리셋되는 현상이다. ESP32에는 **브라운아웃 검출기**가 있고, `ESP_RST_BROWNOUT`으로 리셋 원인을 남긴다.

- 브라운아웃 검출기는 **칩의 공급 전압(3.3V 계통)**을 본다. 12V 배터리 전압을 직접 재는 회로가 아니다.
- ESP-IDF에서는 `CONFIG_ESP_BROWNOUT_DET`으로 켜고, `CONFIG_ESP_BROWNOUT_DET_LVL_SEL_*`로 임계값을 고른다.
- ESP32 클래식의 임계값은 약 2.43V, 2.48V, 2.58V, 2.62V, 2.67V, 2.70V, 2.77V, 2.80V(±0.05V 추정)이고, 기본 레벨은 0(약 2.43V)이다. 데이터시트·Kconfig 버전에 따라 값이 다를 수 있다.
- 브라운아웃 검출기는 **마지막 방어선**이다. 배터리 보호를 위해 12V 전압을 감시하려면 별도의 분압·ADC·비교기 회로가 필요하다(22장).

브라운아웃이 반복되면 코드를 의심하기 전에 전원을 본다.

- USB 전원과 차량 전원을 동시에 넣어 역전류·접지 루프가 생기지 않았는가
- 12V→3.3V 강압 모듈의 입력 범위·출력 전류·드롭아웃이 충분한가
- CAN 트랜시버·릴레이·모터가 순간 전류를 끌어 3.3V가 흔들리지 않는가
- 커넥터·퓨즈·접지가 느슨하지 않은가
- 배터리 전압이 낮은데 OTA·Wi-Fi 송신을 시작하지 않았는가

브라운아웃 리셋은 **소프트웨어로 복구할 수 없는 경우가 많다.** 리셋 원인을 기록하고, 전원 설계를 고치는 것이 먼저다. 소프트웨어에서는 재시도 백오프, 저전압 시 고전류 작업 금지, 안전 모드 진입으로 피해를 줄인다.

## 21.6 리셋 루프를 막는 설계

워치독이 울릴 때마다 무조건 재부팅하면, 같은 원인으로 계속 죽는 **리셋 루프**에 빠질 수 있다. 웹의 CrashLoopBackOff처럼, 장치는 "계속 재시작"이 아니라 **잠시 멈추고 안전 모드로 들어가는** 방법을 알아야 한다.

### 부팅 카운터

부팅할 때마다 카운터를 올리고, 일정 시간 정상 동작하면 카운터를 지운다.

```text
부팅
  ├─ NVS에서 boot_count 읽기
  ├─ boot_count += 1, NVS에 쓰기
  ├─ boot_count > 3 이면 안전 모드
  ├─ 정상 초기화·자체 시험 통과
  ├─ 60초 동안 리셋 없이 동작
  └─ boot_count = 0
```

- **NVS를 쓴다.** NVS는 플래시에 있어 전원이 꺼져도 남는다. `RTC_DATA_ATTR`는 deep sleep에서는 유지되지만 전원이 완전히 꺼지면 사라진다.
- **매 부팅마다 NVS에 쓰면 플래시 수명에 부담**이 된다. 리셋이 잦은 장치라면 쓰기 횟수를 줄이는 정책이 필요하다. 예를 들어 deep sleep 깨어남은 RTC 메모리로 세고, 콜드 부팅만 NVS에 쓴다.
- **정상 동작 시간은 "부팅했다"가 아니라 "임무를 완수했다"로 정한다.** 예: 60초 동안 하트비트 성공, CAN 응답 3회 성공, 센서 값 유효.
- **전원 인가 리셋과 고장 리셋을 구분한다.** 사용자가 전원을 뽑았다 꽂는 것은 고장이 아니다. `esp_reset_reason()`이 `ESP_RST_POWERON`이면 카운터를 다르게 다룰 수 있다.

### 안전 모드

안전 모드는 "모든 기능을 끄고, 복구 경로만 남기는" 상태다.

| 기능 | 안전 모드에서 |
|---|---|
| CAN 송신 | 금지. 수신·로그만 |
| 액추에이터·릴레이 | 금지. 출력 끔 |
| Wi-Fi | OTA·진단용 최소한만, 또는 AP 모드 |
| 센서 | 읽기만, 필수 센서 확인 |
| 로그 | 리셋 원인·부팅 횟수·오류 코드를 남김 |
| OTA | 허용. 복구의 유일한 원격 경로일 수 있다 |
| 슬립 | 짧게, 복구 명령을 받을 수 있게 |

안전 모드의 목적은 **고장을 반복하지 않으면서 복구 수단을 남기는 것**이다. 안전 모드에서도 같은 리셋이 반복되면 카운터를 더 올리지 말고, 재시도 간격을 늘리거나 사용자에게 LED·부저·로그로 알린다.

### 리셋 루프 시뮬레이션

다음 파이썬 코드는 부팅 카운터와 안전 모드 진입을 흉내 낸다. 실제 NVS가 아니라 정책을 확인하는 모델이다.

```python
def simulate(boots):
    count = 0
    safe = False
    log = []
    for i, outcome in enumerate(boots, 1):
        if safe:
            log.append(f"{i}: safe mode, skip normal boot")
            continue
        count += 1
        log.append(f"{i}: boot_count={count}, outcome={outcome}")
        if count > 3:
            safe = True
            log.append(f"{i}: enter safe mode (count={count})")
            continue
        if outcome == "ok":
            log.append(f"{i}: stable, clear boot_count")
            count = 0
        elif outcome == "crash":
            log.append(f"{i}: crash before stable")
    return log


for line in simulate(["crash", "crash", "crash", "ok", "crash"]):
    print(line)
```

```text
1: boot_count=1, outcome=crash
1: crash before stable
2: boot_count=2, outcome=crash
2: crash before stable
3: boot_count=3, outcome=crash
3: crash before stable
4: boot_count=4, outcome=ok
4: enter safe mode (count=4)
5: safe mode, skip normal boot
```

위 출력은 이 코드를 실제로 실행한 결과다. 세 번 연속 실패하면 네 번째 부팅에서 안전 모드로 들어간다.
- 안전 모드에서는 정상 부팅을 건너뛰고 복구 경로만 남긴다.
- "ok"가 나와도 카운터가 임계값을 넘은 뒤에는 안전 모드가 우선한다. 안전 모드 해제는 사용자의 명시적 조작(버튼·OTA 성공·진단 명령)으로 한다.

실제 구현에서는 안전 모드 진입 조건에 **시간 창**을 둔다. 예를 들어 "10분 안에 3회 리셋"이면 안전 모드, "한 달에 한 번 리셋"은 정상으로 본다. 시간 창이 없으면 오래 사용한 장치의 누적 리셋이 안전 모드를 잘못 켤 수 있다.

### 안전 모드에서 빠져나오는 길

안전 모드가 영구적이면 장치는 현장에서 쓸 수 없다. 다음 중 하나를 남긴다.

- **OTA**: 서버에서 수정된 펌웨어를 받아 자체 시험을 통과하면 안전 모드 해제.
- **물리 버튼**: 부팅 시 버튼을 길게 누르면 카운터 초기화. 차량 장치라면 운전자가 접근하기 어려운 위치에 두지 않는다.
- **진단 명령**: 로컬 시리얼·BLE·Wi-Fi AP로 "clear boot count" 명령. 인증 없이 열지 않는다.
- **자동 해제**: 일정 시간 안전 모드로 정상 동작하면 카운터를 줄인다. 단, 같은 고장이 반복되면 다시 안전 모드로 돌아간다.

## 21.7 크래시 덤프로 원인 찾기

리셋 원인만으로는 "왜"를 알 수 없다. 패닉이 났다면 **core dump**가 도움이 된다. ESP-IDF의 core dump는 패닉 시 태스크 스택·레지스터·일부 메모리를 저장한다.

### 저장 위치

- **Flash**: `data`/`coredump` 파티션에 저장한다. 기본 파티션 테이블에는 포함되지만, 커스텀 테이블이라면 직접 추가해야 한다.
- **UART**: Base64로 출력한다. 모니터가 디코딩하거나, 파일로 저장해 `idf.py coredump-info -c <file>`로 분석한다.
- 둘 중 하나를 고르는 설정이다. 기본값은 끄기인 경우가 많으므로 `sdkconfig`를 확인한다.

```text
# 파티션 테이블에 추가하는 예
coredump, data, coredump, , 64K,
```

- Flash 암호화를 켰다면 `coredump` 파티션에 `encrypted` 플래그를 붙일 수 있다. 그러면 덤프가 암호화되어 저장되지만, 호스트의 `idf.py coredump-info`/`coredump-debug`가 플래시의 암호문을 직접 읽을 수 없다. 이때는 장치에서 복호화된 덤프를 받아 `idf.py coredump-info -c <file>`로 분석한다.
- 파티션 크기는 태스크 수·스택 크기에 따라 달라진다. ESP-IDF 문서는 `20 + max_tasks × (12 + TCB size + max stack)` 이상을 권장한다.
- PSRAM을 태스크 스택으로 쓰는 경우 Flash core dump가 제한될 수 있다. 외부 RAM 내용은 일부만 캡처된다.

### 분석

```bash
# Flash에 저장된 덤프
idf.py coredump-info

# ELF로 저장하고 GDB로 열기
idf.py coredump-debug
```

- **펌웨어와 정확히 같은 빌드의 ELF**가 필요하다. 빌드가 다르면 주소가 어긋나 스택을 잘못 해석한다. 버전·커밋 해시를 함께 보관한다.
- core dump는 "패닉 순간"의 상태다. 그 전에 어떤 일이 있었는지는 로그·카운터·하트비트로 따로 남긴다.
- core dump에 VIN·GPS·사용자 설정이 들어갈 수 있다. 공개 이슈·클라우드에 올리기 전에 개인정보를 제거한다.
- core dump를 항상 켜 두면 플래시 쓰기와 부팅 시간이 늘어난다. 개발·시험 빌드에서는 켜고, 양산 빌드에서는 정책을 정한다.

## 21.8 헬스 체크와 재시작 정책

Kubernetes의 개념을 펌웨어에 그대로 옮길 수는 없지만, 설계 언어로는 유용하다.

| Kubernetes | 펌웨어 | 구현 |
|---|---|---|
| liveness probe | 태스크가 살아 있는가 | TWDT, 하트비트 카운터 |
| readiness probe | 임무를 수행할 수 있는가 | 자체 시험, CAN/센서/네트워크 상태 |
| startup probe | 초기화가 끝났는가 | 부팅 유예, 초기화 완료 플래그 |
| `restartPolicy: Always` | 실패 시 리셋 | 워치독, `esp_restart()` |
| `restartPolicy: OnFailure` | 정상 종료는 재시작하지 않음 | 안전 모드·정상 종료 상태 구분 |
| CrashLoopBackOff | 리셋 루프 백오프 | 부팅 카운터, 안전 모드, 재시도 간격 |
| Pod 조건·이벤트 | 상태 스냅샷 | 리셋 원인, 오류 카운터, 마지막 성공 시각 |
| 노드 드레인 | OTA·정비 모드 | CAN 송신 중지, 안전 상태, 업데이트 |

- **liveness는 "프로세스가 살아 있다"가 아니라 "일이 진행된다"**로 정의한다. 하트비트를 보내는 태스크가 살아 있어도, CAN 수신 태스크가 죽었으면 장치는 건강하지 않다.
- **readiness는 "요청을 받을 수 있다"**로 정의한다. 부팅 직후 Wi-Fi가 아직 안 붙었으면 readiness는 false다. 이때 liveness까지 false로 만들면 재시작 루프에 빠진다.
- **startup은 "느린 초기화를 기다려 주는 시간"**이다. 센서 초기화가 10초 걸리는데 워치독이 5초면 부팅할 때마다 리셋된다. 초기화가 끝난 뒤 워치독을 시작하거나 타임아웃을 늘린다.
- **재시작 정책은 "무조건 Always"가 아니다.** 안전 모드로 진입할 수 있는 장치는 `OnFailure`에 가깝다. 정상 종료·정비 모드와 고장 리셋을 구분한다.

### 관측으로 이어 붙이기

28장의 대시보드는 `/api/health`로 `lastSampleAgeMs`, `roundTripMs`, `reconnects`, `lastError`를 노출한다. 펌웨어도 같은 생각으로 다음을 남긴다.

- 리셋 원인별 카운터 (`poweron`, `task_wdt`, `int_wdt`, `panic`, `brownout`)
- 부팅 횟수, 마지막 정상 동작 시각
- 태스크별 하트비트, 큐 깊이, 드롭 수
- CAN TEC/REC, Bus-Off 횟수, 마지막 오류
- OTA 버전, 마지막 OTA 결과
- 전압(가능하면), 온도(가능하면)

이 값들은 "장치가 죽었다"는 보고를 "무엇이 먼저 무너졌는가"로 바꾼다.

## 21.9 흔한 실수

| 실수 | 결과 | 예방 |
|---|---|---|
| ISR·타이머에서 워치독 리셋 | 메인 루프가 죽어도 리셋 안 됨 | 일이 끝난 태스크 문맥에서 리셋 |
| 모든 태스크가 같은 카운터만 리셋 | 한 태스크의 정지가 숨겨짐 | 태스크별 책임 범위에서 리셋 |
| 워치독 타임아웃을 너무 짧게 | 정상 부팅·OTA도 리셋 | 최악 정상 시간보다 길게, 긴 작업 분리 |
| 타임아웃을 너무 길게 | 행을 늦게 발견 | 단계별 타임아웃, 하트비트와 함께 |
| 리셋 원인을 안 남김 | "가끔 멈춘다"만 남음 | 부팅 초기에 `esp_reset_reason()` 기록 |
| 브라운아웃을 코드 문제로 오해 | 전원 설계를 안 고침 | 전압·리셋 원인·부하 로그 확인 |
| 리셋 루프에 안전 모드 없음 | 같은 고장으로 무한 재시작 | 부팅 카운터, 시간 창, 안전 모드 |
| 안전 모드에서 CAN 송신 지속 | 고장 상태로 버스에 프레임 | 안전 모드에서 송신·액추에이터 금지 |
| core dump 없이 패닉만 봄 | 원인 추적 불가 | coredump 파티션·UART, 동일 ELF 보관 |
| core dump에 개인정보 포함 | 유출 | 공개 전 VIN·GPS 제거 |
| 디버거에서 워치독 동작을 오해 | 실물과 다른 결과 | OpenOCD의 WDT 정지 동작 확인 |

- [ ] TWDT를 켜고, 핵심 태스크를 각각 구독했는가
- [ ] 워치독 리셋이 ISR이 아니라 일이 끝난 태스크에서 호출되는가
- [ ] 긴 작업(OTA·플래시)의 타임아웃·분할 정책이 있는가
- [ ] IWDT를 켜고, 크리티컬 섹션·ISR을 짧게 유지했는가
- [ ] `esp_reset_reason()`을 부팅 로그에 남기는가
- [ ] 브라운아웃과 소프트웨어 리셋을 구분해 기록하는가
- [ ] 부팅 카운터와 안전 모드 진입 조건이 있는가
- [ ] 안전 모드에서 CAN 송신·액추에이터를 멈추는가
- [ ] 안전 모드 해제 경로(OTA·버튼·진단)가 있는가
- [ ] core dump 저장 위치와 동일 빌드 ELF를 보관하는가
- [ ] 하트비트·오류 카운터·마지막 성공 시각을 관측하는가
- [ ] 리셋 루프 시험을 벤치에서 했는가
- [ ] 차량에서는 리셋 후 안전 상태로 돌아가는가

## 장 요약

- 워치독은 "살아 있음"이 아니라 "일이 진행됨"을 감시해야 한다. ISR·타이머에서 리셋하면 의미가 없다.
- TWDT는 태스크 단위, IWDT는 인터럽트 지연을 본다. 둘은 서로를 대신하지 못한다.
- `esp_reset_reason()`으로 리셋 원인을 남기고, 브라운아웃은 전원 문제로 따로 다룬다.
- 리셋 루프를 막으려면 부팅 카운터, 시간 창, 안전 모드, 해제 경로를 설계한다.
- core dump는 패닉의 "왜"를 보여 주지만, 그 전의 이야기는 로그·카운터가 담당한다.
- Kubernetes의 liveness/readiness/startup, restartPolicy, CrashLoopBackOff는 펌웨어의 워치독·자체 시험·안전 모드·백오프로 대응된다.

다음 장에서는 장치가 **차량 배터리를 방전시키지 않도록** 전력을 설계하는 방법을 다룬다. 슬립 모드, 깨우기 원천, 시동 감지, 저전압 차단이 주제다.

## 연습 문제

### 1. (기초) TWDT와 IWDT

TWDT와 IWDT가 각각 무엇을 감시하는지 한 문장씩 쓰고, 하나가 다른 하나를 대신할 수 없는 이유를 설명하라.

### 2. (중급) 워치독 리셋 위치

다음 중 워치독을 리셋해도 되는 위치와 안 되는 위치를 고르고 이유를 쓰라.

```text
(a) 1초 주기 타이머 ISR
(b) CAN 프레임을 큐에 넣은 직후의 수신 태스크
(c) OBD 요청·응답 사이클을 끝낸 처리 태스크
(d) 무한 루프 안의 매 반복
```

### 3. (중급) 리셋 원인 해석

장치가 10분에 세 번 리셋되었다. `esp_reset_reason()`이 각각 `ESP_RST_TASK_WDT`, `ESP_RST_BROWNOUT`, `ESP_RST_PANIC`이었다. 각 원인에 대해 가장 먼저 확인할 것을 하나씩 쓰라.

### 4. (심화) 안전 모드 설계

차량 OBD 장치가 리셋 루프에 빠졌을 때 들어갈 안전 모드를 설계하라. CAN 송신, Wi-Fi, 센서, 로그, OTA, 슬립을 각각 어떻게 할지 정하고, 안전 모드에서 빠져나오는 조건을 쓰라.

### 5. (심화) core dump 운영

현장 장치에서 패닉이 간헐적으로 발생한다. core dump를 수집·분석·보관하는 절차를 설계하라. 개인정보와 저장 공간, 빌드 버전 관리를 포함하라.

## 정답과 해설

### 1.

TWDT는 **태스크가 정해진 시간 안에 진행되는지** 감시한다. IWDT는 **인터럽트가 너무 오래 막혀 있지 않은지** 감시한다. 태스크가 멈춰도 인터럽트는 돌 수 있고, 인터럽트가 막혀도 태스크 스케줄러는 살아 있는 것처럼 보일 수 있다. 고장 지점이 다르므로 둘 다 필요하다.

### 2.

- (a) 안 된다. 타이머 ISR은 메인 루프가 죽어도 계속 돌 수 있어 워치독을 속인다.
- (b) 된다. 수신 태스크가 프레임을 받아 큐에 넣는 책임을 완료했다.
- (c) 된다. 처리 태스크가 요청·응답 사이클을 끝냈다.
- (d) 안 된다. 무한 루프에서 매 반복 리셋하면 "진행" 없이도 워치독이 만족한다. 반복 단위의 실제 완료(예: 청크 처리 성공)에 리셋을 붙인다.

### 3.

- `ESP_RST_TASK_WDT`: 어떤 태스크가 굶었는지 본다. TWDT 로그의 태스크 이름, 스택, 우선순위, 블로킹 호출을 확인한다.
- `ESP_RST_BROWNOUT`: 전원을 먼저 본다. 3.3V 레일, 12V 입력, 강압 모듈, 부하(릴레이·모터·Wi-Fi 송신), 접지·커넥터를 확인한다.
- `ESP_RST_PANIC`: 백트레이스와 core dump를 본다. NULL 역참조, 스택 오버플로, 정렬 위반, `abort()` 호출을 확인한다.

### 4.

예:

- **CAN 송신**: 금지. 수신과 로그만. 다른 ECU에 영향을 주지 않는다.
- **Wi-Fi**: OTA·진단을 위해 최소한으로 켠다. 또는 AP 모드로 띄우고 인증을 건다.
- **센서**: 필수 센서만 읽고, 값이 이상하면 로그만 남긴다.
- **로그**: 리셋 원인·부팅 횟수·마지막 오류·펌웨어 버전을 남긴다.
- **OTA**: 허용. 수정된 펌웨어를 받아 자체 시험을 통과하면 안전 모드 해제.
- **슬립**: 짧게 자거나 자지 않는다. 복구 명령을 받을 수 있어야 한다.
- **해제 조건**: OTA 후 자체 시험 통과, 물리 버튼, 인증된 진단 명령, 일정 시간 정상 동작.

안전 모드에서도 같은 고장이 반복되면 재시도 간격을 늘리고, LED·부저·로그로 사용자에게 알린다.

### 5.

예:

1. **수집**: `data`/`coredump` 파티션에 저장하고, 부팅 후 Wi-Fi가 붙으면 서버로 업로드한다. 업로드 성공을 확인한 뒤에만 덤프를 지운다.
2. **식별**: 펌웨어 버전·커밋 해시·빌드 시각·칩 리비전·리셋 원인을 함께 보낸다.
3. **보관**: 같은 빌드의 ELF·map 파일을 CI 아티팩트로 보관한다. 덤프와 ELF가 맞지 않으면 분석할 수 없다.
4. **개인정보**: VIN·GPS·사용자 설정이 덤프에 들어갈 수 있으므로, 공개 이슈·클라우드 업로드 전에 제거하거나 접근을 제한한다.
5. **용량**: 덤프가 파티션을 넘으면 저장되지 않는다. 태스크 수·스택 크기를 계산하고, 오래된 덤프를 덮어쓰는 정책을 정한다.
6. **재현**: 가능하면 같은 펌웨어를 벤치에서 돌려 패닉을 재현한다. core dump는 단서이고, 재현과 수정이 목표다.
