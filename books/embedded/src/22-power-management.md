# 22장 전력 관리: 차를 방전시키지 않는 장치

## 이 장에서

16장의 ESP32 OBD 장치는 OBD-II 커넥터의 16번 핀에서 전원을 받는다. 16번은 **차량 배터리와 연결된 상시 전원**이다. 시동을 꺼도 전원이 남아 있을 수 있다. 장치가 50mA를 계속 쓰면 70Ah 배터리 기준 이론상 58일 만에 완전 방전되고, 실제로는 그 전에 차가 시동되지 않을 수 있다. 15.3절에서 이 계산을 처음 했다.

웹 개발자에게 "유휴 비용"은 서버가 켜져 있는 시간이다. 클라우드에서는 오토스케일링으로 유휴 인스턴스를 0으로 줄인다. 차량 장치에서 "0으로 줄이는 것"은 **deep sleep**이고, "콜드 스타트"는 **깨어나서 Wi-Fi에 다시 붙는 시간**이다. 비용은 전기요금이 아니라 **배터리 전압과 방전 일수**다.

이 장의 주제는 **전력 관리**다.

| 웹 | 임베디드 |
|---|---|
| 오토스케일링·scale-to-zero | deep sleep, light sleep |
| 웜 풀(warm pool) | modem-sleep, light sleep |
| 콜드 스타트 | 깨우기 → 주변장치 재초기화 → Wi-Fi 재연결 |
| 시간당 비용 | 평균 전류(mA) × 시간 |
| 예산 알림 | 저전압 차단, 배터리 방전 계산 |
| 헬스 체크 | 깨우기 원인, 마지막 성공 시각 |
| 유휴 트래픽 | 불필요한 CAN 요청·Wi-Fi 재연결 |

이 장에서 다루는 것:

- 평균 전류와 배터리 지속 시간 계산
- ESP32의 modem-sleep·light sleep·deep sleep·hibernation
- 타이머·GPIO(ext0/ext1)·ULP 깨우기와 한계
- deep sleep에서 돌아온 뒤의 재초기화
- 시동 상태 감지: 전압, CAN 트래픽, ACC/IGN
- 저전압 차단과 배터리 보호
- CAN 활동으로 깨우기의 한계
- 오토스케일링·유휴 비용 절감과의 대응

**안전 원칙:** 이 장의 전원 실험은 **벤치 전원**으로 한다. 차량 12V 배선을 개조하거나, OBD 포트에 임의의 전원 회로를 붙이지 않는다. 차량에서는 정차 상태에서 읽기만 하고, 배터리 방전이 의심되면 장치를 즉시 뺀다. 12V 배선은 퓨즈·역극성 보호·TVS·강압을 거친다(15장). 이 장은 특정 배터리 전압 임계값을 권하지 않는다. 차량·배터리 문서와 실측으로 정한다.

## 22.1 전력 예산: 평균 전류가 비용이다

장치가 항상 같은 전류를 쓰지 않는다. 깨어 있을 때는 수십~수백 mA, 잘 때는 µA~mA다. 배터리 지속 시간을 결정하는 것은 **평균 전류**다.

```text
평균 전류 = (활성 전류 × 활성 시간 + 슬립 전류 × 슬립 시간) / 주기
```

예를 들어 60초 주기로 2초 동안 80mA를 쓰고, 나머지 58초를 deep sleep 10µA로 보낸다면:

```text
(80mA × 2s + 0.01mA × 58s) / 60s = 2.676mA
```

70Ah 배터리 기준 이론상 지속 시간은:

```text
70,000mAh / 2.676mA = 26,158시간 ≈ 1,090일
```

하지만 이 계산은 **칩 단독**이다. 개발 보드에는 LDO/DC-DC, USB-UART 칩, 전원 LED, 풀업 저항이 붙어 있어 deep sleep에서도 mA 단위가 흐르는 경우가 많다. 보드 전체 슬립 전류가 5mA라면 같은 조건에서 평균은 7.5mA, 지속 시간은 약 389일로 줄어든다. 50%만 사용 가능하다고 보면 194일이다.

```python
BATTERY_AH = 70.0


def avg_ma(active_ma, active_s, sleep_ma, sleep_s):
    period = active_s + sleep_s
    return (active_ma * active_s + sleep_ma * sleep_s) / period


def days(ma, usable=1.0):
    return BATTERY_AH * 1000 * usable / ma / 24


scenarios = [
    ("칩 deep sleep 10µA, 60초 중 2초 활성 80mA", 80, 2, 0.01, 58),
    ("보드 deep sleep 5mA, 60초 중 2초 활성 80mA", 80, 2, 5, 58),
    ("보드 deep sleep 1mA, 60초 중 2초 활성 80mA", 80, 2, 1, 58),
    ("light sleep 0.8mA, 10초 중 1초 활성 80mA", 80, 1, 0.8, 9),
    ("항상 켜짐 50mA", 50, 1, 50, 0),
]

for name, a_ma, a_s, s_ma, s_s in scenarios:
    avg = avg_ma(a_ma, a_s, s_ma, s_s)
    print(f"{name}: 평균 {avg:.3f}mA, "
          f"100% {days(avg):.0f}일, 50% {days(avg, 0.5):.0f}일")
```

```text
칩 deep sleep 10µA, 60초 중 2초 활성 80mA: 평균 2.676mA, 100% 1090일, 50% 545일
보드 deep sleep 5mA, 60초 중 2초 활성 80mA: 평균 7.500mA, 100% 389일, 50% 194일
보드 deep sleep 1mA, 60초 중 2초 활성 80mA: 평균 3.633mA, 100% 803일, 50% 401일
light sleep 0.8mA, 10초 중 1초 활성 80mA: 평균 8.720mA, 100% 334일, 50% 167일
항상 켜짐 50mA: 평균 50.000mA, 100% 58일, 50% 29일
```

위 표는 이 코드를 실제로 실행한 결과다. **데이터시트 값은 칩 단독**이다. 보드 전체 전류는 멀티미터로 측정한다.
- **배터리를 100% 방전시키는 계산은 설계 기준이 아니다.** 차량 배터리는 보호를 위해 훨씬 일찍 분리해야 한다. 이 책은 특정 방전 한계를 권하지 않는다.
- **평균 전류를 줄이는 방법은 세 가지**다. 활성 시간을 줄이고, 활성 전류를 줄이고, 슬립 전류를 줄인다. 슬립 전류가 크면 활성 시간을 아무리 줄여도 소용없다.
- **측정 없이는 최적화하지 않는다.** "deep sleep이면 10µA"라고 가정하지 말고, USB를 뽑고 배터리 입력으로 재운 상태에서 전류를 잰다.

### 웹 비용과 비교

| 웹 | 임베디드 | 계산 |
|---|---|---|
| 인스턴스 시간당 요금 | 평균 전류 × 시간 | mAh |
| scale-to-zero | deep sleep | 슬립 전류 × 슬립 시간 |
| 웜 풀 | light/modem sleep | 상태 유지 비용 |
| 콜드 스타트 지연 | 깨우기 + 재초기화 + Wi-Fi | 활성 시간·지연 |
| 예산 알림 | 저전압 차단 | 전압 임계값 |
| 오버프로비저닝 | 큰 배터리·태양광 | 용량 vs 소비 |

"항상 켜 두면 편하다"는 것은 웹에서도 비싸다. 임베디드에서는 배터리를 죽인다.

## 22.2 ESP32의 sleep 모드

ESP32 데이터시트(v5.3)의 전력 소비 표를 기준으로 정리하면 다음과 같다. 조건은 데이터시트 표를 확인한다.

| 모드 | 전류(일반값) | 유지되는 것 | 깨우는 방법 |
|---|---:|---|---|
| Active (Wi-Fi 동작) | 수십~수백 mA | 전부 | - |
| Modem-sleep (240MHz 듀얼) | 30~68 mA | CPU, 주변장치. 무선은 꺼짐 | 인터럽트, 타이머 |
| Light-sleep | 0.8 mA | 디지털 주변장치·RAM 상태, CPU 일시 정지 | 타이머, GPIO, UART, 터치 등 |
| Deep-sleep (RTC timer + RTC memory) | 10 µA | RTC 메모리·RTC 주변장치 | 타이머, ext0/ext1, 터치, ULP |
| Deep-sleep (ULP 동작) | 150 µA | ULP 코프로세서 | ULP 조건 |
| Hibernation (RTC timer only) | 5 µA | RTC 타이머 일부, 일부 RTC GPIO | RTC 타이머, RTC GPIO |

- **Modem-sleep**은 CPU가 돌고 Wi-Fi/Bluetooth 무선이 꺼진 상태다. 주변장치를 계속 다루면서 무선만 잠시 쉬고 싶을 때 쓴다. Wi-Fi 연결 유지와 함께 쓰는 방법은 ESP-IDF 절전 문서를 따른다.
- **Light-sleep**은 CPU를 멈추지만 RAM과 주변장치 상태를 유지한다. 깨어나는 시간이 짧고, 상태를 다시 만들 필요가 적다. 대신 deep sleep보다 전류가 크다.
- **Deep-sleep**은 CPU·대부분의 RAM·APB 클록 주변장치를 끈다. `RTC_DATA_ATTR`로 표시한 변수와 RTC 메모리만 유지된다. 깨어나면 리셋과 같은 경로로 `app_main()`이 다시 실행된다.
- **Hibernation**은 RTC 타이머와 일부 RTC GPIO만 남긴다. 가장 적게 쓰지만 유지되는 것이 거의 없다. ESP-IDF API로 직접 다루기보다 데이터시트 모드로 이해해 두면 된다.

### 무엇을 잃는가

| 모드 | 잃는 것 | 다시 해야 하는 일 |
|---|---|---|
| Modem-sleep | 무선 연결(설정에 따라) | Wi-Fi 재연결 |
| Light-sleep | CPU 실행 문맥은 유지, 주변장치는 설정에 따라 | 일부 주변장치 재설정 |
| Deep-sleep | 앱 상태, 힙, 태스크, 대부분의 변수 | 주변장치·태스크·큐·TWAI 재초기화 |
| Hibernation | 거의 모든 상태 | 전체 부팅 |

Deep sleep은 "잠깐 멈추는" 것이 아니라 **거의 리셋에 가깝다.** 깨어난 뒤 `app_main()`이 처음부터 실행되고, 전역 변수는 초기화된다. `RTC_DATA_ATTR`에 부팅 카운터·마지막 상태·측정값만 남긴다. 아래 ESP32 코드는 ESP-IDF 문서의 API와 대조했지만 실물에서 확인하지 않았다. **실물 확인 필요.**

```c
#include "esp_attr.h"
#include "esp_sleep.h"
#include "esp_system.h"
#include "esp_log.h"

static const char *TAG = "power";
RTC_DATA_ATTR static uint32_t wake_count;

void app_main(void) {
    wake_count++;
    esp_sleep_wakeup_cause_t cause = esp_sleep_get_wakeup_cause();

    ESP_LOGI(TAG, "wake=%lu cause=%d", (unsigned long)wake_count, (int)cause);
    if (cause == ESP_SLEEP_WAKEUP_TIMER) {
        /* 주기 작업 */
    } else if (cause == ESP_SLEEP_WAKEUP_EXT0 ||
               cause == ESP_SLEEP_WAKEUP_EXT1) {
        /* 버튼·CAN 트랜시버 wake */
    }

    /* 깨어난 뒤 주변장치를 다시 초기화한다. */

    esp_sleep_enable_timer_wakeup(60ULL * 1000000ULL);  /* 60초 */
    esp_deep_sleep_start();  /* 돌아오지 않는다 */
}
```

- `esp_deep_sleep_start()`는 돌아오지 않는다. 그 아래 코드는 실행되지 않는다.
- 깨어난 뒤 `esp_reset_reason()`은 `ESP_RST_DEEPSLEEP`을 돌려준다. 정상적인 깨어남과 고장 리셋을 구분한다.
- `RTC_DATA_ATTR` 변수는 deep sleep에서 유지되지만, 전원이 완전히 꺼지면 사라진다. 영구 카운터는 NVS에 쓴다.
- 깨어난 뒤 Wi-Fi 연결은 끊어져 있다. 재연결에 수백 ms~수 초가 걸릴 수 있으므로, 활성 시간과 평균 전류에 포함한다.

### Light sleep

Light sleep은 상태를 유지하면서 CPU만 멈춘다. 깨어나는 시간이 짧고, UART·GPIO로 깨울 수 있다. 아래 ESP32 코드도 문서 대조만 했으며 **실물 확인 필요**다.

```c
#include "driver/gpio.h"
#include "esp_sleep.h"

void light_sleep_until_pin(void) {
    gpio_wakeup_enable(GPIO_NUM_21, GPIO_INTR_LOW_LEVEL);
    esp_sleep_enable_gpio_wakeup();
    esp_light_sleep_start();   /* 여기서 돌아온다 */
}
```

- Light sleep은 `esp_light_sleep_start()`에서 돌아온다. Deep sleep처럼 `app_main()`이 다시 시작되지 않는다.
- ESP32에서 GPIO 깨우기는 터치·ULP wake와 충돌할 수 있다. 사용하는 기능 조합을 확인한다.
- UART 깨우기는 ESP32에서 UART2를 지원하지 않는 등 제약이 있다. 문서를 확인한다.

## 22.3 깨우기 원천

ESP32의 깨우기 원천은 sleep 모드에 따라 다르다.

| 원천 | 모드 | API | 특징 |
|---|---|---|---|
| RTC 타이머 | Light/Deep | `esp_sleep_enable_timer_wakeup()` | 가장 예측 가능. 주기 작업에 적합 |
| EXT0 | Deep | `esp_sleep_enable_ext0_wakeup()` | RTC GPIO 하나, 레벨 지정 |
| EXT1 | Deep | `esp_sleep_enable_ext1_wakeup_io()` | 여러 RTC GPIO, ESP32는 any-high/all-low |
| GPIO | Light | `esp_sleep_enable_gpio_wakeup()` | 모든 GPIO 가능(칩별 제약) |
| 터치패드 | Light/Deep | `esp_sleep_enable_touchpad_wakeup()` | 터치 센서 |
| ULP | Deep | `esp_sleep_enable_ulp_wakeup()` | ULP가 센서·ADC를 주기적으로 확인 |
| UART | Light | `esp_sleep_enable_uart_wakeup()` | ESP32는 UART2 미지원 등 제약 |

### RTC GPIO

Deep sleep의 ext0/ext1은 **RTC GPIO**에서만 동작한다. ESP32 데이터시트의 핀 표에서 `RTC_GPIO0`~`RTC_GPIO17`로 표시된 핀이다. 대표적으로 GPIO0, 2, 4, 12~15, 25~27, 32~39가 해당한다. GPIO34~39는 입력 전용이다.

- **GPIO21은 ESP32의 RTC GPIO가 아니다.** 16장 예제의 CAN RX가 GPIO21이라면, 그 핀을 ext0/ext1 깨우기로 쓸 수 없다. 보드를 설계할 때 RX를 RTC GPIO로 옮기거나, 트랜시버의 wake 출력을 RTC GPIO에 연결한다.
- `ext0`은 RTC GPIO 하나의 레벨을 본다. RTC 주변장치를 켜 두므로 deep sleep 전류가 데이터시트의 10µA보다 올라갈 수 있다.
- `ext1`은 여러 RTC GPIO를 묶는다. ESP32는 **모두 LOW** 또는 **하나라도 HIGH**만 지원하고, 핀마다 다른 레벨을 지정할 수 없다.
- ext0/ext1로 깨어난 뒤 그 핀을 일반 GPIO로 쓰려면 `rtc_gpio_deinit()`이 필요할 수 있다. 문서의 깨우기 후 처리를 따른다.

```c
/* GPIO33은 ESP32의 RTC GPIO다. 레벨 0에서 깨운다. 실물 확인 필요. */
esp_sleep_enable_ext0_wakeup(GPIO_NUM_33, 0);
esp_deep_sleep_start();
```

### 타이머 깨우기

가장 단순하고 예측 가능한 방법이다. "1분마다 깨어나 상태를 확인한다"처럼 주기 작업에 적합하다.

- CAN 활동이 없어도 깨어나므로 평균 전류는 늘어난다.
- 프레임을 놓칠 위험은 적다. 깨어난 뒤 버스 상태를 확인하고 요청을 보낸다.
- 주기를 너무 짧게 잡으면 슬립 전류보다 **깨어나는 비용**이 커진다. Wi-Fi 재연결이 필요한 장치라면 1분 주기가 10초 주기보다 효율적일 수 있다.

### ULP

ULP(Ultra-Low-Power) 코프로세서는 deep sleep 중에도 간단한 프로그램을 실행할 수 있다. ADC로 센서를 읽고, 임계값을 넘으면 MCU를 깨우는 식이다.

- ULP는 전체 CAN 스택이나 Wi-Fi를 돌리지 못한다. "센서를 주기적으로 확인하다가 조건이 맞으면 깨운다" 정도로 생각한다.
- ULP를 쓰면 deep sleep 전류가 10µA에서 150µA 수준으로 올라간다(데이터시트의 ULP 동작 조건). 항상 깨어 있는 것보다는 훨씬 적다.
- ULP 프로그램은 별도 툴체인·API가 필요하다. 이 책은 개념만 다룬다.

## 22.4 깨어난 뒤: 콜드 스타트 비용

Deep sleep에서 깨어나는 것은 콜드 스타트에 가깝다. 다음을 다시 해야 한다.

```text
1. 부팅 로그, wake 원인 기록
2. NVS/RTC 메모리에서 상태 복원
3. 전원·클록·GPIO 초기화
4. 센서·CAN 트랜시버 초기화
5. TWAI 드라이버 설치·시작, 큐·태스크 생성
6. Wi-Fi 연결, 시각 동기화(필요하면)
7. 첫 요청·첫 하트비트
8. 작업 후 다시 sleep
```

- **첫 CAN 프레임을 놓칠 수 있다.** 다른 노드가 ACK를 대신하므로 수신 자체는 가능하지만, 버스가 조용하면 요청을 보내야 응답이 온다.
- **워치독은 sleep 중에 의미가 없다.** 깨어난 뒤 태스크와 워치독을 다시 등록한다(21장).
- **OTA 중에는 sleep에 들어가지 않는다.** OTA가 끝나고 자체 시험이 통과한 뒤에 잔다.
- **시각**: deep sleep 동안 RTC가 시간을 유지할 수 있지만, Wi-Fi/TLS를 쓰려면 SNTP로 시각을 맞춘다. 인증서 유효기간 검사에 필요하다.
- **로그**: 깨어날 때마다 로그를 플래시에 쓰면 수명과 전력에 영향을 준다. UART가 없으면 링 버퍼·NVS·서버 업로드 정책을 정한다.

## 22.5 시동 상태 감지

"차가 시동 중인가"를 알아야 하는 이유는 세 가지다.

1. **충전 중인지** 판단해 OTA·무거운 작업을 허용한다.
2. **주차 중**에는 sleep을 늘리고 통신을 줄인다.
3. **저전압**일 때 고전류 작업을 막는다.

방법은 세 가지가 있고, 장단점이 다르다.

| 방법 | 장점 | 단점 | 주의 |
|---|---|---|---|
| 전압 변화 | 추가 배선 없음, OBD 16번으로 가능 | 노이즈·부하·온도·스마트 충전에 따라 변함 | 히스테리시스·디바운스·다중 샘플 |
| CAN 트래픽 유무 | 추가 배선 없음, 버스 상태를 직접 봄 | 시동 꺼도 ECU가 한동안 깨어 있음, 게이트웨이가 주기적으로 깨움 | "트래픽 없음"이 시동 OFF의 증거가 아님 |
| ACC/IGN 신호 | 가장 직접적 | 배선·퓨즈·절연·차량별 핀 확인 필요 | 차량 배선 개조 금지 원칙, 전문 설치 |

### 전압으로 보기

- 주행·충전 중에는 12V 계통이 대략 13~14V대로 올라가고, 시동을 끄면 12V대(또는 그 이하)로 내려간다. 15.1절에서 본 것처럼 실제 전압은 9~16V 범위에서 변한다.
- 부하(헤드램프·에어컨·릴레이)가 걸리면 순간적으로 떨어진다. 한 번의 ADC 값으로 판단하지 않고, 여러 샘플의 중앙값·평균을 쓰고 히스테리시스를 둔다.
- 스마트 충전(alternator 제어)이나 전압 강하가 있는 차량은 "충전 전압"이 항상 높지 않을 수 있다. 차량 문서와 실측으로 확인한다.
- 분압 회로는 12V를 ADC 범위로 낮춘다. 4·5장의 분압 계산을 따르고, 최대 입력(점프스타트·load dump)에서 ADC가 넘지 않게 보호한다(15장).

```c
/* 예시: 임계값은 차량·배터리 문서로 정한다. */
#define IGN_ON_MV   13000u   /* 확인 필요: 차량별로 다름 */
#define IGN_OFF_MV  12000u   /* 히스테리시스 */

static bool ignition_on(uint32_t vbat_mv, bool prev) {
    if (prev) {
        return vbat_mv > IGN_OFF_MV;
    }
    return vbat_mv > IGN_ON_MV;
}
```

- 위 숫자는 **예시일 뿐**이다. 이 책은 특정 차량의 임계값을 권하지 않는다.
- 히스테리시스가 없으면 경계에서 상태가 빠르게 뒤집힌다.
- 전압은 시동 크랭킹 중 순간적으로 크게 떨어진다. 크랭킹 중에는 판단을 보류하고, 안정된 뒤 다시 본다.

### CAN 트래픽으로 보기

- 시동이 켜지면 ECU들이 프레임을 활발히 보낸다. 시동이 꺼지면 대부분의 ECU가 잠들지만, 일부는 한동안 깨어 있거나 주기적으로 깨운다.
- **"트래픽이 없다"가 시동 OFF를 보장하지 않는다.** 게이트웨이가 주기적으로 버스를 깨우거나, 충전 중에도 텔레매틱스가 통신할 수 있다.
- **"트래픽이 있다"가 시동 ON을 보장하지 않는다.** 차량이 문을 열면 일부 ECU가 깨어난다.
- CAN 트래픽은 **보조 신호**로 쓰고, 전압·시간·ACC/IGN과 조합한다.

### ACC/IGN 신호

가장 직접적인 방법은 점화 스위치의 ACC/IGN 신호를 받는 것이다.

- 차량 배선에 직접 연결하는 것은 개조다. 이 책의 실습 범위를 벗어난다. 필요하면 퓨즈를 넣고, 절연·보호 회로를 갖춘 전문 설치로 한다.
- 차량별로 ACC/IGN 핀·휴즈·극성이 다르다. 정비 문서와 실측 없이 추측하지 않는다.
- OBD 포트에는 ACC/IGN 신호가 없다. OBD 16번은 상시 전원, 4/5번은 접지다.

이 책의 차량 실습은 **OBD 포트에서 읽기만** 한다. ACC/IGN 배선을 추가하는 것은 다루지 않는다.

## 22.6 저전압 차단: 브라운아웃에 맡기지 않는다

브라운아웃 검출기는 칩의 3.3V 공급이 떨어질 때 리셋한다. 하지만 그것은 **배터리 보호 장치가 아니다.**

- 브라운아웃은 3.3V 레일이 이미 무너진 뒤에 동작한다. 배터리는 그 전에 이미 깊게 방전됐을 수 있다.
- 12V 배터리 전압을 직접 재지 않는다. 강압 모듈의 드롭아웃·부하에 따라 3.3V는 배터리 상태와 다르게 흔들린다.
- 브라운아웃 리셋이 반복되면 장치는 계속 재시작하며 전류를 쓴다. 배터리를 더 빨리 소모한다.

저전압 차단은 **별도의 전압 감시 회로**로 만든다.

```text
12V ── 퓨즈 ── 역극성 보호 ── TVS ──┬── 강압/레귤레이터 ── 3.3V
                                   │
                                   └── 분압 ── ADC 또는 비교기
                                                  │
                                          MCU: 저전압 판단
                                                  │
                                          부하 스위치 OFF / sleep
```

- **ADC 방식**: 분압한 전압을 주기적으로 읽고, 임계값 아래로 내려가면 CAN 송신을 멈추고 sleep에 들어간다. 임계값·히스테리시스·디바운스를 코드로 정한다.
- **비교기 방식**: 하드웨어 비교기로 임계값을 넘으면 MCU에 신호를 준다. MCU가 멈춰도 동작할 수 있다.
- **래치**: MCU가 자기 전원을 끊으면 다시 켤 수 없다. 점화 신호나 버튼으로 다시 켜지는 래치·로드 스위치를 검토한다.
- **퓨즈·역극성·TVS는 그대로 둔다.** 저전압 차단은 전원 보호를 대체하지 않는다.

임계값은 **차량·배터리 문서와 실측**으로 정한다. 이 책은 "11.8V에서 차단" 같은 값을 권하지 않는다. 배터리 종류(납산·AGM), 온도, 차량의 암전류, 배터리 나이에 따라 다르다.

저전압 차단의 동작 순서 예:

```text
1. 전압이 임계값 아래로 N회 연속 측정됨
2. CAN 송신 중지, 트랜시버 standby
3. 액추에이터·릴레이 OFF
4. 로그 flush, 마지막 전압·시각 기록
5. deep sleep 또는 전원 차단 래치
6. 전압이 회복되면(점화·충전) 재기동
```

- **차단 전에 안전 상태로 간다.** 주행 중 갑자기 전원을 끊는 것은 위험하다. 차량 장치는 시동 상태·주행 여부를 함께 본다.
- **차단 후 재기동 조건을 정한다.** 전압이 조금 올라왔다고 바로 켜면 다시 방전된다. 히스테리시스와 지연을 둔다.
- **차단은 최후의 수단**이다. 그 전에 sleep·통신 주기·활성 시간을 줄인다.

## 22.7 CAN 활동으로 깨우기: 문서로 확인된 한계

"CAN 프레임이 오면 ESP32를 deep sleep에서 깨운다"는 요구는 생각보다 까다롭다. ESP-IDF의 TWAI 문서는 **CAN 활동을 sleep 깨우기 원천으로 지원한다고 설명하지 않는다.** TWAI는 깨어 있는 동안의 수신·송신·경보를 담당하고, sleep과 깨우기는 ESP32의 sleep API와 트랜시버 회로가 담당한다.

방법은 세 가지다.

1. **타이머로 주기적으로 깨우기**: 가장 단순하고 예측 가능하다. 1분마다 깨어나 버스 상태를 확인한다. CAN 활동이 없어도 깨어나므로 평균 전류는 늘지만, 프레임을 놓칠 위험이 적다.
2. **트랜시버 RXD를 RTC GPIO에 연결**: SN65HVD230을 standby로 두면 수신기가 살아 있어 RXD가 버스 레벨을 반영한다. RXD를 ext0/ext1 깨우기 핀에 연결해 dominant 레벨에서 깨운다.
3. **wake 출력이 있는 트랜시버/partial networking**: 버스 활동을 감지해 MCU에 wake 신호를 주는 트랜시버를 쓴다. 부품별로 동작·전류·설정이 다르므로 데이터시트를 확인한다.

### 왜 2번이 잘 안 되는가

CAN 프레임은 짧고, 깨우기 신호는 일정 시간 유지되어야 한다.

- 500kbps에서 한 비트는 **2µs**다.
- CAN의 비트 스터핑은 같은 레벨이 5비트를 넘지 않게 한다. 최대 연속 dominant 구간은 약 **5비트 = 10µs**다.
- ESP-IDF 문서는 HP 주변장치 power-down 시의 GPIO 깨우기(`esp_sleep_enable_gpio_wakeup_on_hp_periph_powerdown()`)에 대해 신호가 **RTC slow clock 3주기 이상** 유지되어야 한다고 설명한다. ext0/ext1에는 같은 최소 펄스 폭이 명시되어 있지 않다.
- 그래도 ext0/ext1의 깨우기 회로는 RTC slow clock 영역에 있다. RTC slow clock이 150kHz라면 1주기가 약 **6.7µs**이므로, 10µs dominant 펄스는 샘플링 위상에 따라 놓칠 수 있다(확인 필요).

그래서 RXD를 직접 RTC GPIO에 연결하는 방식은 **프레임을 놓칠 수 있다.** 래치·펄스 확장 회로로 dominant 신호를 수십 µs 이상 유지하거나, wake 출력이 있는 트랜시버를 쓰거나, 타이머 깨우기를 함께 쓴다.

- **핀 선택**: RTC GPIO만 ext0/ext1에 쓸 수 있다. GPIO21은 RTC GPIO가 아니므로 16장 예제의 RX=21로는 deep sleep ext0/ext1을 쓸 수 없다.
- **전류**: SN65HVD230 standby는 370µA 수준이다(16.9절, 데이터시트). ESP32 deep sleep 10µA보다 크다. 트랜시버를 완전히 sleep시키는 부품은 수신기도 꺼져 CAN 깨우기를 못 한다.
- **첫 프레임**: 깨어난 뒤 TWAI를 다시 초기화하는 동안 프레임을 놓칠 수 있다. 버스가 조용하면 요청을 보내야 응답이 온다.
- **실차 시험**: 정차 상태에서만, 벤치에서 먼저 시험한다. 주행 중 깨우기 시험은 하지 않는다.

> 결론: CAN 깨우기는 "되면 좋은 최적화"이지, 안전 기능의 전제가 아니다. 배터리 보호의 기본은 **타이머 깨우기 + 사용 후 분리 + 저전압 차단**이다.

## 22.8 오토스케일링·유휴 비용과의 대응

| 클라우드 | 임베디드 | 설계 질문 |
|---|---|---|
| scale-to-zero | deep sleep | "자는 동안 무엇을 잃어도 되는가" |
| 웜 풀 | light/modem sleep | "깨어나는 지연을 얼마나 줄일 것인가" |
| 콜드 스타트 | 깨우기 + 재초기화 | "첫 요청까지 몇 초 걸리는가" |
| 오토스케일링 정책 | 주기·이벤트 기반 깨우기 | "언제 깨어날 것인가" |
| 비용 모니터링 | 평균 전류 측정 | "mA·일을 아는가" |
| 예산 알림 | 저전압 차단 | "배터리를 언제 지킬 것인가" |
| 과잉 프로비저닝 | 큰 배터리·태양광 | "용량으로 덮을 것인가, 소비를 줄일 것인가" |

- **scale-to-zero에도 비용이 있다.** deep sleep 10µA도 0이 아니다. 1년이면 87.6mAh다. 작아 보이지만, 보드 전체가 5mA면 43.8Ah로 배터리의 절반이 넘는다.
- **웜 풀은 공짜가 아니다.** light sleep 0.8mA는 deep sleep 10µA의 80배다. 빠른 응답이 정말 필요한지 묻는다.
- **콜드 스타트를 측정한다.** Wi-Fi 재연결, TLS 핸드셰이크, CAN 초기화에 걸리는 시간을 재고, 그 시간의 전류를 평균에 넣는다.
- **예산은 전압으로 확인한다.** 평균 전류 계산은 추정이고, 실제 배터리 전압·암전류·온도는 다르다. 저전압 차단과 사용 후 분리가 최후의 안전장치다.

## 22.10 체크리스트

- [ ] 활성·슬립 전류를 데이터시트가 아니라 **보드 전체**로 측정했는가
- [ ] 평균 전류와 배터리 지속 시간을 계산했는가
- [ ] sleep 모드와 깨우기 원천을 표로 정리했는가
- [ ] deep sleep에서 잃는 상태와 복원 방법을 정했는가
- [ ] ext0/ext1에 RTC GPIO를 썼는가
- [ ] CAN 깨우기의 펄스 폭 한계를 벤치에서 시험했는가
- [ ] 시동 감지 방식(전압·CAN·ACC/IGN)의 장단점을 문서화했는가
- [ ] 저전압 차단 회로와 히스테리시스가 있는가
- [ ] 저전압 차단 임계값을 차량·배터리 문서로 확인했는가
- [ ] OTA·워치독·sleep이 서로 충돌하지 않는가
- [ ] 차량에서는 정차·읽기 전용을 지키는가
- [ ] 배터리 방전이 의심되면 즉시 장치를 빼는가

## 장 요약

- 배터리 지속 시간을 결정하는 것은 순간 최대 전류가 아니라 **평균 전류**다. 활성 시간·활성 전류·슬립 전류를 함께 줄인다.
- ESP32는 modem-sleep(30~68mA), light-sleep(0.8mA), deep-sleep(10µA), hibernation(5µA)을 제공한다. 데이터시트 값은 칩 단독이며 보드 전체는 측정해야 한다.
- Deep sleep은 거의 리셋이다. `RTC_DATA_ATTR`와 NVS에 필요한 상태만 남기고, 깨어난 뒤 주변장치·태스크·TWAI를 다시 초기화한다.
- 깨우기 원천은 타이머, ext0/ext1(RTC GPIO), light sleep GPIO, 터치, ULP가 있다. GPIO21은 ESP32 RTC GPIO가 아니다.
- CAN 활동 깨우기는 TWAI API로 지원되지 않는다. RXD를 RTC GPIO에 연결하는 방식은 짧은 프레임 펄스 때문에 놓칠 수 있어 벤치 시험이 필요하다.
- 시동 감지는 전압·CAN 트래픽·ACC/IGN의 장단점을 조합한다. "트래픽 없음"이나 "전압 하나"로 단정하지 않는다.
- 브라운아웃은 배터리 보호가 아니다. 12V 전압 감시·저전압 차단·히스테리시스·래치를 별도로 설계한다.
- 웹의 scale-to-zero·웜 풀·콜드 스타트·비용 알림은 deep sleep·light sleep·깨우기 비용·저전압 차단으로 대응된다.

다음 장부터는 차 없이 반복하는 실습으로 돌아간다. 23장의 가상 CAN, 24장의 Web Serial, 25장의 테스트 전략이 그 시작이다.

## 연습 문제

### 1. (기초) sleep 모드

Modem-sleep, light-sleep, deep-sleep, hibernation을 전류가 작은 순서로 나열하고, 각각 유지되는 것과 잃는 것을 한 줄씩 쓰라.

### 2. (중급) 평균 전류

장치가 5분마다 3초 동안 120mA로 동작하고, 나머지 시간은 0.5mA로 잔다. 70Ah 배터리에서 50%만 사용할 때 이론상 며칠 버티는가? 계산 과정을 쓰라.

### 3. (중급) 깨우기 원천 선택

다음 요구에 가장 적합한 깨우기 원천을 고르고 이유를 쓰라.

```text
(a) 10분마다 온도를 읽어 서버로 보낸다.
(b) 사용자가 버튼을 누르면 깨어난다.
(c) 문이 열리면(리드 스위치) 깨어난다.
(d) CAN 프레임이 오면 깨어나고 싶다.
```

### 4. (심화) 시동 감지 설계

OBD 포트만 사용할 수 있는 차량 장치에서 "시동 중"을 판단하려 한다. 전압·CAN 트래픽·시간대를 조합한 상태 기계를 설계하고, 오판정 시나리오와 대응을 쓰라.

### 5. (심화) 저전압 차단

12V 배터리로 동작하는 장치에 저전압 차단을 넣으려 한다. ADC 방식과 비교기 방식의 장단점, 히스테리시스·래치·재기동 조건, 차량 안전을 고려한 차단 순서를 설명하라.

## 정답과 해설

### 1.

전류가 작은 순서: **hibernation(5µA) → deep-sleep(10µA, RTC timer+memory) → light-sleep(0.8mA) → modem-sleep(30~68mA)**. (조건에 따라 값은 달라진다.)

- Hibernation: RTC 타이머·일부 RTC GPIO만 유지. 거의 모든 상태를 잃는다.
- Deep-sleep: RTC 메모리·RTC 주변장치 유지. 앱 상태·힙·태스크는 잃고, 깨어나면 `app_main()`부터 다시 시작한다.
- Light-sleep: RAM·디지털 주변장치 상태 유지, CPU 일시 정지. 깨어나는 시간이 짧다.
- Modem-sleep: CPU·주변장치 유지, 무선 꺼짐. Wi-Fi 연결 유지 기법과 함께 쓴다.

### 2.

주기 300초, 활성 3초, 슬립 297초.

```text
평균 = (120mA × 3s + 0.5mA × 297s) / 300s
     = (360 + 148.5) / 300
     = 1.695mA
```

70Ah의 50% = 35,000mAh.

```text
35,000mAh / 1.695mA = 20,649시간 ≈ 860일
```

이론값이다. 실제로는 보드 전체 전류, 온도, 배터리 노화, 충전 상태에 따라 달라진다.

### 3.

- (a) **RTC 타이머**. 주기 작업에 가장 예측 가능하고 구현이 쉽다.
- (b) **ext0 또는 light sleep GPIO**. 버튼 레벨을 RTC GPIO로 받는다. 버튼이 RTC GPIO가 아니면 light sleep GPIO 깨우기를 쓴다.
- (c) **ext0/ext1**. 리드 스위치를 RTC GPIO에 연결하고, 열림/닫힘 레벨을 지정한다. 채터링 방지(디바운스)를 넣는다.
- (d) **타이머 깨우기 + CAN 상태 확인**을 기본으로 하고, 필요하면 RXD를 RTC GPIO에 연결한 깨우기를 보조로 쓴다. 짧은 프레임 펄스는 놓칠 수 있으므로 벤치에서 시험한다. TWAI 자체는 deep sleep 깨우기 원천이 아니다.

### 4.

예:

```text
상태: PARKED, CRANKING, RUNNING, UNKNOWN

PARKED:
  - 전압이 임계값 이상으로 N회 연속 → RUNNING
  - CAN 트래픽이 M초 이상 지속 → RUNNING 후보(전압 확인)
  - 아니면 sleep 주기 유지

CRANKING:
  - 전압이 크게 떨어졌다가 회복 → RUNNING
  - 일정 시간 안에 회복 없음 → UNKNOWN/저전압

RUNNING:
  - 전압이 임계값 아래로 N회 연속 + CAN 트래픽 감소 → PARKED 후보
  - OTA·무거운 작업 허용

UNKNOWN:
  - 전압·CAN·시간을 다시 확인, 고전류 작업 금지
```

오판정 시나리오:

- **충전 중이지만 시동은 꺼짐**: 전압이 높다. CAN 트래픽·시간대를 함께 본다.
- **시동 중이지만 전압이 낮음**: 스마트 충전·부하. CAN 트래픽을 본다.
- **문을 열어 ECU가 깨어남**: CAN 트래픽만으로 RUNNING 판단하지 않는다.
- **배터리 노화로 전압이 낮음**: 임계값을 차량 문서로 정하고, 히스테리시스를 둔다.

대응: 단일 신호로 단정하지 않고, 상태 전이에 시간·횟수 조건을 둔다. 불확실할 때는 **고전류 작업을 하지 않는 쪽**으로 실패한다.

### 5.

- **ADC 방식**: 분압한 12V를 MCU ADC로 읽는다. 유연하고 임계값을 소프트웨어로 바꿀 수 있지만, MCU가 자고 있으면 못 읽고, 노이즈·ADC 오차·기준 전압 문제가 있다.
- **비교기 방식**: 하드웨어 비교기로 임계값을 넘으면 인터럽트를 준다. MCU가 멈춰도 동작하고 응답이 빠르지만, 임계값을 하드웨어로 정해야 하고 부품이 늘어난다.

공통 설계:

- **히스테리시스**: 차단 임계값과 복귀 임계값을 다르게 둔다.
- **디바운스**: 여러 샘플·시간 조건을 둔다.
- **래치**: MCU가 자기 전원을 끊으면 다시 켤 수 없다. 점화·버튼·충전 신호로 재기동하는 래치를 둔다.
- **재기동 조건**: 전압이 복귀 임계값 이상으로 일정 시간 유지될 때만 켠다.
- **차단 순서**: CAN 송신 중지 → 액추에이터 OFF → 로그 flush → 트랜시버 standby → sleep/전원 차단. 주행 중에는 차단하지 않는다.
- **안전**: 차단은 최후의 수단이고, 그 전에 sleep·통신 주기를 줄인다. 임계값은 차량·배터리 문서와 실측으로 정한다.
