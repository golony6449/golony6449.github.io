# 30장 J1939: 트럭과 중장비의 CAN

## 이 장에서

웹 개발자에게 "API가 하나 더 있다"는 말은 익숙하다. 같은 HTTP 위에 REST도 있고 GraphQL도 있고 gRPC도 있다. 전송은 HTTP로 같지만, 경로·메시지 모양·에러 규칙·인증 방식은 서로 다르다. CAN도 똑같다. 7장에서 본 물리·링크 계층은 같고, 그 위에 올라가는 약속이 분야마다 다르다.

지금까지 이 책의 차량 예시는 승용차의 OBD-II(ISO 15765-4)였다. OBD-II는 배출가스 규제에서 출발한 **진단용 창구**다. 트럭·버스·건설기계·농기계는 같은 CAN을 쓰지만 OBD-II 대신 **SAE J1939**를 쓴다. J1939는 진단만을 위한 규격이 아니라, 차량의 ECU들이 주행 중에 데이터를 주고받는 **차량 내 응용 프로토콜**이다.

이 장의 목표는 J1939를 완전히 구현하는 것이 아니다. 다음을 이해하는 것이다.

- 29비트 CAN ID가 **우선순위·PGN·소스 주소**로 나뉘는 방식
- PGN(메시지 묶음)과 SPN(신호)의 관계, OBD-II PID와의 차이
- 주소 클레임(address claim)으로 ECU가 소스 주소를 얻는 과정
- 8바이트를 넘는 메시지를 보내는 TP.CM/TP.DT와 BAM
- DM1 활성 고장 코드를 읽고 SPN·FMI로 해석하는 법
- python-can 가상 버스에서 29비트 프레임을 만들고 해석하는 실습

**안전 규칙은 11장과 같다.** 실제 차량에서는 정차 상태에서 읽기만 한다. DM1은 읽어도 되지만, DM3(고장 코드 삭제)나 임의 프레임 송신은 실제 차량에 보내지 않는다. 송신 실습은 이 장의 가상 버스나 벤치에서만 한다.

## 30.1 OBD-II와 무엇이 다른가

OBD-II와 J1939는 같은 CAN 위에 있지만 출발점이 다르다.

| | OBD-II | J1939 |
|---|---|---|
| 출발점 | 배출가스 규제·검사 | 상용차 ECU 간 통신 |
| 주 사용자 | 정비사·검사 장비·운전자 앱 | 엔진·변속기·브레이크·차체 ECU |
| ID | 주로 11비트 | 29비트 확장 ID |
| 주소 방식 | 진단 요청 주소 `7DF`/`7E0`~`7E7`, 응답 `7E8`~`7EF` | PGN + 소스 주소(SA), 필요하면 목적지 주소(DA) |
| 메시지 | 요청/응답(PID) 중심 | 주기 브로드캐스트 + 요청/응답 + 진단 |
| 데이터 정의 | PID별 공식(SAE J1979) | PGN 안의 SPN별 해상도·오프셋(SAE J1939-71) |
| 큰 메시지 | ISO-TP(ISO 15765-2) | J1939 TP(TP.CM/TP.DT) |
| 진단 | Mode 01~0A, DTC | DM1/DM2, SPN/FMI/OC |
| 물리 속도 | 250k/500k(차종별) | 250k(J1939-11), 500k(J1939-14) |

가장 큰 차이는 **"누가 말하는가"를 프레임에 싣는다**는 점이다. OBD-II는 진단 도구가 질문하고 ECU가 답하는 구조라, 질문자의 주소는 보통 문제가 되지 않는다. J1939는 여러 ECU가 같은 버스에서 주기적으로 자신의 데이터를 broadcast하므로, 수신자는 "이 PGN을 보낸 소스 주소가 누구인가"를 함께 봐야 한다. 같은 PGN이라도 엔진 ECU가 보낸 것과 변속기 ECU가 보낸 것은 다른 의미일 수 있다.

J1939는 하나의 문서가 아니라 여러 부분으로 이루어진다.

- **J1939-11/-14**: 물리 계층(250k/500k)
- **J1939-21**: 데이터 링크·전송 프로토콜(TP)
- **J1939-71**: 차량 응용 계층(PGN/SPN)
- **J1939-73**: 진단 메시지(DM1~DM3 등)
- **J1939-81**: 네트워크 관리(주소 클레임)

이 책은 공개된 2차 자료와 공개 구현으로 확인한 범위만 설명한다. 표준 원문은 유료이므로, 실제 제품 구현에서는 해당 개정판을 확인해야 한다.

## 30.2 29비트 ID: 우선순위, PGN, 소스 주소

클래식 CAN의 29비트 확장 ID는 J1939에서 다음처럼 나뉜다.

```text
bit 28-26   bit 25   bit 24   bit 23-16   bit 15-8   bit 7-0
[Priority]  [EDP]    [DP]     [PF]        [PS]       [SA]
   3비트      1비트    1비트     8비트       8비트      8비트
```

- **Priority(3비트)**: 0이 가장 높다. CAN 중재에서 ID가 작을수록 먼저 이긴다. J1939는 메시지 종류별로 기본 우선순위를 정해 둔다.
- **EDP/DP**: 확장 데이터 페이지. PGN의 상위 비트다. 대부분 0이다.
- **PF(PDU Format)**: 메시지 묶음의 종류를 크게 나눈다.
- **PS(PDU Specific)**: PF 값에 따라 의미가 달라진다.
- **SA(Source Address)**: 보낸 ECU의 주소다. 0x00은 Engine #1, 0x03은 Transmission #1이 대표적이다. 0xFE는 아직 주소를 얻지 못한 null, 0xFF는 목적지 주소로만 쓰는 global이다.

### PDU1과 PDU2

PGN을 계산할 때 PS를 어떻게 다루는지가 핵심이다.

| 형식 | 조건 | PS의 의미 | PGN |
|---|---|---|---|
| PDU1 | PF < 240 (`0x00`~`0xEF`) | 목적지 주소(DA) | EDP·DP·PF, PS는 0으로 둔다 |
| PDU2 | PF ≥ 240 (`0xF0`~`0xFF`) | 그룹 확장(GE) | EDP·DP·PF·PS 전체 |

예를 들어 DM1은 PGN 65226(`0x00FECA`)이고 PF가 `0xFE`라서 PDU2다. PS `0xCA`가 PGN의 일부다. 반면 TP.CM은 PGN 60416(`0x00EC00`)이고 PF가 `0xEC`라서 PDU1이다. PS는 목적지 주소이며 PGN에는 포함되지 않는다.

```text
DM1  : PF=0xFE(PDU2), PS=0xCA(그룹 확장)  -> PGN 0x00FECA = 65226
TP.CM: PF=0xEC(PDU1), PS=DA(목적지)       -> PGN 0x00EC00 = 60416
```

CAN ID에서 PGN을 꺼낼 때 PDU1의 PS를 그대로 두면 PGN이 목적지 주소에 따라 달라진다. 그래서 라이브러리는 PDU1이면 PS를 0으로 지운다. 이 책의 예제도 그렇게 한다.

### 공개된 PGN 예

다음 값은 공개 자료와 공개 구현에서 확인한 대표 PGN이다. 차량·ECU에 따라 지원 여부와 주기는 다르다.

| 이름 | PGN | 16진수 | 형식 | 기본 우선순위 | 내용 |
|---|---:|---|---|---:|---|
| EEC1 | 61444 | `0x00F004` | PDU2 | 3 | 엔진 회전수·토크 |
| ET1 | 65262 | `0x00FEEE` | PDU2 | 6 | 냉각수·연료·오일 온도 |
| CCVS | 65265 | `0x00FEF1` | PDU2 | 6 | 차속·크루즈 상태 |
| DM1 | 65226 | `0x00FECA` | PDU2 | 6 | 활성 고장 코드 |
| DM2 | 65227 | `0x00FECB` | PDU2 | 6 | 과거 고장 코드 |
| Request | 59904 | `0x00EA00` | PDU1 | 6 | PGN 요청 |
| Address Claimed | 60928 | `0x00EE00` | PDU1 | 6 | 주소 클레임 |
| TP.CM | 60416 | `0x00EC00` | PDU1 | 7 | 전송 프로토콜 제어 |
| TP.DT | 60160 | `0x00EB00` | PDU1 | 7 | 전송 프로토콜 데이터 |

예를 들어 DM1을 소스 주소 0x00에서 보내면 CAN ID는 `0x18FECA00`이다.

```text
0x18FECA00
  └─ 0x18 = 0b110 << 26  -> priority 6
     0x00FECA << 8       -> PGN 65226
     0x00                -> SA 0 (Engine #1)
```

CAN ID를 그대로 "PGN"이라고 부르면 안 된다. 같은 PGN도 우선순위와 소스 주소에 따라 CAN ID가 달라지고, PDU1이면 목적지 주소에 따라서도 달라진다.

### 웹 개념과 대응

| 웹 | J1939 | 차이 |
|---|---|---|
| URL 경로/토픽 | PGN | 메시지 종류를 나타내는 번호. 계층 구조가 아니다 |
| 요청 헤더의 우선순위 | Priority | CAN 중재에 직접 쓰인다. 높을수록 먼저 |
| 발행자 ID | Source Address | 주소는 클레임으로 얻고, 정체성은 NAME이 나타낸다 |
| DM(다이렉트 메시지) | PDU1 + DA | 특정 노드에만 보낸다 |
| 브로드캐스트 채널 | PDU2 | 버스의 모든 노드가 받는다 |
| QoS 클래스 | Priority + PGN | 메시지 종류별 기본 우선순위가 정해져 있다 |

## 30.3 PGN과 SPN: 메시지와 신호

J1939에서 **PGN(Parameter Group Number)**은 메시지 묶음이고, **SPN(Suspect Parameter Number)**은 그 안의 개별 신호다. OBD-II의 PID와 SPN은 둘 다 "데이터 정의 번호"지만 쓰임이 다르다.

| | OBD-II PID | J1939 SPN |
|---|---|---|
| 위치 | Mode 01 요청의 1바이트 | PGN 데이터의 특정 비트·바이트 |
| 접근 | 요청/응답 | 주기 broadcast를 수신 |
| 정의 | SAE J1979의 PID 표 | SAE J1939-71의 SPN 표 |
| 예 | PID `0C` 엔진 회전수 | SPN 190 엔진 회전수 |
| 단위·해상도 | PID 공식 | SPN별 해상도·오프셋 |
| 진단 코드 | P0xxx 2바이트 | SPN 19비트 + FMI 5비트 |

### 대표 SPN

| SPN | 이름 | PGN | 위치(1부터) | 해상도 | 오프셋 | 예 |
|---:|---|---|---|---:|---:|---|
| 190 | Engine Speed | 61444 EEC1 | 바이트 4~5 | 0.125 rpm/bit | 0 | 9600 -> 1200 rpm |
| 110 | Engine Coolant Temperature | 65262 ET1 | 바이트 1 | 1°C/bit | −40°C | 130 -> 90°C |
| 84 | Wheel-Based Vehicle Speed | 65265 CCVS | 바이트 2~3 | 1/256 km/h/bit | 0 | 15360 -> 60 km/h |
| 100 | Engine Oil Pressure | 65263 EFL/P1 | 바이트 4 | 4 kPa/bit | 0 | 확인 필요 |

- J1939는 다바이트 값을 **리틀 엔디언**으로 보낸다. 바이트 4가 하위 바이트, 바이트 5가 상위 바이트다.
- 해상도와 오프셋은 SPN마다 다르다. `raw * resolution + offset`으로 물리량을 계산한다.
- "위치"는 1부터 세는 바이트 번호다. 코드에서는 0부터 세므로 하나씩 당겨야 한다.
- 표에 없는 SPN은 공개 PGN 데이터베이스나 제조사 문서로 확인한다. **확인 필요** 표시를 지우지 않는다.

### 계산 예

EEC1의 엔진 회전수(SPN 190)는 바이트 4~5에 있다. `80 25`로 왔다면 리틀 엔디언으로 `0x2580 = 9600`이고, `9600 × 0.125 = 1200 rpm`이다. ET1의 냉각수(SPN 110)가 `0x82`라면 `130 − 40 = 90°C`다. CCVS의 차속(SPN 84)이 `00 3C`라면 `0x3C00 = 15360`이고, `15360 ÷ 256 = 60 km/h`다.

```text
EEC1  data[3..4] = 80 25 -> 0x2580 = 9600 -> 1200 rpm
ET1   data[0]    = 82    -> 130 - 40 = 90 °C
CCVS  data[1..2] = 00 3C -> 0x3C00 = 15360 -> 60 km/h
```

OBD-II PID `0C`도 엔진 회전수를 주지만, J1939에서는 요청하지 않아도 ECU가 주기적으로 보낸다. 그래서 J1939 수신기는 "요청-응답 클라이언트"보다 **스트림 구독자**에 가깝다.

## 30.4 주소 클레임: 소스 주소를 얻는 법

J1939 노드는 소스 주소 0~253 중 하나를 가져야 한다. 주소는 고정된 설정값일 수도 있지만, 같은 종류의 ECU가 여러 개 붙거나 정비 중 ECU를 교체하면 충돌이 생긴다. J1939-81은 **동적 주소 클레임**으로 이 문제를 푼다.

### 절차

1. 노드가 전원을 켜면 원하는 주소로 **Address Claimed(PGN 60928)**를 보낸다. 목적지 주소는 global(`0xFF`), 데이터는 8바이트 **NAME**이다.
2. 다른 노드가 같은 주소를 이미 쓰고 있으면, 둘 다 자신의 NAME을 비교한다. **64비트 NAME 값이 작은 쪽이 이긴다.**
3. 진 쪽은 다른 주소로 다시 클레임한다. 빈 주소가 없으면 소스 주소 `0xFE`(null)로 "Cannot Claim Address"를 보낸다.
4. 클레임이 끝나면 노드는 그 주소를 소스 주소로 사용한다. 초기 클레임에서는 250ms 동안 경쟁 클레임을 기다린다.

### NAME 64비트

NAME은 "이 노드가 무엇인가"를 나타내는 정체성이다. 공개 자료에서 확인한 필드 구성은 다음과 같다.

| 필드 | 비트 수 | 의미 |
|---|---:|---|
| Identity Number | 21 | 제조사가 부여한 고유 번호 |
| Manufacturer Code | 11 | 제조사 코드 |
| ECU Instance | 3 | 같은 기능의 몇 번째 ECU인가 |
| Function Instance | 5 | 같은 기능의 인스턴스 |
| Function | 8 | ECU 기능(엔진, 변속기 등) |
| Reserved | 1 | 예약 |
| Vehicle System | 7 | 차량 시스템 |
| Vehicle System Instance | 4 | 시스템 인스턴스 |
| Industry Group | 3 | 산업 그룹(도로, 농업, 해양 등) |
| Arbitrary Address Capable | 1 | 동적 주소를 쓸 수 있는가 |

작은 NAME이 이긴다는 것은, 예를 들어 제조사 코드와 일련번호가 더 작은 노드가 주소를 차지한다는 뜻이다. 이 규칙은 **주소가 정체성이 아니다**라는 점을 보여 준다. 주소는 바뀔 수 있고, NAME이 진짜 ID다.

### 합성 예

다음 NAME은 설명을 위해 만든 **합성 값**이다. 실제 제품의 NAME이 아니다.

```text
NAME = 0x8000000024612345
     = 0b1 000 0000 0000 0000 0000 0000 0010 0100 0110 0001 0010 0011 0100 0101
```

- Arbitrary Address Capable = 1
- Industry Group = 0
- Vehicle System = 0
- Function = 0
- Manufacturer Code = 0x123
- Identity Number = 0x12345
- 나머지 필드 = 0

리틀 엔디언 바이트로는 `45 23 61 24 00 00 00 80`이다.

### 주소 클레임 요청

버스에 어떤 노드가 있는지 알고 싶으면 **Request(PGN 59904)**로 PGN 60928을 요청한다. 데이터는 요청할 PGN 3바이트를 리틀 엔디언으로 쓴다.

```text
18EAFF80  00 EE 00   -> "PGN 60928(주소 클레임)을 모두 응답하라"
18EEFF80  45 23 61 24 00 00 00 80  -> SA 0x80이 자기 NAME을 클레임
```

### 웹 개념과 대응

| 웹 | J1939 | 차이 |
|---|---|---|
| 서비스 디스커버리(mDNS, Consul) | Address Claim | TTL·헬스 체크가 아니라 NAME 비교로 승자를 정한다 |
| 인스턴스 ID | Source Address | 주소는 바뀔 수 있다 |
| 노드 ID/인증서 | NAME | 64비트 정체성. 주소와 분리되어 있다 |
| 브로드캐스트 검색 | Request PGN 59904 | 특정 PGN을 모두에게 요청한다 |

## 30.5 큰 메시지: TP.CM과 TP.DT

클래식 CAN 프레임은 데이터가 8바이트뿐이다. J1939의 PGN 중에는 8바이트를 넘는 것이 많다. 예를 들어 DTC가 여러 개인 DM1, 소프트웨어 식별 정보, 구성 데이터는 수십~수백 바이트다. J1939-21의 **전송 프로토콜(TP)**이 이를 나눠 보낸다.

### 구조

- **TP.CM(PGN 60416)**: 연결 관리. BAM, RTS, CTS, EndOfMsgACK, Abort 같은 제어 메시지.
- **TP.DT(PGN 60160)**: 데이터. 첫 바이트가 시퀀스 번호(1~255), 나머지 7바이트가 payload다.
- TP 기준 최대 메시지 크기는 **1785바이트**다. `255패킷 × 7바이트`다. J1939-21에는 이보다 큰 ETP(Extended Transport Protocol)도 있지만, 이 책은 다루지 않는다.
- 마지막 패킷의 남는 바이트는 `0xFF`로 채운다.

### BAM과 RTS/CTS

| 방식 | 제어 | 목적지 | 흐름 제어 | 용도 |
|---|---|---|---|---|
| BAM(Broadcast Announce Message) | TP.CM 제어 바이트 `0x20` | global `0xFF` | 없음 | 한 번에 모두에게 |
| RTS/CTS | `0x10` RTS, `0x11` CTS, `0x13` EndOfMsgACK, `0xFF` Abort | 특정 DA | 수신자가 CTS로 허용 | 연결형 전송 |

BAM은 수신자가 없어도 보낼 수 있지만, 패킷 사이 간격을 **50~200ms**로 둔다. 흐름 제어가 없으므로 손실되면 그대로 잃는다. RTS/CTS는 수신자가 CTS로 "몇 번째 패킷부터 몇 개를 보내라"고 지시하고, 마지막에 EndOfMsgACK를 보낸다.

### BAM 프레임 예

10바이트 DM1 payload를 BAM으로 보내는 예를 보자.

```text
TP.CM: 20 0A 00 02 FF CA FE 00
       │  │     │  │  └─ PGN 0x00FECA (DM1), 리틀 엔디언
       │  │     │  └─ 예약(0xFF)
       │  │     └─ 총 패킷 수 2
       │  └─ 메시지 크기 0x000A = 10바이트
       └─ 제어 바이트 0x20 = BAM

TP.DT: 01 04 FF 64 00 01 01 6E
TP.DT: 02 00 00 01 FF FF FF FF
```

- 첫 TP.DT의 시퀀스는 1, 두 번째는 2다.
- 두 번째 패킷의 실제 데이터는 `00 00 01` 세 바이트이고, 나머지는 `FF` 패딩이다.
- 수신자는 TP.CM의 크기(10)만큼만 잘라 `04 FF 64 00 01 01 6E 00 00 01`을 복원한다.

### ISO-TP와 비교

| | ISO-TP(ISO 15765-2) | J1939 TP |
|---|---|---|
| 제어 | SF/FF/CF/FC | TP.CM/TP.DT |
| 큰 메시지 최대 | 표준 개정에 따라 다름(고전 형식 4095바이트) | 1785바이트 |
| 데이터 프레임당 | CF 7바이트(클래식) | TP.DT 7바이트 |
| 흐름 제어 | 수신자의 FC(BS/STmin) | RTS/CTS 또는 BAM |
| 주소 | CAN ID로 요청/응답 | PGN + SA/DA |
| 용도 | 진단(OBD/UDS) | J1939 응용 데이터 |

둘 다 "8바이트보다 큰 메시지를 나눈다"는 점은 같지만, 제어 프레임의 이름과 흐름 제어 방식이 다르다. OBD-II용 ISO-TP 코드를 J1939에 그대로 쓰면 안 된다.

## 30.6 진단: DM1, SPN, FMI

J1939의 진단 메시지는 **DM(Diagnostic Message)** 계열이다. 가장 중요한 것은 **DM1(PGN 65226)**이다.

- DM1은 **현재 활성화된 고장 코드**를 broadcast한다.
- 고장이 생기거나 사라질 때, 그리고 고장이 남아 있는 동안 약 1초마다 보낸다.
- 고장이 없으면 SPN 524287(0x7FFFF) 같은 "all clear" 값을 보낸다.
- DTC가 여러 개라 8바이트를 넘으면 TP로 나눠 보낸다.
- **DM2(PGN 65227)**는 과거 고장 코드다. 보통 Request로 읽는다.
- **DM3**는 과거 고장 코드를 지우는 메시지다. 실제 차량에서는 보내지 않는다.

### DM1 프레임 구조

```text
바이트 1: 램프 상태
  bit 7-6 MIL, bit 5-4 Red Stop, bit 3-2 Amber Warning, bit 1-0 Protect
  00 = off, 01 = on
바이트 2: 램프 점멸 상태
바이트 3-6: DTC 1 (4바이트)
바이트 7-8: DTC 2가 이어질 수 있는 자리(또는 FF)
```

DTC 하나는 4바이트다.

| DTC 바이트 | 내용 |
|---|---|
| 1 | SPN 하위 8비트 |
| 2 | SPN 중간 8비트 |
| 3 | bit 8-6: SPN 상위 3비트, bit 5-1: FMI 5비트 |
| 4 | bit 8: CM, bit 7-1: OC(발생 횟수) 7비트 |

- **SPN**: 19비트. 0~524287.
- **FMI(Failure Mode Identifier)**: 5비트. 고장의 종류.
- **OC(Occurrence Count)**: 7비트. 같은 고장이 몇 번 발생했는가. 127은 "사용할 수 없음"이다.
- **CM(SPN Conversion Method)**: 1비트. SPN 표기 방식.

### FMI 예

| FMI | 의미(대표) |
|---:|---|
| 0 | 데이터가 유효하지만 정상 범위 위 |
| 1 | 데이터가 유효하지만 정상 범위 아래 |
| 2 | 간헐적·불규칙 |
| 3 | 전압이 정상보다 높음 |
| 4 | 전압이 정상보다 낮음 |
| 5 | 회로가 열림 |
| 6 | 회로가 접지에 단락 |
| 7 | 기계적 고장 |
| 31 | 조건이 존재(원인 불명) |

FMI는 "센서가 고장 났다"는 뜻이 아니라 **어떤 방식으로 잘못됐는가**를 나타낸다. 같은 SPN 100(오일 압력)이라도 FMI 1(낮음)과 FMI 5(회로 열림)는 정비 절차가 다르다.

### 예제

```text
18FECA00  04 FF 64 00 01 01 FF FF
          │  │  └─────┬─────┘
          │  │        └─ DTC: 64 00 01 01
          │  └─ 램프 점멸 상태(FF = 사용할 수 없음)
          └─ 램프 상태: 0x04 = Amber Warning on

DTC 64 00 01 01
  SPN = 0x064 = 100 (Engine Oil Pressure)
  FMI = 0x01 & 0x1F = 1 (정상 범위 아래)
  OC  = 0x01 & 0x7F = 1
  CM  = 0
```

이 프레임은 "오일 압력이 정상 범위 아래"라는 활성 고장을 알린다. 실제 차량에서 이 프레임을 받았다면 **읽기만 하고**, DM3로 지우거나 액추에이터를 조작하지 않는다. 정비는 제조사 절차를 따른다.

### OBD-II DTC와 비교

| | OBD-II DTC | J1939 DM1 DTC |
|---|---|---|
| 크기 | 2바이트 | 4바이트(SPN 19 + FMI 5 + OC 7 + CM 1) |
| 표기 | P0301 같은 코드 | SPN 100/FMI 1처럼 번호 조합 |
| 전달 | Mode 03 요청/응답 | 주기 broadcast |
| 삭제 | Mode 04(하지 않음) | DM3(하지 않음) |
| 범위 | 배출가스 중심 | 차량 전체 ECU |

OBD-II의 P 코드는 "고장 코드 번호" 하나로 의미가 완결되지만, J1939는 **무엇이(SPN) 어떻게(FMI)** 고장 났는지를 조합한다. 그래서 진단 도구가 SPN과 FMI를 따로 보여 주는 경우가 많다.

## 30.7 python-can 가상 버스 실습

python-can 4.x에는 J1939 전용 인터페이스가 내장되어 있지 않다. J1939 지원은 별도 `python-can-j1939` 패키지로 분리되어 있다. 이 절에서는 원리를 보이기 위해 **29비트 ID를 직접 조립·해석**하고, 가상 버스에서 프레임을 주고받는다.

```python
import can


def j1939_id(priority: int, pgn: int, sa: int, da: int = 0xFF) -> int:
    """J1939 29비트 ID를 만든다. PDU1이면 PS에 목적지 주소를 넣는다."""
    pf = (pgn >> 8) & 0xFF
    cid = (priority << 26) | ((pgn & 0x3FFFF) << 8) | sa
    if pf < 240:                      # PDU1: PS는 목적지 주소
        cid = (cid & ~0xFF00) | (da << 8)
    return cid


def j1939_parse(cid: int):
    priority = (cid >> 26) & 0x07
    pgn = (cid >> 8) & 0x3FFFF
    pf = (pgn >> 8) & 0xFF
    if pf < 240:                      # PDU1: PGN에서 DA를 지운다
        da = pgn & 0xFF
        pgn &= 0x3FF00
    else:
        da = 0xFF
    return priority, pgn, cid & 0xFF, da


bus = can.Bus(interface="virtual", channel="j1939-demo",
              receive_own_messages=True)

# EEC1: 엔진 1200 rpm -> raw 9600 = 0x2580
eec1 = bytes([0x00, 0xFF, 0x00, 0x80, 0x25, 0x00, 0x00, 0x00])
msg = can.Message(arbitration_id=j1939_id(3, 0x00F004, 0x00),
                  data=eec1, is_extended_id=True)
bus.send(msg)

got = bus.recv(timeout=1.0)
prio, pgn, sa, da = j1939_parse(got.arbitration_id)
rpm = int.from_bytes(got.data[3:5], "little") * 0.125
print(f"prio={prio} pgn={pgn} sa=0x{sa:02X} da=0x{da:02X} rpm={rpm}")

# DM1: SPN 100, FMI 1, OC 1, Amber 경고등
spn, fmi, oc = 100, 1, 1
dtc = bytes([
    spn & 0xFF,
    (spn >> 8) & 0xFF,
    ((spn >> 16) & 0x07) << 5 | (fmi & 0x1F),
    oc & 0x7F,
])
dm1 = bytes([0x04, 0xFF]) + dtc + b"\xFF\xFF"
bus.send(can.Message(arbitration_id=j1939_id(6, 0x00FECA, 0x00),
                     data=dm1, is_extended_id=True))
got = bus.recv(timeout=1.0)
d = got.data[2:6]
print("SPN", d[0] | (d[1] << 8) | ((d[2] >> 5) << 16),
      "FMI", d[2] & 0x1F, "OC", d[3] & 0x7F)

bus.shutdown()
```

실행 결과는 다음과 같다.

```text
prio=3 pgn=61444 sa=0x00 da=0xFF rpm=1200.0
SPN 100 FMI 1 OC 1
```

- `is_extended_id=True`를 빠뜨리면 11비트 ID로 해석되어 PGN이 깨진다.
- `j1939_parse`에서 PDU1의 PS를 지우지 않으면 PGN에 목적지 주소가 섞인다.
- DM1의 세 번째 DTC 바이트는 **하위 5비트가 FMI, 상위 3비트가 SPN 상위 비트**다. 이 순서를 뒤집으면 SPN과 FMI가 모두 틀린다.
- 가상 버스는 전기·중재·오류 카운터를 재현하지 않는다. 물리 계층 시험은 23장의 벤치 절차를 따른다.

### TP.BAM까지 확인하기

10바이트 DM1을 BAM으로 나눠 보내고 다시 붙여 보자.

```python
payload = bytes([0x04, 0xFF, 0x64, 0x00, 0x01, 0x01,
                 0x6E, 0x00, 0x00, 0x01])
cm = bytes([0x20, len(payload) & 0xFF, len(payload) >> 8,
            (len(payload) + 6) // 7, 0xFF, 0xCA, 0xFE, 0x00])
frames = [bytes([i + 1]) + payload[i * 7:(i + 1) * 7].ljust(7, b"\xFF")
          for i in range(cm[3])]

print(cm.hex(" ").upper())
for f in frames:
    print(f.hex(" ").upper())

reassembled = b"".join(f[1:] for f in frames)[:cm[1] | (cm[2] << 8)]
print(reassembled.hex(" ").upper())
```

```text
20 0A 00 02 FF CA FE 00
01 04 FF 64 00 01 01 6E
02 00 00 01 FF FF FF FF
04 FF 64 00 01 01 6E 00 00 01
```

TP.CM의 패킷 수는 `ceil(길이 / 7)`이다. 코드에서는 `(길이 + 6) // 7`로 쓸 수 있다. 위 예는 10바이트라 `(10 + 6) // 7 = 2`이고, 20바이트라면 `(20 + 6) // 7 = 3`이다. 각 TP.DT가 7바이트를 나르므로 이 계산이 맞다.

## 30.8 흔한 실수

| 증상 | 원인 | 확인 |
|---|---|---|
| PGN이 목적지에 따라 달라진다 | PDU1의 PS를 PGN에 포함 | PF < 240이면 PS를 0으로 |
| 11비트 ID로 보낸다 | `is_extended_id=False` | 29비트 프레임은 반드시 확장 ID |
| 회전수가 8배 틀린다 | 해상도 0.125를 빠뜨림 | `raw * 0.125` |
| 온도가 40도 틀린다 | 오프셋 −40을 빠뜨림 | `raw - 40` |
| DM1의 SPN이 엉뚱하다 | DTC 바이트 오프셋·FMI 비트 순서 | 2바이트 램프 + 4바이트 DTC |
| TP가 1패킷 모자란다 | 패킷 수 계산 오류 | `ceil(길이/7)`, 0xFF 패딩 |
| 주소 충돌 | 클레임을 하지 않음 | NAME과 250ms 규칙 |
| 실제 차량이 응답하지 않는다 | OBD-II 도구/주소로 J1939를 조회 | PGN·SA·29비트 확인 |
| 차량에서 고장 코드가 지워졌다 | DM3를 보냄 | 실제 차량에서는 읽기만 |

특히 **실제 차량에서 DM3를 보내지 않는다.** DM3는 과거 고장 코드를 지우는 쓰기 동작이다. 배출가스 검사·보증·정비 이력에 영향을 줄 수 있고, 11장에서 설명한 읽기 전용 원칙을 어긴다.

- [ ] TP.CM/TP.DT와 BAM의 차이를 설명할 수 있다.

- [ ] 실제 차량에서는 읽기만 하고 DM3를 보내지 않는다.

## 장 요약

- J1939는 트럭·버스·건설기계·농기계의 CAN 응용 프로토콜이다. OBD-II와 같은 CAN 위에 있지만 목적·주소·메시지 정의가 다르다.
- 29비트 ID는 Priority(3) + EDP/DP + PF(8) + PS(8) + SA(8)로 구성된다. PGN은 PF/PS/DP로 계산하고, PDU1에서는 PS가 목적지 주소다.
- PGN은 메시지 묶음, SPN은 그 안의 신호다. SPN마다 해상도·오프셋이 다르고, J1939는 리틀 엔디언을 쓴다.
- 소스 주소는 Address Claimed(PGN 60928)로 얻는다. NAME이 작은 노드가 이기고, 초기 클레임에는 250ms 대기한다.
- 8바이트를 넘는 메시지는 TP.CM/TP.DT로 나른다. BAM은 broadcast, RTS/CTS는 연결형이며 최대 1785바이트다.
- DM1(PGN 65226)은 활성 고장을 주기적으로 알린다. DTC는 SPN 19비트 + FMI 5비트 + OC 7비트 + CM 1비트다.
- 실제 차량에서는 읽기만 한다. DM3·임의 송신은 가상 버스나 벤치에서만 한다.

## 연습 문제

### 1. (중급) 29비트 ID 해석

CAN ID `0x18FEF100`을 해석하라. 우선순위, PGN, PF, PS, PDU 형식, 소스 주소를 구하고, 이 PGN이 무엇인지 쓰라.

### 2. (중급) SPN 계산

EEC1 프레임의 데이터가 `00 FF FF 40 1F 00 00 00`이다. 엔진 회전수를 계산하라. 또 ET1의 첫 바이트가 `0x64`라면 냉각수 온도는 얼마인가?

### 3. (중급) 주소 클레임

두 노드의 NAME이 `0x8000000024612345`와 `0x8000000012345678`이다. 같은 주소를 클레임하면 어느 쪽이 이기는가? 그 이유와, 진 노드가 다음에 할 일을 쓰라.

### 4. (중급) DM1 해석

다음 DM1 프레임을 해석하라.

```text
18FECA00  04 FF 6E 00 00 01 FF FF
```

램프 상태, SPN, FMI, OC를 구하고, 이 고장이 무엇을 의미하는지 쓰라. 실제 차량이라면 이 프레임을 받은 뒤 무엇을 해야 하는가?

### 5. (심화) BAM 패킷 수

20바이트 payload를 BAM으로 보내려 한다. TP.CM의 메시지 크기·총 패킷 수를 쓰고, TP.DT의 시퀀스 번호와 마지막 패킷의 패딩을 설명하라.

## 정답과 해설

### 1.

`0x18FEF100`:

- Priority = `(0x18FEF100 >> 26) & 0x07` = 6
- PGN = `(0x18FEF100 >> 8) & 0x3FFFF` = 65265 (`0xFEF1`)
- PF = `0xFE`, PS = `0xF1`
- PF ≥ 240이므로 PDU2(그룹 확장). PS는 PGN의 일부다.
- SA = `0x00` (Engine #1)
- PGN 65265는 CCVS(차속·크루즈 상태)다.

### 2.

EEC1의 엔진 회전수는 바이트 4~5(0부터 세면 `data[3:5]`)이다. `40 1F`는 리틀 엔디언으로 `0x1F40 = 8000`이고, `8000 × 0.125 = 1000 rpm`이다.

ET1의 첫 바이트 `0x64 = 100`이고, 오프셋이 −40이므로 `100 − 40 = 60°C`다.

### 3.

`0x8000000012345678`이 이긴다. NAME을 64비트 unsigned로 비교했을 때 더 작기 때문이다. 진 노드는 자신의 주소를 포기하고 다음 후보 주소로 다시 Address Claimed를 보낸다. 빈 주소가 없으면 소스 주소 `0xFE`로 Cannot Claim Address를 보낸다. 주소는 정체성이 아니므로, 수신자는 NAME을 함께 기록해야 한다.

### 4.

- 램프 상태 `0x04` = Amber Warning on (bit 3-2 = 01)
- DTC `6E 00 00 01`:
  - SPN = `0x06E` = 110 (Engine Coolant Temperature)
  - FMI = `0x00` = 데이터가 유효하지만 정상 범위 위
  - OC = 1
- 해석: 냉각수 온도가 정상 범위보다 높다는 활성 고장이 1회 발생했다.

실제 차량이라면 **읽기만 한다.** 냉각수 온도 상승은 엔진 손상으로 이어질 수 있으므로, 주행을 멈추고 제조사 정비 절차에 따라 점검한다. DM3로 코드를 지우거나 임의로 냉각팬을 구동하지 않는다. 이 책의 실습은 가상 버스에서만 한다.

### 5.

- 메시지 크기 = 20 (`0x0014`), TP.CM 바이트 2~3에 `14 00`.
- 총 패킷 수 = `ceil(20 / 7) = 3`. TP.CM 바이트 4에 `03`.
- TP.DT 시퀀스는 1, 2, 3이다.
- 첫 패킷은 7바이트, 두 번째는 7바이트, 세 번째는 6바이트를 나르고 마지막 1바이트는 `0xFF`로 채운다.
- BAM이면 목적지 주소는 `0xFF`, 제어 바이트는 `0x20`, 패킷 간격은 50~200ms다.
