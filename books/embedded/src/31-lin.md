# 31장 LIN: 창문과 시트를 맡는 싼 버스

## 이 장에서

차 안의 모든 통신이 CAN은 아니다. 창문을 올리고, 사이드미러를 접고, 시트를 앞뒤로 움직이고, 공조 플랩을 여닫는 일은 **정해진 순서로 천천히** 일어나면 된다. 이런 액추에이터마다 CAN 트랜시버와 컨트롤러를 붙이면 배선과 부품 비용이 빠르게 늘어난다. LIN(Local Interconnect Network)은 이 틈을 노리는 **싼 보조 버스**다.

웹 개발자에게 LIN은 "cron으로 도는 작은 폴링 표"에 가깝다. 마스터가 정해진 시간표에 따라 슬레이브에게 "네 차례다"라고 헤더를 보내고, 지정된 슬레이브만 응답한다. 슬레이브는 먼저 말할 수 없고, 충돌 중재도 없다. CAN이 여러 노드가 자유롭게 말하는 pub/sub라면, LIN은 **마스터가 순서를 정하는 폴링 루프**다.

이 장은 LIN의 단일 선 물리 계층, 헤더(브레이크·싱크·PID)와 응답, 체크섬, 스케줄 테이블, CAN과의 역할 분담을 다룬다. PID 패리티와 체크섬은 PC에서 파이썬으로 계산해 확인한다. 차종별 LIN 프레임 ID는 쓰지 않는다.

이 장에서 다루는 것:

- LIN이 필요한 이유와 CAN과의 역할 분담
- 단일 선, 12V, UART 8N1, 1~20kbps, 1 master + 15 slave
- 브레이크·싱크·PID로 이루어진 헤더와 1~8바이트 응답
- 6비트 frame ID와 2비트 패리티(P0/P1)
- 클래식·확장 체크섬과 진단 프레임의 예외
- 스케줄 테이블, event-triggered·sporadic 프레임
- 진단 프레임(0x3C/0x3D)과 노드 관리
- CAN 게이트웨이를 통한 역할 분담
- 파이썬으로 PID·체크섬 계산하기
- 실차에서 하지 말아야 할 일

## 31.1 왜 LIN인가

CAN은 노드마다 컨트롤러와 차동 트랜시버가 필요하고, 배선도 두 선(CAN_H/CAN_L)에 종단 저항을 갖춘다. 창문 모터나 시트 모터처럼 **느리고 단순한 액추에이터**에는 과하다. LIN은 다음과 같이 비용을 줄인다.

- **단일 선**과 차체 접지로 통신한다. 차동 쌍이 필요 없다.
- 슬레이브는 정확한 크리스털 없이 RC 오실레이터로 동작할 수 있다. 마스터가 보내는 싱크 바이트로 보율을 보정한다.
- 최대 20kbps면 창문·미러·시트·공조 플랩·와이퍼·비·광센서에 충분하다.
- 마스터 하나가 최대 15개의 슬레이브를 관리한다. 노드를 추가해도 배선이 크게 늘지 않는다.
- 마스터가 스케줄을 정하므로, 슬레이브는 "언제 말할지"를 몰라도 된다. 충돌 중재가 없다.

LIN은 CAN의 하위 호환이나 CAN의 느린 버전이 아니다. **별도의 표준(ISO 17987)** 이고, 물리 계층·프레임·체크섬·진단이 모두 다르다. 차량에서는 보통 **바디 계열 ECU**가 LIN 마스터가 되어 로컬 액추에이터를 묶고, 그 ECU가 CAN 게이트웨이와 연결된다.

| 항목 | LIN | CAN |
|---|---|---|
| 물리 | 단일 선 + 접지, 12V | 차동 쌍 CAN_H/CAN_L |
| 속도 | 1~20kbps | 최대 1Mbps(클래식), FD는 데이터 구간 5~8Mbps |
| 토폴로지 | 1 master + 최대 15 slave | 다중 마스터 버스 |
| 중재 | 없음(마스터 스케줄) | ID 우선순위 중재 |
| 프레임 | 헤더 + 1~8바이트 응답 + 체크섬 | 0~8바이트(클래식), 0~64바이트(FD) |
| 오류 검출 | 패리티, 체크섬, 비트 오류 | CRC, ACK, 스터프, 오류 카운터 |
| 전형적인 용도 | 창문·시트·미러·공조 액추에이터 | 파워트레인·샤시·바디·진단 |

> 2019 쏘렌토 UM 2.2 디젤의 LIN 버스 구성과 프레임 ID는 이 책에서 확인하지 않았다. 차종별 LIN ID·스케줄은 제조사 문서 없이 쓰지 않는다. OBD-II 포트에서 보이는 것은 CAN 진단 트래픽이지 LIN이 아니다.

## 31.2 물리 계층

LIN 버스는 **한 개의 신호선**과 **공통 접지**로 이루어진다. 신호는 차체 접지에 대한 전압으로 판정한다.

- **recessive(1)**: 버스가 배터리 전압 근처로 올라간 상태. 마스터·슬레이브 쪽의 풀업이 유지한다.
- **dominant(0)**: 트랜시버가 선을 접지로 당긴 상태.
- LIN 트랜시버(예: TJA1021, MCP2003 계열)가 MCU의 UART 신호를 12V 버스 레벨로 바꾼다. MCU의 UART TX/RX를 트랜시버에 연결하고, 트랜시버의 LIN 핀을 버스에 붙인다.
- 공통 접지가 없으면 기준 전압이 떠서 통신이 깨진다. CAN보다 단일 종단이라 접지 의존도가 더 크다.
- 차동 신호가 아니므로 CAN처럼 120Ω 종단을 두지 않는다. LIN에 CAN 종단 저항을 붙이면 버스가 제대로 동작하지 않는다.
- 버스 길이는 19.2kbps에서 최대 40m 정도다. 속도를 낮추면 더 길게 갈 수 있지만, 차량 내부 로컬 버스 용도라 보통 짧다.

### UART 설정과 비트 시간

LIN은 UART 프레임을 쓴다. **8데이터 비트, 1스톱 비트, 패리티 없음(8N1)** 이다. 19.2kbps에서 한 비트는 약 **52µs**다.

- 브레이크 필드는 UART 프레임이 아니다. 최소 11비트 시간 동안 dominant를 유지한다. 보통 13비트로 구현한다.
- 싱크 필드는 `0x55`다. 이진수로 `01010101`이라 에지가 많아, RC 오실레이터를 쓰는 슬레이브가 보율을 맞추기 쉽다.
- PID는 6비트 frame ID와 2비트 패리티를 합친 8비트다.
- 응답은 1~8바이트 데이터와 1바이트 체크섬이다. 데이터 바이트도 8N1로 보낸다.

```text
마스터 헤더                          응답(슬레이브 또는 마스터)
┌──────────┬──────────┬──────────┐   ┌──────────────────────────────┐
│ break    │ sync     │ PID      │   │ data 1~8바이트 + checksum    │
│ ≥11비트  │ 0x55     │ 6bit+P0P1│   │ 8N1                          │
└──────────┴──────────┴──────────┘   └──────────────────────────────┘
```

## 31.3 프레임: 헤더와 응답

LIN의 통신은 항상 마스터가 시작한다.

1. 마스터가 **브레이크**를 보내 버스의 모든 슬레이브를 깨운다.
2. 마스터가 **싱크 `0x55`** 를 보내 슬레이브가 보율을 맞추게 한다.
3. 마스터가 **PID**를 보내 "이번 프레임은 ID 몇 번"이라고 알린다.
4. PID에 해당하는 슬레이브(또는 마스터 자신)가 **응답**을 보낸다. 데이터 1~8바이트와 체크섬이다.

```text
master ── break ── sync(55) ── PID(0x50) ──────────────┐
                                                       ↓
slave  ───────────────────────────────────── data ... + checksum
```

- 슬레이브는 헤더를 받기 전에는 말할 수 없다. 마스터가 헤더를 보내지 않으면 아무 일도 일어나지 않는다.
- 한 ID에 응답하는 노드는 하나다. 마스터가 자기 자신의 헤더에 응답할 수도 있다.
- 응답 데이터 길이는 프레임마다 정해져 있다. 보통 2·4·8바이트를 쓴다. 수신 측은 길이를 미리 알고 있어야 한다.
- 체크섬은 데이터 뒤에 붙는 1바이트다. 계산 방식은 31.5절에서 다룬다.

### frame ID의 종류

| ID | 용도 |
|---|---|
| 0x00~0x3B | 일반 신호 프레임(unconditional) |
| 0x3C | 마스터 진단 요청(master request) |
| 0x3D | 슬레이브 진단 응답(slave response) |
| 0x3E | 사용자 정의(user-defined) |
| 0x3F | 예약(reserved) |

- 일반 신호 프레임은 마스터가 헤더를 보낼 때마다 정해진 슬레이브가 응답한다.
- 진단 프레임 0x3C/0x3D는 항상 8바이트 데이터를 쓴다. 진단은 31.7절에서 더 다룬다.
- **frame ID는 차종마다 의미가 다르다.** "0x10은 운전석 창문" 같은 매핑은 제조사 문서 없이 단정하지 않는다. 이 책은 특정 차종의 LIN ID를 쓰지 않는다.

### event-triggered와 sporadic

LIN에는 주기 프레임 외에 두 가지 변형이 있다.

- **event-triggered frame**: 슬레이브가 데이터가 바뀌었을 때만 응답한다. 바뀐 것이 없으면 응답이 없어 버스가 조용하다. 여러 슬레이브가 동시에 응답하면 충돌이 나므로, 마스터는 충돌을 감지하면 해당 ID들을 **unconditional frame으로 하나씩 폴링**해 값을 확인한다.
- **sporadic frame**: 마스터가 보낼 데이터가 있을 때만 헤더를 보내는 프레임이다. 마스터 자신이 응답한다.

이 두 가지는 "이벤트가 있을 때만 말한다"는 점에서 웹의 웹훅·SSE와 비슷해 보이지만, **충돌을 허용하지 않는 마스터 주도 버스**라는 점이 다르다. 슬레이브가 자유롭게 push하는 구조가 아니다.

## 31.4 PID: 6비트 ID + 2비트 패리티

LIN의 frame ID는 6비트다. 그대로 보내지 않고, 2비트 패리티를 붙여 **PID(Protected Identifier)** 로 보낸다. 수신 측은 패리티를 검사해 헤더가 깨졌는지 판단한다.

frame ID의 비트를 `ID0`(LSB)부터 `ID5`(MSB)까지라 하면, 패리티는 다음과 같다.

```text
P0 = ID0 ⊕ ID1 ⊕ ID2 ⊕ ID4
P1 = ¬(ID1 ⊕ ID3 ⊕ ID4 ⊕ ID5)
PID = P1 P0 ID5 ID4 ID3 ID2 ID1 ID0   (P1이 비트7, P0이 비트6)
```

- P0는 ID0·ID1·ID2·ID4의 **짝수 패리티**다.
- P1은 ID1·ID3·ID4·ID5의 **홀수 패리티**다. 그래서 전체에 NOT을 쓴다.
- PID 바이트의 상위 2비트가 패리티, 하위 6비트가 frame ID다.

예를 들어 보자.

| frame ID | 이진수(ID5~ID0) | P0 | P1 | PID |
|---|---:|---:|---:|---:|
| 0x00 | 000000 | 0 | 1 | 0x80 |
| 0x01 | 000001 | 1 | 1 | 0xC1 |
| 0x10 | 010000 | 1 | 0 | 0x50 |
| 0x3C | 111100 | 0 | 0 | 0x3C |
| 0x3D | 111101 | 1 | 0 | 0x7D |

- 0x3C(Master Request)의 PID는 0x3C다.
- 0x3D(Slave Response)의 PID는 0x7D다. frame ID와 PID가 다르다는 점을 기억하자.
- 수신 측이 계산한 PID와 받은 PID가 다르면 **ID 패리티 오류**다. 헤더를 버리고 다음 헤더를 기다린다.
- 패리티는 1비트 오류 검출이지, 체크섬처럼 데이터 전체를 보호하지 않는다. 데이터는 응답의 체크섬으로 보호한다.

## 31.5 체크섬: 클래식과 확장

LIN의 체크섬은 **end-around carry 합을 반전**한 값이다. 바이트를 더하다가 0xFF를 넘으면 올림을 다시 LSB에 더한다. 그 합의 1의 보수를 체크섬으로 보낸다.

```text
sum = 0
for each byte:
    sum = sum + byte
    if sum > 0xFF:
        sum = (sum & 0xFF) + 1
checksum = ~sum & 0xFF
```

두 가지 방식이 있다.

| 방식 | 계산 범위 | 쓰는 곳 |
|---|---|---|
| 클래식(Classic) | 데이터 바이트만 | LIN 1.x, 진단 프레임 0x3C/0x3D |
| 확장(Enhanced) | PID + 데이터 바이트 | LIN 2.x의 일반 프레임 |

- **LIN 2.x에서도 진단 프레임 0x3C/0x3D는 항상 클래식 체크섬을 쓴다.** 이 예외를 놓치면 진단 응답이 체크섬 오류로 버려진다.
- 수신 측은 데이터(+PID)와 체크섬을 모두 더해 end-around sum이 `0xFF`인지 확인한다. `0xFF`가 아니면 체크섬 오류다.
- 체크섬 방식은 프레임마다 정해져 있다. 마스터와 슬레이브가 같은 방식을 써야 한다. 한쪽이 클래식, 다른 쪽이 확장을 쓰면 값이 맞지 않는다.
- event-triggered 프레임과 그에 대응하는 unconditional 프레임은 같은 체크섬 방식을 써야 한다.

### 계산 예

데이터 `4A 55 93 E5`를 보자.

```text
4A + 55 = 9F
9F + 93 = 132 → 32 + 1 = 33
33 + E5 = 118 → 18 + 1 = 19
~19 = E6
```

- 클래식 체크섬은 `0xE6`이다.
- 같은 데이터를 frame ID 0x10(PID 0x50)의 확장 체크섬으로 계산하면 `19 + 50 = 69`, `~69 = 96`이므로 `0x96`이다.
- 수신 측에서 `PID 0x50 + 데이터 4바이트 + 체크섬 0x96`을 더하면 `0xFF`가 된다.

## 31.6 스케줄 테이블과 노드 관리

LIN 마스터는 **스케줄 테이블**에 따라 프레임을 보낸다. 표에는 "어떤 ID를, 어떤 순서로, 얼마의 간격으로"가 들어 있다.

- 마스터는 표의 각 항목에 대해 헤더를 보내고, 해당 슬레이브의 응답을 기다린다.
- 프레임 슬롯은 그 프레임을 보내는 데 필요한 시간보다 길어야 한다. 슬롯이 짧으면 다음 프레임과 겹치거나 응답이 잘린다.
- 슬레이브는 스케줄 테이블을 모른다. 그저 헤더가 오면 자기 ID인지 보고 응답한다.
- 스케줄 테이블은 여러 개를 둘 수 있다. 정상 주행용, 진단용, 슬립 전환용처럼 상황에 따라 바꾼다.
- 마스터는 슬립/웨이크를 관리한다. 슬립 명령과 웨이크업 펄스의 정확한 바이트·타이밍은 ISO 17987-2를 따른다. 이 책에서는 개념만 다룬다.

```text
schedule table (예)
┌──────────┬─────────┬──────────────┐
│ slot     │ frame   │ response     │
├──────────┼─────────┼──────────────┤
│ 0ms      │ ID 0x10 │ slave A, 4B  │
│ 10ms     │ ID 0x11 │ slave B, 2B  │
│ 20ms     │ ID 0x10 │ slave A, 4B  │
│ 30ms     │ ID 0x20 │ slave C, 8B  │
└──────────┴─────────┴──────────────┘
```

스케줄은 **결정성**을 준다. CAN은 여러 노드가 동시에 말하려 할 때 중재로 순서를 정하므로, 최악 지연을 계산하려면 우선순위와 트래픽을 분석해야 한다. LIN은 마스터가 순서를 정하므로, 각 프레임이 언제쯤 나가는지가 표에 적혀 있다. 대신 슬레이브는 긴급한 데이터를 즉시 보낼 수 없다. 다음 슬롯을 기다려야 한다.

## 31.7 진단과 노드 관리

LIN에도 진단이 있다. 마스터는 ID 0x3C로 진단 요청을 보내고, 슬레이브는 ID 0x3D로 응답한다.

- 진단 프레임은 항상 **8바이트 데이터**와 **클래식 체크섬**을 쓴다.
- 슬레이브는 **NAD(Node Address for Diagnostics)** 로 구분한다. NAD는 7비트이고 1~127 범위다. 제조사·기능·버전에 따라 값이 정해진다.
- 진단 서비스로는 노드 식별자 읽기, 설정 읽기/쓰기, 오류 읽기 등이 있다. 정확한 서비스 번호와 프레임 형식은 ISO 17987-2/LIN 2.2A를 확인한다.
- 진단 프레임은 일반 신호 프레임과 같은 버스에서 시간을 나눠 쓴다. 마스터가 진단 스케줄로 전환해 진단 프레임을 보낸다.
- LIN 진단은 CAN의 UDS와 이름이 비슷한 부분이 있지만 **같은 프로토콜이 아니다.** UDS 서비스 번호를 LIN에 그대로 보내면 안 된다.

차량에서 LIN 진단을 사용하려면 제조사 문서와 진단 장비가 필요하다. 이 책의 범위는 PC에서 PID·체크섬을 계산하고, LIN이 CAN과 어떻게 역할을 나누는지 이해하는 데까지다. 실제 차량의 LIN 버스에 프레임을 보내는 실습은 하지 않는다.

## 31.8 CAN과의 역할 분담, 게이트웨이

LIN은 차량 전체를 잇는 버스가 아니다. **로컬 액추에이터 클러스터**를 묶고, 그 클러스터의 마스터가 CAN 게이트웨이와 연결된다.

```text
                 ┌────────────────────┐
                 │   바디/도어 ECU     │
                 │  LIN master + CAN   │
                 └───────┬─────┬──────┘
                         │     │
              LIN        │     │ CAN
        ┌────────────────┘     └──────────────┐
        │                                      │
┌───────▼───────┐  ┌──────────────┐   ┌────────▼────────┐
│ 창문 모터      │  │ 시트 모터     │   │ 파워트레인 CAN   │
│ (LIN slave)   │  │ (LIN slave)  │   │ 500kbps          │
└───────────────┘  └──────────────┘   └─────────────────┘
```

- 도어 ECU가 LIN 마스터가 되어 창문·미러·도어 램프를 묶고, 같은 ECU가 CAN으로 차량의 다른 도메인과 통신한다.
- 게이트웨이는 LIN 신호를 CAN 메시지로 변환하거나, 반대로 CAN 명령을 LIN 액추에이터에 전달한다.
- OBD-II 포트는 보통 CAN 진단 창구다. LIN은 OBD 포트에 직접 노출되지 않고, 게이트웨이를 거쳐 간접적으로만 접근된다. 차종에 따라 다르므로 문서로 확인한다.
- LIN 버스의 프레임 ID와 신호 매핑은 제조사 고유다. CAN DBC처럼 공개된 LIN 정의 파일(LDF)이 있지만, 배포·라이선스·버전을 확인해야 한다.
- LIN 노드는 저가이므로, 고장 진단도 CAN처럼 정교하지 않다. 체크섬 오류·무응답·패리티 오류를 세고, 마스터가 재시도·대체값을 결정한다.

### 안전: LIN은 액추에이터를 움직인다

LIN은 창문·시트·미러·테일게이트처럼 **사람의 손이나 몸이 닿는 액추에이터**를 제어한다. 실제 차량의 LIN 버스에 임의 프레임을 보내면 창문이 올라오거나 시트가 움직일 수 있다.

- 실제 차량에서는 LIN 프레임을 **보내지 않는다.** 읽기만 한다.
- LIN 실습은 격리된 벤치에서, 모터 부하를 분리한 상태로 한다.
- 창문·시트 기구에 손이 끼일 수 있는 위치에서 시험하지 않는다.
- 12V 전원은 퓨즈를 넣고, 차량 배선을 개조하지 않는다.
- 11장의 읽기 전용·정차·개인정보 원칙이 LIN에도 그대로 적용된다.

## 31.9 파이썬으로 PID와 체크섬 계산하기

다음 예제는 PC에서 LIN의 PID와 체크섬을 계산한다. 하드웨어 없이 돌릴 수 있고, 계산 결과를 표와 대조할 수 있다.

```python
def pid(frame_id: int) -> int:
    """6비트 frame ID -> 8비트 PID(ID0..ID5, P0, P1)."""
    if not 0 <= frame_id <= 0x3F:
        raise ValueError("LIN frame ID는 0x00~0x3F")
    b = [(frame_id >> i) & 1 for i in range(6)]   # b[0] = ID0
    p0 = b[0] ^ b[1] ^ b[2] ^ b[4]
    p1 = 1 ^ b[1] ^ b[3] ^ b[4] ^ b[5]            # NOT(...)
    return frame_id | (p1 << 7) | (p0 << 6)


def _sum_with_carry(values) -> int:
    total = 0
    for v in values:
        total += v
        if total > 0xFF:
            total = (total & 0xFF) + 1             # end-around carry
    return total


def checksum_classic(data: bytes) -> int:
    return (~_sum_with_carry(data)) & 0xFF


def checksum_enhanced(frame_id: int, data: bytes) -> int:
    return (~_sum_with_carry([pid(frame_id), *data])) & 0xFF


def checksum_for(frame_id: int, data: bytes) -> tuple[str, int]:
    # 진단 프레임 0x3C/0x3D는 LIN 2.x에서도 클래식 체크섬을 쓴다.
    if frame_id in (0x3C, 0x3D):
        return "classic(diagnostic)", checksum_classic(data)
    return "enhanced", checksum_enhanced(frame_id, data)


for fid in (0x00, 0x01, 0x10, 0x3C, 0x3D, 0x3F):
    print(f"ID 0x{fid:02X} -> PID 0x{pid(fid):02X}")

data = bytes.fromhex("4A 55 93 E5")
print("classic 4A 55 93 E5 ->", f"0x{checksum_classic(data):02X}")
print("enhanced ID 0x10     ->", f"0x{checksum_enhanced(0x10, data):02X}")
print("mode for 0x3D        ->", checksum_for(0x3D, data))
```

실행 결과는 다음과 같다.

```text
ID 0x00 -> PID 0x80
ID 0x01 -> PID 0xC1
ID 0x10 -> PID 0x50
ID 0x3C -> PID 0x3C
ID 0x3D -> PID 0x7D
ID 0x3F -> PID 0xBF
classic 4A 55 93 E5 -> 0xE6
enhanced ID 0x10     -> 0x96
mode for 0x3D        -> ('classic(diagnostic)', 230)
```

- `checksum_for(0x3D, ...)`가 `classic(diagnostic)`을 돌려주는 것에 주목하자. 진단 프레임은 LIN 2.x에서도 확장 체크섬을 쓰지 않는다.
- `pid(0x3D)`가 `0x7D`인 것은 frame ID와 PID가 다르기 때문이다. 버스에는 PID가 나간다.
- 이 계산은 PC에서만 했다. 실제 LIN 트랜시버·오실로스코프로 파형을 확인한 것은 아니다.

## 31.11 체크리스트

- [ ] LIN은 CAN과 다른 표준(ISO 17987)임을 알고 있는가
- [ ] 단일 선·공통 접지·12V·8N1을 확인했는가
- [ ] 마스터가 하나이고 슬레이브가 15개 이하인가
- [ ] 브레이크·싱크 `0x55`·PID 순서를 맞췄는가
- [ ] P0/P1 패리티를 계산해 PID를 만들었는가
- [ ] 프레임별 클래식/확장 체크섬을 구분했는가
- [ ] 진단 프레임 0x3C/0x3D에 클래식 체크섬을 썼는가
- [ ] 스케줄 슬롯이 프레임 길이보다 긴가
- [ ] CAN 종단 저항을 LIN에 붙이지 않았는가
- [ ] 실제 차량에서는 LIN 프레임을 보내지 않았는가
- [ ] 액추에이터 부하를 분리한 벤치에서만 시험했는가

## 장 요약

- LIN은 단일 선·12V·1~20kbps의 저가 보조 버스다. 1 master + 최대 15 slave다.
- 마스터가 브레이크·싱크(0x55)·PID로 헤더를 보내고, 지정된 슬레이브가 1~8바이트 응답과 체크섬을 보낸다.
- frame ID는 6비트이고, P0/P1 패리티를 붙여 PID로 보낸다. 0x3D의 PID는 0x7D다.
- 체크섬은 end-around carry 합의 반전이다. 클래식은 데이터만, 확장은 PID+데이터를 쓴다.
- 진단 프레임 0x3C/0x3D는 LIN 2.x에서도 클래식 체크섬을 쓴다.
- 마스터의 스케줄 테이블이 프레임 순서와 주기를 정한다. 슬레이브는 헤더에만 반응한다.
- event-triggered 프레임은 충돌 시 unconditional 프레임으로 폴링해 해결한다.
- LIN은 도어·시트·공조 같은 로컬 액추에이터를 묶고, 게이트웨이를 통해 CAN과 연결된다.
- OBD-II 포트는 보통 LIN을 직접 노출하지 않는다. LIN 진단은 게이트웨이 너머의 별도 세계다.
- 실제 차량의 LIN 버스에 프레임을 보내지 않는다. 액추에이터가 움직일 수 있다.
- 이 장의 PID·체크섬 계산은 PC에서 실행해 확인했다. 실제 LIN 하드웨어 시험은 하지 않았다.

다음 장에서는 차량 네트워크의 반대쪽 극단, 즉 카메라·레이다·중앙 컴퓨터를 잇는 **차량 이더넷**과 그 위의 DoIP·SOME/IP를 본다. CAN FD가 버스의 대역폭을 늘렸다면, 이더넷은 버스 자체를 스위치 기반 네트워크로 바꾼다.

## 정답과 해설

### 1.

`브레이크 → 싱크(0x55) → PID → 응답 데이터 → 체크섬`. 브레이크·싱크·PID는 마스터가 보내는 헤더이고, 응답은 지정된 슬레이브(또는 마스터)가 보낸다.

### 2.

1. 0x00: P0=0, P1=1 → PID 0x80.
2. 0x10: P0=1, P1=0 → PID 0x50.
3. 0x3D: P0=1, P1=0 → PID 0x7D.

### 3.

1. 클래식: `4A+55=9F`, `+93=132→33`, `+E5=118→19`, `~19=E6` → 0xE6.
2. 확장: PID 0x50을 더해 `19+50=69`, `~69=96` → 0x96.
3. 수신 측은 `PID 0x50 + 4A + 55 + 93 + E5 + 체크섬 0x96`을 end-around carry로 더해 `0xFF`인지 확인한다.

### 4.

한 비트는 `1/19200 = 52.08µs`, 한 바이트(10비트)는 520.8µs, 헤더 33비트는 1.719ms다.

| 프레임 | 데이터 | 프레임 시간 | 100ms당 횟수 | 합계 |
|---|---:|---:|---:|---:|
| A | 2B | 1.719 + 3×0.521 = 3.28ms | 10 | 32.8ms |
| B | 4B | 1.719 + 5×0.521 = 4.32ms | 5 | 21.6ms |
| C | 8B | 1.719 + 9×0.521 = 6.41ms | 1 | 6.4ms |
| D | 1B | 1.719 + 2×0.521 = 2.76ms | 2 | 5.5ms |

합계는 약 66.3ms다. 100ms 안에 들어가고, 약 33.7ms의 여유가 있다. 다만 실제로는 프레임 간 간격·클록 오차·재전송·진단 슬롯이 붙으므로, 20~30%의 여유를 더 두는 편이 좋다.

### 5.

1. 창문·시트는 LIN 슬레이브에 붙어 있고, OBD-II 포트는 CAN 진단 창구다. 게이트웨이가 LIN 신호를 CAN으로 변환하지 않으면 OBD 포트에서는 보이지 않는다.
2. 해당 LIN 클러스터의 마스터(도어 ECU 등)와 LIN 버스에 접근해야 한다. 제조사 문서, LIN 설명 파일(LDF), 진단 절차가 필요하다. OBD 포트만으로는 부족하다.
3. 창문·시트·미러가 움직여 손이 끼거나 차량이 손상될 수 있다. 실제 차량에서는 LIN 프레임을 보내지 않고, 격리된 벤치에서만 시험한다.
