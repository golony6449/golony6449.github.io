# 31장 이상값과 결측: 없는 값과 틀린 값을 구분하기

## 이 장에서

웹 API에서 `null`과 `0`을 구분하지 않으면 장애가 난다. 사용자가 없어서 `0`인지, 조회에 실패해서 `null`인지에 따라 화면과 알람이 달라져야 한다. 센서 데이터도 같다. 냉각수가 0°C인 것과 센서가 없어서 값을 못 읽은 것은 전혀 다르다. 그런데 많은 대시보드가 둘 다 `0`으로 표시한다.

이 장의 흐름은 다음과 같다.

```text
원본 값 → 범위 검사 → 변화율 검사 → 무효값 판정 → 결측 표시 → 보간 여부 결정 → 이상 탐지
             │             │              │             │              │
             └─ 거부/플래그  └─ 거부/플래그   └─ missing    └─ stale      └─ 검토 큐
```

웹과 대응시키면 다음과 같다.

| 웹 | 센서 데이터 |
|---|---|
| 스키마 검증(범위·형식) | 범위 검사·변화율 검사 |
| `null` vs `0` | 결측 vs 실제 0 |
| `NaN` | 계산 불가·무효값 |
| 4xx/5xx vs 빈 200 | 무효값 vs 결측 |
| 데이터 품질 모니터링 | 결측률·이상값률 |
| 알람 중복 제거 | 지속 시간·히스테리시스 |

이 장에서 다루는 것:

- 물리적으로 불가능한 값과 변화율 검사
- OBD에서 확인된 무효값·미지원 PID·포화값
- `null`과 `0`을 구분하는 저장·표시 방법
- 보간해도 되는 값과 안 되는 값
- z-점수와 MAD를 이용한 이상 탐지 기초
- 파이프라인 어느 단계에서 거를 것인가

## 31.1 물리적으로 불가능한 값: 범위 검사

가장 싸고 확실한 검사는 **범위**다. 신호마다 최소·최대가 정해져 있다. OBD Mode 01의 표준 PID는 공식이 공개되어 있으므로 범위를 계산할 수 있다.

| PID | 신호 | 공식 | 표현 범위 | 비고 |
|---|---|---|---|---|
| `01 0C` | 엔진 rpm | `(256A+B)/4` | 0~16,383.75 rpm | 음수 없음 |
| `01 0D` | 차속 | `A` | 0~255 km/h | 음수 없음 |
| `01 05` | 냉각수 온도 | `A-40` | -40~215°C | -40은 무효값일 수 있음 |
| `01 11` | 스로틀 | `A×100/255` | 0~100% | |
| `01 42` | 제어 모듈 전압 | `(256A+B)/1000` | 0~65.535V | 12V 차량에서 0은 비정상 |
| `01 0B` | 흡기 절대압 | `A` | 0~255 kPa | 255는 범위 끝 |
| `01 2F` | 연료 탱크 | `A×100/255` | 0~100% | |
| `01 1F` | 시동 후 경과 | `256A+B` | 0~65,535초 | 1초 해상도 |

- 공식과 범위는 SAE J1979 계열 표준과 공개 PID 표를 따른 것이다(9장, 부록 C.1). 실제 구현에서는 차량·연식·PID 정의를 확인한다.
- 범위를 벗어나면 **디코딩 오류·바이트 순서 오류·센서 고장·무효값** 중 하나다. 값을 그대로 표시하지 않고 `invalid`로 표시한다.
- 범위 안이라고 해서 유효한 것은 아니다. 시동 OFF에서 rpm 0은 정상이고, 주행 중 rpm 0은 이상하다. **상태 문맥**이 필요하다.
- 단위를 함께 검사한다. `0.25` 배율을 빼먹으면 rpm 1,200이 4,800으로 보인다. 범위 검사는 이런 배율 오류도 잡는다.

## 31.2 변화율 검사

범위 안의 값이라도 갑자기 뛰면 이상하다. 변화율 검사는 시간당 변화량을 본다.

```text
rate = (x[n] - x[n-1]) / (t[n] - t[n-1])
```

- `dt`가 0이거나 음수면 계산하지 않는다. 같은 타임스탬프·역순 표본은 별도 품질 문제다.
- 신호마다 한계가 다르다. 냉각수는 1초에 수십 도씩 변하지 않지만, rpm은 0에서 6,000까지 1초 안에 갈 수 있다.
- 변화율 한계는 **물리 법칙이 아니라 공학적 임계값**이다. 차량·센서·샘플링 주기에 따라 달라지므로 `확인 필요`로 두고, 데이터를 보고 조정한다.
- 상태 전환(시동, 기어 변속, 주유, 센서 교체)에서는 큰 변화가 정상이다. 상태를 구간으로 나눈 뒤 구간 안에서만 검사한다.

예시:

| 신호 | 예시 임계값 | 근거 |
|---|---|---|
| 냉각수 | 5°C/s | 열용량이 큰 액체, 실제로는 더 느림. 예시 |
| 흡기 온도 | 10°C/s | 센서 응답과 위치에 따라 다름. 예시 |
| rpm | 12,000 rpm/s | 0→6,000을 0.5초에 도달하는 경우. 예시 |
| 차속 | 10 km/h/s | 급가속·급제동 범위. 예시 |
| 연료량 | 5%/s | 주유 중에는 예외. 예시 |

- 위 값은 **예시**다. 실제 차량에서 정상 주행 로그를 모아 분포를 보고 정한다.
- 변화율 검사는 스파이크와 바이트 오류를 잘 잡는다. 하지만 급가속·급제동 같은 정상 이벤트도 잡을 수 있으므로, 알람이 아니라 **품질 플래그**로 먼저 쓴다.
- 변화율을 계산하려면 이전 표본과 `dt`가 필요하다. 결측 뒤 첫 표본은 이전 값과의 간격이 크므로, `dt`가 허용 범위를 넘으면 변화율 검사를 건너뛴다.

## 31.3 센서 고유의 무효값

프로토콜과 센서에는 "값이 없음"을 나타내는 고유한 표현이 있다. 이것을 실제 값과 구분하지 않으면 대시보드에 엉뚱한 숫자가 뜬다.

### 미지원 PID

- 지원하지 않는 PID를 요청하면 ELM327은 `NO DATA`를 돌려주거나, ECU가 부정 응답 `7F 01 xx`를 보낼 수 있다. `NO DATA`는 "응답이 없다"는 뜻이지 "값이 0"이 아니다(9장, 10장).
- UDS `0x22`에서 없는 DID는 `7F 22 31`(requestOutOfRange)이다(10장). `0x31`은 "그 DID가 없다"는 뜻이므로 재시도해도 결과가 같다.
- PID 지원 비트마스크는 **능력**을 나타낸다. `0100`이 "지원한다"고 답한 PID도 실제 값이 없거나 고정값일 수 있다.
- 9.4절의 실차 사례: 약 29개 PID가 지원된다고 답했지만 항상 0이었다. 대시보드에서 걸러야 한다.

### 포화값과 고정값

- **PID 0B 흡기 절대압**: 쏘렌토에서 255 kPa에서 더 올라가지 않았다(실차 확인). 1바이트 PID의 표현 범위 끝(`0xFF`)에 닿은 사례다. 과급 디젤의 실제 부스트를 표준 PID로 다 읽지 못한다.
- **PID 5C 오일 온도**: 항상 `00`, 즉 -40°C였다(실차 확인). 센서가 없거나 PID가 구현되지 않은 것으로 추정한다.
- **PID 46 외기 온도**: 51°C에 고정되어 있었다(실차 확인). 무효값으로 추정한다.
- **PID 78·7A·7C**: 규격보다 짧은 응답(5/3/3바이트)이 왔다(실차 확인). 길이를 고정해 파싱하면 다음 바이트를 잘못 읽는다.
- 이런 값은 범위 안에 있을 수 있다. -40°C는 냉각수 공식의 정상 범위 끝이고, 51°C는 외기 온도로 가능한 값이다. **범위 검사만으로는 잡히지 않는다.** 같은 값이 반복되는지, 다른 신호와 모순되는지, 시동 상태와 맞는지를 함께 본다.

### `0xFF`를 무조건 무효로 보면 안 된다

`0xFF`는 프로토콜에 따라 패딩·최대값·미정의값 등 의미가 다르다. J1939 TP의 마지막 패킷은 남는 바이트를 `0xFF`로 채우고(33장), 어떤 신호는 `0xFF`가 실제 최대값일 수 있다. **신호 정의를 확인하기 전에는 특정 바이트 값을 무효값으로 단정하지 않는다.** OBD에서는 PID별 공식과 실차 관찰을 근거로 판단한다.

### 전기차·하이브리드의 추가 함정

9.4절에서 본 것처럼 `0x5B`, `0x9A`, `0xB2`, `0xB7` 같은 배터리 관련 PID는 선택 지원이다. 지원 비트마스크에 있어도 `NO DATA`가 오거나, 0~100% 범위를 벗어나거나, 실제 SoC와 다른 값일 수 있다. 표준 PID 이름과 실제 의미가 다를 수 있으므로 `확인 필요`로 둔다.

## 31.4 결측의 표시: `null`과 `0`을 구분한다

값이 없는 것을 `0`으로 저장하면 나중에 구분할 수 없다. 저장·전송·표시 단계마다 "없음"을 표현하는 방법이 다르므로, 하나의 규칙을 정하고 지킨다.

| 계층 | 없음의 표현 | 주의 |
|---|---|---|
| JSON | `null` | `0`과 구분된다. 필드 자체를 빼면 "없음"과 "모름"이 섞인다 |
| JavaScript/TypeScript | `null`, `undefined` | `number \| null` 타입, `0`과 비교하지 않기 |
| Python | `None` | `float('nan')`은 전파·비교 함정 |
| SQLite/SQL | `NULL` | `NULL = NULL`은 참이 아님, `IS NULL` 사용 |
| InfluxDB | 필드 없음 | 결측과 0 구분, 태그로 품질 표시 가능 |
| 대시보드 | `--`, 회색, 공백 | `0`으로 표시하지 않음 |

### 품질 플래그를 함께 저장한다

값 하나만 저장하지 말고 **품질**을 함께 저장한다.

```text
quality: ok | stale | invalid | missing | estimated
```

- `ok`: 검사를 통과한 실제 값.
- `stale`: 마지막 값이 너무 오래되어 현재값으로 볼 수 없음. 값은 참고용으로 남긴다.
- `invalid`: 범위·변화율·무효값 검사에서 거부됨.
- `missing`: 표본 자체가 없음.
- `estimated`: 보간·모델로 채운 값.

JSON 예:

```json
{
  "ts": 1793197633.123,
  "signal": "coolant",
  "value": null,
  "quality": "missing",
  "source": "obd",
  "age_s": 3.2
}
```

TypeScript 타입 예:

```typescript
type Quality = "ok" | "stale" | "invalid" | "missing" | "estimated";

interface Sample {
  ts: number;
  value: number | null;
  quality: Quality;
  ageS?: number;
}
```

- `value: number | null`로 두면 `0`과 `null`을 타입으로 구분할 수 있다. `strictNullChecks`가 켜져 있어야 한다.
- `NaN`은 JSON으로 직렬화하면 `null`이 된다. 의도한 `null`인지 계산 실패인지 구분하려면 `quality`를 함께 본다.
- SQL에서는 `WHERE value IS NOT NULL AND quality = 'ok'`처럼 값과 품질을 함께 필터링한다. `value != 0`은 실제 0을 결측으로 오해한다.
- 대시보드는 `null`이면 `--`를, `stale`이면 마지막 값과 나이를, `invalid`면 오류 아이콘을 보여 준다. **0을 보여 주는 것이 가장 나쁘다.**

## 31.5 보간해도 되는 값과 안 되는 값

보간은 결측을 메우는 것이 아니라 **가정을 추가하는 것**이다. 29.5절의 정렬 방법을 값의 성질에 맞춰 고른다.

| 값 | 보간 | 최대 구멍(예) | 이유 |
|---|---|---|---|
| 냉각수·외기 온도 | 선형 보간 가능 | 2~5초 | 열용량이 커서 급변하지 않음 |
| rpm·차속 | 짧은 구간만 | 0.5~1초 | 운전 상태가 급변, 이벤트를 만들 수 있음 |
| 기어·시동 상태 | 안 함 | - | 이산 상태, 중간값이 없음 |
| DTC·이벤트 | 안 함 | - | 발생 시각이 핵심 |
| 주행거리·경과 시간 | 안 함 | - | 카운터, 차분으로 계산 |
| 연료량 | 짧은 구간만 | 5~10초 | 주유·경사에서 계단 변화 |
| 배터리 전압 | 짧은 구간만 | 1~2초 | 부하 변화가 빠름 |

- **상태 전환을 가로질러 보간하지 않는다.** 키 ON/OFF, 시동, 기어 변속, 주유, 센서 교체 사이에는 값의 생성 과정이 다르다.
- **긴 구멍은 보간하지 않는다.** 구멍의 시작·끝·길이를 기록하고 `missing`으로 남긴다. 구멍 자체가 USB 끊김·Bus-Off·전원 문제의 단서다.
- **보간한 값에는 `estimated`를 붙인다.** 원본과 섞어 저장하면 나중에 구분할 수 없다.
- **보간값으로 알람을 만들지 않는다.** 알람은 실제 표본과 지속 시간으로 판단한다. 보간은 표시·추세용이다.
- **역방향 보간(backfill)은 특히 조심한다.** 미래 값을 과거에 채우면 "그때 알았어야 하는데"를 만들 수 있다.

## 31.6 이상 탐지 기초: z-점수와 MAD

이상값을 자동으로 찾으려면 "얼마나 떨어져 있으면 이상한가"를 정해야 한다. 가장 흔한 두 방법이 z-점수와 MAD다.

### z-점수

```text
z = (x - mean) / std
```

- 평균에서 표준편차 몇 배 떨어졌는지를 나타낸다.
- 보통 `|z| > 3`을 이상 후보로 본다. 이는 경험칙이며, 정규분포에서 약 0.3%가 해당한다.
- **평균과 표준편차가 이상값에 끌려간다.** 이상값이 많으면 std가 커져서 이상값의 z가 작아진다. 이것을 masking이라고 한다.

### 수정 z-점수와 MAD

중앙값과 중앙절대편차(MAD)를 쓰면 이상값에 덜 끌린다.

```text
median = 중앙값(x)
MAD = median(|x - median|)
modified_z = 0.6745 × (x - median) / MAD
```

- `0.6745`는 정규분포에서 `MAD ≈ 0.6745σ`가 되도록 하는 상수다.
- Iglewicz와 Hoaglin은 `|modified_z| > 3.5`를 이상 후보로 권한다. NIST/SEMATECH 핸드북도 이 기준을 소개한다.
- MAD가 0이면 나눗셈이 불가능하다. 값이 모두 같거나 분해능 이하로 뭉친 경우이므로 별도 처리한다.
- 수정 z-점수도 정규분포를 가정한다. 추세·계절성·비정규 분포에서는 정상 값이 이상으로 잡힐 수 있다. **임계값은 삭제 명령이 아니라 검토 신호다.**

### 비교 예

400개 표본에 표준편차 0.5의 잡음을 넣고, 40개(10%)에 ±15 스파이크를 섞었다.

```python
import numpy as np

rng = np.random.default_rng(1)
n = 400
base = 80 + rng.normal(0, 0.5, n)
idx = rng.choice(n, 40, replace=False)
x = base.copy()
x[idx] += rng.choice([-15, 15], 40)

med = np.median(x)
mad = np.median(np.abs(x - med))
z = (x - x.mean()) / x.std()
mz = 0.6745 * (x - med) / mad

print("std", round(float(x.std()), 2), "MAD", round(float(mad), 2))
print("z>3", int((np.abs(z) > 3).sum()), "mz>3.5", int((np.abs(mz) > 3.5).sum()))
print("spikes caught by z", int((np.abs(z[idx]) > 3).sum()))
print("spikes caught by mz", int((np.abs(mz[idx]) > 3.5).sum()))
print("normal flagged by z", int((np.abs(np.delete(z, idx)) > 3).sum()))
print("normal flagged by mz", int((np.abs(np.delete(mz, idx)) > 3.5).sum()))
```

실행 결과(2026-10-30, numpy 2.5.4):

```text
std 4.76 MAD 0.34
z>3 38 mz>3.5 40
spikes caught by z 38
spikes caught by mz 40
normal flagged by z 0
normal flagged by mz 0
```

- 원래 잡음의 표준편차는 0.5였는데, 스파이크 때문에 전체 std가 4.76으로 부풀었다. 그 결과 z-점수는 40개 중 38개만 잡았다.
- MAD는 0.34로 스파이크에 거의 영향받지 않았다. 수정 z-점수는 40개를 모두 잡았고, 정상 값은 하나도 잡지 않았다.
- 스파이크가 10%나 되는 극단적인 예이지만, masking의 원리를 잘 보여 준다. 실제로는 1% 미만이 흔하다.

### 스트리밍에서 쓰기

- **창을 정한다.** 최근 N개(예: 31·61)의 중앙값·MAD로 판정한다. 창이 길면 느린 변화에 강하고, 짧으면 급변에 민감하다.
- **워밍업을 둔다.** 창이 차기 전에는 판정하지 않는다. 초기 몇 개의 작은 표본에서 MAD가 작아져 오탐이 나기 쉽다.
- **추세를 제거한다.** 온도가 천천히 오르는 중이면 중앙값도 따라가야 한다. 창 기반 방법은 어느 정도 따라가지만, 긴 추세에는 차분(difference)을 먼저 적용한다.
- **이상값을 바로 삭제하지 않는다.** `invalid`로 표시하고, 원본은 보존한다. 알람·집계에서 제외할지는 목적별로 정한다.
- **안전 판단에 쓰지 않는다.** 이상 탐지는 데이터 품질 도구다. 과열·충돌 같은 안전 판단은 차량 ECU의 경고와 별도 로직으로 한다.

## 31.7 어느 단계에서 거르는가

26장의 파이프라인과 28장의 캡스톤 대시보드에 이 장의 검사를 연결한다.

- **보간·대체는 가능한 한 늦게** 한다. 대시보드별로 다른 보간을 쓰려면 원본이 있어야 한다.

28장의 수집기는 `ok: false`와 `values: {}`로 실패를 표시하고, `NO DATA`를 통신 오류와 구분한다. 여기에 `quality`를 붙이면 대시보드가 `--`를 표시하고, 26장의 `signals` 테이블에는 `quality` 컬럼을 추가한다.

## 장 요약

- 범위 검사는 가장 싼 검사다. OBD PID의 공식과 표현 범위로 불가능한 값을 거른다.
- 변화율 검사는 범위 안의 스파이크·바이트 오류를 잡지만, 정상 이벤트와 구분하려면 상태 문맥이 필요하다.
- OBD에는 `NO DATA`, 부정 응답, -40°C 고정값, 255 kPa 포화, 항상 0인 PID처럼 "지원하지만 의미 없는" 값이 있다. 지원 비트마스크는 유효 보장이 아니다.
- 결측은 `null`과 `quality`로 표시한다. `0`으로 저장하면 실제 0과 구분할 수 없다.
- 보간은 가정을 추가하는 일이다. 느린 연속값은 짧은 구간만, 상태·이벤트·카운터는 보간하지 않는다.
- z-점수는 이상값이 많으면 masking된다. MAD 기반 수정 z-점수(`0.6745`, 임계값 3.5)가 더 강하다. 임계값은 삭제가 아니라 검토 신호다.
- 검사는 장치·수집기·저장소·대시보드·알람 단계에 나눠 배치하고, 원본과 품질 플래그를 항상 남긴다.

## 정답과 해설

### 1.

1. `A=0xFF`, `B=0xFF`이므로 `(255×256 + 255)/4 = 65,535/4 = 16,383.75 rpm`이다.
2. 공식의 표현 범위 끝이라 형식상 가능하지만, 실제 엔진이 그 rpm까지 도는 경우는 드물다. 값 자체보다 **응답이 0xFF로 채워졌는지**를 의심한다.
3. 미지원 PID의 더미 응답, 통신 오류, 패딩, 디코딩 오류를 의심한다. 같은 요청을 반복해 같은 값이 오는지, 다른 PID는 정상인지, 시동 상태가 맞는지 확인한다.

### 2.

1. 0°C는 실제 냉각수 온도로 가능한 값이다. 결측과 구분할 수 없어 추세·평균·알람이 모두 왜곡된다. 사용자는 센서가 고장 난 것을 눈치채지 못한다.
2. `value: null`, `quality: "missing"`, `age_s`를 저장하고, 대시보드에는 `--`를 표시한다. 마지막 값이 있으면 `stale`로 나이와 함께 보여 준다. 0으로 대체하지 않는다.
3. 냉각수는 열용량이 커서 3초 구멍은 짧은 편이다. 보간할 수는 있지만 `estimated`를 붙이고, 구멍의 시작·끝을 기록한다. 알람에는 사용하지 않는다. 구멍이 반복되면 배선·USB·전원 문제를 조사한다.

### 3.

1. `30°C / 0.1s = 300°C/s`다.
2. 액체 냉각수에서는 물리적으로 불가능하다. 센서 자체의 열시상수도 이보다 훨씬 길다.
3. 바이트 오류, 배율·오프셋 오류, 순간 접촉 불량, 다른 PID와의 혼동, 통신 프레임 섞임을 의심한다. 값은 `invalid`로 표시하고 원본을 남긴다.

### 4.

1. 수정 z-점수다. z-점수는 평균과 표준편차를 쓰므로 스파이크가 많으면 둘 다 부풀어 스파이크의 z가 작아진다(masking). MAD는 중앙값 기준이라 스파이크 5% 정도에는 거의 영향받지 않는다.
2. MAD가 0이면 모든 값이 같거나 분해능 이하로 뭉친 것이다. 이상 탐지를 건너뛰고 `MAD=0` 상태를 품질 플래그로 남긴다. 작은 상수를 더하는 방법은 임계값을 왜곡할 수 있어 신중히 쓴다.
3. 안 된다. 임계값은 검토 신호다. 원본을 보존하고 `invalid`로 표시한 뒤, 원인(센서·배선·통신·디코딩)을 확인한다. 알람·집계에서 제외할지는 목적별로 정한다.

### 5.

1. 장치: 범위·변화율·센서 상태, 즉시 거부. 수집기: 타임스탬프·중복·결측 구간·`NO DATA` 분류. 저장소: 원본 프레임과 품질 플래그, 디코딩 버전. 대시보드: `null` 표시, `stale` 나이, `invalid` 경고. 알람: 지속 시간·히스테리시스·결측 정책.
2. 원본 값(또는 원시 프레임)과 `quality`, `age_s`, `filter`, `estimated` 플래그를 함께 저장한다. 파생 테이블은 원본에서 다시 만들 수 있어야 한다.
3. 결측률의 시작 시각과 함께 USB·시리얼 연결, 전원, Bus-Off, 어댑터 상태, 로그 드롭 카운터를 본다. 26.6절의 드롭 메트릭과 28.8절의 재연결 상태를 함께 확인한다. 센서 값 문제인지 통신 문제인지 먼저 분리한다.
