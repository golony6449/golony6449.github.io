# 32장 CAN 보안: 인증 없는 버스를 지키는 법

## 이 장에서

웹 개발자에게 "인증 없는 API"는 상상하기 어렵다. 요청마다 토큰을 확인하고, 세션을 검증하고, TLS로 감싸고, 권한을 최소화한다. 그런데 차량의 CAN 버스에는 그런 것이 거의 없다. 프레임에는 송신자를 증명하는 필드가 없고, 수신자는 보낸 사람이 누구인지 확인하지 않는다. CAN ID는 "누가 보냈나"가 아니라 "무슨 메시지인가"를 나타낸다.

이것은 구현 실수가 아니라 **설계상의 선택**이다. 1980년대에 만들어진 CAN은 폐쇄된 차량 내부 네트워크, 짧은 프레임, 결정적인 실시간성, 낮은 비용을 전제로 했다. 그 전제가 깨진 지금, 자동차 업계는 게이트웨이·메시지 인증·침입 탐지·진단 접근 통제·규제로 그 빈틈을 메우고 있다.

이 장은 **공격 방법을 가르치는 장이 아니다.** 방어를 이해하기 위해 위협 모델과 구조적 한계를 설명하지만, 공격 절차·익스플로잇 코드·보안 접근 우회·특정 차량의 메시지 ID는 쓰지 않는다. 실차에서는 읽기만 한다. 송신과 검증 실습은 23장의 가상 버스에서만 한다.

이 장에서 다루는 것:

- CAN 프레임에 송신자 인증과 암호화가 없는 구조적 이유
- 위협 모델: OBD 포트, 텔레매틱스, 인포테인먼트, 공급망
- 방어 계층: 게이트웨이와 도메인 분리, AUTOSAR SecOC, CAN IDS, UDS 0x27/0x29
- 2015년 Jeep Cherokee 사례에서 무엇이 문제였고 무엇이 바뀌었나
- UN R155·R156, ISO/SAE 21434의 개요
- 가상 CAN 버스에서 HMAC과 카운터로 SecOC를 흉내 내는 실습

## 32.1 웹 개발자의 눈으로 본 CAN: 인증이 없는 버스

### 프레임에 없는 것

클래식 CAN 프레임을 웹 요청에 견주면 이상할 정도로 비어 있다.

| CAN 프레임 필드 | 하는 일 | 웹 요청의 대응 |
|---|---|---|
| SOF | 프레임 시작 | TCP 연결/HTTP 요청 시작 |
| Arbitration ID | 메시지 종류와 우선순위 | URL 경로 + 우선순위 |
| RTR / IDE | 원격 요청, 확장 ID 여부 | 메서드/버전 협상 |
| DLC | 데이터 길이(0~8) | `Content-Length` |
| Data | 0~8바이트 페이로드 | 본문 |
| CRC | 비트 오류 검출 | TCP 체크섬 |
| ACK | 수신 확인 | TCP ACK |
| EOF | 프레임 끝 | 메시지 경계 |

여기에 **송신자 필드가 없다.** 수신자 필드도 없다. 서명도, 토큰도, 세션 ID도, 암호화 필드도 없다. CAN 데이터링크 계층은 "이 프레임이 버스 위에 올라왔다"는 사실만 보장한다. 누가 올렸는지는 보장하지 않는다.

### CAN ID는 송신자 ID가 아니다

CAN ID는 중재(arbitration)에 쓰이는 우선순위이자 메시지 식별자다. 관례적으로 `0x7E0`은 엔진 ECU 요청, `0x7E8`은 그 응답처럼 주소처럼 쓰이지만, 표준이 "이 ID는 이 ECU만 보낼 수 있다"고 강제하지 않는다. 버스에 연결된 노드는 같은 ID의 프레임을 보낼 수 있다.

이 책에서 `7DF`로 기능 요청(functional request)을 보내면 여러 ECU가 응답한다. `7E0`으로 물리 요청(physical request)을 보내면 특정 ECU가 응답한다. 이 주소 규약은 **편의와 관례**이지 인증이 아니다. 악의적인 노드가 같은 ID로 프레임을 보내도 CAN 컨트롤러는 그것을 구분하지 않는다.

### CRC는 인증이 아니다

CAN의 CRC는 전기적 잡음·비트 오류를 검출한다. 공격자가 프레임을 의도적으로 변조하는 것은 막지 못한다. CRC를 다시 계산해 보내면 수신자는 정상 프레임으로 받아들인다. 3장에서 다룬 UART CRC, 7장의 CAN CRC 모두 마찬가지다.

| | CRC | MAC(메시지 인증 코드) |
|---|---|---|
| 목적 | 우발적 오류 검출 | 의도적 변조·위조 검출 |
| 키 | 없음 | 송신자·수신자가 공유하는 비밀 키 |
| 공격자가 재계산 | 가능 | 키 없이는 불가능 |
| 재전송 공격 | 막지 못함 | 신선도 값과 함께 막음 |
| 비용 | 매우 낮음 | 연산·키 관리·프레임 공간 필요 |

**"CRC가 있으니 무결성은 보장된다"는 말은 보안 문맥에서 틀렸다.** CRC는 데이터가 깨지지 않았다는 뜻이지, 데이터가 신뢰할 수 있는 주체에서 왔다는 뜻이 아니다.

### 왜 이렇게 설계했나

CAN이 만들어진 시대의 전제는 다음과 같았다.

- 차량 내부는 **물리적으로 폐쇄**되어 있다. 버스에 접근하려면 차를 분해해야 한다.
- 노드는 **신뢰할 수 있는 부품**이다. 제조사가 승인한 ECU만 연결한다.
- 프레임은 **짧고 빨라야** 한다. 8바이트 payload에 서명을 넣을 공간이 없다.
- ECU는 **저렴하고 작아야** 한다. 암호 연산과 키 저장은 비용이다.
- **결정적 실시간성**이 중요하다. 인증 핸드셰이크와 재전송은 지연을 만든다.

이 전제는 1980년대에는 합리적이었다. 문제는 차량이 외부와 연결되면서 전제가 깨졌다는 것이다. 텔레매틱스, 인포테인먼트, OTA, 스마트폰 연동, 진단 포트가 생기면서 **폐쇄망이 열린 네트워크의 일부**가 되었다. CAN의 설계는 그대로인데 경계는 사라졌다.

### 웹과의 차이를 한 표로

| 웹 | CAN | 차이 |
|---|---|---|
| HTTPS/TLS | 없음(상위 계층에서 추가 가능) | CAN 자체는 기밀성·무결성·인증을 제공하지 않는다 |
| 쿠키/세션 | 없음 | 요청 간 상태가 없다. 수신자는 매 프레임을 독립적으로 판단한다 |
| API 키/JWT | 없음 | 송신자 신원을 실을 필드가 없다 |
| 방화벽/WAF | 게이트웨이·IDS로 보완 | 버스 안에서는 패킷 필터가 기본이 아니다 |
| 최소 권한 | 진단 세션/보안 레벨로 일부 구현 | ECU마다 정책이 다르고, 버스 자체에는 권한 개념이 없다 |
| 재전송 방지 nonce | 신선도 값(freshness value) | 왕복 핸드셰이크 없이 카운터/타임스탬프로 처리 |
| 중앙 인증 서버 | 없음 | 사전 공유 키와 게이트웨이 정책에 의존한다 |

이 표의 마지막 줄이 중요하다. 웹은 중앙에서 인증을 처리할 수 있지만, 차량은 **각 ECU와 게이트웨이가 분산해서** 판단해야 한다. 그래서 키 관리와 정책 배포가 웹보다 어렵다.

## 32.2 위협 모델: 어디서 들어오나

보안은 "무엇을 지킬 것인가"에서 시작한다. 위협 모델은 자산(asset), 진입점(entry point), 신뢰 경계(trust boundary), 영향(impact), 완화책(mitigation)을 정리하는 작업이다. 웹에서 위협 모델링을 해 봤다면 같은 사고방식으로 접근하면 된다.

### 자산

| 자산 | 예 | 훼손되었을 때 |
|---|---|---|
| 안전 기능 | 제동·조향·구동·에어백 | 사고, 부상 |
| 차량 제어 | 문·시동·공조·변속 | 도난, 불편, 안전 문제 |
| 진단·정비 기능 | DTC, DID, 루틴, 코딩 | 정비 방해, 배출가스 조작 |
| 키·인증서 | SecOC 키, 진단 키, TLS 인증서 | 위조·도청·재전송 |
| 소프트웨어 | 펌웨어, 설정, 업데이트 | 벽돌, 악성코드, 롤백 공격 |
| 데이터 | 위치, 주행 기록, 연락처, 음성 | 개인정보 침해 |
| 가용성 | 버스 대역, ECU 응답 | 서비스 거부, 안전 상태 오작동 |

### 진입점

| 진입점 | 접근 방식 | 공격자가 얻는 것 | 1차 방어 |
|---|---|---|---|
| OBD-II 포트 | 물리 | 진단 요청, 버스 프레임 관찰·주입 | 포트 접근 통제, 진단 게이트웨이, 물리 잠금 |
| 텔레매틱스(TCU) | 셀룰러 | 원격 서비스, 차량 네트워크로의 피벗 | 인바운드 최소화, DMZ, 게이트웨이 분리 |
| 인포테인먼트(IVI) | Wi-Fi·BT·USB·앱 | 헤드유닛, 내부 네트워크 | 서비스 축소, 서명 검증, 도메인 분리 |
| 애프터마켓 동글 | OBD/BLE | 진단·텔레매틱스 | 공급망 검증, 최소 권한, 사용자 인지 |
| 정비 도구 | 물리·네트워크 | 진단 세션, 보안 접근 | 정비사 인증, 감사 로그, 세션 제한 |
| 공급망 | 빌드·배포 | 펌웨어·키·업데이트 | SBOM, 서명, 재현 빌드, 공급업체 평가 |
| OTA 백엔드 | 인터넷 | 업데이트 채널 | 상호 인증, 서명, 롤백 방지, 모니터링 |

- **OBD-II 포트는 차량의 정비 문이다.** 8장에서 본 것처럼 포트는 차량 내부 버스와 연결된다. 물리 접근은 가장 강력한 진입점이므로, 최신 차량은 진단 게이트웨이를 두고 포트에서 접근 가능한 ECU·서비스를 제한한다.
- **텔레매틱스와 인포테인먼트는 원격 진입점이다.** 이들은 외부 네트워크와 연결되면서 동시에 차량 내부 버스와 연결된다. 2015년 Jeep 사례(32.5절)가 이 경로를 보여 준다.
- **모든 진입점을 막을 수는 없다.** 정비·업데이트·사용자 편의를 위해 포트와 연결은 필요하다. 그래서 "막는다"보다 "경계를 긋고, 그 경계를 지나가는 것을 검증한다"가 현실적인 목표다.

### 2019년 쏘렌토는?

이 책의 예시 차량인 기아 쏘렌토 UM 2019년식 2.2 디젤에 대해 이 장은 다음과 같이 말한다.

- 이 책은 그 차에서 **정차 상태로 읽기만** 했다. 보안 접근, 세션 전환, 쓰기, 키 관련 조작은 하지 않았다.
- 그 차의 텔레매틱스·게이트웨이 구성, 진단 접근 제어, 지원하는 UDS 서비스는 **확인 필요**다. 이 책의 실차 기록에는 그 내용이 없다.
- 이 차량이 UN R155·R156의 형식 승인 대상인지, 국내 적용 시점이 언제인지는 **단정하지 않는다.** 형식 승인 시점, 국가별 적용 일정, 차량 구성에 따라 다르다. 제조사와 인증기관 문서로 확인해야 한다.
- "2019년식이니까 대상이 아니다" 또는 "대상이다"라고 말할 근거를 이 책은 가지고 있지 않다.

### 위협 모델링 순서

웹에서 하던 방식과 크게 다르지 않다.

```text
1. 자산을 나열한다. (안전, 제어, 키, 데이터, 가용성)
2. 진입점과 신뢰 경계를 그린다. (OBD, TCU, IVI, OTA, 정비)
3. 각 경로의 공격자 능력을 가정한다. (물리, 원격, 공급망)
4. 영향을 평가한다. (안전 > 개인정보 > 편의)
5. 완화책을 겹쳐 놓는다. (구조, 인증, 감시, 접근 통제, 업데이트)
6. 남은 위험을 기록하고, 모니터링한다.
```

중요한 것은 **완화책 하나로 끝내지 않는 것**이다. 게이트웨이만 있어도 부족하고, SecOC만 있어도 부족하고, IDS만 있어도 부족하다. 서로 다른 층이 겹쳐야 한다. 이것을 심층 방어(defense in depth)라고 부른다.

## 32.3 방어 계층 1: 구조로 막기 — 게이트웨이와 도메인 분리

### 모든 ECU가 같은 버스에 있으면 안 된다

차량 네트워크는 기능별 도메인으로 나뉜다. 파워트레인, 섀시, 바디, 인포테인먼트, 텔레매틱스가 대표적이다. 도메인을 나누고 그 사이에 **게이트웨이**를 두면, 한 도메인의 문제가 다른 도메인으로 곧바로 번지지 않는다.

```text
[텔레매틱스] ─┐
[인포테인먼트] ─┼──▶ [중앙 게이트웨이] ──▶ [파워트레인 CAN]
[OBD-II 포트] ─┘         │                [섀시 CAN]
                          ├──────────────▶ [바디 CAN]
                          └──────────────▶ [진단/정비]
```

- **라우팅**: 게이트웨이는 버스 사이의 프레임을 전달한다. 모든 프레임을 전달하지 않고, 허용한 ID만 전달한다.
- **필터링**: 방향별 allowlist를 둔다. 텔레매틱스에서 파워트레인으로 갈 수 있는 ID를 최소화한다.
- **속도 제한**: 특정 ID의 프레임률을 제한한다. 버스 부하·서비스 거부를 줄인다.
- **진단 방화벽**: OBD 포트에서 접근할 수 있는 ECU·서비스·세션을 제한한다.
- **로깅**: 차단·허용된 프레임과 이상 징후를 기록한다. 사후 분석과 IDS의 입력이 된다.

### 웹 개념과 대응

| 웹 | 차량 | 핵심 차이 |
|---|---|---|
| 방화벽 | 중앙 게이트웨이의 ID/방향 필터 | IP 주소·포트가 아니라 CAN ID와 방향으로 필터링 |
| DMZ | 텔레매틱스·IVI 도메인 분리 | 외부 연결 ECU를 안전-critical 버스와 직접 붙이지 않는다 |
| API 게이트웨이 | 차량 게이트웨이 | 라우팅·인증·rate limit·로깅을 한 지점에 모은다 |
| 리버스 프록시 | 진단 게이트웨이 | OBD 요청을 그대로 통과시키지 않고 정책을 적용한다 |
| 네트워크 ACL | 게이트웨이 allowlist | 기본 거부(default deny)가 원칙이다 |
| 서비스 메시 | 도메인별 버스 | 모든 통신을 중앙에서 본다기보다 경계마다 정책을 둔다 |

### 한계

- **게이트웨이 안쪽 버스는 여전히 인증이 없다.** 게이트웨이를 통과한 프레임, 또는 게이트웨이에 연결된 악성 노드가 보낸 프레임은 내부에서 그대로 신뢰될 수 있다.
- **게이트웨이는 단일 장애점이 될 수 있다.** 게이트웨이가 뚫리거나 멈추면 여러 도메인이 영향을 받는다.
- **설정 오류가 곧 취약점이다.** allowlist가 넓거나, 진단 라우팅이 과도하거나, 개발용 우회 경로가 남아 있으면 분리의 의미가 줄어든다.
- **레거시 차량은 구조를 바꾸기 어렵다.** 그래서 신차 설계에서는 처음부터 도메인과 게이트웨이를 넣고, 기존 차량은 진단 포트·애프터마켓 접근을 통제하는 쪽으로 간다.

NHTSA의 2022년 사이버보안 지침도 무선 연결 ECU와 안전-critical 제어 시스템 사이에 **네트워크 분리·격리**를 적용할 것을 권고한다. 이 지침은 법적 구속력이 없는 권고이지만, 업계가 참고하는 기준이다.

## 32.4 방어 계층 2: 메시지 인증 — AUTOSAR SecOC

### MAC만으로는 부족하다

메시지에 MAC을 붙이면 변조와 위조를 막을 수 있다. 하지만 **재전송(replay)**은 막지 못한다. 공격자가 어제의 정상 프레임을 녹음해 오늘 그대로 다시 보내면, MAC은 여전히 유효하다. 그래서 인증에는 "이 메시지가 지금 처음 온 것인가"를 확인하는 **신선도(freshness)**가 함께 필요하다.

웹에서는 nonce, 타임스탬프, 세션 ID, TLS의 sequence number로 이 문제를 푼다. 차량에서는 왕복 핸드셰이크 없이 짧은 프레임 안에서 해결해야 하므로, **신선도 값(freshness value)**과 **잘라 낸 MAC(truncated MAC)**을 쓴다.

### SecOC의 구조

AUTOSAR의 SecOC(Secure Onboard Communication)는 PDU 단위로 진위와 신선도를 검증하는 규격이다. Secured I-PDU는 대략 다음과 같다.

```text
[Secured I-PDU Header (선택)]
[Authentic I-PDU: 원래 payload]
[Freshness Value의 일부 (선택, 잘라 냄)]
[Authenticator: MAC의 일부 (잘라 냄)]
```

- 송신 측 SecOC 모듈은 **인증자(Authenticator)**를 계산해 붙인다. 인증자는 키, Data ID, 원래 payload, **전체 신선도 값**으로 계산한다.
- 신선도 값을 프레임에 다 싣지 않아도, **MAC 계산에는 전체 값이 들어간다.** 수신자는 자신이 가진 신선도 값으로 같은 계산을 해 보고 비교한다.
- 신선도 값은 외부의 **Freshness Manager**가 관리한다. 카운터 기반이면 송신 전에 증가시키고, 타임스탬프 기반이면 동기화된 시간을 쓴다.
- 수신 측은 MAC과 신선도를 함께 검사한다. MAC이 맞아도 신선도가 오래되었거나 이미 본 값이면 폐기한다.

AUTOSAR SecOC 규격은 세 가지 보안 프로파일을 예시한다.

| 프로파일 | MAC | 신선도 값 | 특징 |
|---|---|---|---|
| Profile 1 (24Bit-CMAC-8Bit-FV) | AES-128 CMAC, 상위 24비트 | 하위 8비트를 전송 | 짧은 프레임에 맞춘 기본형 |
| Profile 2 (24Bit-CMAC-No-FV) | AES-128 CMAC, 상위 24비트 | 전송하지 않음 | 동기화된 신선도 값이 없을 때 |
| Profile 3 (JASPAR) | AES-128 CMAC, 상위 28비트 | 64비트 중 하위 4비트를 전송 | CAN용으로 명시된 프로파일 |

- **MAC을 잘라 쓰는 이유**는 프레임 공간이다. 클래식 CAN은 payload가 8바이트뿐이라 전체 MAC을 넣기 어렵다.
- 잘라 낸 MAC은 위조 확률이 커진다. 24비트 MAC이면 무작위 위조가 한 번에 통과할 확률은 `2^-24` 수준이다. 그래서 SecOC는 게이트웨이·IDS·rate limit 같은 다른 층과 함께 쓴다.
- **신선도 값을 잘라 전송하면 재전송 창이 생긴다.** 수신자가 허용하는 범위 안의 오래된 값은 구분하지 못할 수 있다. 프로파일과 구현이 이 창을 어떻게 관리하는지가 중요하다.
- SecOC는 **기밀성을 제공하지 않는다.** payload는 암호화되지 않는다. 도청을 막으려면 별도의 암호화(예: TLS, 애플리케이션 계층 암호화)가 필요하다.

### 웹 개념과 대응

| 웹 | SecOC | 차이 |
|---|---|---|
| HMAC 서명 | AES-128 CMAC | 대칭 키, 짧은 태그, 하드웨어 가속 |
| nonce/재전송 방지 | Freshness Value | 왕복 없이 카운터/타임스탬프로 처리 |
| mTLS | SecOC(단방향에 가까움) | 수신자는 송신자를 검증하지만, 송신자는 수신자를 검증하지 않는다 |
| 키 교환 | 사전 프로비저닝 | 차량 생산·정비 단계에서 키를 심는다 |
| TLS 레코드 | Secured I-PDU | 프레임마다 인증 정보가 붙는다 |
| 인증서 폐기 | 키 교체/재프로비저닝 | 차량에서는 키 교체가 훨씬 어렵다 |

### 현실적인 한계

- **모든 ECU에 넣을 수 없다.** 레거시 ECU는 연산·메모리·키 저장 공간이 부족할 수 있다. 그래서 게이트웨이가 일부 구간만 보호하거나, 중요한 메시지에만 적용한다.
- **키 관리가 어렵다.** 차량마다 키를 다르게 넣어야 하고, 정비·교체·폐기 절차가 필요하다. 공용 키를 모든 차에 넣으면 하나가 뚫릴 때 전체가 뚫린다.
- **신선도 동기화가 필요하다.** 배터리 방전, ECU 교체, 장시간 미동작 후에는 카운터가 어긋날 수 있다. 재동기화 절차가 없으면 정상 메시지가 거부된다.
- **성능·지연**이 든다. 암호 연산과 검증은 공짜가 아니다. 실시간 제어 메시지에는 영향 분석이 필요하다.
- **SecOC가 만능은 아니다.** 인증되지 않은 다른 메시지, 게이트웨이 설정 오류, 키 유출, 공급망 공격은 여전히 위험이다.

SecOC는 "CAN에 인증을 추가하는 한 가지 방법"이지, "CAN을 안전하게 만드는 스위치"가 아니다. 실제 채택 여부와 프로파일은 제조사·플랫폼마다 다르며, 이 책은 특정 차량의 SecOC 적용 여부를 확인하지 않았다.

## 32.5 공개 사례: 2015년 Jeep Cherokee

### 무슨 일이 있었나

2015년 7월, Charlie Miller와 Chris Valasek은 **2014년형 Jeep Cherokee**를 대상으로 한 원격 공격 연구를 공개했다. 연구의 핵심은 다음과 같다.

- 대상 차량은 **변조되지 않은 양산차**였다.
- 공격 경로는 **셀룰러 네트워크 → Uconnect 헤드유닛 → 차량 내부 네트워크 → ECU**로 이어졌다.
- 공격자는 차량에 물리적으로 접근하지 않고 원격에서 제어를 시도할 수 있었다.
- 연구진은 2014년 10월부터 FCA에 문제를 알렸고, 2015년 7월 FCA는 패치를 배포했다.
- 2015년 7월 24일 FCA는 약 **140만 대**를 자발적 리콜했다. 이동통신 사업자도 문제 트래픽을 차단했다.
- 패치는 원격 OTA가 아니라 **USB 또는 딜러 방문**으로 설치해야 했다.

이 사례는 "차량 보안은 이론이 아니라 리콜로 이어지는 문제"라는 것을 업계에 각인시켰다. 동시에 **연결성과 안전-critical 버스가 같은 신뢰 경계에 있으면 얼마나 위험한가**를 보여 주었다.

### 방어 관점에서 무엇이 문제였나

| 문제 | 설명 | 웹 대응 |
|---|---|---|
| 외부에 열린 서비스 | 헤드유닛이 셀룰러망에서 접근 가능한 서비스를 제공했다 | 인터넷에 노출된 관리 포트 |
| 평평한 네트워크 | 헤드유닛과 차량 제어 버스가 충분히 분리되지 않았다 | 웹 서버와 DB가 같은 서브넷에 있는 구조 |
| 인증 없는 버스 | 내부 CAN 프레임에 송신자 인증이 없었다 | 내부 API에 인증이 없는 구조 |
| OTA 부재 | 패치를 원격으로 배포할 수 없어 리콜·방문이 필요했다 | 수동 패치만 가능한 레거시 시스템 |
| 사후 감시 부재 | 이상 프레임을 탐지·차단하는 층이 없었다 | 로그·IDS·WAF가 없는 구조 |

### 어떤 방어가 생겼나

- **즉시 조치**: 외부에서 들어오는 불필요한 트래픽을 차단하고, 헤드유닛 패치를 배포하고, 리콜로 차량을 업데이트했다.
- **구조적 조치**: 텔레매틱스·인포테인먼트를 안전-critical 버스와 분리하고, 게이트웨이에서 라우팅·필터링하는 설계가 확산했다.
- **탐지**: 차량 내부 네트워크의 이상을 감시하는 IDS와 보안 관제(V-SOC) 개념이 커졌다.
- **업데이트**: OTA와 서명·롤백 검증을 갖춘 업데이트 체계가 중요해졌다. UN R156이 이 영역을 규제한다. ESP32 수준에서 A/B 파티션·서명·롤백을 구현하는 방법은 20장에서 다룬다.
- **규제·표준**: UN R155/R156과 ISO/SAE 21434가 생겼다. 32.8절에서 다룬다.

### 이 사례를 재현하지 않는다

이 책은 위 사례의 **공격 절차, 익스플로잇, 특정 메시지 ID, 우회 방법을 쓰지 않는다.** 독자도 다음을 하지 않는다.

- 타인의 차량에 무단으로 접근하지 않는다.
- 실제 차량에서 보안 접근 우회, 키·이모빌라이저 관련 조작, 펌웨어 변조를 시도하지 않는다.
- 주행 중인 차량에서 보안 실험을 하지 않는다.
- 공개된 취약점을 이용해 다른 차량·서비스에 접근하지 않는다.

이 장의 실습은 **가상 버스에서 방어 로직을 검증하는 것**까지다. 11장의 안전·법·윤리 규칙이 그대로 적용된다.

## 32.6 방어 계층 3: 감시 — CAN 침입 탐지(IDS)

### 예방만으로는 부족하다

게이트웨이와 SecOC를 넣어도 모든 프레임을 완벽하게 보호할 수는 없다. 레거시 ECU, 설정 오류, 키 유출, 새로운 공격은 남는다. 그래서 **정상과 다른 것을 탐지하는 층**이 필요하다. 웹에서 WAF·SIEM·이상 탐지를 두는 것과 같은 이유다.

### 무엇을 볼 수 있나

CAN IDS는 버스 위의 프레임과 시간 정보를 본다.

- **ID와 방향**: 어떤 ID가 어느 버스에서 오가는가.
- **주기**: 주기 메시지가 일정 간격으로 오는가.
- **길이**: DLC가 예상과 다른가.
- **payload 패턴**: 값의 범위·변화율·엔트로피가 평소와 다른가.
- **순서·카운터**: 시퀀스 번호·카운터가 건너뛰거나 반복되는가.
- **물리 특성**: 전압 파형·상승 시간으로 송신 ECU를 지문처럼 구분할 수 있는가.

### 탐지 방식

| 방식 | 보는 것 | 잡는 것 | 한계 |
|---|---|---|---|
| 서명/룰 | 알려진 공격 패턴, 허용 ID 목록 | 알려진 공격, 정의되지 않은 ID | 새로운 공격, 정상 범위 안의 변조 |
| 주기·타이밍 | 메시지 간격, 주기 이탈 | 주입·중단·마스커레이드 | 공격자가 주기를 흉내 내면 약함 |
| 클록 지문 | ECU별 클록 오차 | 다른 ECU가 보낸 위조 프레임 | 긴 학습 시간, 환경 영향 |
| payload 이상 | 값 범위·엔트로피·상관관계 | 비정상 제어 값 | 정상 변화와 구분 어려움 |
| 물리 지문 | 전압 파형 | 송신자 위조 | 하드웨어·온도·배선 영향 |

### CIDS: 주기와 클록 지문

USENIX Security 2016의 CIDS(Clock-based IDS)는 주기 메시지의 **도착 간격**을 측정해 ECU의 클록 오차(skew)를 지문으로 삼는다. 정상 상태의 클록 거동을 RLS(recursive least squares)로 학습하고, CUSUM으로 이상 변화를 탐지한다. 논문은 위조·변조·마스커레이드 공격을 탐지하고, 오탐률 0.055%를 보고하며, 공격한 ECU를 역추적(root-cause)할 수 있다고 설명한다. CAN 버스 프로토타입과 실제 차량(2013 Honda Accord), 실차 로그로 검증했다.

이 접근의 핵심은 **"메시지 내용"이 아니라 "누가 언제 보냈는가"**를 본다는 점이다. SecOC가 없는 버스에서도 적용할 수 있고, SecOC가 있는 버스에서도 보조층으로 쓸 수 있다.

### IDS의 한계

- **탐지는 차단이 아니다.** 경고를 받아도 게이트웨이·ECU가 즉시 막지 못하면 피해는 진행된다.
- **오탐과 미탐**이 있다. 임계값이 낮으면 경고 폭주, 높으면 놓친다.
- **정상 기준(baseline)이 필요하다.** 차량·펌웨어·주행 상황마다 정상 패턴이 다르다.
- **자원이 제한된다.** ECU에서 IDS를 돌리려면 CPU·메모리·전력이 든다.
- **개인정보**: 로그에 위치·주행 패턴이 섞일 수 있다. 11장의 개인정보 원칙을 적용한다.
- **공격자는 IDS를 알고 있다.** 주기를 흉내 내거나, 학습 구간을 오염시키거나, 경고를 끄려 할 수 있다.

### 어디에 두나

- **게이트웨이**: 도메인 경계에서 모든 프레임을 볼 수 있어 가장 현실적이다.
- **중앙 관제(V-SOC)**: 여러 차량의 경고를 모아 패턴을 분석한다. 개인정보·통신 비용을 고려한다.
- **ECU 내부**: 중요한 ECU에 경량 룰을 넣는다. 자원 제약이 크다.
- **벤치·개발 환경**: 23장의 가상 버스에서 IDS 로직을 먼저 시험한다. 실제 차량 송신 없이 임계값·오탐을 조정할 수 있다.

웹의 SIEM과 비슷하게, IDS는 **로그·경고·대응 절차**가 함께 있어야 의미가 있다. 경고만 쌓이고 아무도 보지 않으면 없는 것과 같다.

## 32.7 방어 계층 4: 진단 접근 통제 — UDS 0x27과 0x29

### 0x27 SecurityAccess: 시드-키

UDS의 `0x27`은 오래된 보안 접근 방식이다.

1. 테스터가 시드(seed)를 요청한다.
2. ECU가 시드를 보낸다.
3. 테스터가 시드와 비밀 알고리즘으로 키(key)를 계산해 보낸다.
4. ECU가 키를 검증하면 보안 잠금이 풀린다.

이 방식은 **공유 비밀(shared secret)**에 의존한다. 테스터와 ECU가 같은 알고리즘·키를 알아야 한다. 구조적인 약점이 있다.

- **단방향**: ECU가 테스터를 검증하지만, 테스터는 ECU를 검증하지 않는다.
- **세션 단위 잠금 해제**: 시드-키 교환으로 보안 레벨을 열면, 세션 종료·S3 타임아웃·ECU 리셋 전까지 유지된다. 테스터의 신원을 인증하는 것이 아니라 잠금을 푸는 것이다.
- **알고리즘 재사용**: 같은 ECU 계열에 같은 시드-키 알고리즘이 쓰이는 경우가 있다. 하나가 역설계되면 계열 전체가 영향을 받을 수 있다.
- **고정 시드**: 시드가 고정되거나 약하면 재전송·추측에 취약하다.

이 책은 `0x27`을 **보내지 않는다.** 10·11장의 읽기 전용 원칙과 같은 이유다.

### 0x29 Authentication: 인증서·도전-응답

ISO 14229-1:2020은 `0x29` Authentication 서비스를 추가했다. `0x27`이 공유 비밀 기반의 잠금 해제라면, `0x29`는 **테스터의 신원을 인증**하는 데 초점을 둔다.

- **인증서 교환(APCE)**: 테스터가 X.509 인증서를 제시하고, ECU가 신뢰하는 CA로 검증한다. 이어서 개인 키 소유를 증명하는 도전-응답을 한다.
- **도전-응답(ACR)**: 사전에 설치된 키로 도전-응답을 한다. PKI를 쓰기 어려운 환경의 대안이다.
- **상호 인증**: 테스터와 ECU가 서로를 검증할 수 있다.
- **역할·권한**: 인증된 신원에 따라 접근 가능한 기능을 나눌 수 있다.
- **폐기**: 문제가 된 테스터 인증서를 폐기할 수 있다. 모든 ECU의 키를 바꾸지 않아도 된다.

`0x29`가 모든 문제를 해결하는 것은 아니다. PKI 구축·인증서 배포·시각 동기화·부트로더 지원이 필요하고, ECU 자원도 더 든다. 그래서 기존 차량은 `0x27`, 신규 플랫폼·외부 진단은 `0x29`를 쓰는 과도기가 이어지고 있다.

### 진단 방화벽과 최소 권한

- **누가**: 정비사·테스터·공장 장비를 구분한다.
- **어디에**: OBD 포트에서 접근 가능한 ECU를 제한한다.
- **무엇을**: 읽기·쓰기·루틴·세션별로 허용 서비스를 나눈다.
- **언제**: 세션 시간 제한, 주행 중 진단 제한, 정차 조건을 둔다.
- **기록**: 누가 어떤 진단을 했는지 감사 로그를 남긴다.

웹의 RBAC·최소 권한·감사 로그와 같은 원리다. 다만 차량에서는 **버스 자체에 권한 개념이 없으므로**, 게이트웨이와 ECU가 정책을 나눠 가진다.

이 책의 실차 실습은 여전히 **정차 상태의 읽기 전용**이다. `0x27`·`0x29`는 개념만 다루고, 실제 차량에서 시도하지 않는다.

지금까지의 방어 계층을 한 표로 정리하면 다음과 같다. 한 계층이 모든 공격을 막지 못하므로, 여러 계층을 겹쳐 쓰는 것이 전제다.

| 계층 | 수단 | 막는 것 | 남는 한계 |
|---|---|---|---|
| 1. 구조 | 게이트웨이, 도메인 분리, 진단 라우팅 최소화 | 외부에서 안전-critical 버스로 직접 접근 | 내부 버스는 여전히 무인증, 게이트웨이는 단일 장애점 |
| 2. 인증 | SecOC(MAC + 신선도) | 위조·변조·재전송 | 레거시 ECU에 넣기 어렵고 키·신선도 동기화가 필요 |
| 3. 감시 | IDS(허용 ID·주기·클록 지문) | 정상 범위를 벗어난 주입·중단·마스커레이드 | 탐지는 차단이 아니며 오탐·자원 제약이 있다 |
| 4. 진단 통제 | 0x27·0x29, 진단 방화벽, 세션 제한 | 진단 포트를 통한 보안 접근·쓰기 | 구현·키 관리에 의존하고 레거시 차량은 소급이 어렵다 |

## 32.8 규제와 표준: R155, R156, ISO/SAE 21434

### 왜 개발자가 규제를 알아야 하나

웹 개발자도 SOC 2, ISO 27001, GDPR, PCI DSS 같은 규제·표준을 만난다. 차량에서는 규제가 **형식 승인(type approval)**과 연결되어, 차량을 판매하려면 사이버보안 관리 체계와 소프트웨어 업데이트 체계를 입증해야 한다. 공급업체라면 완성차 제조사의 요구가 계약·감사로 내려온다.

### UN R155: 사이버보안 관리 체계(CSMS)

- **정식 이름**: UN Regulation No. 155 — Cyber security and cyber security management system
- **채택**: 2020년 6월 24일, UNECE WP.29
- **발효**: 2021년 1월 22일
- **적용 대상(개요)**: ECU를 1개 이상 갖춘 L·M·N·O 범주 차량. 2025년 1월 10일 발효된 Supplement 3에서 L 범주가 포함되었다. 원문(2021년)은 M·N, ECU가 있는 O, 자동화 수준 3 이상의 L6/L7이었다.
- **요구**: 사이버보안 관리 체계(CSMS)를 수립·운영하고, 위험 기반 프로세스, 책임·거버넌스, 공급망 관리, 사고 탐지·대응, 차량 Fleet 모니터링을 입증한다.
- **인증**: 승인 기관이 CSMS를 심사한다. 완성차 제조사만 형식 승인을 받을 수 있다.

### UN R156: 소프트웨어 업데이트 관리 체계(SUMS)

- **정식 이름**: UN Regulation No. 156 — Software update and software updates management system
- **채택·발효**: R155와 같은 2020년 6월 24일 채택, 2021년 1월 22일 발효
- **적용 대상(개요)**: 소프트웨어 업데이트가 가능한 M·N·O·R·S·T 범주 차량
- **요구**: 소프트웨어 업데이트 관리 체계(SUMS), 안전·보안을 고려한 OTA, 무결성·진위 확인, 소프트웨어 식별자(RXSWIN), 실패 시 롤백·안전 상태
- **인증**: 승인 기관이 SUMS를 심사한다. ISO 24089가 관련 표준으로 언급된다.

### ISO/SAE 21434: 사이버보안 엔지니어링

- **공표**: 2021년 8월 31일
- **범위**: 도로 차량의 E/E 시스템(구성품·인터페이스 포함)에 대해 개념·개발·생산·운영·유지·폐기 전 단계의 사이버보안 위험 관리 요구를 정의한다.
- **특징**: 특정 기술(SecOC, IDS, TLS 등)을 강제하지 않고 **프로세스와 공통 언어**를 제공한다.
- **적용**: 공표 이후 개발·수정이 시작된 양산 차량 E/E 시스템에 적용된다.

### 규제·표준·기술의 관계

```text
UN R155/R156 (형식 승인 요구)
        │
        ▼
ISO/SAE 21434 (사이버보안 엔지니어링 프로세스)
        │
        ▼
기술적 조치 (게이트웨이, SecOC, IDS, 0x29, OTA 서명, 키 관리)
```

- 규제는 "무엇을 입증해야 하는가"를 정한다.
- 표준은 "어떤 프로세스로 그 증거를 만드는가"를 정한다.
- 기술은 "실제로 무엇을 구현하는가"를 정한다.
- 셋 중 하나만 있어도 부족하다. 프로세스 없는 기술은 유지보수가 안 되고, 기술 없는 프로세스는 빈 서류가 된다.

### 적용 시점과 예시 차량

| 날짜 | 사건 |
|---|---|
| 2020-06-24 | UN R155·R156 채택 |
| 2021-01-22 | 두 규정 발효 |
| 2021-08-31 | ISO/SAE 21434 공표 |
| 2022-07-06 | EU, R155·R156 신규 형식 승인 적용 |

- 2020~2021년의 UN 채택·발효와 2021년 ISO 공표는 **EU 일정이 아니다.** EU 적용일은 마지막 두 행이다. R156의 세부 적용일은 차종·승인 종류에 따라 더 나뉜다.
- UN 1958 협정에 가입한 국가가 규정을 채택하면 그 국가의 일정이 따로 있다.
- 한국의 적용 시점·방식은 **확인 필요**다. 이 책은 국내 인증 일정을 확인하지 않았다.
- 이 책의 예시 차량(2019년 쏘렌토)이 R155/R156 대상인지 **단정하지 않는다.** 형식 승인 시점, 국가별 적용 일정, 차량 구성에 따라 다르다. 제조사·인증기관 문서로 확인해야 한다.

## 32.9 개발자 실천: 가상 버스에서 SecOC 흉내 내기

### 먼저, 하지 말아야 할 것

이 실습은 **23장의 가상 CAN 버스에서만** 한다. 실제 차량에서는 다음을 하지 않는다.

- 보안 접근(`0x27`·`0x29`) 시도, 키·이모빌라이저 관련 조작
- 임의 프레임 송신, 세션 전환, 고장 코드 삭제, 코딩·플래싱
- 주행 중 보안 실험
- 타인 차량·서비스에 대한 스캔·공격

이 장의 코드는 **교육용 장난감**이다. 실제 AUTOSAR SecOC와 다르다. 실제 SecOC는 AES-128 CMAC, Freshness Manager, 프로파일별 잘라 내기, 키 관리, 게이트웨이 연동을 포함한다. 이 코드는 그중 **MAC과 카운터 검증의 개념**만 흉내 낸다.

### 설계

클래식 CAN의 8바이트 payload 안에 다음을 넣는다.

```text
[Counter 2바이트][Payload 2바이트][MAC 4바이트]
```

- `Counter`는 신선도 값의 역할을 한다. 수신자는 마지막으로 본 카운터보다 큰 값만 받는다.
- `Payload`는 2바이트 명령이라고 가정한다. 실제 제어 값이 아니다.
- `MAC`은 `HMAC-SHA256(key, CAN ID || Counter || Payload)`의 앞 4바이트다. 실제 SecOC의 AES-CMAC 대신 표준 라이브러리의 HMAC을 쓴다.
- CAN ID를 MAC 계산에 묶어, 다른 ID로 같은 payload를 재사용하는 것을 어렵게 만든다. 실제 SecOC는 Data ID를 쓴다.

### 코드

`uv` 프로젝트에서 `python-can`을 추가하고 실행한다.

```bash
uv init secoc-lab
cd secoc-lab
uv add python-can
uv run python secoc_toy.py
```

```python
"""가상 CAN 버스에서 SecOC 흉내 내기.

실제 AUTOSAR SecOC가 아니다. 교육용 장난감이다.
- CAN ID 0x321, 데이터 8바이트: [counter 2][payload 2][MAC 4]
- MAC = HMAC-SHA256(key, CAN ID || counter || payload)의 앞 4바이트
- 수신자는 MAC과 counter(재전송)를 검사한다.
"""

from __future__ import annotations

import hashlib
import hmac

import can

CHANNEL = "vcan0"
SECURED_ID = 0x321
KEY = b"toy-key-do-not-use-in-a-real-vehicle"
MAC_BYTES = 4
COUNTER_BYTES = 2
PAYLOAD_BYTES = 2


def mac(can_id: int, body: bytes) -> bytes:
    msg = can_id.to_bytes(4, "big") + body
    return hmac.new(KEY, msg, hashlib.sha256).digest()[:MAC_BYTES]


def build(counter: int, payload: bytes) -> bytes:
    if len(payload) != PAYLOAD_BYTES:
        raise ValueError("이 장난감의 payload는 2바이트다")
    body = counter.to_bytes(COUNTER_BYTES, "big") + payload
    return body + mac(SECURED_ID, body)


class Receiver:
    def __init__(self) -> None:
        self.last_counter: dict[int, int] = {}

    def verify(self, msg: can.Message) -> tuple[bool, str]:
        data = bytes(msg.data)
        if len(data) != COUNTER_BYTES + PAYLOAD_BYTES + MAC_BYTES:
            return False, "length"
        body, tag = data[:-MAC_BYTES], data[-MAC_BYTES:]
        counter = int.from_bytes(body[:COUNTER_BYTES], "big")
        if not hmac.compare_digest(tag, mac(msg.arbitration_id, body)):
            return False, "mac"
        last = self.last_counter.get(msg.arbitration_id, -1)
        if counter <= last:
            return False, "replay"
        self.last_counter[msg.arbitration_id] = counter
        return True, f"counter={counter} payload={body[COUNTER_BYTES:].hex()}"


def send(bus: can.BusABC, data: bytes) -> None:
    bus.send(can.Message(arbitration_id=SECURED_ID, is_extended_id=False, data=data))


def main() -> None:
    sender = can.Bus(interface="virtual", channel=CHANNEL)
    receiver_bus = can.Bus(interface="virtual", channel=CHANNEL)
    receiver = Receiver()

    def deliver(label: str) -> None:
        msg = receiver_bus.recv(0.2)
        if msg is None:
            print(f"{label:<24} -> NO FRAME")
            return
        ok, reason = receiver.verify(msg)
        print(f"{label:<24} -> {'ACCEPT' if ok else 'REJECT'}: {reason}")

    try:
        # 1. 정상 프레임 3개
        for counter in (1, 2, 3):
            send(sender, build(counter, b"\x01\x00"))
            deliver(f"valid counter={counter}")

        # 2. 같은 프레임을 그대로 다시 보낸다 (재전송 공격)
        send(sender, build(2, b"\x01\x00"))
        deliver("replay counter=2")

        # 3. payload만 바꾸고 MAC은 그대로 둔다 (변조)
        tampered = bytearray(build(4, b"\x01\x00"))
        tampered[2] = 0x02
        send(sender, bytes(tampered))
        deliver("tampered counter=4")

        # 4. 공격자가 자기 키로 MAC을 계산해 counter를 올린다 (위조)
        body = (5).to_bytes(2, "big") + b"\x01\x00"
        forged_mac = hmac.new(
            b"attacker-key",
            SECURED_ID.to_bytes(4, "big") + body,
            hashlib.sha256,
        ).digest()[:MAC_BYTES]
        send(sender, body + forged_mac)
        deliver("forged counter=5")

        # 5. 정상 프레임이 다시 온다
        send(sender, build(6, b"\x00\x01"))
        deliver("valid counter=6")
    finally:
        sender.shutdown()
        receiver_bus.shutdown()


if __name__ == "__main__":
    main()
```

실행 결과는 다음과 같다.

```text
valid counter=1          -> ACCEPT: counter=1 payload=0100
valid counter=2          -> ACCEPT: counter=2 payload=0100
valid counter=3          -> ACCEPT: counter=3 payload=0100
replay counter=2         -> REJECT: replay
tampered counter=4       -> REJECT: mac
forged counter=5         -> REJECT: mac
valid counter=6          -> ACCEPT: counter=6 payload=0001
```

### 무엇을 확인했나

- **정상 프레임**은 MAC과 카운터가 맞아 수락된다.
- **재전송**은 카운터가 이미 본 값이라 거부된다. MAC만으로는 막을 수 없었던 공격이다.
- **변조**는 payload가 바뀌어 MAC이 맞지 않아 거부된다.
- **다른 키로 위조**한 프레임도 MAC이 맞지 않아 거부된다.
- **정상 프레임**이 다시 오면 수락된다. 카운터가 앞으로 나아갔기 때문이다.

### 이 장난감이 하지 않는 것

- **기밀성**: payload는 평문이다. SecOC도 기본적으로 기밀성을 제공하지 않는다.
- **실제 프로파일**: AES-128 CMAC, 잘라 낸 MAC/FV 길이, Data ID 구성이 다르다.
- **신선도 동기화**: 카운터가 65535를 넘으면 감싸진다(wrap). 재동기화·리셋·트립 카운터가 없다.
- **키 관리**: 키가 코드에 하드코딩되어 있다. 실제로는 차량별 키를 안전하게 주입·보관·폐기해야 한다.
- **게이트웨이·IDS 연동**: 검증 실패 시 경고·차단·로그를 남기는 운영 계층이 없다.
- **실시간성**: 암호 연산 시간과 버스 지연을 측정하지 않는다.

### 확장 아이디어

1. **주기 검사**: ID별 도착 간격을 기록하고, 예상 주기에서 벗어나면 경고하는 IDS를 붙인다.
2. **allowlist**: 게이트웨이처럼 허용 ID만 통과시키고, 나머지는 로그를 남기고 버린다.
3. **키 교체**: 키를 파일·환경 변수에서 읽고, 키 ID를 payload에 넣어 본다. 키를 로그에 남기지 않는다.
4. **재동기화**: 카운터가 크게 점프하거나 wrap 될 때의 정책을 설계한다.
5. **테스트**: 25장의 방식으로 정상·재전송·변조·위조 프레임을 pytest 케이스로 만든다.

## 32.11 체크리스트

- [ ] 자산·진입점·신뢰 경계를 그림으로 정리했는가
- [ ] OBD·텔레매틱스·IVI·OTA·공급망을 위협 모델에 넣었는가
- [ ] 게이트웨이 allowlist가 기본 거부인가
- [ ] 안전-critical 도메인과 외부 연결 도메인을 분리했는가
- [ ] 중요한 메시지에 인증(MAC)과 신선도(카운터)를 적용했는가
- [ ] 키를 차량별로 주입·보관·폐기하는 절차가 있는가
- [ ] IDS의 정상 기준·임계값·경고 대응 절차가 있는가
- [ ] 진단 접근을 역할·서비스·시간별로 제한했는가
- [ ] OTA의 서명·무결성·롤백·안전 상태를 검증했는가
- [ ] 로그에서 VIN·위치·키를 제거했는가
- [ ] 실차에서는 읽기만 하고, 송신은 가상 버스에서만 했는가
- [ ] 11장의 안전·법·윤리 규칙을 따랐는가

## 장 요약

- CAN 데이터링크 계층에는 송신자 인증도 암호화도 없다. CAN ID는 메시지 식별자이지 신원이 아니다.
- CRC는 우발적 오류 검출이고, MAC은 키를 가진 주체만 만들 수 있는 인증 태그다.
- 위협 모델은 OBD 포트(물리), 텔레매틱스·IVI(원격), 공급망·OTA(소프트웨어)를 함께 본다.
- 게이트웨이와 도메인 분리는 피해 범위를 줄인다. 그러나 내부 버스는 여전히 신뢰 경계 안에 있다.
- AUTOSAR SecOC는 AES-128 CMAC과 신선도 값으로 진위·신선도를 검증한다. 기밀성은 제공하지 않는다.
- CAN IDS는 주기·클록·payload 이상을 보고 탐지한다. 탐지는 차단이 아니므로 대응 절차가 필요하다.
- UDS 0x27은 공유 비밀 기반 잠금 해제, 0x29는 인증서·도전-응답 기반 인증이다. 이 책은 둘 다 실차에서 시도하지 않는다.
- UN R155(CSMS)·R156(SUMS)은 2021년 발효되었고, ISO/SAE 21434는 사이버보안 엔지니어링 프로세스를 정의한다. 적용 일정과 개별 차량 해당 여부는 확인 필요다.
- 방어는 한 층으로 끝나지 않는다. 구조·인증·감시·접근 통제·업데이트·키 관리가 겹쳐야 한다.

다음 장에서는 이 책 전체를 어떤 순서로 학습할지 정리한다. 보안은 그 경로의 마지막에 붙는 선택 과목이 아니라, 차량 시스템을 만들고 운영할 때 계속 따라오는 관점이다.

## 정답과 해설

### 1.

1. CRC는 전기적 잡음·비트 오류 같은 우발적 손상을 검출한다. 의도적인 변조는 검출하지 못한다. 공격자가 CRC를 다시 계산하면 통과한다.
2. 수신자는 변조된 프레임을 정상으로 받아들인다. CRC가 맞기 때문이다.
3. MAC은 비밀 키를 가진 주체만 계산할 수 있다. 공격자는 키 없이 올바른 MAC을 만들 수 없다. CRC는 키가 없어 누구나 계산할 수 있다.

### 2.

1. OBD-II 포트: (a) 진단 요청, 버스 프레임 관찰·주입, DTC·DID 읽기 (b) 포트 접근 통제, 진단 게이트웨이, 물리 잠금.
2. 텔레매틱스: (a) 원격 서비스, 차량 네트워크로의 피벗 (b) 인바운드 최소화, DMZ, 게이트웨이 분리.
3. 인포테인먼트: (a) 헤드유닛, 내부 네트워크 접근 (b) 서비스 축소, 서명 검증, 도메인 분리.
4. OTA 백엔드: (a) 업데이트 채널, 펌웨어·키 (b) 상호 인증, 서명, 롤백 방지, 모니터링.

### 3.

1. 정상 프레임을 녹음해 그대로 다시 보내는 재전송 공격이 가능하다. MAC은 그 프레임이 유효하다고 말하지만, "지금 처음 온 것"인지는 말하지 않는다.
2. MAC 계산에는 **전체 신선도 값**이 들어가고, 수신자는 자신이 가진 값으로 같은 계산을 할 수 있기 때문이다. 프레임에는 일부만 실어 공간을 아낀다.
3. 24비트 MAC은 프레임 공간을 아끼지만, 무작위 위조가 통과할 확률이 `2^-24` 수준으로 커진다. 그래서 rate limit·IDS·게이트웨이 같은 보조층이 필요하다. 보안 강도와 프레임 크기·실시간성의 trade-off다.

### 4.

1. 단방향 인증(ECU만 테스터를 검증), 세션 단위 잠금 해제(신원 인증 아님), ECU 계열에 재사용되는 알고리즘, 고정 시드·약한 키 함수 등.
2. 인증서 기반 신원(APCE), 상호 인증, 역할·권한, 인증서 폐기 중 세 가지.
3. 0x27·0x29는 보안 잠금을 여는 서비스다. 실차에서 시도하면 쓰기·루틴·플래싱의 문을 열 수 있고, 안전·보증·법적 문제가 생긴다. 이 책은 정차 상태의 읽기 전용이며, 보안 접근은 개념만 다룬다.

### 5.

예시 답안이다. 실제 코드는 32.9절의 `Receiver`를 확장한다.

```python
ALLOWED_IDS = {0x321}
EXPECTED_PERIOD = 0.1
PERIOD_TOLERANCE = 0.05
JUMP_THRESHOLD = 100

class Receiver:
    def __init__(self) -> None:
        self.last_counter: dict[int, int] = {}
        self.last_time: dict[int, float] = {}

    def verify(self, msg: can.Message, now: float) -> tuple[bool, str]:
        if msg.arbitration_id not in ALLOWED_IDS:
            return False, "id"
        # ... 길이·MAC·카운터 검사는 32.9절과 같다 ...
        last_time = self.last_time.get(msg.arbitration_id)
        if last_time is not None:
            gap = now - last_time
            if abs(gap - EXPECTED_PERIOD) > PERIOD_TOLERANCE:
                print(f"WARN: period gap={gap:.3f}")
        self.last_time[msg.arbitration_id] = now
        if counter - last > JUMP_THRESHOLD:
            print(f"WARN: jump {last} -> {counter}")
        self.last_counter[msg.arbitration_id] = counter
        return True, f"counter={counter}"
```

- allowlist는 게이트웨이의 기본 거부 정책을 흉내 낸다.
- 주기 검사는 IDS의 가장 단순한 형태다. 실제로는 학습 구간·임계값·오탐 처리가 필요하다.
- 카운터 점프 경고는 재동기화·결함·공격을 구분하는 출발점이다. 경고만으로 공격이라고 단정하지 않는다.
