# 35장 CAN 위의 프로토콜 고르기

## 이 장에서

7~10장은 승용차의 OBD-II와 UDS를, 33장은 트럭·중장비의 J1939를, 34장은 산업의 CANopen과 선박의 NMEA 2000을 다뤘다. 이제 "내 프로젝트에는 무엇을 골라야 하나"라는 질문에 답할 차례다.

웹에서 REST·GraphQL·gRPC·WebSocket을 고를 때처럼, CAN 위의 프로토콜도 **요구사항**으로 고른다. "CAN을 쓴다"는 결정은 절반이다. 나머지 절반은 "그 위에 어떤 약속을 올릴 것인가"다.

이 장은 다음을 정리한다.

- OBD-II, UDS, J1939, CANopen, NMEA 2000을 같은 기준으로 비교
- 각 프로토콜을 웹 개념에 대응
- 상황별 선택 흐름
- 다른 세계로 넘어갈 때 달라지는 도구·문서·안전 규칙

## 35.1 같은 버스, 다른 계약

CAN은 **물리·링크 계층**이다. 프레임을 주고받고, 중재하고, 오류를 검출하는 것까지가 CAN의 일이다. 그 위에 "이 ID는 무슨 뜻이고, 데이터의 첫 바이트는 무엇이며, 큰 메시지는 어떻게 나누는가"를 정의하는 것은 상위 프로토콜의 몫이다.

```text
응용:   OBD-II / UDS / J1939 / CANopen / NMEA 2000
전송:   ISO-TP / J1939 TP / SDO segment / fast packet
링크:   CAN (11비트 또는 29비트)
물리:   CAN_H/CAN_L, 120Ω 종단, 트랜시버
```

같은 CAN 버스에 OBD-II 요청과 J1939 프레임이 섞여 흐를 수는 있지만, 서로의 PGN/PID를 이해하지는 못한다. **계층이 같다고 계약이 같은 것은 아니다.**

이 장은 **CAN 위의 응용 계약**을 비교한다. CAN 자체의 세대(클래식 CAN·CAN FD·CAN XL)와 LIN·차량 이더넷은 36~38장에서 다룬다. "버스를 무엇으로 만들 것인가"는 36~38장의 비교표를, "그 위에 어떤 약속을 올릴 것인가"는 이 장의 표를 보면 된다.

## 35.2 한눈에 비교

| 항목 | OBD-II (ISO 15765-4) | UDS (ISO 14229) | J1939 | CANopen | NMEA 2000 |
|---|---|---|---|---|---|
| 주 용도 | 배출가스·차량 진단 | 제조사 진단·ECU 프로그래밍 | 트럭·버스·건설·농기계 | 산업 자동화·모션 | 선박 전자장비 |
| ID | 주로 11비트 | 11비트 또는 29비트 | 29비트 | 11비트 | 29비트 |
| 주소 | `7DF` 기능, `7E0`~`7E7` 물리 | CAN ID + 세션 | PGN + SA, PDU1이면 DA | Node ID 1~127, COB-ID | PGN + SA |
| 데이터 정의 | PID(SAE J1979) | DID/서비스(ISO 14229) | PGN/SPN(J1939-71) | 객체 사전(CiA 301) | PGN 표(NMEA 2000) |
| 큰 메시지 | ISO-TP | ISO-TP | TP.CM/TP.DT, 최대 1785B | SDO segmented | fast packet, 최대 223B |
| 진단 | Mode 01~0A, DTC | 0x19 DTC, 0x22 DID, 0x27/0x29 | DM1/DM2, SPN/FMI | EMCY, 오류 레지스터 | PGN 진단·제조사 정의 |
| 속도 | 250k/500k | 차량에 따름 | 250k/500k | 10k~1M | 250k |
| 문서 | PID 표 | 서비스·DID 표 | PGN/SPN 표, DBC | EDS, OD | PGN 표, canboat |
| 인증 | 배출가스 규제 | 제조사·규제 | SAE 적합성 | CiA 적합성 | NMEA 인증 |
| 이 책 | 9장 | 10장 | 33장 | 34장 | 34장 |

### 표를 읽는 법

- **ID 길이**는 "한 프레임에 주소를 얼마나 넣을 수 있는가"다. 11비트는 ID 공간이 좁아 노드 수와 메시지 종류가 제한된다. 29비트는 PGN·SA·DA를 넣을 수 있어 대규모 네트워크에 유리하다.
- **주소 방식**은 "누가 누구에게 말하는가"다. OBD-II는 진단 도구와 ECU의 역할이 고정되어 있고, J1939/NMEA 2000은 소스 주소가 동적이며, CANopen은 노드 ID가 COB-ID에 직접 들어간다.
- **큰 메시지**는 "8바이트를 넘을 때 어떻게 하는가"다. ISO-TP, J1939 TP, SDO segmented, fast packet은 이름도 규칙도 다르다.
- **진단**은 "고장을 어떻게 알리는가"다. OBD-II는 요청/응답, J1939는 DM1 broadcast, CANopen은 EMCY와 오류 레지스터다.
- **문서**는 "스키마가 어디에 있는가"다. PID 표, DID 표, PGN/SPN 표, EDS, PGN 표는 모두 코드 밖에 있다.

## 35.3 웹 프로토콜에 대응시키기

| 웹 | CAN 위의 대응 | 닮은 점 | 다른 점 |
|---|---|---|---|
| 공개 REST API | OBD-II | 정해진 엔드포인트(PID)와 공개 스키마 | 요청/응답이 느리고, 지원 PID가 차종마다 다르다 |
| 사내 RPC/gRPC | UDS | 서비스·세션·인증·에러 코드 | CAN ID로 라우팅하고, ISO-TP로 나눈다 |
| MQTT pub/sub | J1939 | 주기 발행, 소스 ID, 우선순위 | 브로커가 없고, 주소 클레임으로 발행자 주소를 정한다 |
| OpenAPI + REST + SSE | CANopen | 객체 사전(스키마), SDO(요청), PDO(이벤트) | 스키마가 장치 안 EDS에 있고, 인덱스로 접근한다 |
| 표준 토픽 사전 + 인증 | NMEA 2000 | 공유 PGN, 발행/구독, 인증 | 데이터링크는 J1939, 사전·물리·인증은 선박용 |
| 서비스 디스커버리 | Address Claim | 노드가 주소를 얻는다 | TTL이 아니라 NAME 비교로 승자를 정한다 |
| 헬스 체크 | 하트비트 | 주기적 생존 신호 | 상태 바이트에 NMT 상태가 들어 있다 |
| 에러 이벤트 | EMCY, DM1 | 오류를 능동적으로 알린다 | 읽기 전용 원칙, 삭제·쓰기 금지 |

이 대응은 **입구**일 뿐이다. "J1939는 MQTT 같다"고 말하면 PGN·SPN·주소 클레임·TP를 놓친다. 비유가 깨지는 지점을 아는 것이 이 책의 방식이다.

```text
1. 대상이 승용차의 배출가스·표준 진단인가?
   ├─ 예: OBD-II (ISO 15765-4) + 필요하면 UDS
   └─ 아니오 ↓

2. 제조사 고유 진단·ECU 프로그래밍인가?
   ├─ 예: UDS (ISO 14229) over ISO-TP
   └─ 아니오 ↓

3. 트럭·버스·건설기계·농기계인가?
   ├─ 예: J1939
   └─ 아니오 ↓

4. 산업 자동화·모션·I/O인가?
   ├─ 예: CANopen (또는 DeviceNet 등 다른 산업 프로토콜)
   └─ 아니오 ↓

5. 선박 전자장비인가?
   ├─ 예: NMEA 2000
   └─ 아니오 ↓

6. 직접 설계하는가?
   ├─ 예: 요구사항(주기, 크기, 주소, 진단, 인증)을 정하고
   │      기존 프로토콜을 확장하거나 최소 프로토콜을 설계
   └─ 아니오: 요구사항을 다시 정리한다
```

### 선택 기준

| 질문 | 영향 |
|---|---|
| 누가 데이터를 요청하는가? | 요청/응답이면 OBD/UDS/SDO, 발행이면 J1939/PDO/NMEA |
| 노드 수가 많은가? | 29비트(PGN/SA)가 유리 |
| 8바이트를 넘는가? | ISO-TP, J1939 TP, SDO segmented, fast packet |
| 고장을 어떻게 알리는가? | DTC, DM1, EMCY |
| 인증·규제가 필요한가? | NMEA 인증, SAE 적합성, 배출가스 규제 |
| 기존 장비와 호환해야 하는가? | 그 세계의 문서·도구를 따라야 한다 |

## 35.5 다른 세계로 넘어갈 때

### 도구

| 세계 | 설명 파일 | 분석 도구 |
|---|---|---|
| OBD-II/UDS | PID/DID 표 | ELM327, `python-can`, `cantools`, `candump` |
| J1939 | PGN/SPN 표, DBC | J1939 분석기, `python-can-j1939`, DBC |
| CANopen | EDS | CANopen 도구, `canopen` 패키지 |
| NMEA 2000 | PGN 표, canboat | NMEA 분석기, canboat |

- ELM327 칩 자체는 J1939를 지원하는 버전이 있지만, OBD-II 전용 클론·앱은 J1939 명령이 빠져 있을 수 있다. J1939에는 `AT SP A`(또는 USER 프로토콜), `AT MP`, `AT DM1` 같은 설정이 필요하다. 지원 여부는 어댑터 데이터시트와 `ATI`로 확인한다.
- J1939 DBC를 NMEA 2000에 그대로 쓰면 PGN 번호가 우연히 맞더라도 의미가 틀린다.
- CANopen EDS가 없으면 객체 사전을 알 수 없다. 추측하지 말고 제조사 문서를 요청한다.

### 안전

- **승용차**: 정차·읽기 전용. OBD-II Mode 01/03/09, UDS 0x22만. 삭제·쓰기·세션·액추에이터 금지.
- **상용차**: DM1/DM2 읽기. DM3(삭제) 금지. 주행 중 조작 금지.
- **산업 설비**: NMT 전환·SDO 쓰기·PDO 송신은 설비를 움직일 수 있다. 격리된 벤치에서만.
- **선박**: NMEA 2000은 조타·엔진·항해 장비와 연결될 수 있다. 실제 네트워크에서 임의 PGN 송신 금지.

### 문서

- 표준 원문은 유료인 경우가 많다. 공개 요약·공개 구현·제조사 문서를 함께 보고, **확인 필요**를 남긴다.
- PGN/SPN/PID/DID의 번호와 해상도는 개정판에 따라 바뀔 수 있다. 사용하는 장비의 문서 버전을 기록한다.
- DBC·EDS·PGN 표는 코드와 함께 버전 관리한다. 26장의 로그 파이프라인에도 같은 문서 버전을 남긴다.

## 35.7 체크리스트

- [ ] OBD-II, UDS, J1939, CANopen, NMEA 2000의 용도를 한 문장으로 말할 수 있다.
- [ ] 각 프로토콜의 ID 길이·주소 방식·큰 메시지 전송을 비교할 수 있다.
- [ ] 웹의 REST/RPC/pub-sub/SSE에 각각 대응시킬 수 있다.
- [ ] "이 프로젝트에는 무엇을 고를까"를 요구사항으로 설명할 수 있다.
- [ ] 다른 세계의 도구·문서·안전 규칙이 다르다는 점을 안다.

## 장 요약

- CAN은 물리·링크 계층이고, 그 위의 계약은 분야마다 다르다.
- OBD-II는 배출가스 진단, UDS는 제조사 진단, J1939는 상용차 응용, CANopen은 산업 객체 모델, NMEA 2000은 선박 PGN이다.
- 11비트/29비트, 요청/응답/발행, ISO-TP/TP/segmented/fast packet, DTC/DM1/EMCY가 핵심 비교 축이다.
- 웹 개념에 대응시키면 이해가 빠르지만, 대응이 깨지는 지점(주소 클레임, PGN 사전, NMT 상태)을 반드시 확인한다.
- 프로토콜 선택은 "무엇을 만드는가"보다 "누가 무엇을 언제 어떻게 주고받는가"로 결정한다.
- 실제 장비에서는 읽기 전용 원칙을 지키고, 송신 실습은 가상 버스·벤치에서만 한다.

## 연습 문제

### 1. (중급) 프로토콜 선택

다음 요구사항에 가장 잘 맞는 프로토콜을 고르라.

```text
a) 2019년식 승용차의 냉각수 온도를 읽고 싶다.
b) 공장 컨베이어의 서보 드라이브 여러 대를 위치·속도로 제어하고 싶다.
c) 30톤 트럭의 엔진 회전수와 활성 고장 코드를 읽고 싶다.
d) 요트의 풍향·풍속·선수 방향을 한 네트워크에서 읽고 싶다.
e) 정비소에서 ECU의 부품 번호와 소프트웨어 버전을 읽고 싶다.
```

### 2. (중급) 주소 방식

OBD-II, J1939, CANopen의 주소 방식을 각각 한 문장으로 설명하고, "노드 주소"와 "메시지 종류"가 어떻게 구분되는지 쓰라.

### 3. (심화) 큰 메시지

ISO-TP, J1939 TP, CANopen SDO segmented, NMEA 2000 fast packet을 "최대 크기·프레임당 데이터·흐름 제어" 기준으로 비교하라.

### 4. (심화) 웹 대응

REST, gRPC, MQTT, SSE에 가장 가까운 CAN 위의 프로토콜을 각각 고르고, 그 비유가 깨지는 지점을 하나씩 쓰라.

## 정답과 해설

### 1.

- a) **OBD-II**: 승용차의 표준 PID `05`(냉각수 온도)를 Mode 01로 읽는다. 차종에 따라 지원 여부를 확인한다.
- b) **CANopen**: CiA 402 모션 프로파일, SDO/PDO, NMT 상태 기계가 산업 모션에 맞다. 제조사 EDS를 확인한다.
- c) **J1939**: EEC1(PGN 61444)의 SPN 190, DM1(PGN 65226)의 SPN/FMI를 읽는다.
- d) **NMEA 2000**: PGN 127250(선수 방향), 130306(바람) 등을 쓴다. 250kbps·120Ω·NMEA 인증을 확인한다.
- e) **UDS**: `0x22`로 DID를 읽는다. 제조사 DID 표가 필요하고, 쓰기·세션 전환은 하지 않는다.

### 2.

- OBD-II: 기능 주소 `7DF`로 여러 ECU에 요청하고, 물리 주소 `7E0`~`7E7`로 특정 ECU에 요청한다. 응답은 `7E8`~`7EF`다.
- J1939: PGN이 메시지 종류, SA가 보낸 노드, PDU1이면 DA가 받는 노드다. 주소는 클레임으로 얻는다.
- CANopen: Node ID(1~127)가 COB-ID에 들어가고, 객체 index/subindex가 데이터 종류를 나타낸다.

OBD-II는 "진단 도구 ↔ ECU" 역할이 고정되어 있어 주소가 메시지 종류와 분리되어 있고, J1939는 PGN(종류)과 SA(노드)를 함께 싣는다. CANopen은 COB-ID에 기능(SDO/PDO/NMT)과 노드 ID를 함께 넣는다.

### 3.

| | 최대 크기 | 프레임당 데이터 | 흐름 제어 |
|---|---:|---:|---|
| ISO-TP | 표준 개정에 따름(고전 4095B) | CF 7B | FC(BS/STmin) |
| J1939 TP | 1785B | TP.DT 7B | RTS/CTS 또는 BAM |
| CANopen SDO segmented | 객체 크기에 따름 | 7B | 토글 비트 |
| NMEA 2000 fast packet | 223B | 첫 6B, 연속 7B | 없음(ACK 없음) |

### 4.

- **REST** → OBD-II 또는 CANopen SDO. 비유가 깨지는 지점: OBD-II는 지원 PID가 차종마다 다르고, SDO는 index/subindex라는 이진 경로를 쓴다.
- **gRPC** → UDS. 비유가 깨지는 지점: UDS는 HTTP/2가 아니라 ISO-TP 위에서 동작하고, 세션·보안 접근이 서비스별로 다르다.
- **MQTT** → J1939. 비유가 깨지는 지점: 브로커가 없고, 주소 클레임으로 발행자 주소를 정하며, PGN은 토픽 계층이 아니다.
- **SSE** → CANopen PDO. 비유가 깨지는 지점: PDO는 매핑을 미리 설정해야 하고, NMT 상태가 아니면 아무것도 오지 않는다.
