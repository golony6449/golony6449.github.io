# 36장 학습 경로와 실습

## 이 장에서

6년차 웹 개발자라면 네트워크·비동기·상태 기계·테스트·Git은 이미 강하다. 새로 메울 것은 **C, 전자 기초, 계측과 하드웨어 디버깅**이다. 이 장은 그 순서를 실습 중심으로 정리한다.

"무엇부터 공부해야 하나"라는 질문은 "무엇을 만들어 보고 싶은가"로 바꾸는 편이 낫다. 이 장의 단계는 각각 **완료 기준**을 가지고 있다. 완료 기준을 통과하지 못했는데 다음 단계로 넘어가면, 나중에 어디서 막혔는지 알기 어려워진다.

책 안에서 어느 장을 어떤 순서로 읽을지는 서문의 '이 책을 읽는 법'에 정리했다. 이 장은 그 경로를 **실습 단계와 완료 기준**으로 바꾸고, 마지막에 **책 밖의 다음 걸음**을 안내한다.

전체 흐름은 다음과 같다.

```text
C·전자 기초 → UART → 프레이밍 → 전기·GPIO → I2C/SPI → RS-485/Modbus → CAN 벤치 → OBD-II → UDS → IoT → ESP32 OBD 장치
              (2장)    (3장)      (4~5장)     (6장)        (12장)         (7장)      (9장)    (10장)  (12장)      (16장)

→ 펌웨어 심화 → 가상 CAN 실습 → TypeScript 클라이언트 → 대시보드 캡스톤 → 테스트 → 로그 파이프라인 → 통합
   (17~19장)        (23장)              (27장)                 (28장)          (25장)     (26장)        (36장)

→ 다른 CAN 세계 → 프로토콜 선택 → 차량 네트워크 세대
   (30~31장)          (32장)          (33~35장)
```

그림의 장 번호가 12장 → 7장 → 9장으로 오르내리는 것은, Modbus가 12장에, CAN이 7장에, OBD-II가 9장에 있기 때문이다. 학습 순서는 Modbus로 RS-485 감각을 잡고 CAN 벤치로 넘어간 뒤, OBD-II와 UDS로 차량 데이터를 읽는 것을 권한다. CAN을 먼저 보고 싶다면 7장을 먼저 읽어도 되지만, 12장의 Modbus 부분은 RS-485 실습과 이어지므로 함께 보는 편이 좋다.

17~19장은 13·16장을 바탕으로 **펌웨어 안쪽**을 파는 심화 트랙이다. 17장은 메모리·ISR·링 버퍼·워치독, 18장은 ESP-IDF FreeRTOS 태스크·큐·TWAI 경보·Bus-Off 복구, 19장은 Rust 소유권·`embedded-hal`·Embassy를 다룬다. 23~26장은 앞 단계를 대체하는 것이 아니라 **반복·검증 트랙**이다. 차가 없거나 장비가 부족하면 23장의 가상 버스로 7~9장을 다시 풀고, 브라우저 데모가 필요하면 24장, 테스트를 붙이려면 25장, 기록을 쌓으려면 26장을 본다. 24장(Web Serial)은 선택이다. CAN 자체를 익히는 데는 23·25·26장이 더 직접적이다. 27~28장은 파이썬으로 익힌 내용을 **TypeScript/Node.js로 다시 구현하는 트랙**이다. 웹 개발자라면 이 트랙에서 가장 빠르게 "내 스택으로 만든다"는 감각을 얻는다. 29장은 이 모든 내용을 **방어 관점**에서 다시 묶는다. 게이트웨이·SecOC·IDS·진단 인증을 이해하고, 23장의 가상 버스에서 HMAC 검증을 직접 돌려 본다. 30~31장은 **승용차 OBD 밖의 CAN 세계**다. J1939(트럭·중장비), CANopen(산업), NMEA 2000(선박)을 같은 29비트/11비트 CAN 위에서 비교하고, 32장에서 요구사항으로 프로토콜을 고르는 기준을 정리한다. 33~35장은 **고전 CAN 다음의 차량 네트워크**다. CAN FD(33장), LIN(34장), 차량 이더넷과 DoIP·SOME/IP(35장)를 다루고, 35.8절에서 세대별 비교표로 묶는다.

## 36.1 먼저 메울 것

### C

- 포인터, 배열, 구조체, `const`, `volatile`, 비트 연산, `stdint.h` 고정폭 타입.
- 컴파일·링크·메모리 배치(플래시/RAM/스택/힙), 헤더/소스 분리.
- C++를 쓰더라도 MCU에서는 STL·예외·RTTI를 쓰지 않는 경우가 많다. "C + 클래스" 정도로 생각한다.
- 웹의 GC·문자열 편의 기능이 없다는 전제로 코드를 읽는 연습이 필요하다.

C를 처음부터 완벽하게 배우고 시작하려 하면 오래 걸린다. 이 책의 예제를 읽고 고칠 수 있을 정도로 익힌 뒤, 실습에서 막히는 부분을 다시 찾는 방식이 효율적이다.

### 전자 기초

- 전압·전류·저항, 옴의 법칙, 직렬/병렬, 전력. 4장에서 계산과 멀티미터 사용까지 다룬다.
- 풀업/풀다운, 오픈 드레인, push-pull, 3.3V/5V 논리 레벨과 레벨 변환.
- 다이오드, LED 저항, 트랜지스터/MOSFET 스위치, 플라이백 다이오드.
- 디커플링, 접지, 브레드보드 배선, 데이터시트의 절대 최대 정격 읽기.
- GPIO 입력·출력, ADC 분해능·기준 전압·분압, PWM 주기·듀티. 5장에서 ESP-IDF API와 대조한다.
- 12V 계통의 실제 전압, load dump, 퓨즈·역전압·TVS 보호. 15장에서 차량 장치에 적용한다.
- 이 정도면 센서·릴레이·모터를 다루는 데 큰 무리가 없다. 회로 설계까지 가려면 더 필요하지만, 입문 단계에서는 dev board와 브레이크아웃으로 충분하다.

### 도구

- 멀티미터 사용법(전압/도통/전류), 로직 분석기, 시리얼 모니터, pyserial.
- USB 전원 전류계(선택)는 보드 전체 소비전류와 대기 전류를 볼 때 유용하다.
- Git, VS Code/PlatformIO, `uv`.
- 데이터시트를 읽는 습관.

## 36.2 단계별 실습

### 단계 0: 환경 만들기

- PlatformIO(VS Code) 또는 Arduino IDE + ESP32 보드 패키지를 설치한다.
- Python은 `uv`로 프로젝트를 만들고 `pyserial`을 추가한다.
- 시리얼 모니터와 `python -m serial.tools.list_ports -v`로 포트를 확인한다.

```bash
uv init embedded-lab
cd embedded-lab
uv add pyserial
```

**완료 기준**: 보드에 업로드하고, PC에서 보드의 출력을 읽고, PC에서 보드로 명령을 보낼 수 있다.

### 단계 1: UART 감각 잡기

- USB-UART 어댑터의 TX-RX를 점퍼로 연결해 루프백한다.
- 보드와 PC를 TX/RX/GND로 연결하고, 보드에서 `Hello`를 주기적으로 출력한다.
- 일부러 보율을 바꿔 깨진 문자를 관찰한다. 9600/115200을 오가 본다.
- 접지를 뺀 상태를 일부러 만들지는 말고, 접지가 없을 때의 증상(쓰레기 값, 간헐 오류)을 기록해 둔다.

**완료 기준**: 보율·8N1·TX/RX·공통 접지가 왜 필요한지 설명할 수 있다. → [2장](02-uart.md)

### 단계 2: 직접 프로토콜 설계하기

- `[SOF][LEN][PAYLOAD][CRC16]` 프레임을 정한다.
- 보드(C)와 PC(Python) 양쪽에 파서를 구현한다.
- 1바이트씩 쪼개 보내기, 두 프레임 붙이기, CRC 한 비트 뒤집기, 쓰레기 바이트 앞뒤에 붙이기를 시험한다.
- 타임아웃·재전송·시퀀스 번호를 넣고, 중복 명령이 두 번 실행되지 않게 만든다.

**완료 기준**: 부분 수신·재동기화·CRC 실패 복구가 테스트로 증명된다. → [3장](03-framing-parsing.md)

### 단계 2.5: 전기와 핀 기초

- 4장의 계산을 직접 해 본다. LED 직렬 저항, 12V 분압, 14.4V에서 ADC 입력이 넘지 않는지 확인한다.
- 멀티미터로 USB 5V, 보드 3.3V, GND 사이 전압을 잰다. 저항·도통 모드는 전원을 끄고 쓴다.
- 5장의 버튼·풀업·디바운스를 구현하고, 디바운스 전후 이벤트 수를 로그로 비교한다.
- ADC로 분압 전압을 읽고 멀티미터 값과 비교한다. ADC 값이 튀면 평균·중앙값을 적용한다.
- PWM으로 LED 밝기를 바꾸고, 주파수와 분해능을 바꿔 차이를 기록한다.

**완료 기준**: 옴의 법칙으로 저항을 계산하고, 분압 회로를 최대 입력에서 검증하며, 디바운스·ADC·PWM 코드를 설명할 수 있다. → [4장](04-electricity-basics.md), [5장](05-gpio-adc-pwm.md)

### 단계 3: I2C/SPI 센서

- I2C: BME280(온습도/기압)이나 MPU-6050(가속도/자이로)을 붙인다. 주소 스캔 → WHO_AM_I/칩 ID 읽기 → 설정 → 측정 순서로 진행한다.
- SPI: SSD1306 OLED, SD 카드, 또는 SPI 플래시를 붙인다. 로직 분석기로 CS/SCLK/MOSI/MISO를 확인한다.

**완료 기준**: 데이터시트의 초기화 시퀀스를 스스로 옮겨 센서 값을 읽는다. 라이브러리 없이 한 번 해 본다. → [6장](06-i2c-spi.md)

### 단계 4: RS-485와 Modbus

- USB-RS485 어댑터 2개를 A/B/GND로 연결하고, 한쪽에서 요청을 보내 다른 쪽에서 받는다. A/B 표기는 제조사에 따라 반대일 수 있으니 통신이 안 되면 A/B를 바꿔 본다.
- Modbus RTU로 03(홀딩 레지스터 읽기) 요청을 만들고 CRC를 직접 계산한다.
- 실제 센서/인버터가 있으면 슬레이브 주소·보율·레지스터 맵을 읽는다.

**완료 기준**: 요청/응답 프레임을 hex로 설명하고, 타임아웃·예외 응답을 처리한다. → [12장](12-iot-protocols.md)

### 단계 5: CAN

- 가장 안전한 시작은 **보드 2개 + CAN 트랜시버 2개 + 120Ω 2개**다. 또는 USB-CAN 어댑터 2개.
- 500kbps로 맞추고 한쪽에서 보내고 다른 쪽에서 받는다. `candump`/`python-can`으로 확인한다.
- 종단을 하나 빼고, 비트레이트를 바꾸고, 노드를 하나만 두었을 때 각각 어떤 오류가 나는지 관찰한다.
- 그다음 실제 차량/장비에 읽기 전용으로 붙는다. 차량에서는 정차 상태에서 OBD-II만 읽는다.
- 차나 벤치가 없으면 23장의 vcan·python-can virtual에서 같은 프레임을 먼저 주고받는다. 물리 계층은 실제 벤치에서 따로 연습한다.

**완료 기준**: CAN_H/CAN_L 파형, 종단 60Ω, ACK, bus-off를 설명할 수 있다. → [7장](07-can.md), [8장](08-car-network.md), [23장](23-can-without-car.md)

### 단계 6: OBD-II 읽기

- ELM327 USB 어댑터를 OBD-II 포트에 꽂고, `ATI` → `ATSP0` → `ATDPN` → `ATRV` → `0100` 순서로 확인한다.
- `010C`, `010D`, `0105`를 읽고 공식으로 값을 계산한다.
- 9장의 `ObdReader`와 Flask 대시보드를 `--demo`로 먼저 실행한 뒤, 실제 차량에서 `--port`를 지정해 실행한다.
- PID 지원 비트마스크를 해석하고, `NO DATA`·`7F ... 78`·`BUFFER FULL`을 구분한다.
- DTC는 읽기만 한다. 지우지 않는다.
- 차가 없으면 23장의 가짜 ECU와 ELM327-emulator로 `AT`·PID·ISO-TP 흐름을 먼저 시험한다.

**완료 기준**: 회전수·차속·냉각수·전압을 1Hz로 읽어 화면에 표시하고, `NO DATA`의 원인을 계층별로 설명할 수 있다. → [9장](09-obd2-in-practice.md), [23장](23-can-without-car.md)

### 단계 7: UDS 제조사 데이터

- `ATSH7E0`으로 엔진 ECU에 `22 F1 87`을 보내 부품번호를 읽는다. 응답의 `62 F1 87`과 ISO-TP 다중 프레임을 확인한다.
- `ATSH7C6`으로 계기판에 `22 B002`를 보내 주행거리를 읽고, 계기판 표시와 비교한다.
- `ATSH7E1`으로 변속기 `22 01A0`을 읽어 rpm·ATF 온도·기어를 해석한다.
- `7F 22 31`, `7F 22 78`, `7F 22 7F`를 구분한다.
- DPF DID는 읽기만 한다. `0x31` 강제 재생은 절대 보내지 않는다.

**완료 기준**: DID 응답에서 바이트 오프셋을 세어 값을 계산하고, `문헌 기반` 값과 `실차 확인` 값을 구분할 수 있다. → [10장](10-uds-manufacturer-diagnostics.md)

### 단계 8: IoT 연결

- ESP32를 Wi-Fi에 붙이고 로컬 Mosquitto 브로커로 MQTT publish/subscribe를 한다.
- 토픽 설계, QoS, retain, will, 재연결 백오프를 구현한다.
- TLS와 클라이언트 인증서로 바꾼다. 인증서 검증을 끄지 않는다.
- OTA, 프로비저닝, 워치독, 상태 토픽을 넣는다.

**완료 기준**: 네트워크를 뽑았다 다시 꽂아도 데이터 유실 없이 복구되고, 중복은 걸러 낸다. → [12장](12-iot-protocols.md)

### 단계 9: ESP32 OBD-II 장치

- 15장의 전원 사슬(퓨즈 → 역극성 → TVS → 넓은 입력 강압 → LDO)을 먼저 설계한다. 12V 배선은 브레드보드에 꽂지 않는다.
- 벤치 전원으로 9V·12V·14.4V를 넣어 리셋·발열·3.3V 출력을 확인한다. 24V 점프스타트·load dump는 재현하지 않는다.
- ESP32 + 3.3V CAN 트랜시버(SN65HVD230 등)를 OBD 6/14번에 연결한다. 16번 전원은 퓨즈·강압 모듈을 거친다.
- 벤치에서 USB-CAN과 120Ω 2개로 먼저 시험한다. 차량에는 120Ω을 추가하지 않는다.
- 수신만 되는지 확인한 뒤 `7DF`로 Mode 01 PID `0C`/`0D`/`05`를 요청한다.
- `7E8` 응답의 `41 <PID>`와 ISO-TP SF 길이를 확인해 rpm·차속·냉각수를 파싱한다.
- Wi-Fi 웹 서버로 최신 값을 JSON과 HTML로 제공한다. 자격 증명은 코드에 커밋하지 않는다.
- Bus-Off 복구, TEC/REC 로그, 응답 타임아웃을 넣는다.
- 25장의 방법으로 파서·PID 공식·가짜 ECU 통합 테스트를 붙인다.

**완료 기준**: 브라우저에서 세 값이 갱신되고, 배선을 하나 빼면 오류 카운터가 올라가며, 복구 후 다시 값이 온다. 차량에는 읽기 요청만 보낸다. → [15장](15-vehicle-power.md), [16장](16-esp32-obd-device.md), [25장](25-testing.md), [11장](11-safety-law-ethics.md)

### 단계 10: 펌웨어 심화

- 17장: PC에서 `gcc`로 SPSC 링 버퍼·줄 파서·고정 풀을 컴파일·실행한다. `size`/map 파일로 메모리 배치를 확인하고, 스택 하이워터마크를 측정한다.
- 18장: ESP-IDF 프로젝트에서 CAN 수신·OBD 요청·경보 태스크를 나눈다. 큐 길이와 우선순위를 표로 설계하고, 벤치에서 Bus-Off를 일부러 만들어 복구를 확인한다.
- 19장: Rust 소유권·파서·SPSC를 호스트에서 실행하고, `embedded-hal` mock 테스트와 Embassy 태스크 정의를 컴파일한다. 여유가 있으면 `esp-hal`로 LED 점멸부터 시험한다.
- ESP32 실물이 없으면 17장의 PC 예제와 18·19장의 설계·컴파일까지 먼저 한다. 실물 확인 항목을 따로 적어 둔다.
- 차량에서는 읽기만 한다. Bus-Off 시험은 벤치 버스에서만 한다.

**완료 기준**: 링 버퍼·파서 테스트가 PC에서 통과하고, 태스크·큐·우선순위 표와 Bus-Off 복구 순서를 설명할 수 있으며, Rust 예제가 호스트에서 컴파일·실행된다. → [17장](17-firmware-time-memory.md), [18장](18-freertos-can-tasks.md), [19장](19-embedded-rust.md)

### 단계 11: 통합 프로젝트

- RS-485 Modbus 센서 → ESP32 게이트웨이 → MQTT → 시계열 DB/대시보드.
- 또는 OBD-II → 파이썬 게이트웨이 → MQTT → 시계열 DB/대시보드.
- 또는 CAN 스니퍼 → SD 카드/서버 로깅 → 신호 디코딩.
- 요구사항: 재부팅 복구, OTA, 오프라인 버퍼링, 관측(하트비트/오류 카운터), 안전 상태, 개인정보 제거.
- 기록은 26장의 형식 비교·원시 로그·디코딩·저장 파이프라인을 따른다.
- 웹 스택으로 같은 구조를 만들려면 28장의 수집기→SQLite→SSE→브라우저 대시보드를 참고한다.

**완료 기준**: 전원을 뽑았다 꽂아도 스스로 복구되고, 24시간 로그에 구멍이 없으며, 공개 가능한 로그에 VIN·위치가 없다. → [26장](26-log-pipeline.md), [28장](28-capstone-dashboard.md)

## 36.3 펌웨어·차 없이·브라우저·테스트·데이터·TypeScript 심화

단계 0~11을 마친 뒤, 또는 중간에 막혔을 때 곁가지로 본다. 이 트랙들은 앞 단계를 대체하지 않고 **반복과 검증**을 담당한다.

### 36.3.1 펌웨어 심화 (17~19장)

- 17장: 메모리 영역·동적 할당·`volatile`·ISR·SPSC 링 버퍼·워치독. PC에서 C 예제를 컴파일·실행한다.
- 18장: ESP-IDF FreeRTOS 태스크·큐·우선순위. TWAI RX 큐·경보·Bus-Off 복구를 태스크 구조로 설계한다.
- 19장: Rust 소유권·`no_std`·`embedded-hal`·Embassy. 호스트 예제와 mock 테스트를 실행한다.
- 18·19장의 ESP32 코드는 실물에서 API·핀·스택을 확인한다. 확인하지 못한 항목은 `실물 확인 필요`로 남긴다.

**완료 기준**: 17장 C 예제가 `-Wall -Wextra -Werror`로 컴파일되고 테스트가 통과하며, 18장 태스크 표와 Bus-Off 복구 순서를 설명하고, 19장 Rust 예제가 호스트에서 실행된다. → [17장](17-firmware-time-memory.md), [18장](18-freertos-can-tasks.md), [19장](19-embedded-rust.md)

### 36.3.2 차 없이 반복하기 (23장)

- Linux에서는 `vcan`과 can-utils로 `candump`·`cansend`·`cangen`·`canplayer`를 익힌다.
- Windows에서는 python-can `virtual`(프로세스 안)과 `udp_multicast`(프로세스 사이)를 구분한다.
- 가짜 ECU를 띄우고 9장의 PID 요청·ISO-TP 조립을 차 없이 돌린다.
- ELM327-emulator로 AT 명령·프롬프트·다중 프레임을 시험한다.
- 실차 로그를 vcan에서 재생해 같은 상황을 반복한다.

**완료 기준**: 가짜 ECU에 `010C`·`010D`·`0902`를 보내 값을 파싱하고, ELM327-emulator에 `ATI`·`ATDPN`·`010C`를 보내 9장 코드를 실행한다. 실제 차량에는 아무것도 보내지 않는다. → [23장](23-can-without-car.md)

### 36.3.3 브라우저에서 시리얼 (24장, 선택)

- Web Serial의 보안 컨텍스트·사용자 제스처·브라우저 지원을 확인한다.
- 청크 경계와 `>` 프롬프트를 처리하는 줄 파서를 만든다.
- 브라우저에서 PID 3개를 읽어 카드로 표시한다.
- BLE 어댑터는 Web Bluetooth, 클래식 SPP는 OS 직렬 포트를 통한 Web Serial로 접근한다.

**완료 기준**: HTTPS/localhost에서 버튼을 눌러 ELM327에 연결하고, PID 0C/0D/05를 1초 주기로 표시한다. 지원하지 않는 브라우저에서는 안내가 나온다. → [24장](24-web-serial.md)

### 36.3.4 테스트 전략 (25장)

- PID 공식·프레임 파서·ISO-TP 조립기의 단위 테스트를 만든다.
- candump 로그를 재생하는 회귀 테스트를 만든다.
- 가짜 ECU를 버스 경계에서 통합 테스트한다.
- HIL의 개념과 이 책 규모의 축소판을 이해한다.
- CI에는 하드웨어 의존 테스트를 넣지 않는다.

**완료 기준**: `pytest -q`가 단위·재생·가짜 ECU 통합 테스트를 모두 통과하고, 실패 시 원시 프레임이 남는다. → [25장](25-testing.md)

### 36.3.5 기록과 데이터 파이프라인 (26장)

- candump·ASC·BLF·MF4의 차이를 알고 용도에 맞게 고른다.
- 원시 프레임을 저장하고 DBC로 디코딩한다.
- SQLite 또는 시계열 DB에 저장하고 SQL/질의로 조회한다.
- 드롭·타임스탬프·중복·보존·개인정보를 설계한다.

**완료 기준**: 로그를 캡처→디코딩→저장→질의하는 한 줄 파이프라인을 만들고, VIN·GPS를 제거한 뒤 공개 가능한 샘플을 만든다. → [26장](26-log-pipeline.md)

### 36.3.6 TypeScript 클라이언트와 대시보드 (27~28장)

- 27장: `serialport`로 ELM327을 열고, CR·에코·`>` 프롬프트를 처리하는 클라이언트를 만든다.
- `NO DATA`, `SEARCHING...`, `7F xx 78`을 구분하고, 다중 PID 응답을 PID 번호로 파싱한다.
- `ATST`·`ATAT`의 의미를 이해하고, 다중 PID와 응답 수 digit으로 처리량을 조정한다.
- Linux에서는 `socketcan`으로 vcan을 읽고, 송신은 vcan/벤치에서만 한다.
- 28장: 수집기 → SQLite → SSE → 브라우저 게이지·차트를 한 프로젝트로 묶는다.
- ELM327-emulator TCP로 차 없이 끝까지 돌리고, 재연결·백오프·정상 종료를 넣는다.
- 대시보드는 `127.0.0.1`에 바인딩하고, VIN·위치를 저장하지 않는다.

**완료 기준**: ELM327-emulator에 붙어 6개 PID를 1Hz로 읽고, SQLite에 저장하며, 브라우저에서 게이지·차트가 갱신되고, 어댑터 연결을 끊었다 다시 붙여도 백오프 후 수집이 재개된다. 실제 차량에서는 정차 상태에서 읽기만 한다. → [27장](27-typescript-elm327.md), [28장](28-capstone-dashboard.md)

### 36.3.7 차량 보안 (29장)

- CAN 프레임에 송신자 인증이 없는 이유와 CRC·MAC의 차이를 설명한다.
- 위협 모델을 OBD 포트·텔레매틱스·IVI·OTA·공급망으로 나눠 표로 정리한다.
- 게이트웨이 allowlist, 도메인 분리, SecOC의 MAC·신선도, IDS의 주기·클록 지문, UDS 0x27·0x29를 개념으로 익힌다.
- 23장의 python-can virtual에서 29.9절의 HMAC 카운터 예제를 돌려 재전송·변조·위조가 거부되는 것을 확인한다.
- UN R155·R156, ISO/SAE 21434의 적용 범위와 날짜를 요약하고, 국내·개별 차량 적용은 `확인 필요`로 남긴다.
- 실제 차량에서는 보안 접근·키 관련 조작·임의 프레임 송신을 하지 않는다. 송신 실습은 가상 버스에서만 한다.

**완료 기준**: 정상·재전송·변조·위조 프레임의 처리 결과를 표로 만들고, "SecOC는 기밀성을 제공하지 않는다"는 점과 "IDS는 차단이 아니다"라는 점을 설명할 수 있다. 규제 날짜와 예시 차량의 해당 여부를 혼동하지 않는다. → [29장](29-can-security.md), [23장](23-can-without-car.md), [11장](11-safety-law-ethics.md)

### 36.3.8 다른 CAN 세계와 프로토콜 선택 (30~32장)

- 30장: 29비트 ID를 priority/PGN/SA로 나누고, PDU1/PDU2에 따라 PGN을 계산한다. EEC1의 SPN 190, DM1의 SPN/FMI를 직접 디코딩한다. TP.CM/TP.DT로 8바이트를 넘는 메시지를 재조립한다.
- 30장 실습: python-can virtual에서 29비트 프레임을 만들고, 가상 버스에서 EEC1·DM1·BAM을 주고받는다. 실제 차량에서는 DM1/DM2 읽기만 한다.
- 31장: CANopen의 객체 사전·NMT·SDO·PDO·하트비트를 익힌다. `canopen` 패키지의 LocalNode/RemoteNode로 가상 버스에서 SDO를 읽고 NMT 상태를 바꾼다.
- 31장 NMEA 2000: PGN 127250(Vessel Heading)과 fast packet을 디코딩한다. NMEA PGN 표와 J1939 PGN 표를 혼동하지 않는다.
- 32장: OBD-II/UDS/J1939/CANopen/NMEA 2000을 용도·ID·주소·큰 메시지·진단으로 비교하고, 요구사항에서 프로토콜을 고르는 흐름을 연습한다.
- 실제 차량·선박·산업 설비에서는 NMT 전환·SDO 쓰기·PDO 송신·DM3를 하지 않는다. 송신 실습은 가상 버스나 격리된 벤치에서만 한다.

**완료 기준**: `0x18FEF100`을 priority/PGN/SA로 해석하고, EEC1의 rpm과 DM1의 SPN/FMI/OC를 계산하며, CANopen SDO `0x1000`을 읽고, NMEA 2000 PGN 127250의 heading을 도로 바꾸며, "이 프로젝트에는 왜 이 프로토콜인가"를 세 문장으로 설명할 수 있다. → [30장](30-j1939.md), [31장](31-canopen-nmea2000.md), [32장](32-protocol-choice.md)

### 36.3.9 차량 네트워크의 다음 세대 (33~35장)

- 33장: CAN FD의 FDF·BRS·ESI·DLC, 클래식 CAN과 섞을 때의 문제, ISO/non-ISO 차이를 익힌다. python-can virtual에서 64바이트 FD 프레임을 `is_fd=True`, `bitrate_switch=True`로 주고받고, ISO-TP SF escape(`00 <SF_DL>`)를 직접 만든다.
- 34장: LIN의 단일 선·master/slave·스케줄 테이블을 익힌다. 파이썬으로 PID 패리티와 클래식/확장 체크섬을 계산하고, `0x3D → 0x7D`, `4A 55 93 E5 → 0xE6`을 확인한다.
- 35장: 100BASE-T1/1000BASE-T1/10BASE-T1S와 도메인·존 아키텍처를 익힌다. DoIP 8바이트 헤더를 만들고 127.0.0.1 루프백에서 차량 탐색→라우팅 활성화→진단 메시지를 주고받는다. SOME/IP 16바이트 헤더와 Length 기준(Client ID부터)을 확인한다.
- 35.8절의 비교표로 "LIN·CAN FD·이더넷 중 무엇을 어디에 쓰는가"를 설명한다. 8장의 지도, 32장의 응용 프로토콜 표와 함께 본다.
- 실제 차량에서는 FD/LIN/DoIP/SOME/IP 프레임을 보내지 않는다. FD는 가상 버스, LIN은 PC 계산, DoIP는 로컬 루프백에서만 시험한다.

**완료 기준**: FD 64바이트 프레임을 보내고 받은 뒤 `dlc`와 와이어 DLC 코드의 차이를 설명하고, LIN PID·체크섬 계산이 표와 일치하며, DoIP 헤더를 해석해 라우팅 활성화 코드 `0x10`을 확인하고, 카메라·창문 모터·OBD 진단에 각각 어떤 네트워크를 고를지 근거와 함께 말할 수 있다. → [33장](33-can-fd.md), [34장](34-lin.md), [35장](35-automotive-ethernet.md)

- 우선순위: **멀티미터 → 저항 키트 → USB-UART 2개 → ESP32 2개 → 로직 분석기 → RS-485 2개 → CAN 트랜시버/종단 → ELM327**. 오실로스코프는 나중이다.
- 차량 작업을 할 계획이면 USB 절연기와 퓨즈 달린 전원 케이블을 먼저 산다. OBD 연장 케이블은 포트 접근이 어려울 때 유용하다. 12V 배선에는 단자대·절연 튜브를 쓴다.
- CAN은 트랜시버 모듈 2개로 시작하고, PC 분석이 필요해지면 USB-CAN 어댑터를 추가한다.
- OBD-II만 읽을 거라면 ELM327 하나로 시작할 수 있다. 원시 CAN 로깅까지 하려면 USB-CAN이 필요하다.

장비를 한 번에 다 사지 않는 이유는 **무엇이 필요한지 몸으로 알기 전에 사면 안 쓰는 장비가 늘어나기 때문**이다. 멀티미터와 USB-UART 두 개, 저항 몇 개만으로도 2~5장의 실습 대부분을 할 수 있다.

## 36.5 프로젝트 아이디어

1. 시리얼 온도 로거: 보드 → PC, CSV 저장, 파서 리플레이.
2. 프레이밍 라이브러리: CRC·재동기화·재전송을 테스트와 함께.
3. I2C 센서 대시보드: 센서 → UART → Python GUI/터미널.
4. Modbus RTU 리더: 레지스터 맵, 32비트 워드 순서, 예외 응답.
5. CAN 스니퍼: 두 보드 사이 트래픽, ID별 주기·변화량 관찰.
6. MQTT 센서 노드: 로컬 브로커 → TLS → 재연결/오프라인 버퍼.
7. OTA 업데이터: A/B 파티션, 서명 검증, 롤백.
8. 차량 OBD-II 대시보드: 9장의 Flask 앱을 확장해 PID 카드·경고·CSV 저장을 붙인다.
9. DPF 모니터: 10장의 `ED03`/`ED94` DID를 1분 주기로 읽어 차압·온도·재생 카운터 추세를 기록한다. 강제 재생은 하지 않는다.
10. UDS DID 탐색기: 알려진 `F1xx` 식별 DID만 읽고, ECU별 부품번호·버전을 표로 만든다. VIN은 제외한다.
11. 차량·장비 CAN 읽기 전용 로거: 정차 상태에서 트래픽을 기록하고 원본을 보존한다.
12. ESP32 OBD-II 웹 게이지: 16장의 장치에 Bus-Off 복구·CSV 저장·여러 PID 카드를 붙인다. 쓰기·삭제 기능은 넣지 않는다.
13. TypeScript OBD 대시보드: 27~28장의 클라이언트·수집기·SSE·SQLite를 확장해 PID 지원 목록, 경고 임계값, CSV 내보내기를 붙인다. 실제 차량에서는 읽기만 한다.
14. SocketCAN 로거: Linux에서 `socketcan`으로 vcan/벤치 트래픽을 받아 26장의 저장 형식으로 남긴다. 실제 차량 버스에는 송신하지 않는다.
15. FreeRTOS CAN 게이트웨이: 18장 구조로 수신·요청·경보 태스크를 나누고, 큐 드롭·Bus-Off 복구·스택 하이워터마크를 로그로 남긴다. Bus-Off 시험은 벤치에서만 한다.
16. Rust OBD 파서: 19장의 파서·SPSC를 crate로 만들고 `cargo test`를 붙인다. 가능하면 `#![no_std]`로 전환하고 고정 배열로 바꾼다.
17. 저전력 OBD 로거: 16.9절의 sleep 시퀀스와 대기 전류 측정을 구현하고, CAN wake를 벤치에서 시험한다. 실차에서는 정차·읽기 전용으로만 확인한다.
18. 가상 CAN 보안 실험실: 29.9절의 SecOC 흉내 내기에 allowlist·주기 IDS·키 교체를 붙이고, 정상·재전송·변조·위조 프레임을 pytest로 검증한다. 실제 차량에는 송신하지 않는다.
19. 분압 전압계: 4·5장의 분압과 ADC로 5V·12V를 읽고, 멀티미터 값과 비교한다. 최대 입력에서 ADC 범위를 넘지 않는지 먼저 계산한다.
20. PWM LED 디머: 5장의 LEDC로 듀티를 바꾸고, 주파수·분해능·평균 전압을 표로 기록한다. 버튼 입력과 디바운스도 붙인다.
21. 차량 전원 로거: 15장의 전원 사슬을 벤치에서 9V·12V·14.4V로 시험하고, 전압·리셋 원인·대기 전류를 기록한다. 실차에서는 정차·읽기만 한다.

프로젝트를 고를 때는 "데모가 되는 것"보다 **실패를 복구하는 것**을 기준으로 잡는 편이 좋다. 네트워크를 뽑았다 꽂기, 전원 차단, 중복 메시지, 장시간 로그가 진짜 실력을 만든다.

## 36.6 데이터시트 읽는 법

데이터시트는 "라이브러리 문서"가 아니라 계약서다. 순서를 정해 읽는다.

1. **Absolute Maximum Ratings**: 넘으면 파괴된다. 설계 기준이 아니다.
2. **Recommended Operating Conditions**: 실제 사용 범위(전압, 온도, 클록).
3. **Pinout / Alternate Functions**: 핀의 기본 기능과 대체 기능, 5V tolerant 여부.
4. **Electrical Characteristics**: VIH/VIL, 출력 전류, 풀업 저항, 소비 전류.
5. **Timing Diagrams**: setup/hold, 변환 시간, 부팅 시간, 버스 타이밍.
6. **Register Map / Initialization Sequence**: 리셋값, 순서, 대기 시간.
7. **Application Circuit**: 데이터시트가 권하는 외부 부품.
8. **Errata**: 알려진 버그와 우회법. 최신 버전을 본다.

- 부품 번호가 정확히 같은 문서를 본다. 패키지·온도 등급·리비전에 따라 다르다.
- "확인 필요"라고 적어 둔 값은 실제 측정이나 데이터시트로 확정한다.
- 라이브러리가 있다고 데이터시트를 안 읽으면, 초기화 순서나 전압 조건을 놓쳐 "가끔 안 되는" 문제를 만든다.

### 데이터시트를 읽는 순서 예

```text
1. Absolute Maximum / Recommended Operating Conditions
2. Pinout / Alternate Functions
3. Electrical Characteristics (VIH/VIL, 전류)
4. Timing Diagrams
5. Register Map / Initialization Sequence
6. Application Circuit
7. Errata
```

이 순서는 "이 부품을 써도 되는가" → "어떻게 연결하는가" → "어떻게 설정하는가" → "무엇이 알려진 문제인가"로 자연스럽게 이어진다.

## 36.7 안전 규칙

- 차량: **정차 상태의 읽기 전용**. 고장 코드 삭제·액추에이터 구동·플래싱·세션 전환은 하지 않는다. 주행 중에는 노트북을 조작하지 않는다.
- 차량 OBD: ELM327을 꽂은 채 오래 두지 않는다. 배터리 방전·USB 끊김·접지 루프를 확인한다.
- 차량 데이터: VIN·위치·주행 기록을 공개 로그에 남기지 않는다.
- 차량 전원은 퓨즈를 넣고, 시동/크랭킹 중 전압 변동과 load dump를 고려한다. 12V를 개발 보드에 직접 넣지 않고, 입력 범위가 넓은 강압 모듈과 TVS를 쓴다. USB 절연기를 쓴다.
- 모터·릴레이·솔레노이드는 첫 시험에서 부하를 분리한다. 회전체에 손이 닿지 않게 한다.
- 리튬 배터리는 과충전·과방전·단락을 피하고, 보호 회로가 있는 모듈을 쓴다.
- 상용 전원(110/220V)은 직접 다루지 않는다. 필요하면 자격·절연·정격 장비를 갖춘다.
- ESD와 열: 보드 만지기 전 접지, 발열 확인, 전원 차단 후 재배선.

## 36.9 책 밖의 다음 걸음

이 책은 입문서다. 여기까지 왔다면 다음은 "더 깊이"와 "실제 현장"이다. 무엇을 더 볼지는 목표에 따라 다르다.

- **C와 전자 기초를 체계적으로**: 포인터·비트 연산·메모리 배치·링커 스크립트를 언어 차원에서 정리한다. 회로는 옴의 법칙·풀업/풀다운·MOSFET 스위치·디커플링까지 익힌 뒤 센서·릴레이 키트로 확장한다(36.1절).
- **표준 원문**: OBD-II는 SAE J1979, CAN 전송은 ISO 15765-2, 진단은 ISO 14229(UDS), 상용차는 SAE J1939, 산업은 CiA 301, 선박은 NMEA 2000 사양을 직접 읽는다. CAN FD·CAN XL은 ISO 11898-1, LIN은 ISO 17987, DoIP는 ISO 13400-2, SOME/IP는 AUTOSAR PRS를 본다. 부록 C에 링크를 모았다.
- **다른 MCU와 RTOS**: STM32·ESP-IDF·다른 RTOS로 같은 CAN 수신·OBD 파서를 옮겨 본다. HAL·클록·전원 구조가 달라도 프레이밍·큐·우선순위 설계는 재사용된다.
- **현장 절차와 자격**: 실제 차량·산업 설비·선박의 정비·인증·안전 절차는 해당 표준과 제조사 문서, 자격을 갖춘 현장 인력의 검토가 필요하다. 이 책의 가상 버스 실습으로 대체할 수 없다.
- **보안·규제**: ISO/SAE 21434, UN R155/R156, SecOC·IDS의 실제 적용은 29장의 개념을 넘어 조직의 CSMS·SUMS와 키 관리가 필요하다.
- **오픈소스 참여**: python-can, can-utils, cantools, Linux SocketCAN 문서에 이슈·문서로 기여하면 실제 코드베이스에서 배운다. 공개 로그를 다룰 때는 VIN·위치를 제거한다.

각 항목은 36.3절의 심화 트랙과 이어진다. 책 안의 읽기 순서는 서문의 '이 책을 읽는 법'으로 돌아가 확인한다.

## 흔한 실수: 지름길의 함정

- **STM32 레지스터 프로그래밍부터 시작**: HAL/Arduino로 감을 잡은 뒤 내려가는 편이 빠르다.
- **오실로스코프부터 구매**: 초반에는 멀티미터와 로직 분석기가 더 자주 쓰인다.
- **커스텀 PCB부터 제작**: dev board와 브레이크아웃으로 검증한 뒤 PCB로 간다.
- **라이브러리 복사 후 핀/전압 무시**: 3.3V/5V, 핀 기능, 주소를 먼저 확인한다.
- **차량에서 바로 시험**: 벤치에서 두 노드로 검증한 뒤 차량에 붙인다.
- **`delay()`와 `String`으로 시작해 그대로 배포**: 상태 기계와 고정 버퍼로 바꾼다.
- **"동작한다"만 확인**: 전원 차단, 재부팅, 노이즈, 오프라인, 장시간 시험을 빼먹는다.
- **로그를 파싱 후 값으로만 저장**: 원시 바이트가 없으면 나중에 원인을 못 찾는다.

| 지름길 | 왜 위험한가 | 대신 할 일 |
|---|---|---|
| 레지스터부터 | 초기 설정에서 막혀 진도가 느려짐 | HAL/Arduino로 동작을 확인한 뒤 내려간다 |
| 비싼 장비부터 | 안 쓰는 장비가 늘어남 | 멀티미터·USB-UART·로직 분석기부터 |
| PCB부터 | 배선 오류를 PCB에 굽는다 | 브레드보드/브레이크아웃으로 검증 |
| 라이브러리 맹신 | 전압·핀·초기화 순서를 놓침 | 데이터시트와 대조 |
| 차량 직행 | 위험하고 재현이 어렵다 | 벤치에서 두 노드로 시험한 뒤 OBD 읽기 |
| `delay()`/`String` | 실시간성·메모리 문제 | 상태 기계·고정 버퍼 |
| "동작한다"로 끝 | 현장에서 재현되는 문제를 놓침 | 전원·재부팅·오프라인·장시간 시험 |
| 파싱 값만 로깅 | 파서 버그를 추적할 수 없음 | 원시 hex + 리플레이 |

## 장 요약

- 웹 개발자의 강점(네트워크·비동기·상태 기계·테스트·Git)은 그대로 쓸 수 있다. 새로 메울 것은 C·전자 기초·계측이다.
- C는 포인터·비트 연산·`volatile`·고정폭 타입·메모리 배치 중심으로 익힌다.
- 전자 기초는 전압·전류·저항, 풀업/풀다운, 다이오드·MOSFET, 접지·디커플링, ADC·PWM, 차량 12V 보호까지가 입문에 충분하다. 4·5·15장이 이 범위를 다룬다.
- 단계 0~11을 완료 기준과 함께 진행한다. 각 단계는 앞 장의 내용과 연결된다.
- 단계 11 이후에는 36.3절의 심화 트랙(17~19장, 23~28장)으로 반복·검증한다.
- 16장의 ESP32 OBD-II 장치는 4·5·7·9·11·14·15장을 한데 묶는 실습이다. 벤치 → listen-only → 차량 요청 순서로 올라간다.
- 16.9절은 OBD 16번 상시 전원의 대기 전류, ESP32 sleep 모드, SN65HVD230 standby, CAN wake의 한계를 다룬다. 사용 후 분리가 가장 확실하다.
- 17장은 스택·힙·정적 메모리, 동적 할당 회피, `volatile`의 한계, ISR, SPSC 링 버퍼, 워치독을 다룬다. C 예제는 PC에서 컴파일·실행해 확인했다.
- 18장은 ESP-IDF FreeRTOS 태스크·큐·우선순위로 CAN 수신·OBD 요청·경보 복구를 나누는 구조를 다룬다. ESP32 코드는 실물 확인이 필요하다.
- 19장은 Rust 소유권·`no_std`·`embedded-hal`·Embassy와 ESP32 Rust 현황을 맛본다. 호스트 예제는 컴파일·실행했고, ESP32 타깃 빌드는 하지 않았다.
- 23장은 차 없이 vcan·가짜 ECU·ELM327-emulator·로그 재생으로 반복하는 방법을, 25장은 단위·재생·통합·HIL 테스트를 다룬다.
- 24장 Web Serial은 설치 없는 현장 확인·데모에 유용하고, 26장은 원시 로그·DBC 디코딩·시계열 저장 파이프라인을 다룬다.
- 27장은 같은 ELM327 대화를 TypeScript/Node.js로 옮기고, 28장은 수집기·SQLite·SSE·브라우저 게이지를 한 프로젝트로 묶는다.
- 27~28장은 ELM327-emulator TCP로 차 없이 끝까지 검증할 수 있다. 실제 차량에서는 정차·읽기 전용을 지킨다.
- 29장은 CAN의 구조적 한계, 위협 모델, 게이트웨이·SecOC·IDS·UDS 인증, UN R155·R156·ISO 21434를 방어 관점에서 묶는다. SecOC 실습은 가상 버스에서만 한다.
- 30장은 J1939의 29비트 ID·PGN/SPN·주소 클레임·TP·DM1을, 31장은 CANopen의 OD/NMT/SDO/PDO와 NMEA 2000의 PGN/fast packet을 다룬다. 32장은 다섯 프로토콜을 요구사항으로 비교한다.
- 33장은 CAN FD의 64바이트 프레임, BRS·ESI·DLC, ISO/non-ISO, ISO-TP FD escape를 다룬다. 가상 버스 예제는 실행해 확인했다.
- 34장은 LIN의 단일 선·master/slave·PID 패리티·클래식/확장 체크섬·스케줄 테이블을 다룬다. PID·체크섬 계산은 PC에서 실행해 확인했다.
- 35장은 100BASE-T1/1000BASE-T1/10BASE-T1S, 도메인·존 아키텍처, DoIP·SOME/IP를 다룬다. DoIP 루프백과 SOME/IP 헤더 예제는 실행해 확인했다.
- 35.8절은 클래식 CAN·CAN FD·CAN XL·LIN·FlexRay·차량 이더넷을 속도·토폴로지·결정성·비용으로 비교한다. 8장의 지도, 32장의 응용 프로토콜 표와 함께 본다.
- J1939·CANopen·NMEA 2000·CAN FD·DoIP·SOME/IP 실습은 python-can virtual과 로컬 루프백으로 차·선박·설비 없이 반복한다. 실제 장비에는 읽기 요청만 보낸다.
- 차량 CAN에는 120Ω을 추가하지 않는다. 12V 전원은 퓨즈·역극성·TVS·강압을 거치고(15장), 웹 서버는 로컬 네트워크에만 둔다.
- 첫 장비는 멀티미터·USB-UART·ESP32·로직 분석기·RS-485·CAN 트랜시버·ELM327 순으로 산다.
- OBD-II는 ELM327 하나로 시작하고, 원시 CAN 로깅이 필요해지면 USB-CAN을 추가한다.
- 프로젝트는 데모보다 복구(전원 차단, 재연결, 중복, 장시간)를 기준으로 고른다.
- 차량 프로젝트는 읽기 전용·정차·개인정보 제거를 완료 기준에 넣는다.
- 데이터시트는 Absolute Maximum → Recommended Operating Conditions → Pinout → Electrical → Timing → Register Map → Application Circuit → Errata 순으로 읽는다.
- 안전 규칙(퓨즈·절연·부하 분리·ESD)을 처음부터 지킨다.
- 지름길은 대개 나중에 더 큰 비용으로 돌아온다.

여기까지 읽었다면 이제 부록에서 용어를 정리하고, 웹 개념과 임베디드 개념을 한 표로 다시 볼 수 있다. 실습을 시작할 때 이 책의 해당 장을 옆에 두고, 막히면 14장의 디버깅 순서로 돌아오면 된다. 펌웨어는 17~19장, 차가 없으면 23장, 브라우저 데모는 24장, 자동 테스트는 25장, 기록은 26장, 내 웹 스택으로 만드는 실전 프로젝트는 27~28장, 방어 설계는 29장, 다른 CAN 세계와 다음 세대 네트워크는 30~35장을 다시 펼친다.

## 연습 문제

### 1. (기초) 학습 순서

다음 단계를 권장 순서대로 나열하라.

```text
CAN, UART, ESP32 OBD 장치, OBD-II, 프레이밍, UDS, I2C/SPI, 통합, RS-485/Modbus, IoT
```

### 2. (중급) 첫 장비

예산이 제한되어 있다. 다음 중 먼저 살 것 세 가지와 나중에 살 것을 고르고 이유를 쓰라.

```text
멀티미터, 오실로스코프, USB-UART 2개, ESP32 2개, 로직 분석기, ELM327
```

### 3. (중급) 완료 기준

프로젝트를 "데모가 된다"가 아니라 "복구된다"로 평가하려 한다. 확인할 항목을 네 가지 쓰라.

### 4. (기초) 데이터시트

데이터시트를 읽는 권장 순서를 쓰라.

### 5. (중급) 차량 시험 계획

16장 장치를 실제 차량에서 처음 시험하려 한다. 안전 체크리스트를 다섯 줄로 쓰라.

## 정답과 해설

### 1.

`UART → 프레이밍 → I2C/SPI → RS-485/Modbus → CAN → OBD-II → UDS → IoT → ESP32 OBD 장치 → 통합`. 앞 단계에서 바이트·경계·버스·프레이밍을 익혀야 뒤 단계가 이해된다. CAN을 먼저 보고 싶다면 7장을 먼저 읽어도 되지만, 3장의 파싱은 한 번 거치는 것이 좋다.

### 2.

먼저: 멀티미터, USB-UART 2개, ESP32 2개(또는 예산에 따라 로직 분석기). 전원·도통·시리얼을 확인하는 도구가 가장 자주 쓰인다. 나중: 오실로스코프. 로직 분석기는 I2C/SPI/CAN을 본격적으로 볼 때, ELM327은 OBD-II를 편하게 읽을 때 추가한다.

### 3.

예: ① 전원을 뽑았다 꽂아도 스스로 복구되는가 ② 네트워크가 끊겼다 돌아와도 데이터가 이어지는가 ③ 24시간 로그에 구멍이 없는가 ④ 공개 로그에 VIN·위치가 없는가. 여기에 "읽기 전용을 유지하는가"를 더한다.

### 4.

Absolute Maximum Ratings → Recommended Operating Conditions → Pinout/Alternate Functions → Electrical Characteristics → Timing Diagrams → Register Map/Initialization → Application Circuit → Errata. "써도 되는가 → 어떻게 연결하는가 → 어떻게 설정하는가 → 알려진 문제" 순서다.

### 5.

예: ① 안전한 곳에 정차하고 P, 주차 브레이크를 건다. ② OBD 커넥터를 뽑은 상태에서 6/14/16/4/5번 배선과 퓨즈·극성을 확인한다. ③ 차량 전원을 끄고 6/14번 저항이 약 60Ω인지 확인한다(120Ω 추가 금지). ④ 첫 연결은 USB 전원·listen-only로 하고, 프레임이 보이는지 확인한다. ⑤ 정상 모드로 Mode 01 읽기만 보내고, 값이 계기판과 맞는지 확인한 뒤 분리한다. 주행 중 조작·DTC 삭제·쓰기·액추에이터 구동은 하지 않는다.
