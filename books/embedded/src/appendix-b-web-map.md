# 부록 B. 웹 개념 대응표

웹에서 익힌 개념을 임베디드에 그대로 적용하면 어긋나는 지점이 있다. 이 부록은 그 대응을 한 표로 모았다. 각 장을 읽다가 "웹에서는 이렇게 했는데"라는 생각이 들 때 돌아오면 된다.

## B.1 요청과 데이터

| 웹 개념 | 임베디드 대응 | 핵심 차이 | 관련 장 |
|---|---|---|---|
| HTTP 요청/응답 | UART 바이트 스트림 + 프레이밍 | 스트림에는 메시지 경계가 없다. 직접 만든다 | 2, 3 |
| `Content-Length`/`Transfer-Encoding` | `LEN`, 구분자, CRC | 헤더를 직접 설계하고 직접 검증한다 | 3 |
| JSON/XML | 고정 길이 바이너리, TLV, 비트 필드 | 스키마가 코드와 데이터시트에 흩어져 있다 | 1, 3 |
| REST 엔드포인트 | 명령 코드, 레지스터 주소 | "주소"가 메모리·CAN ID·I2C 주소로 겹쳐 쓰인다 | 4, 5, 6 |
| URL 경로 | CAN ID, MQTT 토픽 | CAN ID는 내용(기능)이고, MQTT 토픽은 계층이다 | 5, 10 |
| 쿼리 문자열 | 레지스터 주소·오프셋 | 0-based/1-based, 워드 순서가 장치마다 다르다 | 4, 10 |
| HTTP 상태 코드 | 오류 코드, Modbus 예외 응답, UDS NRC | 받아 줄 런타임이 없어 코드로 처리한다 | 1, 8, 10 |
| WebSocket | MQTT, BLE notify, WebSocket | 장치 쪽 TCP/TLS 비용이 크다 | 10 |
| OBD-II PID / UDS DID | PID/DID 정의표 | PID/DID마다 길이·공식이 다르다 | 5, 7, 8 |
| API 게이트웨이 | 차량 진단 게이트웨이 | 버스별 라우팅·필터링, OBD 포트가 전체를 보여 주지 않음 | 6 |
| 요청 ID/트레이스 ID | PID 에코, DID, CAN ID | 응답을 요청과 매칭해야 한다 | 3, 5, 7 |
| 응답 스키마 | PID/DID 정의표, OBDb | 스키마가 데이터 밖에 있다 | 7, 8 |
| 개인정보 마스킹 | VIN 해시/별칭 | 로그·토픽·공개 저장소에서 제거 | 9, 10 |
| 서버 푸시/SSE | MQTT 구독, BLE notify/indicate | CCCD를 켜야 notify가 온다 | 10, 19 |
| 주기적 폴링 | MQTT pub/sub, CoAP observe | 배터리와 트래픽에 불리하다 | 10, 19 |
| 페이지네이션 | 레지스터 블록 읽기 | 최대 길이와 타임아웃을 정해야 한다 | 3, 10 |

| 큐·메시지 브로커 | 링 버퍼, 인터럽트 | 생산자와 소비자가 ISR과 메인 루프로 나뉜다 | 11 |

| 서킷 브레이커 | 연속 실패 시 링크 리셋/안전 상태 | 실패가 기계를 멈출 수 있다 | 1, 3 |
| 가비지 컬렉션 | 정적 버퍼, 풀, Rust 소유권 | 조각화와 해제 시점을 직접 관리한다 | 1, 11, 14, 16 |
| 메모리 프로파일러 | `size`, 맵 파일, 스택 하이워터마크 | "컴파일된다"와 "들어간다"는 다르다 | 1, 11, 14, 15 |
| CPU 프로파일러 | 오실로스코프, 로직 분석기, GPIO 토글 | 시간이 코드 밖에서 결정된다 | 11, 12 |
| `console.log` | UART 로그, LED | 로그를 볼 수 없는 현장이 많다 | 12 |

## B.4 웹 습관을 옮길 때의 규칙

### 그대로 가져와도 되는 것

- Git, 이슈 트래킹, 코드 리뷰
- 테스트 자동화, 린터, CI
- 상태 기계, 의존성 주입, 계층 분리
- 인터페이스 뒤에 하드웨어 숨기기, 목(mock)으로 테스트
- 문서화, 로그를 남기는 습관

### 반드시 바꿔야 하는 것

| 웹 습관 | 임베디드에서의 문제 | 바꿀 습관 |
|---|---|---|
| "읽으면 메시지 하나" | 부분 수신·합쳐짐 | 상태 기계 파서, `parse(full) == parse(byte_by_byte)` |
| "JSON이 알아서 해석" | 자기 설명적이지 않은 바이너리 | 엔디언·부호·폭·스케일 명시 |
| "메모리는 넉넉" | KB 단위 RAM, GC 없음 | 정적 버퍼, 풀, 사용량 측정 |
| "빠르면 된다" | 최악 지연이 중요 | 타임아웃·워치독·상태 기계 |
| "예외가 던져지면 잡지" | 잡아 줄 런타임 없음 | 오류 코드, 재시도, 안전 상태 |
| "재시도하면 되지" | 중복 실행 | 멱등성, 시퀀스 번호 |
| "로그 보면 되지" | 로그를 볼 수 없는 현장 | 원시 바이트, LED, 로직 분석기 |
| "배포 후 롤백" | 벽돌 위험 | A/B 파티션, 서명, 롤백 |
| "코드만 보면 된다" | 배선·전원·접지 문제 | 계층별 디버깅, 계측기 |
| "내 환경에서는 된다" | 하드웨어가 재현 조건 | 전원·케이블·보드·온도 기록 |

### 새로 추가해야 하는 것

- **원시 바이트 로그와 단조 시각**: 파서가 틀렸을 때 되돌아갈 수 있는 유일한 원본이다.
- **계층별 디버깅 순서**: 전원 → 접지 → 배선 → 레벨 → 설정 → 프레이밍 → 의미 → 타이밍.
- **데이터시트 읽기**: 라이브러리 문서가 아니라 계약서다.
- **계측기**: 멀티미터, 로직 분석기, 오실로스코프.
- **안전 상태와 워치독**: 처음부터 설계에 넣는다.
- **하드웨어를 포함한 재현 조건**: "내 책상에서는 된다"를 버린다.

## B.6 한 문장 요약

웹에서는 **런타임과 네트워크가 대신 처리해 주던 것**을 임베디드에서는 **코드와 전기 설계로 직접 처리**한다. 그 차이를 인정하고, 경계·전압·시간·메모리·오류를 명시적으로 다루면 웹 개발자의 경험은 그대로 무기가 된다.
