# 부록 D. 트러블슈팅 사례집

이 부록은 "증상 → 원인 후보 → 확인 방법 → 조치" 순서로 정리한 실전 사례집이다. 모든 항목을 한 번에 적용하지 말고, **위에서 아래로 계층을 따라간다.** 전원 → 접지 → 배선 → 레벨 → 설정 → 프레이밍 → 의미 → 타이밍 순서다.

사례 중 일부는 필자가 기아 쏘렌토 UM 2019 2.2 디젤에서 ELM327 v1.5 클론(CH340)으로 실습하며 겪은 것이다. 그 부분은 `실차`로 표시했다. 나머지는 공개 자료와 일반적인 CAN·OBD-II 동작에서 정리한 후보이며, 차량·어댑터·펌웨어에 따라 결과가 다를 수 있다.

## D.1 먼저 확인할 것

문제를 만났을 때 바로 코드를 고치지 않는다. 다음 순서로 상태를 수집한다.

1. **시각**: 마지막 성공 시각, 실패 시각, 재현 간격
2. **전원**: 배터리 전압, 어댑터 LED, USB 전원, 접지
3. **포트**: 장치 관리자/`list_ports`, COM 번호, 드라이버
4. **설정**: 보율, 프로토콜, 헤더/에코/공백 설정
5. **프레임**: 원시 hex, CAN ID, ISO-TP PCI, 타임아웃
6. **의미**: PID 공식, 바이트 순서, 길이, 지원 여부
7. **환경**: 시동 상태, 온도, USB 허브, 다른 소프트웨어

이 순서를 로그로 남기면, 같은 증상이 다시 왔을 때 비교할 수 있다.

## D.2 연결과 포트

| 증상 | 원인 후보 | 확인 방법 | 조치 |
|---|---|---|---|
| 포트 목록에 장치가 없음 | USB 케이블이 충전 전용, 드라이버 없음, 보드 전원 없음 | 다른 케이블, 장치 관리자, `python -m serial.tools.list_ports -v` | 데이터 케이블로 교체, CH340/CP210x 드라이버 설치, 전원 확인 |
| 포트가 보이는데 열리지 않음(`Access is denied`) | 시리얼 모니터·다른 스크립트가 점유 | 같은 포트를 쓰는 프로그램 확인 | 모두 닫고 다시 열기, 재부팅 |
| 어댑터를 다시 꽂았더니 COM 번호가 바뀜 | Windows가 새 장치로 인식 | 포트 목록의 VID/PID·설명 확인 | 포트 이름 하드코딩 대신 VID/PID로 찾기, 설정 파일 갱신 |
| 주행/크랭킹 중 USB 장치가 사라짐 | USB 전원·케이블·허브, 차량 전원 변동, 접지 루프 | 앱 로그의 끊김 시각, Windows 이벤트 로그의 장치 제거 | USB 절연기, 외부 전원 허브, 짧은 케이블, 크랭킹 중 로깅 중지 |
| `ATZ` 응답이 `STOPPED` | 프롬프트 전에 입력, 어댑터가 명령을 놓침 | 같은 명령을 `\r`로 다시 보내기 | `ATZ` 재시도, 그래도 안 되면 전원 재인가 |
| `UNABLE TO CONNECT` | 시동 OFF, OBD 커넥터 접촉 불량, 차량 프로토콜 불일치 | `ATRV`, 커넥터 체결, 다른 차량/어댑터 | 시동 ON, 커넥터 재체결, `ATSP0` 재검색 |
| `SEARCHING...`이 오래 지속 | 프로토콜 자동 검색 중, 차량 응답 없음 | `ATDPN`, `ATSP0` 타임아웃 | 잠시 기다린 뒤 `ATDPN`, 필요하면 프로토콜 수동 지정 |
| 명령마다 `?` | 명령 오타, 클론이 지원하지 않는 AT 명령 | 데이터시트의 명령 철자, `ATI` 버전 | 철자 수정, 미지원 명령 제거 |

`실차` 사례: CH340 어댑터가 주행 중 USB에서 사라졌고, Windows 이벤트 로그에 `USB\VID_1A86&PID_7523` 장치가 버스에서 누락된 기록이 남았다. 재연결 후 COM 번호가 `COM5`에서 `COM6`으로 바뀌었다. 앱이 포트 이름을 고정하고 있었다면 다시 열지 못했을 것이다. 포트를 VID/PID나 설명으로 찾고, `SerialException`에서 재연결하는 코드가 필요하다.

## D.3 프로토콜과 응답

| 증상 | 원인 후보 | 확인 방법 | 조치 |
|---|---|---|---|
| `NO DATA` | PID 미지원, 시동 상태, 응답 타임아웃, 헤더/필터 | 같은 PID를 단독으로 요청, `ATST` 확인, `ATH1` | 지원 PID 확인, 시동 ON, 타임아웃 늘리기, 필터 해제 |
| `BUFFER FULL` | 응답이 길거나 빠름, 보율이 낮음, 소비자가 느림 | `ATH0`/`ATS0`, 요청 주기, 응답 길이 | 보율 높이기, 헤더/공백 끄기, 수신 필터, 요청 전 입력 비우기 |
| `BUFFER FULL` 뒤 다음 응답에 이전 프레임이 섞임 | 어댑터 버퍼에 남은 조각 | 원시 로그의 응답 길이·순서 | `BUFFER FULL`이 난 응답은 버리고, 요청 전 버퍼 비우기 |
| `STOPPED` | 이전 명령이 중단됨, 리셋 실패 | `ATZ` 재시도, 전원 | 어댑터 전원 재인가, 설정 재적용 |
| 여러 ECU 응답이 섞임 | 기능 주소 `7DF`, `ATH0` | `ATH1`로 응답 ID 확인 | 물리 주소 `7E0`/`7E1` 사용, 응답 ID별 파서 분리 |
| `7F 22 78` | ECU가 바쁨, 응답 대기 | 잠시 뒤 같은 요청의 실제 응답 | 재요청하지 말고 기다리기, 타임아웃 조정 |
| `7F 22 7F` | 현재 세션에서 미지원 | 기본 세션 여부, DID 문서 | 세션 전환하지 말고 읽기 포기(11장) |
| `7F 22 31` | DID 없음, 범위 밖 | DID 목록, 다른 ECU | 같은 요청 반복 금지, 다른 DID/ECU 시도 |
| `ATCRA`에 `?` | 클론이 인자 없는 `ATCRA` 미지원 | `ATAR` 응답 | `ATAR`로 수신 필터 해제, 이후 `ATCRA <주소>` 사용 |
| 긴 VIN/제조사 응답이 첫 줄만 옴 | FC 미전송, 필터, 버퍼 | `ATH1` 원시 프레임, ISO-TP PCI | FC 설정(`ATFCSH`/`ATFCSD`/`ATFCSM`), 3장 코드 |
| 응답 길이가 매번 다름 | 다중 PID 응답 순서·길이 가변, 잔여 프레임 | PID별 길이 표, 원시 hex | PID 번호로 찾기, 응답별 길이 검증 |

### 값이 이상할 때

| 증상 | 원인 후보 | 확인 방법 | 조치 |
|---|---|---|---|
| rpm이 0으로 고정 | 시동 OFF, PID 미지원, 응답 파싱 오류 | `010C` 단독, `41 0C` 확인 | 시동 ON, PID 지원 확인, 바이트 순서 확인 |
| 냉각수가 −40°C | 센서 없음, 무효 값, `A−40` 공식 | 시동 후 변화, 다른 차량 | 표시에서 제외, 센서 유무 확인 |
| 흡기압이 255 kPa에서 막힘 | 표준 PID 범위 포화, 과급 디젤 | 여러 부하에서 값 변화 | 제조사 PID/다른 센서 사용, 표준 PID만으로 단정하지 않기 |
| 외기 온도가 51°C 고정 | 무효 값, 센서 없음 | 시동/주행 후 변화 | 표시에서 제외 |
| PID가 지원된다는데 항상 0 | 구현만 있고 값이 무효 | 여러 주행 조건에서 측정 | 유효성 검사, 대시보드에서 제외 |
| 응답은 오는데 규격보다 짧음 | 제조사 구현 차이 | PID별 실제 길이 | 길이를 고정하지 말고 `len` 검사 |
| 값이 갑자기 이전 값으로 돌아감 | 오래된 응답·잔여 프레임·캐시 | 타임스탬프, 원시 로그 | 응답 ID·PID·시각 확인, 오래된 값 만료 |

`실차` 사례: 쏘렌토 엔진(7E0)은 표준 PID 79개를 지원했지만, PID `0x5C`(오일 온도)는 항상 `00`(−40°C), PID `0x46`(외기)은 51°C 고정이었다. PID `0x78`/`0x7A`/`0x7C`는 규격보다 짧게 응답했다. "지원한다"와 "의미 있는 값을 준다"는 다르다.

## D.4 전원·배선·버스

| 증상 | 원인 후보 | 확인 방법 | 조치 |
|---|---|---|---|
| 배터리가 방전됨 | OBD 16번 상시 전원, 어댑터 대기 전류 | 사용 후 배터리 전압, 소비전류 | 사용 후 분리, 슬립/스위치, 퓨즈 |
| 노트북이 간헐적으로 리셋 | 접지 루프, USB 전원, 차량 과도 전압 | 리셋 시각과 크랭킹 시점 | USB 절연기, 외부 전원, 크랭킹 중 분리 |
| CAN 통신이 불안정 | 차량에 120Ω 추가, 종단 중복/누락, 스텁 | 전원 OFF에서 6/14 저항, 모듈 120Ω | 차량 종단 추가 제거, 벤치에서만 종단 |
| Bus-Off가 반복됨 | 배선 단선, 비트레이트 불일치, 전원 불안정 | TEC/REC, bus_error_count, 파형 | 배선·종단·속도 확인, 복구 절차 |
| OBD 포트에서 아무 프레임도 안 보임 | 게이트웨이가 진단 요청 전까지 침묵, 시동 OFF, CAN 핀 오류 | `ATDPN`, 6/14 도통, 다른 도구 | 시동 ON, 요청 전송, ELM327로 교차 확인 |
| ESP32가 차량에서만 리셋 | load dump·크랭킹 전압 강하, 전원 부족 | 전압 로그, 리셋 원인 | 자동차용 강압·TVS, USB 전원 분리 |
| MCP2515가 초기화되지 않음 | 크리스탈 주파수 불일치, CS/SPI 배선, 5V/3.3V | 모듈 표기, `MCP_8MHZ`/`MCP_16MHZ`, SPI 파형 | 크리스탈에 맞춘 인자, 배선·전원 확인 |
| TWAI 초기화 실패 | GPIO 충돌, 드라이버 중복 설치, 코어 API 차이 | 사용 핀, 부팅 로그, 코어 버전 | 다른 GPIO, 리셋, 공식 예제 확인 |

## D.5 개인정보·안전

| 증상/상황 | 위험 | 확인 | 조치 |
|---|---|---|---|
| 로그에 VIN이 그대로 남음 | 차량·소유자 식별, 추적 | 로그 검색, `09 02` 응답 | VIN 필드 제거·해시, 원본 접근 제한 |
| GPS·주행 경로가 함께 저장됨 | 이동 패턴 노출 | 로그 스키마 | 위치 필드 분리·삭제, 공개 금지 |
| DTC를 지우고 싶음 | readiness 초기화, 진단 근거 손실, 검사 불합격 | DTC 원인, 프리즈 프레임 | 지우지 않는다. 원인 진단 후 정비 |
| 주행 중 화면을 봄 | 사고 위험 | 운전자 조작 여부 | 정차 후 확인, 조수석·기록 장치 사용 |
| 타인 차량을 스니핑함 | 법·윤리 위반 | 소유자 허가 | 즉시 중단, 허가 없는 기록 삭제 |

DTC 삭제와 쓰기 서비스의 위험은 11장에서 자세히 다룬다. 이 부록의 어떤 조치도 **삭제·쓰기·액추에이터 구동**을 권하지 않는다.

## D.6 로그를 남기는 방법

재현되지 않는 문제는 로그가 없으면 해결하기 어렵다. 최소한 다음을 남긴다.

```text
시각(단조) | 방향 | CAN ID | DLC | 원시 바이트 | 해석 | 오류
```

- 시각은 `time.monotonic()` 또는 하드웨어 타임스탬프를 쓴다. 벽시계는 NTP/수동 변경으로 점프할 수 있다.
- 원시 바이트와 해석 값을 함께 남긴다. 파서가 틀렸을 때 원본이 필요하다.
- 요청·응답·타임아웃을 구분한다. "응답 없음"과 "응답이 늦게 옴"은 다른 문제다.
- USB 끊김은 앱 로그의 마지막 성공 시각과 OS 이벤트 로그를 대조한다.
- 로그를 공개하기 전에 VIN·GPS·경로·차량 번호를 제거한다.
- 재현 테스트는 원시 로그를 리플레이해서 만든다. 차량 없이 파서를 시험할 수 있다.

## D.7 한 줄 요약

- 포트가 안 보이면 케이블·드라이버·점유를 본다.
- `NO DATA`는 "차가 고장났다"가 아니라 "이 요청에 응답이 없다"는 뜻이다.
- `BUFFER FULL`은 소비자가 생산자를 못 따라가는 문제다.
- 값이 이상하면 공식·길이·바이트 순서·센서 유무를 본다.
- 차량에서는 전원·접지·종단을 먼저, 코드를 나중에 본다.
- 읽기 전용·정차·개인정보 제거는 문제 해결 중에도 유지한다.

## D.8 가상 버스·브라우저·로그

| 증상 | 원인 후보 | 확인 방법 | 조치 |
|---|---|---|---|
| vcan에서 프레임이 안 보임 | 인터페이스 `DOWN`, 이름 불일치, 모듈 미로드 | `ip -details link show vcan0`, `dmesg` | `modprobe vcan`, `ip link add`, `ip link set up` |
| `modprobe vcan` 실패 | 구버전·커스텀 커널이거나 모듈 미탑재 | `uname -r`, WSL 커널 설정 | python-can virtual로 대체, 필요하면 커스텀 커널 |
| virtual 버스에서 두 프로세스가 안 통함 | virtual은 프로세스 안에서만 동작 | 두 프로그램의 채널·프로세스 확인 | `udp_multicast`, vcan, 실제 인터페이스 |
| 가짜 ECU가 응답하지 않음 | 채널 불일치, 스레드 미시작, 요청 주소 오류 | 양쪽 `channel`, `ecu.start()`, `0x7DF` 확인 | 채널 통일, 스레드 시작, 주소 확인 |
| 다중 프레임이 FF만 옴 | FC 미송신, STmin/BS 불일치 | FF 후 `30 00 00` 송신 여부 | FC 송신, 타임아웃·버퍼 정리 |
| ELM327-emulator 연결 거부 | 에뮬레이터 미실행, 포트 충돌 | `python -m elm -s car -n 35000` 실행 로그 | 포트 변경, 방화벽 확인 |
| 에뮬레이터 값이 쏘렌토와 다름 | `scenario car`는 Toyota 시나리오 | `ATDPN`, 시나리오 문서 | AT/PID 파싱 시험용으로만 사용 |
| `navigator.serial` 없음 | 비보안 컨텍스트, 미지원 브라우저 | 주소창 `https`/`localhost`, `'serial' in navigator` | HTTPS·localhost, Chrome/Edge/Firefox 151+ |
| 포트 선택 창이 안 뜸 | 사용자 제스처 밖 호출 | 클릭 핸들러 안에서 호출했는지 | 버튼 클릭 이벤트에서 `requestPort()` |

- 펌웨어 문제는 "코드가 틀렸다"보다 **스택·큐·우선순위·전원**이 원인인 경우가 많다. 리셋 원인과 카운터를 먼저 본다.
- FreeRTOS API를 ISR에서 쓸 때는 이름에 `FromISR`이 있는지 확인한다. 없으면 잘못된 것이다.
- Rust에서도 `unsafe`, 논리 오류, 스택 오버플로, 데드락은 남는다. 소유권은 만능이 아니다.
- ESP32 코드는 사용하는 ESP-IDF/Arduino-ESP32 코어 버전의 TWAI API를 확인한다. v6.x는 `twai_node_*`다.

## D.11 J1939·CANopen·NMEA 2000

| 증상 | 원인 후보 | 확인 방법 | 조치 |
|---|---|---|---|
| J1939 PGN이 목적지마다 달라짐 | PDU1의 PS(DA)를 PGN에 포함 | PF < 240인지, PGN low byte | PS를 0으로 지우고 PGN 계산 |
| J1939 프레임이 안 보임 | 11비트로 송신, 29비트 필터 누락 | `is_extended_id`, CAN ID 상위 비트 | 29비트 확장 ID 사용, 필터 확인 |
| SPN 값이 8배·40도 틀림 | 해상도·오프셋 누락 | SPN 표의 resolution/offset | `raw*res+offset` 적용 |
| DM1 SPN/FMI가 엉뚱함 | DTC 오프셋·FMI 비트 순서 | 2바이트 램프 뒤 4바이트 DTC | byte3 하위 5비트=FMI, 상위 3비트=SPN high |
| TP 메시지가 1패킷 모자람 | 패킷 수 계산 오류 | `ceil(len/7)`, TP.CM byte4 | 0xFF 패딩, 시퀀스 1부터 |
| J1939 주소 충돌 | 클레임 누락·NAME 비교 오류 | PGN 60928, 250ms | NAME 작은 쪽이 이김, 재클레임 |
| CANopen SDO 무응답 | NMT Stopped, node ID 불일치 | `0x600+ID`/`0x580+ID`, NMT 상태 | Pre-operational/Operational로 |
| SDO Abort `0x06020000` | OD에 없는 index | EDS, index/subindex | 객체 존재 여부 확인 |
| PDO가 안 옴 | 매핑·전송 형식·NMT 상태 | `0x1A00`, transmission type | Operational, 매핑 일치 |
| 하트비트 끊김 | 주기 0, 케이블, 노드 리셋 | `0x1017`, `0x700+ID` | 주기 설정, 전원·배선 확인 |
| NMEA PGN이 이상함 | J1939 PGN 사전으로 해석 | NMEA PGN 표, canboat | NMEA 사전으로 디코딩 |
| fast packet 깨짐 | 시퀀스/프레임 카운터 무시 | 상위 3비트/하위 5비트 | 순서·총 길이 검사 |

- J1939·CANopen·NMEA 2000은 **같은 CAN이라도 문서가 다르다.** DBC·EDS·PGN 표를 섞지 않는다.
- 실제 차량·선박·설비에서는 NMT 전환·SDO 쓰기·PDO 송신·DM3를 하지 않는다. 진단은 읽기 전용으로 시작한다.
- 가상 버스에서 먼저 재현하고, 실제 장비는 제조사 문서와 안전 절차를 확인한 뒤 읽기만 한다.

|---|---|---|---|
| deep sleep 전류가 데이터시트보다 크다 | LDO·USB-UART·LED, 트랜시버 standby 미설정, RTC 주변장치 | 전원 회로 분리 측정, `RS` 핀 | 불필요 부품 제거, standby, wake source 최소화 |
| 잠들지 않는다 | Wi-Fi/BT 미종료, 열린 소켓, 태스크 블로킹 | `esp_sleep_start()` 전 로그, 전류 | 무선 종료, 태스크 정리, sleep API 확인 |
| 타이머 wake가 안 된다 | 단위(µs) 오류, 0 설정, sleep 모드 불일치 | 설정값, wake cause | `esp_sleep_enable_timer_wakeup(us)` 확인 |
| ext0/ext1 wake가 안 된다 | RTC GPIO 아님(GPIO21 등), 레벨 오류, ext1 모드 | 핀 목록, `esp_sleep_get_wakeup_cause()` | RTC GPIO로 변경, 레벨·모드 확인 |
| 깨어나자마자 다시 잔다 | wake 핀이 계속 활성, wake source 미해제 | 핀 전압, wake 설정 | `rtc_gpio_deinit()`, wake source 해제, 디바운스 |
| CAN 프레임으로 못 깨운다 | TWAI는 wake 원천 아님, 펄스 폭 부족, GPIO21 | 벤치 파형, wake cause | 타이머 wake, 래치·펄스 확장, wake 트랜시버 |
| 배터리가 빨리 준다 | 평균 전류 과다, Wi-Fi 재연결 반복, 저전압 차단 없음 | 전류 로그, 하트비트, 전압 | 활성 시간·주기·송신 전력 축소, 차단 |
| 브라운아웃 리셋이 반복된다 | 3.3V 레일 강하, 부하·배선·커넥터 | 리셋 원인, 전압 파형 | 전원 설계, 디커플링, 부하 분리 |
| 깨어난 뒤 CAN이 안 된다 | TWAI 재초기화 누락, 트랜시버 standby | 부팅 로그, `RS` 핀 | sleep 시퀀스 역순으로 재초기화 |
| deep sleep 뒤 시각이 틀린다 | RTC 시각 미유지, SNTP 미실행 | 로그 시각, SNTP 결과 | wake 후 SNTP, TLS 전 시각 확인 |
| OTA 중 sleep에 들어간다 | 절전 태스크가 OTA를 모름 | OTA·sleep 로그 | OTA 중 sleep 금지 플래그 |

## D.15 신호 처리·데이터 품질

| 증상 | 원인 후보 | 확인 방법 | 조치 |
|---|---|---|---|
| 대시보드에 0°C·0rpm이 뜬다 | 결측을 0으로 채움, `NO DATA`를 숫자로 변환 | 원본 응답, `quality` 플래그 | `null`+`missing`, 화면에는 `--` |
| 오일 온도가 항상 -40°C다 | PID 5C 미구현·센서 없음, `00`을 정상값으로 해석 | 같은 값 반복, 다른 온도 PID와 비교 | 무효값으로 표시, PID 제외 |
| 외기 온도가 51°C에 고정된다 | PID 46 무효값·고정값 | 시동·주행 중 변화 여부 | `invalid`, 다른 소스와 교차 확인 |
| 흡기압이 255kPa에서 안 올라간다 | 1바이트 PID 포화(`0xFF`), 과급압을 표준 PID로 못 읽음 | 부스트 실제값과 비교 | 범위 끝 표시, 제조사 PID 검토 |
| 지원되는 PID가 항상 0이다 | ECU가 더미 값을 반환, 센서 없음 | 지원 비트마스크와 값 분포 | 대시보드에서 제외, `invalid` |
| 응답 길이가 규격과 다르다 | 제조사 구현 차이, 짧은 응답 | 원시 바이트 길이, PID별 기대 길이 | 길이를 고정하지 말고 실제 길이로 파싱 |
| 10Hz로 읽었는데 값이 1초마다만 바뀐다 | ECU 내부 갱신 1Hz, PID 1F의 1초 해상도 | 값 변화 시각, ECU 문서 | 폴링 주기를 낮추거나 `확인 필요` 표시 |
| 빠른 진동이 느린 주기로 보인다 | 에일리어싱 | 샘플링 주파수와 신호 주파수 계산 | 샘플링 속도 상향, 안티에일리어싱 |
| 두 로그의 시간이 수 초 어긋난다 | 시계 드리프트, NTP 미동기, 타임존 | `sync_error_ms`, 마지막 동기화 | UTC·단조 시계 분리, 동기화 오차 기록 |
| 재부팅 후 시간 계산이 음수다 | 단조 시계 기준점 초기화, 벽시계 점프 | 부팅 ID, `monotonic` 값 | 세션 ID와 함께 저장, 벽시계는 경과에 쓰지 않음 |
| 리샘플 후 값이 계단처럼 보인다 | 최근값 유지(ffill) | `age_s`, 원본 타임스탬프 | 허용 나이, `stale` 표시, 짧은 구간만 보간 |
| 필터 후 알람이 늦다 | 필터 지연(τ, (N-1)/2) | 원본과 필터 값의 교차상관 | 지연 예산, 알람은 원본·지속 시간으로 |
| 이상 탐지가 정상 값을 잡는다 | 추세·비정규 분포, 작은 MAD, 워밍업 부족 | 롤링 창, MAD, 임계값 | 창·임계값 조정, `invalid`는 검토용 |
| 결측률이 갑자기 오른다 | USB 끊김, Bus-Off, 전원, 어댑터 | 드롭 카운터, 재연결 로그, 전원 | 배선·전원·어댑터 점검, 결측 자체를 알람으로 |
