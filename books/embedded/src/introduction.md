# 서문: 이 책의 독자와 읽는 법

## 이런 독자를 생각하며 썼다

이 책은 **웹 개발을 몇 년 해 본 사람이 임베디드로 내려가는 길**을 다룬다. 특히 HTTP·JSON·데이터베이스·클라우드·CI/CD에 익숙하고, C는 대학 이후로 멀리했으며, 전자 회로는 브레드보드 수준부터 시작하는 독자를 염두에 두었다.

웹 개발자에게 임베디드가 갑자기 필요해지는 순간은 여러 모양으로 온다. 센서 값을 받아 대시보드에 띄워야 할 때, 공장 장비나 차량의 데이터를 읽어야 할 때, ESP32 같은 보드에 Wi-Fi를 붙여 서버로 보내야 할 때, 혹은 "이 요청이 왜 이렇게 느리지"를 네트워크 아래쪽까지 따라가 보고 싶을 때다. 어느 쪽이든 공통점이 있다. **웹에서 당연하게 여겼던 것들이 하나씩 사라진다.**

- 메시지 경계가 없다. 바이트가 줄줄이 온다.
- JSON 같은 자기 설명적 포맷이 없다. 위치와 길이와 의미를 약속으로만 안다.
- 메모리가 넉넉하지 않고, 가비지 컬렉터가 없다.
- 예외를 받아 줄 런타임이 없고, 프로세스를 격리해 줄 OS도 없다.
- 버그가 코드가 아니라 배선·전원·접지에 숨어 있다.

이 책은 그 차이를 하나씩 풀어 놓는다. 동시에 웹 개발자가 이미 가진 것이 임베디드에서도 그대로 강력하다는 점을 계속 상기시킨다. 상태 기계, 계층 분리, 인터페이스 뒤에 구현 숨기기, 자동 테스트, Git, 코드 리뷰, 로그를 남기는 습관은 여기서도 똑같이 쓸모 있다.

## 이 책의 약속

**첫째, 웹의 개념에 빗대어 시작한다.** HTTP 요청/응답은 UART 바이트 스트림과 프레이밍에, JSON은 고정 길이 바이너리와 TLV에, 데이터베이스는 플래시·EEPROM·NVS에, 큐는 링 버퍼와 인터럽트에 대응한다. 비유는 입구일 뿐이다. 비유가 깨지는 지점을 정확히 짚는 것이 이 책의 목적이므로, "비슷하다"에서 멈추지 않고 "어디서 달라지는가"까지 간다.

**둘째, 계층 순서를 지킨다.** 임베디드에서 무언가 안 될 때는 코드부터 읽고 싶은 유혹이 크다. 하지만 실제 원인은 대개 아래쪽에 있다. 이 책은 다음 순서를 반복해서 사용한다.

```text
전원 → 접지 → 배선 → 레벨 → 설정 → 프레이밍 → 의미 → 타이밍
```

**셋째, 확인하지 않은 값을 단정하지 않는다.** 데이터시트나 실측으로 확정하지 않은 값에는 `확인 필요`라고 적는다. 전압·속도·거리·가격은 대표값이나 경험칙인 경우가 많으므로, 실제 설계에 쓸 때는 반드시 부품의 데이터시트와 현장 조건을 확인해야 한다.

**넷째, 예시는 작게 유지한다.** 파이썬 예시는 `uv`를 기준으로 한다. `uv init`으로 프로젝트를 만들고 `uv add pyserial`처럼 의존성을 추가한 뒤 `uv run`으로 실행하는 흐름이다. C 예시는 마이크로컨트롤러의 최소 구조를 보여 주는 데 집중하고, 특정 벤더의 라이브러리 API에 기대지 않는다.

## 읽는 순서

처음 접한다면 목차 순서대로 읽는 것을 권한다.

1. **1장 웹 개발자의 사고 전환** — 이 책 전체의 지도다. 웹 습관 중 무엇을 버리고 무엇을 가져갈지 정한다.
2. **2장 UART** — 시리얼의 물리·전기·설정. "보레이트가 뭐예요"에서 시작해 루프백까지 간다.
3. **3장 프레이밍과 파싱** — 이 책의 심장이다. 바이트 스트림에서 메시지를 만들어 내는 방법과, 그 파서를 테스트하는 방법을 다룬다.
4. **4장 I2C와 SPI** — 보드 안에서 센서·메모리·디스플레이와 대화하는 버스.
5. **5장 CAN** — 여러 노드가 한 쌍의 선을 공유하는 버스. 중재와 오류 처리.
6. **6장 IoT 프로토콜** — MQTT·BLE·Modbus·Wi-Fi·LoRaWAN 등 "무엇으로 보낼까"의 지도.
7. **7장 마이크로컨트롤러** — 인터럽트, 링 버퍼, 메인 루프, 메모리, GPIO.
8. **8장 도구와 디버깅** — 멀티미터, 로직 분석기, pyserial, python-can, 로깅 습관.
9. **9장 학습 경로와 실습** — 무엇부터 사고 무엇을 만들어 볼지.

이미 목표가 정해져 있다면 해당 장부터 읽어도 된다. 예를 들어 센서를 붙이는 일이 급하면 4장과 7장을, 장비와 통신해야 하면 2·3장을, 클라우드로 데이터를 보내야 하면 6장을 먼저 봐도 된다. 다만 3장의 프레이밍과 파싱은 어떤 경로로 읽어도 한 번은 거치는 것이 좋다. 시리얼 통신에서 마주치는 문제의 절반이 여기에 있기 때문이다.

각 장은 같은 구조를 따른다.

- **도입**: 왜 알아야 하는지, 웹에서 비슷한 것이 무엇인지
- **본문**: 원리와 실무 함정
- **예시**: 코드, 바이트 덤프, 표, ASCII 그림
- **흔한 실수**: 증상과 원인
- **장 요약**: 다음 장으로 넘어가기 전에 남겨야 할 것

## 이 책이 다루지 않는 것

범위를 분명히 해 두면 기대가 어긋나지 않는다.

- **차량 진단(OBD-II·UDS·ELM327)의 실무는 다루지 않는다.** 5장에서 CAN의 일반 원리와 상위 프로토콜의 지도만 설명하고, 차량별 주소·PID·서비스·도구 사용법은 책 밖의 자료로 남긴다. 차량에서 무언가를 읽을 때 지켜야 할 **읽기 전용** 원칙은 안전 규칙으로만 짧게 언급한다.
- **PCB 설계와 아날로그 회로 설계**는 다루지 않는다. 개발 보드와 브레이크아웃 모듈로 검증하는 데 필요한 전자 기초까지만 설명한다.
- **C 언어 문법 전체**를 가르치지 않는다. 포인터·비트 연산·`volatile`·고정폭 정수처럼 임베디드에서 특히 중요한 부분만 짚는다.
- **RTOS 내부 구현**은 다루지 않는다. 베어메탈 상태 기계로 충분한 경우와 RTOS가 필요한 경우를 구분하는 정도까지 간다.
- **상용 전원(110/220V)과 고전압 장비**는 직접 다루지 않는다.

## 표기 규칙

- 숫자는 특별한 말이 없으면 10진수다. 바이트와 ID는 `0x123`, `A5 01 02`처럼 16진수로 쓴다.
- `확인 필요`는 데이터시트·실측으로 확정하지 않은 값이나 경험칙이다. 실제 설계에 쓸 때는 데이터시트를 확인한다.
- 전압·속도·거리·가격은 대표값이나 경험칙인 경우가 많다. 부품·케이블·환경에 따라 달라진다.
- 코드 블록의 언어 표기는 `python`, `c`, `bash`, `text`를 쓴다.

## 웹 개발자가 이미 가진 것

임베디드를 처음 시작하면 "나는 아무것도 모른다"는 기분이 들 수 있다. 하지만 웹 개발 경력은 이 분야에서 생각보다 큰 자산이다.

- **상태 기계**: 화면의 로딩·성공·오류 상태를 다뤄 본 경험은 통신 상태 기계와 펌웨어 상태 기계에 그대로 통한다.
- **비동기와 타임아웃**: "응답이 안 오면 어떻게 할 것인가"를 고민해 본 경험은 재전송·백오프·멱등성 설계로 이어진다.
- **테스트와 리팩터링**: 하드웨어 접근을 인터페이스로 분리하면 PC에서 파서와 상태 기계를 단위 테스트할 수 있다. 이 습관 하나가 디버깅 속도를 크게 바꾼다.
- **Git과 코드 리뷰**: 펌웨어에도 똑같이 적용된다.
- **로그와 관측**: 웹의 APM에 해당하는 것이 임베디드에서는 원시 바이트 로그, 하트비트, 오류 카운터, 리셋 원인이다.

새로 메워야 할 것은 **C, 전자 기초, 계측과 하드웨어 디버깅**이다. 이 책은 그 세 가지를 통신이라는 실습 가능한 주제로 묶어서 설명한다.

이제 1장에서 웹 개발자의 사고방식이 어디서 어긋나는지부터 보자.
