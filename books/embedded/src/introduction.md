# 서문: 이 책의 독자와 읽는 법

## 이런 독자를 생각하며 썼다

이 책은 **웹 개발을 몇 년 해 본 사람이 임베디드로 내려가는 길**을 다룬다. 특히 HTTP·JSON·데이터베이스·클라우드·CI/CD에 익숙하고, C는 대학 이후로 멀리했으며, 전자 회로는 브레드보드 수준부터 시작하는 독자를 염두에 두었다.

웹 개발자에게 임베디드가 갑자기 필요해지는 순간은 여러 모양으로 온다. 센서 값을 받아 대시보드에 띄워야 할 때, 공장 장비나 차량의 데이터를 읽어야 할 때, ESP32 같은 보드에 Wi-Fi를 붙여 서버로 보내야 할 때, 혹은 "이 요청이 왜 이렇게 느리지"를 네트워크 아래쪽까지 따라가 보고 싶을 때다. 어느 쪽이든 공통점이 있다. **웹에서 당연하게 여겼던 것들이 하나씩 사라진다.**

- 메시지 경계가 없다. 바이트가 줄줄이 온다.
- JSON 같은 자기 설명적 포맷이 없다. 위치와 길이와 의미를 약속으로만 안다.
- 메모리가 넉넉하지 않고, 가비지 컬렉터가 없다.
- 예외를 받아 줄 런타임이 없고, 프로세스를 격리해 줄 OS도 없다.
- 버그가 코드가 아니라 배선·전원·접지에 숨어 있다.

이 책은 그 차이를 하나씩 풀어 놓는다. 동시에 웹 개발자가 이미 가진 것이 임베디드에서도 그대로 강력하다는 점을 계속 상기시킨다. 상태 기계, 계층 분리, 인터페이스 뒤에 구현 숨기기, 자동 테스트, Git, 코드 리뷰, 로그를 남기는 습관은 여기서도 똑같이 쓸모 있다.

## 이 책을 꿰는 예시: 자동차의 OBD-II와 CAN

개념만 나열하면 금방 잊는다. 이 책은 **자동차의 OBD-II 진단 포트와 CAN 버스**를 책 전체를 관통하는 실전 예시로 쓴다. 2장에서는 ELM327 어댑터와 PC 사이의 시리얼을 들여다보고, 3장에서는 그 응답의 경계를 파싱하며, 5장에서는 요청과 응답이 오가는 CAN 버스를 본다. 6~9장은 차량 네트워크, OBD-II 실전, UDS, 안전 문제를 깊게 다룬다. 10~13장의 IoT·MCU·도구·하드웨어 실습에 이어, 14~16장은 펌웨어의 메모리·인터럽트·FreeRTOS 태스크·Rust를 다룬다. 17~20장은 차 없이 반복하는 가상 CAN 실습·브라우저 시리얼·테스트·로그 파이프라인이고, 21~22장은 웹 개발자의 주력 스택인 TypeScript/Node.js로 ELM327 클라이언트와 실시간 대시보드를 끝까지 만든다. 23장에서 차량 보안을 방어 관점에서 정리하고, 24~25장에서 승용차 OBD 밖의 CAN 세계(J1939·CANopen·NMEA 2000)를 보여 주며, 26장에서 프로토콜 선택 기준을 정리한다. 27장은 학습 경로다.

예시 차량은 **기아 쏘렌토 UM 2019년식 2.2 디젤**이다. 필자가 실제로 이 차에서 ELM327 호환 어댑터로 읽은 기록을 1차 근거로 삼았다. 다만 다음을 분명히 해 둔다.

- 차량마다, 연식마다, 펌웨어마다 주소와 PID가 다르다. 이 책의 쏘렌토 값은 **그 차 한 대에서 확인한 사례**이지 모든 쏘렌토의 정답이 아니다.
- 제조사 고유 PID·DID 공식은 공개 데이터베이스(OBDb)와 실차 응답을 대조한 것이다. 공식 정비 문서가 아니므로 `문헌 기반` 또는 `확인 필요`로 표시한다.
- VIN, 차대 번호, 위치 기록처럼 개인을 특정할 수 있는 값은 책에 쓰지 않는다. 독자도 공개 로그에서 이런 값을 지워야 한다.
- **이 책의 모든 차량 실습은 정차 상태의 읽기 전용이다.** 주행 중 조작, 쓰기, 코딩, 고장 코드 삭제, 액추에이터 구동, 플래싱은 다루지 않는다. 9장에서 그 이유를 자세히 설명한다.
- 예시 차량은 **내연기관 디젤**이다. 7.4절의 전기차·하이브리드 OBD 한계는 개념 설명이며, 특정 EV의 비공개 PID는 출처 없이 싣지 않는다.

차량이 없어도 실습할 수 있다. 17장에서 Linux vcan과 python-can virtual, OBD-II 요청에 응답하는 가짜 ECU, ELM327-emulator, 저장한 원시 로그 재생을 다룬다. 18장은 브라우저에서 ELM327에 붙는 Web Serial 예제를, 19장은 가짜 버스와 기록을 이용한 테스트 전략을, 20장은 로그 형식과 데이터 파이프라인을 다룬다. 21~22장은 TypeScript/Node.js로 같은 ELM327 대화를 다시 구현하고, 수집기·SQLite·SSE·브라우저 게이지를 한 프로젝트로 묶는다. 차량은 마지막에 붙인다.

## 이 책의 약속

**첫째, 웹의 개념에 빗대어 시작한다.** HTTP 요청/응답은 UART 바이트 스트림과 프레이밍에, JSON은 고정 길이 바이너리와 TLV에, 데이터베이스는 플래시·EEPROM·NVS에, 큐는 링 버퍼와 인터럽트에 대응한다. 비유는 입구일 뿐이다. 비유가 깨지는 지점을 정확히 짚는 것이 이 책의 목적이므로, "비슷하다"에서 멈추지 않고 "어디서 달라지는가"까지 간다.

**둘째, 계층 순서를 지킨다.** 임베디드에서 무언가 안 될 때는 코드부터 읽고 싶은 유혹이 크다. 하지만 실제 원인은 대개 아래쪽에 있다. 이 책은 다음 순서를 반복해서 사용한다.

```text
전원 → 접지 → 배선 → 레벨 → 설정 → 프레이밍 → 의미 → 타이밍
```

**셋째, 확인하지 않은 값을 단정하지 않는다.** 데이터시트나 실측으로 확정하지 않은 값에는 `확인 필요`라고 적는다. 전압·속도·거리·가격은 대표값이나 경험칙인 경우가 많으므로, 실제 설계에 쓸 때는 반드시 부품의 데이터시트와 현장 조건을 확인해야 한다.

이 책은 근거의 성격을 다음과 같이 구분한다.

| 표기 | 뜻 |
|---|---|
| **실차 확인** | 필자가 해당 차량에서 실제로 요청·응답을 보고 계기판 등과 대조했다 |
| **문헌 기반** | 공개 데이터베이스·표준 해설·데이터시트의 공식을 실차 응답에 적용했다. 값의 의미는 아직 확정하지 않았다 |
| **확인 필요** | 출처가 없거나, 차량·부품·법규에 따라 달라지거나, 아직 검증하지 못했다 |
| **추정** | 근거는 있지만 확정은 아니다. 틀릴 수 있음을 전제로 읽는다 |

**넷째, 예시는 작게 유지한다.** 파이썬 예시는 `uv`를 기준으로 한다. `uv init`으로 프로젝트를 만들고 `uv add pyserial python-can`처럼 의존성을 추가한 뒤 `uv run`으로 실행하는 흐름이다. TypeScript 예시는 Node 24와 `npm`을 기준으로 하며, Node의 타입 제거로 `.ts`를 직접 실행하고 `tsc --noEmit`으로 타입을 검사한다. C 예시는 **PC에서 gcc로 컴파일·실행해 확인한 것**과, MCU에서만 의미가 있어 의사코드로 남긴 것을 구분한다. Arduino 스타일 API를 쓰는 경우에는 그 사실과 헬퍼 함수를 밝히고, 다른 MCU로 옮길 때 바꿔야 할 부분을 적는다. Rust 예시는 호스트에서 `rustc`/`cargo`로 확인하고, ESP32 타깃 빌드가 필요한 코드는 `실물 확인 필요`로 표시한다.

## 이 책을 읽는 법

이 절은 **책 안에서** 어느 장을 어떤 순서로 읽을지 정한다. 각 장을 읽은 뒤 무엇을 직접 만들어 보고, 책을 덮은 뒤 무엇을 더 배울지는 27장에서 다룬다.

### 목적별 읽기 경로

| 목적 | 먼저 읽을 장 | 이어서 읽을 장 | 함께 보면 좋은 장 |
|---|---|---|---|
| OBD-II로 내 차 읽기 | 2장 UART → 3장 프레이밍 → 5장 CAN → 6장 차량 네트워크 | 7장 OBD-II → 8장 UDS | 9장 안전, 17장 가상 CAN |
| 펌웨어 입문 | 11장 MCU → 13장 ESP32 | 14장 시간·메모리 → 15장 FreeRTOS → 16장 Rust | 2·3장 시리얼, 12장 도구 |
| 웹 대시보드 만들기 | 3장 프레이밍 → 7장 OBD-II → 17장 가상 CAN | 18장 Web Serial → 19장 테스트 → 20장 로그 → 21장 TypeScript → 22장 캡스톤 | 5·6장 CAN, 23장 보안 |
| 산업·상용차 CAN | 5장 CAN → 6장 차량 네트워크 | 24장 J1939 → 25장 CANopen/NMEA 2000 → 26장 프로토콜 선택 | 3장 프레이밍, 9장 안전, 23장 보안 |

표는 "무엇을 만들고 싶은가"에서 출발한다. 모든 장을 다 읽을 필요는 없지만, **3장 프레이밍과 5장 CAN은 어떤 경로에서도 한 번은 거치는 편이 좋다.** 시리얼과 CAN에서 마주치는 문제의 절반이 이 두 장에 있기 때문이다.

### 장 의존 관계

화살표는 "앞 장을 먼저 읽으면 뒤 장이 쉽다"는 권장 선수 관계다. 필수는 아니다.

```text
1장 사고 전환
   │
   ├─▶ 2장 UART ─▶ 3장 프레이밍 ─┬─▶ 5장 CAN ─▶ 6장 차량 네트워크 ─▶ 7장 OBD-II ─▶ 8장 UDS
   │                              └─▶ 4장 I2C/SPI ─▶ 11장 MCU ─▶ 13장 ESP32
   ├─▶ 9장 안전과 법·윤리 ─▶ 23장 CAN 보안
   └─▶ 12장 도구와 디버깅

5장 CAN ─▶ 24장 J1939 ─▶ 25장 CANopen/NMEA 2000 ─▶ 26장 프로토콜 선택
7장 OBD-II ─▶ 17장 가상 CAN ─▶ 18장 Web Serial ─▶ 19장 테스트 ─▶ 20장 로그
7장 OBD-II ─▶ 21장 TypeScript ─▶ 22장 캡스톤
11장 MCU ─▶ 13장 ESP32 ─▶ 14장 시간·메모리 ─▶ 15장 FreeRTOS ─▶ 16장 Rust
```

10장 IoT는 7장과 13장을 읽은 뒤에, 23장 보안은 5·8·17장을 읽은 뒤에 펼치면 연결이 쉽다. 27장은 이 그림을 실습 단계와 완료 기준으로 바꾸고, 책 밖의 다음 걸음을 안내한다.

처음 접한다면 목차 순서대로 읽는 것을 권한다.

1. **1장 웹 개발자의 사고 전환** — 이 책 전체의 지도다. 웹 습관 중 무엇을 버리고 무엇을 가져갈지 정한다.
2. **2장 UART** — 시리얼의 물리·전기·설정. ELM327과 PC 사이의 대화도 여기서 시작한다.
3. **3장 프레이밍과 파싱** — 이 책의 심장이다. ELM327의 줄 단위 응답과 ISO-TP 다중 프레임을 직접 파싱한다.
4. **4장 I2C와 SPI** — 보드 안에서 센서·메모리·디스플레이와 대화하는 버스. 차량 ECU 보드와 실습용 디스플레이를 통해 본다.
5. **5장 CAN** — 여러 노드가 한 쌍의 선을 공유하는 버스. 중재, 오류 처리, ISO-TP, OBD-II의 7DF/7E0/7E8 주소.
6. **6장 자동차는 거대한 CAN 네트워크다** — 파워트레인·바디·게이트웨이, OBD-II 포트 핀 배치, 프로토콜 지도.
7. **7장 OBD-II 실전** — 쏘렌토에서 실제로 PID를 읽고, 값을 계산하고, 파이썬 대시보드로 띄운다.
8. **8장 UDS와 제조사 진단** — 0x22 DID, 세션, 음성 응답, DPF 데이터. 읽기와 쓰기의 경계를 배운다.
9. **9장 안전과 법·윤리** — 주행 중 조작, 쓰기 명령, 배터리, 보증, 개인정보.
10. **10장 IoT 프로토콜 지도** — MQTT·BLE·Modbus·Wi-Fi·LoRaWAN, 그리고 차량 데이터를 클라우드로 보내는 구조.
11. **11장 마이크로컨트롤러** — 인터럽트, 링 버퍼, 메인 루프, 메모리, GPIO.
12. **12장 도구와 디버깅** — 멀티미터, 로직 분석기, pyserial, python-can, ELM327, SocketCAN.
13. **13장 ESP32로 만드는 OBD-II 웹 게이지** — TWAI, CAN 트랜시버, 전원·종단, Wi-Fi 웹 화면, 저전력.
14. **14장 펌웨어의 시간과 메모리** — 스택·힙·정적 메모리, `volatile`, ISR, 링 버퍼, 워치독.
15. **15장 FreeRTOS로 CAN 수신 태스크 나누기** — 태스크·큐·우선순위, TWAI RX 큐·경보, Bus-Off 복구.
16. **16장 임베디드 Rust 맛보기** — 소유권, `embedded-hal`, Embassy, ESP32 Rust 현황.
17. **17장 차 없이 시작하는 CAN 실습실** — vcan, can-utils, python-can virtual, 가짜 ECU, ELM327-emulator, 로그 재생.
18. **18장 브라우저에서 시리얼 다루기** — Web Serial, ELM327 줄 파싱, Web Bluetooth BLE.
19. **19장 테스트 전략** — 단위 테스트, 로그 재생 회귀, 가짜 ECU 통합, HIL.
20. **20장 CAN 기록과 데이터 파이프라인** — candump/ASC/BLF/MF4, DBC 디코딩, SQLite/InfluxDB, 알람.
21. **21장 TypeScript로 CAN과 ELM327 다루기** — serialport, 프롬프트 파서, PID 타입, 응답 시간·처리량, socketcan.
22. **22장 캡스톤: 실시간 차량 대시보드 만들기** — 수집기, SQLite, SSE, 브라우저 게이지, 재연결, ELM327-emulator 검증.
23. **23장 CAN 보안** — 인증 없는 버스의 구조적 이유, 위협 모델, 게이트웨이·SecOC·IDS·UDS 인증, 규제, 가상 버스 실습.
24. **24장 J1939** — 트럭·중장비의 29비트 ID, PGN/SPN, 주소 클레임, TP.CM/TP.DT, DM1, 가상 버스 실습.
25. **25장 CANopen과 NMEA 2000** — 객체 사전, NMT, SDO/PDO, 하트비트, 선박 PGN과 fast packet.
26. **26장 CAN 위의 프로토콜 고르기** — OBD-II/UDS/J1939/CANopen/NMEA 2000 비교와 웹 프로토콜 대응.
27. **27장 학습 경로와 실습** — 무엇부터 사고 무엇을 만들어 볼지.

이미 목표가 정해져 있다면 위의 목적별 경로에서 시작해도 된다. 센서를 붙이는 일이 급하면 4장과 11장을, 장비와 통신해야 하면 2·3장을, 차량 데이터를 읽어야 하면 5·6·7·8장을 먼저 봐도 된다. 펌웨어 쪽을 먼저 보고 싶다면 11장 → 13장 → 14·15·16장 순서가 자연스럽다. 웹 스택으로 바로 만들어 보고 싶다면 21·22장을 먼저 펼쳐도 되지만, 3장의 프레이밍과 파싱은 한 번은 거치는 것이 좋다.

각 장은 같은 구조를 따른다.

- **도입**: 왜 알아야 하는지, 웹에서 비슷한 것이 무엇인지
- **본문**: 원리와 실무 함정
- **예시**: 코드, 바이트 덤프, 표, ASCII 그림
- **흔한 실수**: 증상과 원인
- **장 요약**: 다음 장으로 넘어가기 전에 남겨야 할 것
- **연습 문제**: 기초 확인부터 설계 문제까지

연습 문제 제목 앞의 `(기초)`·`(중급)`·`(심화)`는 난이도다. 기초는 본문 개념 확인, 중급은 계산·적용, 심화는 설계·판단이 필요한 문제다.

## 이 책이 다루지 않는 것

범위를 분명히 해 두면 기대가 어긋나지 않는다.

- **차량의 쓰기·코딩·플래싱은 다루지 않는다.** UDS의 쓰기 서비스가 무엇인지, 왜 위험한지는 설명하지만, 실제 차량에 보내는 방법은 실습하지 않는다. 고장 코드 삭제(Mode 04, UDS 0x14)도 마찬가지다. 읽기 전용 원칙은 9장에서 자세히 다룬다.
- **PCB 설계와 아날로그 회로 설계**는 다루지 않는다. 개발 보드와 브레이크아웃 모듈로 검증하는 데 필요한 전자 기초까지만 설명한다.
- **C 언어 문법 전체**를 가르치지 않는다. 포인터·비트 연산·`volatile`·고정폭 정수처럼 임베디드에서 특히 중요한 부분만 짚는다.
- **Rust 언어 전체**를 가르치지 않는다. 16장은 소유권·`embedded-hal`·Embassy를 맛보는 정도이며, Rust 입문서를 대체하지 않는다.
- **RTOS 내부 구현**은 다루지 않는다. 스케줄러 알고리즘을 구현하지는 않지만, ESP-IDF FreeRTOS로 CAN 수신 태스크를 나누는 사용법은 15장에서 다룬다.
- **CAN FD·CAN XL·차량 이더넷 실습**은 다루지 않는다. 6장에서 개념과 어댑터 지원 범위만 정리한다. 실제 차량의 FD/DoIP 진단은 해당 차량 문서와 장비가 필요하다.
- **J1939·CANopen·NMEA 2000은 개념과 가상 버스 실습까지** 다룬다. 실제 트럭·산업 설비·선박의 제어·정비·인증은 해당 표준 원문과 제조사 문서, 자격을 갖춘 현장 절차가 필요하다.
- **상용 전원(110/220V)과 고전압 장비**는 직접 다루지 않는다. 전기차의 고전압 배터리·구동계도 이 책의 범위 밖이다.

## 표기 규칙

- 숫자는 특별한 말이 없으면 10진수다. 바이트와 ID는 `0x123`, `A5 01 02`처럼 16진수로 쓴다.
- 영문 약어를 처음 풀어 쓸 때는 `OBD-II(On-Board Diagnostics II)`처럼 괄호를 붙여 쓴다. 괄호 안이 원어가 아니라 설명·조건이면 띄어 쓴다.
- `확인 필요`는 데이터시트·실측으로 확정하지 않은 값이나 경험칙이다. 실제 설계에 쓸 때는 데이터시트를 확인한다.
- 전압·속도·거리·가격은 대표값이나 경험칙인 경우가 많다. 부품·케이블·환경에 따라 달라진다.
- 코드 블록의 언어 표기는 `python`, `typescript`, `javascript`, `html`, `css`, `json`, `c`, `bash`, `text`를 쓴다.
- 차량 예시에서 `7E0`은 요청 주소, `7E8`은 그 응답 주소를 뜻한다. 응답 주소는 보통 요청 주소 + 8이다.
- "ECU"는 전자 제어 장치, "PCM"은 파워트레인 제어 모듈, "TCM"은 변속기 제어 모듈을 뜻한다. 차량에 따라 같은 장치를 다른 이름으로 부른다.

## 웹 개발자가 이미 가진 것

임베디드를 처음 시작하면 "나는 아무것도 모른다"는 기분이 들 수 있다. 하지만 웹 개발 경력은 이 분야에서 생각보다 큰 자산이다.

- **상태 기계**: 화면의 로딩·성공·오류 상태를 다뤄 본 경험은 통신 상태 기계와 펌웨어 상태 기계에 그대로 통한다.
- **비동기와 타임아웃**: "응답이 안 오면 어떻게 할 것인가"를 고민해 본 경험은 재전송·백오프·멱등성 설계로 이어진다.
- **테스트와 리팩터링**: 하드웨어 접근을 인터페이스로 분리하면 PC에서 파서와 상태 기계를 단위 테스트할 수 있다. 이 습관 하나가 디버깅 속도를 크게 바꾼다.
- **Git과 코드 리뷰**: 펌웨어에도 똑같이 적용된다.
- **로그와 관측**: 웹의 APM에 해당하는 것이 임베디드에서는 원시 바이트 로그, 하트비트, 오류 카운터, 리셋 원인이다.
- **문서화**: OBD-II처럼 스키마가 코드 밖에 흩어진 세계에서는 문서화가 곧 디버깅 도구다.

새로 메워야 할 것은 **C, 전자 기초, 계측과 하드웨어 디버깅**이다. 이 책은 그 세 가지를 통신이라는 실습 가능한 주제로 묶어서 설명한다.

이제 1장에서 웹 개발자의 사고방식이 어디서 어긋나는지부터 보자.
