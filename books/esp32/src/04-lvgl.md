# 4장 화면이 잘려 나온다: LVGL 데모와 남의 보드 설정

## 4.1 이번에는 AI가 직접 빌드하고 올린다

온보딩의 마지막 과제는 Waveshare 위키의 **LVGL 데모**였다. LVGL은 마이크로컨트롤러용 GUI 라이브러리다. 웹으로 치면 DOM과 CSS 없이 직접 그리는 작은 UI 프레임워크다.

> **질문 노트** — "너도 빌드하고 업로드할수 있지? 너가 1~4까지 해봐."

Claude는 Arduino IDE에 들어 있는 명령줄 도구(`arduino-cli`)로 IDE와 같은 설정을 써서 빌드하고 올릴 수 있다. 이번에는 사람이 버튼을 누르는 대신 Claude가 명령으로 진행했다.

## 4.2 데모 zip 열어 보기

위키의 데모 zip(약 93MB)을 받아 안을 먼저 봤다. 위키에 적힌 라이브러리와 실제 들어 있는 것이 조금 달랐다(**실측**).

| 라이브러리 | zip 안의 버전 | 위키 설명 |
|---|---|---|
| lvgl | 8.4.0 | 8.4.0 |
| ESP32_Display_Panel | 1.0.0 | 0.1.4 이상 |
| ESP32_IO_Expander | 1.0.1 | 0.0.4 이상 |
| **esp-lib-utils** | 0.1.2 | 언급 없음. 하지만 필요하다 |

라이브러리 폴더 넷과 LVGL 설정 파일 `lv_conf.h`를 Arduino 라이브러리 폴더(`문서\Arduino\libraries\`)에 복사했다. `ESP32_Display_Panel` 안에는 제조사 쪽 CMake 빌드 찌꺼기(`build/`, 실행 파일 포함)가 섞여 있어서 빼고 복사했다.

데모 스케치(`09_lvgl_Porting`)는 LVGL에 들어 있는 **위젯 데모**(`lv_demo_widgets`)를 띄운다. 탭, 버튼, 슬라이더가 있어서 터치를 확인하기 좋다.

## 4.3 첫 빌드는 10분이 넘었다

파티션을 `16M Flash (3MB APP/9.9MB FATFS)`로 두고 빌드했다. LVGL은 파일이 많아서 **첫 빌드가 10분을 넘겼다**(**실측**). 결과는 약 759KB였고, 한도가 3MB로 표시되어 파티션 설정이 먹었다는 것도 확인했다. 두 번째 빌드부터는 캐시 덕분에 훨씬 빨랐다.

> **알게 된 점** — 웹의 첫 `npm install` + 첫 번들링처럼, 임베디드도 첫 빌드가 가장 느리다. 이후로는 바뀐 파일만 다시 컴파일한다.

## 4.4 업로드가 "포트가 없다"고 한다

```text
A fatal error occurred: Could not open COM9, the port doesn't exist
```

그런데 장치 관리자에는 COM9가 멀쩡히 있었다. 더 새 버전의 esptool(v5)로 같은 포트를 열어 보자 진짜 이유가 나왔다.

```text
could not open port 'COM9': PermissionError(13, '액세스가 거부되었습니다.', None, 5)
```

3장 시리얼 테스트 때 열어 둔 **IDE의 Serial Monitor가 포트를 잡고 있었다.** Windows의 COM 포트는 한 번에 한 프로그램만 열 수 있다. 다른 프로세스가 독점 잠금으로 연 파일에 쓰려는 것과 같다. 옛 esptool(v4.6)은 이 상황을 "포트가 없다"고 잘못 보여 줬다.

Serial Monitor를 닫자 업로드가 됐다. 이번에는 BOOT+RESET 없이 자동 리셋으로 들어갔다(**실측**). 3장의 수동 다운로드 모드는 첫 한 번만 필요했다.

> **감탄 노트** — "오. 초기 화면이다."

## 4.5 어디서 헤맸나: 잘린 화면, 안 되는 터치

> **질문 노트** — "터치안되고, 화면도 이상해. 짤려 나오는데?"

화면은 떴지만 오른쪽과 아래가 잘렸고, 터치는 전혀 반응하지 않았다. 처음 의심한 것은 1장의 초기불량이었지만, 공장 데모에서는 화면과 터치가 모두 정상이었다. 그러면 남는 것은 설정이다.

데모 폴더의 보드 설정 파일 `esp_panel_board_custom_conf.h` 맨 위에 답이 있었다.

```c
#define ESP_PANEL_USE_1024_600_LCD (1)  // 0: 800x480, 1: 1024x600
#define ESP_OPEN_TOUCH 0                // 1: 터치 켬, 0: 터치 끔
```

이 파일은 4.3B 전용이 아니었다. 아래쪽에 보드 이름이 `ESP32-S3-Touch-LCD-5B`(1024×600)와 `ESP32-S3-Touch-LCD-5`(800×480)로 적혀 있다. **5인치 보드와 함께 쓰는 설정 파일**이고, 기본값이 1024×600에 터치 꺼짐이었다.

- 800×480 화면에 1024×600짜리 화면을 그리니 오른쪽과 아래가 잘렸다
- 터치는 처음부터 초기화되지 않았다

## 4.6 고칠 값은 어디서 가져오나

해상도와 터치 스위치만 바꾸면 될 것 같았지만, 800×480 쪽의 타이밍 값도 5인치 보드용이었다. 근거 없이 손대지 않기로 하고, 라이브러리(`ESP32_Display_Panel`)에 들어 있는 **4.3B 전용 정의**와 한 줄씩 비교했다(**문헌 기반**).

| 항목 | 데모 설정(800×480 쪽) | 라이브러리의 4.3B 정의 |
|---|---|---|
| 해상도 | 800×480 | 800×480 |
| 픽셀 클럭 | 16MHz | 16MHz |
| 수평 타이밍 HPW/HBP/HFP | 4 / 8 / 8 | 4 / 8 / 8 |
| **수직 타이밍 VBP/VFP** | **16 / 16** | **8 / 8** |
| 터치 | GT911, INT=GPIO4 | GT911, INT=GPIO4 |
| IO 확장 | CH422G | CH422G |

다른 것은 수직 여백 두 값뿐이었다. 결국 네 줄을 고쳤다.

```diff
-#define ESP_PANEL_USE_1024_600_LCD (1)
+#define ESP_PANEL_USE_1024_600_LCD (0)
-#define ESP_OPEN_TOUCH 0
+#define ESP_OPEN_TOUCH 1
-    #define ESP_PANEL_BOARD_LCD_RGB_VBP (16)
-    #define ESP_PANEL_BOARD_LCD_RGB_VFP (16)
+    #define ESP_PANEL_BOARD_LCD_RGB_VBP (8)
+    #define ESP_PANEL_BOARD_LCD_RGB_VFP (8)
```

> **알게 된 점** — VBP·VFP는 무엇인가. RGB LCD는 화면을 위에서 아래로 한 줄씩, 쉬지 않고 다시 그린다. 한 장(프레임)과 다음 장 사이에는 그림이 없는 줄이 몇 개 끼는데, 그림 앞쪽 여백이 Back Porch, 뒤쪽 여백이 Front Porch다. 화면 컨트롤러는 이 박자에 맞춰 신호를 기다리므로, 박자가 화면과 맞지 않으면 화면이 밀리거나 떨릴 수 있다(**문헌 기반**). 애니메이션 프레임 사이의 빈 시간을 양쪽이 같은 값으로 약속하는 것이라고 이해했다.

다시 빌드하자 크기가 759KB에서 771KB로 늘었다. 꺼져 있던 터치 드라이버(GT911)가 빌드에 들어간 만큼이다. 올리고 나니 화면 전체에 위젯 데모가 나왔고, 탭·버튼·슬라이더·네 귀퉁이 터치가 모두 반응했다(**실측**).

> **감탄 노트** — "화면도 터치도 정상이야."

## 4.7 데모 안에 이미 RTOS가 있었다

데모 코드는 이렇게 생겼다(요약).

```cpp
void setup() {
    Board *board = new Board();
    board->init();
    board->begin();
    lvgl_port_init(board->getLCD(), board->getTouch());

    lvgl_port_lock(-1);      // 뮤텍스 잡기
    lv_demo_widgets();       // UI 만들기
    lvgl_port_unlock();      // 뮤텍스 놓기
}

void loop() {
    Serial.println("IDLE loop");
    delay(1000);
}
```

`loop()`는 1초마다 `IDLE loop`를 찍고 잠든다. 그런데 그동안에도 화면은 부드럽게 움직이고 터치에 반응한다. LVGL이 **자기 태스크에서 따로** 화면을 그리고 터치를 처리하기 때문이다.

그리고 LVGL은 스레드 안전하지 않다. 그래서 `setup()`은 UI를 만들기 전에 `lvgl_port_lock()`으로 뮤텍스를 잡는다. 공유 자원(UI 트리)을 두 스레드가 동시에 건드리지 않게 하는, 웹 백엔드에서도 익숙한 패턴이다.

앞으로 할 RTOS 실험의 주제(태스크, 뮤텍스)가 첫 데모에 이미 들어 있었다.

## 알게 된 점

- 제조사 데모가 그 보드용이라는 보장은 없다. 설정 파일 맨 위부터 읽는다
- 값을 고칠 때는 근거를 찾는다. 이번에는 라이브러리에 든 그 보드의 정의가 근거였다
- 업로드가 "포트가 없다"고 하면, 다른 프로그램이 포트를 잡고 있는지 먼저 본다
- 화면이 움직이는 동안 `loop()`는 잠들어 있었다. 태스크는 이미 여럿이었다
