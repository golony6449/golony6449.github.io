# 5장 주니어에게 첫 태스크를 맡기다

## 5.1 AI 셋이 일하는 방식

이 실험실에서는 AI가 역할을 나눠 일한다. 회사의 개발 조직과 비슷하다.

| 역할 | 맡은 AI | 하는 일 |
|---|---|---|
| PL(리드) | Claude Code | 사용자와 대화, 계획 작성, 실행, 실제 보드 확인, 정리 |
| 주니어 | DeepSeek | 격리된 작업 폴더(워크트리)에서 구현하고 PR을 연다 |
| 리뷰어 | Qwen | PR의 diff를 계획과 대조해 검토한다 |

규칙은 하나다. **위험하거나 크리티컬한 일이 아니면 구현은 주니어에게 적극 맡긴다.** 비용이 싸고, PL의 토큰을 아낄 수 있기 때문이다.

## 5.2 LVGL 데모는 왜 맡기지 않았나

4장에서 필자가 먼저 제안했다.

> **질문 노트** — "가능하면 주니어에게 위임도 시켜볼래?"

Claude는 이번에는 맡기지 않았다. 이유는 둘이었다.

- 그 작업에는 **짤 코드가 없었다.** 라이브러리 복사, 컴파일, 업로드뿐이었다. 주니어의 흐름(구현 → PR → diff 검토)에서 검토할 diff가 생기지 않는다
- 주니어는 워크트리 밖의 파일을 건드릴 수 없다(안전장치). 라이브러리는 워크트리 밖인 `문서\Arduino\libraries`에 깔아야 했다

> **질문 노트** — "이 워크트리 내에서 하면 되지?"

기술적으로는 된다. `arduino-cli`에 라이브러리 폴더를 따로 지정하면 된다. 하지만 그러면 LVGL을 포함한 약 2,300개 파일을 공개 저장소에 커밋해야 한다. 웹으로 치면 `node_modules`를 커밋하는 셈이다.

대신 이 질문에서 좋은 아이디어가 나왔다. **저장소 안에 빌드 스크립트를 두면**, 주니어도 워크트리 안에서 자기가 짠 스케치가 실제로 컴파일되는지 확인할 수 있다. 다음 과제부터 그렇게 했다.

## 5.3 계획을 쓴다

주니어는 이 대화를 볼 수 없다. 그래서 PL이 쓰는 **계획 문서**가 주니어의 유일한 맥락이다. 계획에는 이런 것을 적었다.

- **지켜야 할 원칙(Global Constraints)**: 한국어 주석, 표준 라이브러리만, `shell=True` 금지, 실험 머리 주석 형식, 그리고 다음 두 함정
  - **ESP32의 FreeRTOS는 스택 크기를 워드가 아니라 바이트로 받는다**
  - 빈 `loop()`는 쉬지 않고 돌아 코어를 차지한다(관찰자 효과)
- **작업 1**: 빌드·업로드 진입점 `tools/build.py`. 함수 이름과 시그니처, 테스트 항목까지 적었다
- **작업 2**: 첫 태스크 실험 `experiments/00_first_task/`. 무엇을 찍을지, 크래시 스위치를 어떻게 둘지
- **리뷰 포인트(Review Focus)**: 리뷰어가 반드시 볼 다섯 가지
- **검사 명령**: 단위 테스트와 **실제 컴파일**

```bash
uv run --with pytest python -m pytest tests -q
python tools/build.py experiments/00_first_task
```

> **알게 된 점** — 주니어는 시그니처와 테스트는 잘 따르지만, 문서에만 적힌 의도("스택은 바이트다")는 놓치기 쉽다. 그래서 그런 원칙은 요약하지 않고 그대로 옮겨 적고, 리뷰 포인트에도 다시 넣었다.

## 5.4 결과: 첫 회차에 통과

주니어가 구현하고, 리뷰어가 검토하고, 지적이 있으면 주니어가 고치는 반복은 스크립트가 알아서 돈다. 이번에는 **첫 회차에 지적 없이 통과**했다.

| 항목 | 값 |
|---|---|
| 회차 | 1 |
| 비용 | 약 $0.039 (주니어 $0.027 + 리뷰) |
| 결과 | PR #1, 파일 6개 (빌드 스크립트, 테스트, 실험 스케치, 문서) |

> **감탄 노트** — 스케치 하나와 빌드 도구, 테스트까지 4센트였다.

## 5.5 머지 전에 보드에서 먼저

리뷰와 컴파일이 통과해도 실제 보드에서 도는지는 모른다. PL은 머지 전에 주니어가 만든 `tools/build.py --upload`로 직접 올려 봤다. 빌드 스크립트의 업로드 경로를 처음 써 보는 시험도 겸했다. 결과는 6장에서 다룬다.

한 가지가 틀려 있었다. 스케치 머리 주석의 예시 출력 `hwm=3948`은 주니어가 **짐작으로 쓴 값**이었다. 실측은 `hwm=2436`이었다. 머지한 뒤 실측값으로 고쳤다.

> **알게 된 점** — 리뷰어는 diff만 본다. 보드에서 찍힌 숫자는 보지 못한다. "실제 장치에서 나오는 값"은 사람(또는 PL)이 장치로 확인해야 한다.

## 5.6 머지가 막혔다

PL이 PR을 머지하고 워크트리를 지우려 하자, Claude Code의 자동 모드 안전장치가 막았다. main에 합치고 폴더를 지우는 일은 되돌리기 어렵다고 판단한 것이다.

PL은 우회하지 않고 멈춰서 물었다. 필자가 "머지해"라고 답한 뒤에도, 워크트리에 커밋하지 않은 변경이 없고 원격 브랜치와 같다는 것을 먼저 확인하고 나서야 머지했다.

> **알게 된 점** — AI에게 일을 맡길 때 가장 중요한 건 "되돌릴 수 없는 일 앞에서 멈추는가"다. 이번에는 멈췄다.

## 알게 된 점

- 주니어에게는 계획 문서가 유일한 맥락이다. 원칙은 요약하지 말고 옮겨 적는다
- 검사 명령에 **실제 컴파일**을 넣으면 임베디드 코드도 위임할 수 있다
- 리뷰를 통과해도 장치에서 나온 값은 따로 확인한다
