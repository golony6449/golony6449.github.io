# 6장 loop()도 태스크였다

## 6.1 실험: 내 태스크 하나

온보딩 B단계의 첫 세 과제를 스케치 하나로 묶었다.

| 과제 | 보는 것 | 소프트웨어 비유 |
|---|---|---|
| B-1 | `xTaskCreate`로 만든 태스크가 `loop()`와 따로 도는가 | 스레드 하나 띄우기 |
| B-2 | 코어를 고정하지 않은 태스크가 어느 코어에서 도는가 | affinity 없는 스레드 |
| B-3 | 스택을 얼마나 쓰는가, 넘치면 어떻게 되는가 | 스레드 스택의 최대 사용량 |

핵심만 줄이면 이렇다.

```cpp
#define STACK_BYTES 4096   // ESP32에서는 바이트 단위

static void my_task(void *arg) {
  for (;;) {
    tick++;
    Serial.printf("tick=%lu core=%d hwm=%u\n",
                  (unsigned long)tick,
                  (int)xPortGetCoreID(),                       // 지금 도는 코어
                  (unsigned)uxTaskGetStackHighWaterMark(NULL)); // 남은 스택(바이트)
    vTaskDelay(pdMS_TO_TICKS(1000));                            // 1초 잠들기
  }
}

void setup() {
  Serial.begin(115200);
  xTaskCreate(my_task, "my_task", STACK_BYTES, nullptr, 1, nullptr);  // 코어 고정 없음
}

void loop() {
  // 처음 한 번 자기 코어를 찍고 영원히 잠든다
  vTaskDelay(portMAX_DELAY);
}
```

`loop()`를 정말 비워 두지 않은 데는 이유가 있다. 빈 `loop()`는 쉬지 않고 다시 불려서 **core 1을 통째로 차지한다**(바쁜 대기). 관찰하려는 태스크가 아닌 곳에서 CPU를 쓰면 결과가 흔들린다. 관찰 장치가 결과를 바꾸는 **관찰자 효과**를 줄이려고 잠들게 했다.

## 6.2 보드에서 나온 줄

```text
tick=10 core=0 hwm=2436
tick=11 core=0 hwm=2436
tick=12 core=0 hwm=2436
...
```

(**실측**. 시리얼을 늦게 붙여 처음 몇 줄은 놓쳤다.)

> **질문 노트** — "이걸로 어떤 결론을 알수있어?"

세 가지를 얻었다.

## 6.3 결론 1: `loop()`도 태스크 하나일 뿐이다

`loop()`는 영원히 잠들어 있는데 `my_task`는 1초마다 계속 찍었다. 둘은 서로 다른 실행 흐름이다.

Arduino의 `setup()`/`loop()`는 특별한 구조가 아니라 FreeRTOS 위에서 도는 **`loopTask`라는 태스크**다. Arduino는 RTOS 위에 얹힌 프레임워크이고, `loop()`는 프레임워크가 대신 띄워 준 메인 스레드다. 웹으로 치면 프레임워크가 만들어 준 이벤트 루프 스레드에서 내 핸들러가 돌고 있었던 것이다.

그리고 잠든 태스크(`vTaskDelay`)는 CPU를 쓰지 않는다. `sleep()`한 스레드처럼, 스케줄러가 깨울 때까지 대기 목록에만 있다.

## 6.4 결론 2: affinity가 없다고 무작위는 아니다

코어를 고정하지 않았는데 줄마다 `core=0`이 나왔다. 태스크를 만든 `setup()`(loopTask)은 core 1에서 돈다(3장의 `core=1`).

"코어를 안 정하면 알아서 고르게 나눠 준다"가 아니다. 스케줄러의 내부 사정을 따른다.

왜 하필 core 0인가는 아직 **추정**이다. ESP32의 FreeRTOS는 시간이 흐르는 것을 세는 **틱 처리를 core 0이 맡는다.** 잠들었던 태스크가 깨어날 때 core 0이 먼저 집어 가는 것으로 보인다. 비유하면 알람을 관리하는 직원이, 알람이 울린 일을 자기가 바로 처리해 버리는 셈이다. 7장에서 이 추정을 받쳐 주는 단서가 하나 더 나온다.

이게 왜 중요한가. ESP32에서는 Wi-Fi와 블루투스 스택이 보통 core 0에서 돈다. 코어를 정하지 않은 태스크는 통신 처리와 같은 코어에서 경쟁하며 타이밍이 흔들릴 수 있다.

## 6.5 결론 3: 스택은 감이 아니라 재서 정한다

`hwm`(high water mark)은 태스크가 지금까지 스택을 **가장 깊이 썼을 때 남은 여유**다. 4096바이트 중 2436바이트가 남았으니, 가장 깊을 때 **약 1,660바이트**를 썼다. 하는 일이라고는 `printf` 한 줄뿐인데 이만큼이다. 대부분은 `printf`가 쓴다.

- 태스크마다 스택이 RAM을 따로 차지한다. 칩 내부 RAM은 512KB다. 태스크가 늘수록 스택을 재서 줄이는 일이 중요해진다
- hwm은 **지금까지 실행된 경로**에서의 최댓값이다. 아직 안 탄 분기(에러 처리 등)는 더 쓸 수 있다. 프로파일러의 최대 메모리가 테스트한 경로만 반영하는 것과 같다. 그래서 잰 값에 여유를 둔다
- 단위는 **바이트**다. 표준 FreeRTOS 자료(워드 단위, 32비트 칩에서 4바이트)를 그대로 따라 하면 4배가 어긋난다

## 6.6 로봇으로 옮기면

BALA2의 밸런싱은 "기울기 읽기 → 모터 제어"를 일정한 주기로, 놓치지 않고 돌려야 한다. 이번 결론을 옮기면 이렇다.

- 제어 루프는 **자기 태스크로 떼고, 코어를 직접 고정한다**(예: core 1). 통신은 core 0에 둔다. 결론 2처럼 맡겨 두면 원하는 코어에 간다는 보장이 없다
- 각 태스크의 스택은 hwm으로 재서 정한다

다음 실험들(타임 슬라이싱, 우선순위 굶주림, 큐, 뮤텍스)은 이렇게 나눈 태스크들이 **서로 부딪칠 때** 무슨 일이 생기는지를 본다.

## 알게 된 점

- Arduino의 `loop()`는 FreeRTOS 태스크다. 비워 두면 바쁜 대기가 된다
- 코어를 고정하지 않은 태스크의 배치는 무작위가 아니다. 중요한 태스크는 직접 고정한다
- 스택은 hwm으로 잰다. ESP32에서는 바이트 단위다
