# 2026-11-21 전체화면 디버그 오버레이 설계

## 1. 출발점 (오후, KST)

사용자: "지금은 HD 해상도로 ETS2를 창 모드로 띄우고, 그 아래에 분석 창을 하나 더 띄워두고 보고 있거든. 이런 형식이 아니라. 게임 화면 위 오버레이처럼 합성이 가능할까?"

- 현재 구조: `render_hud_frame()`이 캡처한 게임 프레임 **사본** 위에 박스·판단 근거·게이지를 그리고 `cv2.imshow`로 별도 창에 띄운다.
- 처음 짚은 위험: 캡처(mss/dxcam)는 화면 픽셀을 그대로 가져오므로, 게임 위에 그린 오버레이가 다음 프레임의 인식 입력에 섞인다(차선 검출기가 자기가 그린 선을 차선으로 읽는 되먹임).

사용자가 밝힌 이유: "듀얼 모니터가 아닌 상황에서, 전체화면으로 디버깅을 하려고 해."
표시 범위 결정: "지금은 모두 항상 나오게 하자."

> 교훈: 오버레이는 "그리는 문제"보다 "내가 그린 것을 내가 다시 보지 않게 하는 문제"가 먼저다.

## 2. 접근 선택

- A. ctypes Win32 투명 오버레이 창(맨 위·클릭 통과·포커스 안 가져감, 픽셀별 알파) + 캡처 제외 — **선택**
- B. PySide(Qt) 투명 창 — 무거운 의존성 대비 얻는 것이 적어 제외
- C. 전체화면 미러 창(게임 사본 + HUD) — 게임이 파이프라인 속도로 끊겨 보여 주행용으로 부적합
- 게임 내부 DirectX 후킹 — 파이썬으로 무리·위험해 제외
- 대안(플랜 B): 캡처 제외가 안 되면 Windows Graphics Capture의 게임 창 단독 캡처로 전환

사용자: "좋아. 그 전에 캡쳐에서 오버레이 빼고 캡처가 되는지 부터 확인하는거지?"

## 3. 스파이크: 캡처 제외 확인

구현 주체: Claude — 결과를 바로 보고 판단해야 하는 일회성 시험 코드.

방법: 화면 (200,200)에 480×320 자홍 오버레이(왼쪽 불투명, 오른쪽 알파 128)를 `UpdateLayeredWindow`로 띄우고, `SetWindowDisplayAffinity`를 `WDA_NONE` → `WDA_EXCLUDEFROMCAPTURE(0x11)`로 바꿔 가며 주변 560×400 영역을 캡처, 자홍 픽셀 비율을 셌다. 프로젝트 venv에는 dxcam이 없어(실주행은 mss 사용 중) dxcam은 `uv run --with dxcam`으로 임시 시험했다.

| 백엔드 | WDA_NONE | WDA_EXCLUDEFROMCAPTURE |
|---|---|---|
| mss | 0.686 (오버레이 찍힘) | 0.000 |
| dxcam | 0.686 | 0.000 |

0.686은 오버레이 면적/캡처 면적(480·320 / 560·400)과 정확히 같다. 제외 시 0%가 "검은 사각형"일 가능성을 이미지로 확인했고, 오버레이 아래의 ETS2 밤 장면이 그대로 찍혔다(당시 ETS2 창 모드 실행 중, Windows 11 빌드 26300).

> 책 소재: 비율 0%만 믿지 말고 그림을 열어 봐야 한다 — 제외된 창이 검게 찍히는 API(`WDA_MONITOR`)도 있다.

## 4. 전체화면 확인과 캡처 성능

사용자: "ETS2 전체화면으로 바꿨어" → 오버레이를 15초 띄워 둠. 사용자: "사각형 봤어. 전체화면은 2560 1600으로 바꿨어."

- 전체화면(2560×1600)에서도 오버레이는 눈에 보이고, mss 캡처에는 아래 게임 화면(차고 메뉴)만 찍혔다. 게임 최소화 없음.
- 그런데 해상도가 커지자 캡처가 문제가 됐다. 2560×1600 전체 캡처 + 1280×720 축소 측정:
  - mss: 잡기 41ms + INTER_AREA 20ms ≈ 61ms → 30Hz 예산(33ms) 초과, 캡처만으로 최대 16Hz
  - dxcam(`uv run --with dxcam` 임시): 잡기 4.2ms + INTER_LINEAR 1.4ms ≈ 6ms
- 코드에서 찾은 것: dxcam은 `live` 묶음에 없었다(실주행은 mss로 돌던 중). dxcam은 화면 변화가 없으면 `None`을 주는데(정지 화면 60회 중 35회) 지금 코드는 이를 실패로 보고 합성 프레임으로 넘어간다. mss는 매 프레임 새로 연다.

> 교훈: "창 하나 더 띄우기"로 시작한 사용성 작업이 해상도를 바꾸는 순간 캡처 성능 문제로 번졌다. 화면 크기는 UI만의 문제가 아니다.

## 5. 설계 문서

`docs/superpowers/specs/2026-11-21-ets2-fullscreen-overlay-design.md` 작성. 오버레이 창(ctypes) + 투명 HUD 층 렌더링 + `--hud-mode` + 캡처 경로 수정(dxcam 추가, None 시 직전 프레임 재사용, mss 재사용) + 실기 검증 도구. 작업 프레임은 1280×720 유지, 전체화면 기준 재캘리브레이션은 운영 절차로 분리.

## 6. 로그 질문과 설계 승인, 계획

사용자: "녹화는 필요없을것 같아. 그런데 분석용 로그들은 필요한데 그건 남는거지?"
→ `frames.jsonl`은 파이프라인의 `DatasetLogger`가 HUD와 무관하게 남기고, 원래 화면 이미지는 기록하지 않는다. 오버레이로 바뀌어도 그대로라고 답했다.

사용자: "설계 승인, 계획 짜줘"

계획(`docs/superpowers/plans/2026-11-21-ets2-fullscreen-overlay-plan.md`)을 쓰면서 설계 두 곳을 다듬었다.
- HUD 층: 좌표를 일일이 바꾸는 대신, 기존 그리기 코드를 1280×720에서 **검은 배경·흰 배경에 두 번** 그려 그 차이로 픽셀별 알파를 구하고 화면 크기로 늘린다. 작업 프레임이 화면을 x·y 비례로 줄인 것이라 박스 위치가 정확히 맞는다(대가: 16:10에서 글자 세로 약 11% 늘어남).
- dxcam `None`: 처음엔 "0.5초 넘으면 실패"로 적었지만, 게임 일시정지처럼 정지 화면이 길면 합성 프레임(가짜 도로)이 인식에 들어간다. `None`은 "화면이 안 바뀌었다"는 뜻이므로 시간 제한 없이 직전 프레임을 재사용하는 것으로 바꿨다.

> 교훈: 투명도는 "두 배경에 그려 보고 차이를 재면" 기존 그리기 코드를 한 줄도 안 고치고 얻을 수 있다.

## 8. 핫키는 오버레이에서도 되나? — 상태 표시 추가와 F10 충돌

사용자: "게임 화면에서 키보드로 오버레이의 내용도 조작이 되는거지? 예를들어 사용자 조작으로 자율주행이 중단되었을 때 F10을 눌러서 재기동을 한다던지 하는것들 말이야."

- 핫키는 `_GlobalHotkeyPoller`(`GetAsyncKeyState`)라 포커스와 무관하고, 오버레이는 입력을 받지 않으니 그대로 동작한다고 답했다.
- 코드를 보다 빈틈 발견: 콘솔이 안 보이는 전체화면에서 F10 일시정지와 F12 비상 정지(래치, F10으로 안 풀림)가 HUD에 똑같이 `⚠ 비상/중립`으로만 보인다. → 사용자 승인("응 181 에 내용 추가해주고 설계 계획도 수정해줘")으로 설계 §5.6 주행 상태 배지(`run_state`: driving/paused/takeover/kill_switch + 키 안내)를 추가하고 SCRUM-181 본문과 계획 Task 2~4를 고쳤다.

사용자: "근데 지금 F10이 스크린샷에 매핑되어 있는것 같거든? 그래서 전달이 안되는것 같은데, 이 부분도 확인해줘"

- 프로필 `controls.sii` 확인: 우리 핫키가 전부 ETS2 단축키와 겹친다. F1 advmouse, F2 showmirrors, **F3 showhud(게임 HUD·미니맵 토글 — 미니맵 인식 입력이 사라짐)**, F4 adjuster, F5 advzoomout, **F10 screenshot**, F12 headreset.
- 하지만 게임이 키를 처리해도 `GetAsyncKeyState`는 키 상태를 읽을 수 있다. 다른 원인 후보: 제어 루프 한 바퀴에 한 번만 "지금 눌려 있나"를 보므로, 전체화면에서 한 바퀴가 100ms를 넘으면 짧은 탭을 놓칠 수 있다.
- 2ms 간격 측정기 1차(60초): 감지 0회. ETS2·파이썬 모두 일반 권한이라 권한(UIPI) 문제는 아님. 측정 중 키를 안 눌렀을 가능성이 있어 3분짜리로 재측정 중.
