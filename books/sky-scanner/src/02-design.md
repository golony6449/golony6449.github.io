# 2장 무엇을 만들지 대화로 정하기

## 2.1 "이걸 만들고 싶어"에서 시작

드라이버 문제를 풀기 전, 첫 대화는 이렇게 시작했다.

> 자 이제 내가 꿈꾸던 에어밴드 수신기를 만들 거야.

Claude는 바로 코드를 짜지 않았다. "브레인스토밍" 절차에 따라, 무엇을 만들고 싶은지 장면으로 설명해 달라고 했다. 이 장은 그 대화로 설계가 어떻게 모양을 잡았는지를 정리한다.

## 2.2 한 번에 하나씩 묻는 대화

에이전트는 한 메시지에 질문을 하나씩만 던졌다. 답을 들으면 이해한 내용을 다시 정리해 보여 주고(플레이백), 틀린 곳이 있는지 물었다. 대화의 흐름은 대략 이랬다.

| 질문 | 답 | 설계에 남은 것 |
|---|---|---|
| 완성되면 어떤 장면을 기대하나 | 처음엔 PC 앞에서 듣고, 결국은 항상 켜 둔 컴퓨터로 받아 다른 기기에서 듣고 싶다. 화면에 교신 내용과 항공기 정보가 뜨면 최고 | 상시 수신, 원격 청취, 지도와 자막 |
| 무엇을 듣고 싶나 | 인천 컨트롤과 항공기의 교신. FM 라디오도 직접 받아서 듣고 싶다 | 에어밴드 + FM 전환 |
| 지금은 어떻게 듣고 있나 | 아직 아무것도. **이제 들어 보고 싶다** | 설계를 잠시 멈추고 바로 들어 보기(1장, 4장) |
| 다 만들었는데 "이건 아닌데" 싶을 상황은 | 자막이 자주 틀리는 것. 라디오 수신이 너무 안 되는 것 | 안티 목표 두 개 |
| 확신이 낮은 자막은 | 흐린 글씨로 "추정"이라고 표시해 달라 | 자막 표시 규칙 |

"이제 들어 보고 싶다"는 답이 흥미로웠다. 설계 대화를 하다가도 실제로 손에 잡히는 걸 먼저 해 보는 게 낫다는 판단이 나왔다. 그 덕분에 드라이버 문제를 첫날 찾았다. 설계부터 끝까지 했다면 코드를 다 짠 뒤에야 "왜 아무것도 안 들리지"를 만났을 것이다.

> **알게 된 점** — 하드웨어가 끼는 프로젝트에서는 설계 문서보다 **"일단 소리가 나는지"**를 먼저 확인하는 게 싸다. 소프트웨어가 아무리 잘 짜여도 그 아래층(드라이버, 안테나)이 안 되면 의미가 없다.

## 2.3 화면은 보고 고른다

화면 배치는 말로 정하기 어렵다. 에이전트가 브라우저에 시안 세 개를 띄웠다.

- **A. 지도 중심:** Flightradar처럼 지도가 크고, 교신 자막은 옆에 쌓인다.
- **B. 교신 중심:** 대화창처럼 교신이 크게 흐르고, 지도는 작은 보조 창이다.
- **C. 비행기 카드 중심:** 비행기마다 카드가 있고, 카드 안에 그 비행기의 최근 교신이 붙는다.

A를 골랐고, "교신을 좀 더 강조해 줘도 좋겠다"는 의견을 냈다. 다음 시안 두 개 중에 **A1(지도 위 실시간 자막)**을 골랐다. 지금 말하는 내용이 영화 자막처럼 지도 아래쪽에 크게 뜨고, 그 비행기가 지도에서 반짝이는 화면이다.

```text
┌──────────────────────────────────────────────────────┐
│ ▶ 서울 접근 119.75  ● 수신중   [FM 전환] 🔊             │
├──────────────────────────────────────┬───────────────┤
│        지도   ✈ KAL714 (강조)          │ 지나간 교신     │
│  ┌────────────────────────────────┐  │ 22:51 KAL714  │
│  │ 🎙 관제 → KAL714                 │  │  ▶ 다시 듣기   │
│  │ Korean Air 714, descend …      │  │               │
│  └────────────────────────────────┘  │               │
└──────────────────────────────────────┴───────────────┘
```

> **알게 된 점** — 시안을 보면 생각이 바뀐다. 말로만 했다면 "지도도 크고 자막도 크게" 같은 모호한 요구로 끝났을 것이다.

## 2.4 어디서 돌릴까: 노트북에서 서버로, 다시 노트북으로

실행할 컴퓨터는 몇 번 바뀌었다.

1. 처음에는 "이 노트북을 계속 켜 둔다"였다.
2. 다음 날 GPU 없는 미니 서버(i5-12500T, 32GB)가 도착한다는 이야기가 나왔다. 설계를 "Ubuntu 서버가 상시 수신, 노트북은 개발용"으로 고쳤다. OS는 Ubuntu Server 24.04로 정했다.
3. 그런데 "서버는 설치할 때 이야기고, **이번에는 이 컴퓨터로 해 보자. 모델도 돌려 보고 싶다**"로 다시 정리했다. 노트북에는 RTX 3060이 있어서 음성 인식 모델을 GPU로 돌려 볼 수 있다.

결과적으로 설계에는 이렇게 남았다.

- 이번 범위는 **Windows 노트북**에서 개발하고 계속 켜 둔다.
- 서버로 옮기는 작업은 **나중**이다. 다만 코드는 처음부터 OS에 묶이지 않고, GPU 없이도 돌게 짠다. 음성 인식 엔진만 바꾸면 서버에서도 돌아가야 한다.

> **알게 된 점** — 이런 왕복은 낭비가 아니다. 설계 문서를 고칠 때마다 "왜 바뀌었나"가 문서에 남았다. 나중에 서버로 옮길 때 무엇을 바꿔야 할지가 이미 정리돼 있다.

## 2.5 듣는 건 괜찮지만, 퍼뜨리면 안 된다

밖에서도 휴대폰으로 듣고 싶다고 했을 때, 에이전트는 공개 URL 대신 **Tailscale**(내 기기끼리만 잇는 사설 네트워크)을 제안했다. 이유는 편의만이 아니었다. 한국 전파법은 수신한 무선 통신의 내용을 다른 사람에게 알리거나 공개하는 것을 금지한다. 그래서 설계에 "나만 보는 화면"을 원칙으로 넣었다. 이 책에서 실제 교신을 그대로 옮기지 않는 이유도 같다.

## 2.6 설계 문서에 남은 것

대화가 끝나고 설계 문서(`docs/superpowers/specs/2026-11-05-airband-receiver-design.md`)가 만들어졌다. 구성은 다음과 같다.

- 의도와 이유, 현재 상태(실측 결과 포함)
- 목표, 하지 않을 것, **이렇게 되면 실패(안티 목표)**
- 화면(A1)
- 제약(동글 하나, 드라이버 V1.4.0 이상, OS 독립, 원격 접속)
- **사용자가 정한 것**과 **에이전트가 정한 것(확인받지 않은 기본값)**을 나눈 표
- 단계(구현 순서)와 검증 방법

가장 유용했던 것은 마지막 구분이다. 에이전트가 임의로 정한 기본값(예: 녹음 보관 7일, 신호 처리를 파이썬으로 직접 짜기)이 "사용자가 동의한 것"처럼 섞이지 않는다. 나중에 읽는 사람이 "이건 바꿔도 되는 값"인지 바로 알 수 있다.

## 2.7 알게 된 점

- **질문은 하나씩, 정리는 자주.** 한 번에 열 개를 물으면 대충 답하게 된다. 하나씩 묻고 매번 정리해 보여 주니 틀린 이해를 일찍 잡았다.
- **안티 목표를 묻는 질문이 강력하다.** "다 만들었는데 아니다 싶을 상황"을 물으니 진짜 우선순위(자막 정확도, 수신 품질)가 나왔다. 이후 모든 계획의 테스트와 검증이 이 두 가지를 향한다.
- **결정한 사람을 기록한다.** "사용자 결정"과 "에이전트 기본값"을 나눠 적으면 문서를 믿을 수 있게 된다.
