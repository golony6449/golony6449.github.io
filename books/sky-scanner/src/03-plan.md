# 3장 계획을 쪼개고 AI에게 맡기기

## 3.1 구현은 DeepSeek에게

설계를 승인하면서 이렇게 말했다.

> 실제 구현은 가능한 최대한으로 딥시크를 사용할 거야. 그거 고려해서 계획 세워 줘.

필자의 작업 환경에서는 역할이 나뉘어 있다.

- **Claude(대화 중인 에이전트):** 설계, 계획, 판단, 실기 검증, 마무리
- **DeepSeek(다른 모델로 돌아가는 코딩 에이전트):** 격리된 작업 폴더(git 워크트리)에서 계획대로 코드와 테스트를 짜고 PR을 만든다
- **Qwen(또 다른 모델):** DeepSeek이 만든 변경을 리뷰한다

DeepSeek은 싸고 빠르지만 대화의 맥락을 모른다. 볼 수 있는 것은 저장소 안의 파일뿐이다. 그래서 **계획 문서가 곧 DeepSeek의 전부**가 된다. 이 장은 그런 상대를 위해 계획을 어떻게 썼는지를 다룬다.

## 3.2 한 번에 다 하지 않는다

설계 전체를 계획 하나에 넣으면 작업이 20개를 넘는다. DeepSeek 작업 하나의 비용 상한(작업당 1달러 정도)을 넘기도 한다. 그래서 설계의 단계별로 계획을 나눴다.

| 일감 | 내용 |
|---|---|
| 1차 | 수신 코어와 최소 웹 화면(채널 분리, 스켈치, 녹음, 실시간 소리, FM 전환) |
| 2차 | 비행기 지도(adsb.lol, 노선, GPS 집 위치) |
| 3차 | 교신 자막(엔진 교차 검증과 비교 화면) |
| 4차 | 자막의 편명을 비행기와 연결 |
| 5차 | 상시 운용(자동 시작, Tailscale) |

각 단계가 끝날 때마다 실제로 써 볼 수 있다. 1차만 끝나도 브라우저로 관제 교신을 들을 수 있다. 이 일감들은 Linear(일감 관리 도구)에 올리고, 앞 단계가 끝나야 다음이 시작되도록 선후 관계를 걸었다.

## 3.3 DeepSeek을 위한 계획의 모양

계획 문서의 작업 하나는 대략 이런 모양이다.

- **파일:** 새로 만들 파일, 고칠 파일, 테스트 파일 경로
- **인터페이스:** 이 작업이 쓰는 것과 내놓는 것의 정확한 이름과 타입
- **실패하는 테스트부터:** 테스트 이름과 검사할 값
- **구현 단계:** 함수 시그니처와 꼭 지켜야 할 값만 적고, 몸체는 맡긴다
- **확인과 커밋:** 실행할 명령과 기대 결과

예를 들어 1차 계획의 채널 분리 작업에는 이런 테스트가 들어 있다.

```python
def test_channelizer_isolates_channels():
    sig = am_tone(+175_000)                         # 119.1MHz 채널(중심 118.925)
    outs = Channelizer(FS, 118_925_000, [118_100_000, 119_100_000, 119_750_000]).process(sig)
    p = [10*np.log10(np.mean(np.abs(o)**2)) for o in outs]
    assert p[1] - max(p[0], p[2]) > 30              # 다른 채널로 새는 양 30 dB 이상 차단
```

실제 전파 대신 **컴퓨터로 만든 신호**로 테스트한다. 그래서 DeepSeek은 동글 없이도 자기 코드가 맞는지 확인할 수 있다.

> **알게 된 점** — 웹 개발에서 외부 API를 목(mock)으로 바꿔 테스트하듯이, 신호 처리도 "알고 있는 신호를 넣고 결과를 재는" 방식으로 테스트할 수 있다. 1kHz 톤을 넣었으면 1kHz가 나와야 한다.

## 3.4 테스트가 못 잡는 것: Review Focus

계획마다 **Review Focus**라는 절을 둔다. 설계가 말하지 않았지만 실제로 사용하는 사람을 괴롭힐 상황 다섯 가지와, 그 상황을 막는 테스트다. 1차 계획에는 이런 것들이 들어갔다.

1. 실행 중에 동글을 뽑았다 꽂으면 → 죽지 않고 다시 붙어야 한다
2. 교신을 녹음하는 도중에 FM으로 전환하면 → 녹음이 버려지면 안 된다
3. 휴대폰 브라우저가 느리면 → 수신 스레드가 막히면 안 된다
4. 디스크에 쓸 수 없으면 → 녹음만 실패하고 수신은 계속돼야 한다
5. 반송파가 계속 켜져 있으면 → 스켈치가 영원히 열려 있으면 안 된다

## 3.5 실제 표본을 넣는다

DeepSeek도, 리뷰하는 Qwen도 실제 데이터를 보지 못한다. 그래서 데이터를 해석하는 작업에는 **실제로 받은 원문**을 계획에 그대로 넣었다.

- 2차 계획: 실제 adsb.lol 응답에서 다섯 항목을 발췌했다. 그중에는 공항 관제탑 장비(`"r": "TWR"`)와 고도가 숫자가 아니라 문자열 `"ground"`인 비행기가 섞여 있다. 테스트는 "이 다섯 개를 넣으면 비행기 세 대만 남아야 한다"를 확인한다.
- 2차 계획: GPS가 실제로 내보낸 NMEA 문장을 넣었다. 단, 좌표는 개인정보라 다른 값으로 바꾸고 체크섬을 다시 계산했다.

> **알게 된 점** — 문서만 보고 짠 파서는 실제 데이터의 이상한 구석(`"ground"` 같은)에서 깨진다. 실제 응답 몇 줄을 테스트에 박아 두는 것이 가장 싼 보험이다.

## 3.6 실기 검증은 사람과 Claude의 몫

동글 입력, 실제 소리, 브라우저 화면은 코드 리뷰로 확인할 수 없다. 그런 작업에는 계획에 **"리스크하기 때문에 Claude가 최종 검증 진행"**이라는 표시를 붙였다. 이 표시가 있는 작업은 테스트를 통과해도, Claude가 실제 장비로 확인한 뒤에 합친다.

## 3.7 지금까지의 상태

이 장을 쓰는 시점(2026-11-06)에는 1~3차 계획이 작성되어 저장소에 올라가 있고, 구현은 아직 시작 전이다. 구현이 진행되면 DeepSeek이 실제로 어떻게 짰는지, 리뷰에서 무엇이 걸렸는지, 실기 검증에서 무엇이 터졌는지를 이 장 뒤에 이어 쓴다.

## 3.8 알게 된 점

- **맥락 없는 구현자에게는 계획이 전부다.** 이름, 타입, 테스트 값, 실제 데이터 표본까지 계획에 들어 있어야 한다.
- **작게 나누면 단계마다 쓸 수 있는 결과가 나온다.** 1차가 끝나면 이미 "듣는 기계"가 된다.
- **사람이 확인해야 하는 곳은 미리 표시한다.** 자동 검증과 실기 검증의 경계를 계획 단계에서 정해 두면, 나중에 "테스트는 통과했는데 소리가 이상해요"를 줄일 수 있다.
