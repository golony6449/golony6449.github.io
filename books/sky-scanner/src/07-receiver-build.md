# 7장 밤사이 만든 수신기: AI 셋이 일하는 방식

## 7.1 "나 자러 간다, 잘 부탁해"

1~3차 계획을 다 쓴 날 밤, 필자는 이렇게 맡기고 잠자리에 들었다.

> 진짜 어쩔 수 없는 부분이나 크리티컬한 부분, 보안 이슈가 있는 부분이 아니면 최대한 딥시크로 개발해 줘. … 나 자러 간다, 잘 부탁해.

이 장은 그날 밤 약 1시간 10분 동안 1차(수신 코어와 최소 웹 화면)가 만들어진 과정이다. 역할은 셋으로 나뉘었다.

| 역할 | 누가 | 한 일 |
|---|---|---|
| 오케스트레이터 | Claude(메인 세션) | 작업 묶기, 지시문 쓰기, 결과 판정, 실기 관점 리뷰, 머지, 기록 |
| 구현자 | DeepSeek | 격리된 워크트리에서 코드와 테스트를 짜고 PR을 만든다 |
| 리뷰어 | Qwen | PR의 diff를 보고 지적한다. 지적이 있으면 DeepSeek이 고치는 반복을 자동으로 돈다 |

## 7.2 묶어서 동시에 돌리기

1차 계획의 작업 8개를 네 묶음으로 나눴다.

| 묶음 | 작업 | 이유 |
|---|---|---|
| A | 프로젝트 뼈대와 설정 | 의존성을 한곳에서 넣어야 뒤 작업이 의존성 파일로 충돌하지 않는다 |
| B(동시 3개) | DSP / 스켈치·녹음·저장 / IQ 소스와 Hub | 서로의 인터페이스에 기대지 않는다 |
| C | 수신 스레드 | B 전부를 쓴다 |
| D | 웹 서버와 화면 | C를 쓴다 |

묶음 B는 DeepSeek 세 개가 각자의 워크트리에서 동시에 일했다. 화면에는 진행 탭 세 개가 나란히 떠서, 각 DeepSeek이 어떤 파일을 읽고 무엇을 고치는지 흘러갔다.

## 7.3 울타리에 부딪힌 AI

시작하자마자 진행 탭에 경고가 떴다.

```text
ds-guard: 워크트리 밖 경로(~/.claude/settings.json)다.
```

> **질문 노트** — "딥시크 세션에서 이 오류는 왜 나?"

DeepSeek 세션에는 자기 워크트리 밖을 건드리지 못하게 막는 훅이 붙어 있다. 로그를 보니 DeepSeek은 `.claude/review.json`(검사 명령 설정)을 만든 직후, 전역 설정의 권한 규칙을 grep으로 들여다보려 했다. 그 폴더에 써도 되는지 확인하려던 것으로 보인다. 훅이 막았고, DeepSeek은 지시문대로 우회하지 않고 작업을 끝냈다.

> **알게 된 점** — AI에게 일을 맡길 때 울타리는 필수다. 대부분 선의의 호기심이지만, 개인 설정이나 다른 프로젝트를 건드리는 순간 사고가 된다. 다음 지시문부터는 "워크트리 밖은 **읽지도** 않는다"를 명시했다.

## 7.4 오케스트레이터의 진짜 일: 인계

묶음이 끝날 때마다 Claude가 한 일 중 가장 중요한 것은 **앞 작업에서 알게 된 사실을 다음 작업에 넘겨주는 것**이었다.

- 1번 작업에서 DeepSeek이 확인했다. "pyrtlsdr는 DLL이 없으면 import하는 순간 ImportError를 낸다." → IQ 소스 작업 지시문에 "rtlsdr import는 open() 안에서, 테스트는 가짜 모듈로"를 넣었다.
- 스켈치 작업 결과를 읽다 보니, 잡음 바닥이 첫 프레임 전에는 `NaN`이었다. 그런데 이 값은 상태 JSON에 실려 브라우저로 간다. **JSON에는 `NaN`을 넣을 수 없다.** → 수신 스레드 작업 지시문에 "NaN은 None으로, `json.dumps(allow_nan=False)` 테스트 추가"를 넣었다.

각 DeepSeek은 자기 작업만 안다. 작업과 작업 사이의 틈은 전체를 보는 쪽이 메워야 한다. 웹 개발로 치면, 백엔드 팀과 프론트엔드 팀 사이에서 API 계약을 챙기는 사람의 일이다.

## 7.5 리뷰어가 놓친 두 결함

Qwen은 PR 여섯 개를 모두 통과시켰다. 그런데 계획에 "Claude가 최종 검증"이라고 표시한 작업들의 코드를 직접 읽어 보니, **실제 동글에서만 터질** 결함이 두 개 있었다.

**첫째, 같은 값을 다시 설정하면 실패한다.** 동글을 열 때 주파수 보정값(ppm)을 0으로 설정하는 코드가 있었다. 그런데 librtlsdr는 현재 값과 같은 ppm을 다시 설정하면 오류 코드(-2)를 돌려주고, pyrtlsdr는 이를 예외로 바꾼다. 장치를 막 열면 ppm은 이미 0이다. 그래서 기본 설정에서는 동글이 **매번 열리지 않는다.**

**둘째, USB는 512바이트 단위다.** 수신 스레드는 한 번에 240,000샘플(480,000바이트)을 읽는다. 이 숫자는 신호 처리 쪽 조건(150의 배수)만 보고 정한 것이었다. 그런데 USB 대량 전송은 보통 512바이트 단위로 움직이고, 480,000은 512의 배수가 아니다(937.5배). 의심이 들어 설치된 pyrtlsdr 코드를 열어 보니 이런 주석이 있었다.

```python
# FIXME: librtlsdr may not be able to read an arbitrary number of bytes
```

요청한 만큼 못 받으면 `Short read` 예외를 내고 장치를 닫는다. 실제 동글이었다면 매 블록 끊기고 다시 붙는 상태가 됐을 것이다.

두 결함 모두 테스트는 통과했다. 테스트가 가짜 모듈을 썼기 때문이다. 그리고 diff만 보는 리뷰어는 **라이브러리 내부의 관습**을 모른다. 이런 결함은 그 라이브러리를 써 본 경험이나, 의심이 들 때 소스를 직접 열어 보는 습관으로만 잡힌다.

> **알게 된 점** — 두 번째 결함은 계획을 쓴 Claude의 실수이기도 하다. 블록 크기를 정할 때 신호 처리 계층의 배수 조건만 보고 USB 계층의 배수 조건을 보지 않았다. **계층마다 배수 조건이 다르다.** 하나의 숫자가 여러 계층을 지나간다면, 모든 계층의 조건을 같이 봐야 한다.

수정은 Claude가 직접 하지 않았다. 두 줄짜리 수정이었지만 "최대한 DeepSeek"이라는 지시와 "고치는 것은 구현한 쪽"이라는 흐름을 지켰다. 지적을 받은 DeepSeek은 그냥 받아들이지 않았다. 설치된 pyrtlsdr 소스를 직접 읽어 지적이 맞는지 확인한 뒤 고쳤고, 재현 테스트까지 넣었다. 세션을 이어 써서 맥락을 다시 읽지 않으니, 수정 비용은 첫 구현의 몇 분의 일이었다.

## 7.6 동글 없이 실서버 돌려 보기

동글은 PC에서 빠져 있었다. 그래도 화면 작업은 실제로 띄워 봐야 했다. 그래서 **전파를 직접 만들었다.**

1. 119.75MHz(중심 118.925MHz에서 +825kHz) 자리에 1kHz AM 톤을 넣는다. 2초 켜고 2초 끄기를 반복한다.
2. 잡음을 섞어 rtl_sdr `.bin` 형식(uint8 I, Q)으로 12초 분량(57MB)을 쓴다.
3. 수신기를 재생 모드(`sky-scanner --replay synth.bin`)로 띄운다.

결과는 이랬다.

- 상태 API: 119.75 채널만 열렸다(신호 -9.7dB / 잡음 -55dB). 옆 채널 두 개는 닫혀 있었다.
- 녹음: WAV 파일이 모두 정확히 **2.82초**였다(톤 2초 + 앞 0.3초 + 뒤 0.5초 + 프레임 반올림).
- 브라우저: 맨 위 막대에서 119.75 칩이 켜지고, 교신 목록이 쌓였다. FM 버튼을 누르자 "FM 청취 중 · 89.1MHz"로 바뀌었다.

> **감탄 노트(오케스트레이터의 것)** — 에어밴드로 돌아왔을 때 목록에 1.7초짜리 교신이 하나 생겨 있었다. FM으로 전환하는 순간 녹음 중이던 교신이 잘린 채 저장된 것이다. 계획에 적어 둔 "전환할 때 녹음을 버리지 않는다"가 눈앞에서 동작한 순간이었다.

이 시험에서 작은 결함도 하나 드러났다. DB의 교신 길이가 3.7초로, WAV(2.82초)보다 길었다. 재생 모드가 블록마다 0.1초를 쉬고 처리 시간이 더해져 실제보다 느리게 돌기 때문이다. 실제 동글은 하드웨어가 속도를 맞추니 재생 모드에서만 생기는 문제다.

## 7.7 숫자로 본 1차

| 항목 | 값 |
|---|---|
| 작업 PR | 6개(작업 8개) |
| 테스트 | 67개 |
| Qwen 판정 | 바로 통과 4, Claude 판정 2(지적 0, 계획에 없던 파일) |
| Claude가 찾은 실기 결함 | 2(둘 다 Qwen이 놓침) |
| 수정 회차 | 2 |
| 비용(DeepSeek + Qwen) | 약 $0.55 |
| 시간 | 약 1시간 10분 |
| 처리 속도(노트북) | 에어밴드 3채널 실시간의 31%, FM 13% |

비용에서 재미있는 점이 있다. 작은 작업에서는 Qwen 리뷰 비용이 DeepSeek 구현 비용보다 컸다. 리뷰는 diff만이 아니라 그 주변 코드와 계획까지 함께 읽기 때문이다.

## 7.8 아직 남은 것

- **실제 동글 검증:** 드라이버 인식(`V4 Lite Detected`), 119.75 교신을 SDR++와 비교해 귀로 듣기, 동글을 뽑았다 꽂기, 휴대폰 화면
- **통합 리뷰:** 1차 전체를 합친 PR은 너무 커서 Qwen이 받지 못했다(`too_large`). 작업별 리뷰와 실서버 확인으로 대신했다.

## 7.9 알게 된 점

- **AI 팀에서 사람(또는 오케스트레이터)의 일은 경계에 있다.** 각 구현자는 자기 작업을 잘한다. 작업 사이의 계약(JSON에 NaN 금지)과 계층 사이의 조건(USB 512바이트)은 전체를 보는 쪽이 챙겨야 한다.
- **가짜로 테스트하면 가짜의 한계까지만 안다.** 하드웨어 라이브러리를 감싼 코드는 실제 라이브러리 소스를 한 번은 열어 봐야 한다.
- **실물이 없으면 실물 같은 입력을 만든다.** 합성 IQ 파일 하나로 동글 없이 끝에서 끝까지 확인할 수 있었다.
