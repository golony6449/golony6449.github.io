# 7장 받아 적기 대신 교차 검증

## 7.1 자막은 어떻게 고를까

화면의 핵심은 자막이다. 그리고 2장에서 정한 안티 목표 1번이 "자막이 자주 틀리는 것"이었다. 그러니 음성 인식 엔진은 실제 교신으로 비교해서 골라야 한다.

처음 계획은 정석이었다. 실제 교신 20~30개를 사람이 듣고 정답을 받아 적은 다음, 엔진마다 정답과 비교해 점수를 매기는 방식이다. 그런데 받아 적는 방법을 묻자 이런 답이 왔다.

> **"오... 그냥 돌려서 3개를 교차 검증하면 안 될까? 듣기 자신이 없는데? 비교해서 처리해 주고 내가 피드백하는 형태로 해 보자."**

관제 교신은 빠르고, 잡음이 섞이고, 약어와 숫자 읽기 규칙("niner", "tree")이 독특하다. 처음 듣는 사람이 정답을 받아 적기는 어렵다. 그런데 이 제안은 그 약점을 피하면서 더 나은 구조를 만들었다.

## 7.2 교차 검증의 구조

- 교신 하나를 **여러 엔진이 각자 받아 적는다.**
- 결과끼리 단어 단위로 비교해 **일치도(0~1)**를 낸다. 일치도가 높으면 다수결 결과를 진하게, 낮으면 흐린 "추정"으로 보여 준다.
- 사람은 처음부터 받아 적지 않는다. **비교 화면**에서 엔진 결과를 나란히 보고(서로 다른 단어는 색으로 강조), 셋 중 하나만 고른다.
  - "이게 맞아"
  - 가장 비슷한 결과를 살짝 고치기
  - "모르겠음"
- 이 피드백으로 엔진별 성적표(정답 일치율, 평균 단어 오류율, "추정이 아닌데 틀린" 비율, 처리 시간)를 만든다.

주의할 점도 있다. 엔진들이 **같은 실수를 함께** 하면 일치도가 높아도 틀린다. 그래서 4차 계획에서는 독립된 단서를 하나 더 쓴다. 알아들은 편명이 지금 근처에 실제로 있는 비행기(ADS-B)와 맞는지다.

> **알게 된 점** — 정답 데이터가 없을 때는 "서로 다른 방식의 여러 판단이 얼마나 일치하는가"가 좋은 대리 지표가 된다. 사람은 처음부터 만드는 대신 고르기와 고치기만 하면 되니 부담이 훨씬 적다.

## 7.3 숫자 읽기를 통일해야 비교가 된다

엔진마다 숫자를 다르게 적는다. 어떤 엔진은 "one one niner", 어떤 엔진은 "119"라고 쓴다. 이 차이를 불일치로 세면 일치도가 엉망이 된다. 그래서 비교 전에 관제 표준 발음을 통일한다.

| 입력 | 통일한 결과 |
|---|---|
| `Korean Air one one niner, descend and maintain three thousand` | `korean air 119 descend and maintain 3000` |
| `contact Incheon Control one three two decimal two` | `contact incheon control 132.2` |
| `squawk four tree fife zero` | `squawk 4350` |

관제 영어에서 9는 "niner", 3은 "tree", 5는 "fife"로 읽는다. 무전 잡음 속에서 잘못 알아듣지 않게 하려는 약속이다.

## 7.4 후보 엔진 여섯

처음에는 Whisper(OpenAI의 공개 음성 인식 모델)와 Qwen API 정도를 생각했다. 조사하면서 후보가 늘었다.

**관제 교신 전용 Whisper가 이미 공개돼 있었다(문헌 기반).** 관제 교신 데이터로 다시 학습시킨 medium 모델은 단어 오류율이 원래 모델의 94.6%에서 15.1%로 내려갔다고 한다. large-v3 기반 모델은 6.5%라고 한다. 다만 미국·유럽 관제 데이터로 학습했으니, 한국 관제사와 조종사의 억양에서는 다를 수 있다.

> **질문 노트** — "Qwen2-Audio(7B), SenseVoice-Small도 같이 고려해 줄래? 특히 SenseVoice는 CPU만으로도 가능하대."

- **SenseVoice-Small:** 알리바바 팀의 소형 모델이다. 공식 설명으로는 Whisper-Small보다 5배 빠르고, CPU만으로 실시간을 따라간다. GPU 없는 서버로 옮길 때 가장 유력한 후보가 됐다. 대신 관제 교신 전용 학습이 없고, 편명 힌트를 넘기는 기능을 찾지 못했다.
- **Qwen2-Audio:** 소리를 이해하는 7B 언어모델이다. 로컬로 돌리면 4비트로 줄여도 4~5GB라서 6GB GPU에서 Whisper와 함께 상시로 돌리기 어렵다. 그런데 필자는 처음부터 **API로 부르는 것**을 생각하고 있었다. 공개 문서를 보니 Qwen2-Audio 계열 API(`qwen-audio-turbo`)는 무료 체험 전용으로 나와 있었고, 대신 Qwen-Omni를 권하고 있었다. 그래서 "계정에서 불리는 모델을 쓰고, 안 되면 Omni"로 정리했다.

최종 후보는 여섯이다.

| 엔진 | 실행 | 비용 |
|---|---|---|
| Whisper medium.en(일반) | 노트북 GPU | 무료 |
| Whisper medium.en ATC 전용 | 노트북 GPU | 무료 |
| Whisper large-v3 ATC 전용(int8) | 노트북 GPU | 무료 |
| SenseVoice-Small | CPU | 무료 |
| Qwen3-ASR | API | 호출당 |
| Qwen 오디오 LLM(편명 힌트) | API | 호출당 |

## 7.5 GPU 6GB를 나눠 쓰는 법

후보가 많아지면 GPU 메모리가 문제다. 그래서 단계를 둘로 나눴다.

- **비교 단계(일괄 처리):** 쌓인 교신을 엔진 하나씩 돌린다. 모델을 올리고, 전부 처리하고, 내린 다음 다음 모델을 올린다. 6GB로 충분하다.
- **평소 운용:** 성적이 좋은 로컬 엔진 두 개만 항상 올려 둔다. 두 엔진의 의견이 갈릴 때만 Qwen API를 불러 세 번째 의견으로 쓴다. API 호출에는 하루 상한(300회)을 둔다.

## 7.6 근처 편명을 힌트로

Whisper에는 "이런 단어가 나올 수 있다"는 힌트를 주는 기능(initial prompt)이 있다. 지금 근처에 있는 비행기의 편명과 항공사 무선 호출 부호(6장의 adsbdb 값)를 넘기면 "Korean Air 714" 같은 말을 더 잘 알아들을 것으로 기대한다(**추정**). Qwen 오디오 LLM에는 같은 정보를 지시문에 넣는다.

## 7.7 지금까지의 상태

이 장을 쓰는 시점에는 3차 계획까지 작성했고, 엔진은 아직 하나도 돌려 보지 않았다. 다음 이야기는 이렇게 이어질 예정이다.

- 노트북 GPU에서 faster-whisper를 처음 돌리며 만나는 CUDA·cuDNN 설정
- large-v3 ATC 모델을 int8로 변환하는 과정
- 실제 교신 30개를 여섯 엔진으로 돌린 첫 성적표
- 비교 화면에서 처음 피드백을 남겨 본 경험

## 7.8 알게 된 점

- **사람이 못 하는 일을 억지로 시키지 않는다.** 받아 적기 대신 고르기와 고치기로 바꾸니 같은 목표(엔진 고르기)를 더 쉽게 이룰 수 있다.
- **비교 전에 표기를 통일한다.** 숫자 읽기 차이를 오류로 세면 지표가 의미를 잃는다.
- **후보는 실행 환경별로 자리를 정한다.** GPU, CPU, API는 비용과 제약이 달라서, 같은 표에 올려도 쓰는 자리가 다르다.
