# 8장 지도 위의 비행기: 2차 구현의 밤

## 8.1 동글 없이 쌓아 올리기

1차 수신기는 동글을 꽂아 확인하는 일만 남았지만, 그날 밤 동글은 PC에서 빠져 있었다. 2차(비행기 지도)는 동글이 필요 없다. 비행기 정보는 인터넷(adsb.lol)에서 오기 때문이다. 그래서 1차가 main에 들어가기를 기다리지 않고, **1차 통합 브랜치 위에 2차를 쌓았다.**

```text
main ← ds/receiver-core(1차) ← ds/map(2차) ← ds/transcription(3차) ← ds/callsign-link(4차)
```

탑처럼 쌓는 방식이다. 아래층이 고쳐지면 위층이 따라잡아야 한다는 비용이 있지만, 기다리는 시간이 없다. 이 탑은 다음 날 아침 사용자의 한마디("PR 머지 순차로 모두 실행해 줘")로 아래층부터 차례로 main에 들어갔다.

작업은 세 묶음으로 나눴다.

| 묶음 | 작업 | 동시 실행 |
|---|---|---|
| A | adsb.lol 공급원과 비행기 모델 | 혼자 |
| B | 노선 조회·트래커 / GPS 집 위치 도구 | 둘이 동시에 |
| C | 웹 API와 지도 화면 | 혼자 |

## 8.2 앞 작업의 교훈을 다음 지시문에 한 줄로

1차에서 상태 JSON에 NaN이 섞여 화면이 깨질 뻔했다. 그래서 2차 트래커 지시문에 한 줄을 넣었다. **"JSON으로 바꿀 수 있어야 한다(NaN 금지)."** DeepSeek은 이 한 줄을 보고 좌표가 NaN인 비행기는 아예 빼고, 숫자가 아닌 속도와 방향은 null로 바꿨다.

AI 구현자는 한 작업이 끝나면 기억을 잃는다. 앞에서 배운 것을 다음 작업에 옮기는 일은 오케스트레이터가 지시문으로 한다. 이 프로젝트에서 지시문의 "앞 작업에서 알게 된 사실" 칸이 점점 길어진 이유다.

> **알게 된 점** — 여러 AI에게 일을 나눠 줄 때, 지식은 사람(또는 오케스트레이터)이 직접 옮겨야 한다. 옮기는 수단은 결국 "다음 지시문에 쓰는 한 줄"이다.

## 8.3 리뷰어가 잡은 JavaScript 함정

이번에는 Qwen이 진짜 버그를 잡았다. 집 위치를 아직 정하지 않으면 API는 `{"lat": null, "lon": null}`을 준다. 화면 코드는 이렇게 검사했다.

```javascript
const lat = Number(home.lat);
if (Number.isFinite(lat)) { /* 집 위치로 지도 이동 */ }
```

`Number(null)`은 `0`이고, `Number.isFinite(0)`은 `true`다. 그래서 지도는 기본 중심(수도권) 대신 위도 0, 경도 0으로 날아간다. 아프리카 기니만 앞바다다. 웹 개발을 해 본 사람이라면 한 번쯤 당해 본 형 변환 함정이다. `typeof home.lat === "number"` 검사로 고쳤다.

## 8.4 범위를 지킨 구현자의 정직한 보고

DeepSeek의 보고서 "남은 문제" 칸에 이런 내용이 있었다.

> 1차의 `test_main_parses_replay`가 예시 설정 때문에 실제 adsb.lol을 부르고 5초가 걸린다. 내 파일이 아니라서 고치지 않았다.

테스트가 외부 서비스를 부르는 것도 문제지만, 그 요청에는 집 근처 좌표가 실린다. 구현자는 "맡은 파일만 고친다"는 규칙을 지켰고, 그 대신 문제를 보고로 올렸다. Claude는 이 보고를 읽고 같은 PR의 수정 지시(R2)로 바꿔 넘겼다. 트래커를 가짜로 바꾸자 그 테스트는 5초에서 0.1초로 줄었다.

> **알게 된 점** — 구현자에게 범위를 엄격히 지키게 하면, 범위 밖 문제는 "보고"로 올라온다. 그 보고를 다시 일감으로 바꾸는 것이 오케스트레이터의 일이다. 보고서를 대충 읽으면 이 틈이 그대로 남는다.

## 8.5 실제 데이터에서만 보인 `@@@@@@@@`

마지막으로 Claude가 실제 adsb.lol 데이터를 받아 브라우저로 화면을 확인했다. 수도권 지도에 비행기 일곱 대가 떴고, 라벨은 `KAL591 · 12,250ft ↑`처럼 나왔다. 마커를 누르면 "Korean Air KAL591 / ICN → VIE / B748"이 나왔고, 몇 초 사이에 고도가 12,250에서 12,425로 바뀌었다. 이륙해서 오르는 중이었다.

그런데 인천공항 위에 이상한 라벨이 하나 있었다. **`@@@@@@@@ · 0ft`.** 원문을 보니 주기장에 서 있는 비행기가 편명으로 `"@@@@@@@@"`를 보내고 있었다. ADS-B 편명 문자표에서 `@`는 빈칸이다. 즉 "편명 없음"이다. 그런데 파서는 이것을 진짜 편명으로 알고 라벨에 쓰고 노선 조회까지 하려 했다.

전날 밤 받아 둔 표본 다섯 개에는 이런 값이 없었다. 새벽이라 주기 중인 비행기가 많았던 시간에만 보인 것이다. `@`를 지우고 비면 "편명 없음"으로 처리하게 했고, 지상 비행기는 `0ft` 대신 `지상`으로 보이게 했다.

> **알게 된 점** — 실제 표본은 한 번 받고 끝나지 않는다. 시간대에 따라 새로운 함정이 나온다. 그리고 이런 결함은 diff만 보는 리뷰어는 잡을 수 없다. 실제 데이터를 화면으로 본 사람만 잡는다.

## 8.6 "웹은 안 만든 거 같은데 맞아?"

다음 날 아침, 3차 작업을 이어 가던 중에 이런 질문이 왔다.

> **"그리고, 지금 웹은 안 만든 거 같은데 맞아?"**

사실 웹 화면은 1차와 2차에서 이미 만들어져 있었다. 상단 상태 줄, FM 전환 버튼, 실시간 듣기, 지난 교신 목록, 그리고 가운데 지도까지. 없는 것은 **지도 아래 자막**이었다. 처음 화면 시안(A1)에서 가장 눈에 띄던 부분이 자막이었으니, 그게 없는 화면은 "아직 안 만든 것"처럼 느껴질 만했다.

개발하는 쪽은 "계획 2개 중 2개 끝"으로 보지만, 쓰는 쪽은 "내가 그린 장면이 보이는가"로 본다. 진행 보고를 할 때 계획 단위보다 **화면의 어느 부분이 됐고 어느 부분이 남았는지**로 말하는 편이 오해가 적다.

## 8.7 알게 된 점

- 기다리지 않으려면 브랜치를 탑처럼 쌓는다. 대신 위층이 아래층을 따라잡는 일을 잊지 않는다.
- 앞 작업의 교훈은 다음 지시문의 한 줄로 옮긴다.
- `Number(null) === 0`. 웹 개발자의 오래된 친구다.
- 실제 데이터는 시간대마다 다른 얼굴을 보여 준다.
- 진행 상황은 "사용자가 상상한 화면" 기준으로 말한다.
