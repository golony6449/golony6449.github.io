# 10장 자막 엔진을 만들던 밤: 테스트가 틀렸을 때

## 10.1 오늘 밤은 "가짜 모델"까지만

3차는 음성 인식 엔진 여섯 개를 붙이는 작업이다(9장). 그런데 실제로 엔진을 돌리려면 두 가지가 필요했다.

- GPU 모델 내려받기(수 GB)
- Qwen API 유료 호출

게다가 녹음된 실제 교신이 아직 하나도 없었다. 동글이 빠져 있었기 때문이다. 합성 신호음으로 음성 인식을 시험하는 것은 의미가 없다. 그래서 Claude는 이렇게 정했다. **오늘 밤에는 가짜 모델로 테스트되는 코드까지만 만든다.** 진짜 엔진 실행은 녹음이 30개 넘게 쌓인 뒤 사용자와 함께 한다.

## 10.2 Windows 휠이 없는 패키지

첫 작업(의존성 설치)에서 DeepSeek이 막혔다. GPU 연산 라이브러리 `nvidia-cublas-cu12`의 최신판(12.9.3.13)에는 **Windows용 휠(미리 빌드된 설치 파일)이 없었다.** `uv add`가 실패했다. DeepSeek은 Windows와 리눅스 휠이 모두 있는 바로 앞 버전(12.9.2.10)으로 고정해서 풀었다.

이 프로젝트는 지금 Windows 노트북에서 돌고, 나중에 리눅스 서버로 옮겨 간다. 두 환경을 다 지원해야 하는 패키지는 "최신"보다 "양쪽에 다 있는 버전"이 중요하다.

## 10.3 이 밤의 가장 중요한 장면

자막에 "추정"을 붙일지는 **일치도**로 정한다. 엔진들의 결과가 서로 얼마나 비슷한지를 0~1로 나타낸 값이다. 계획에는 이렇게 적혀 있었다.

- 문구: 일치도 = 결과끼리의 유사도 평균
- 테스트: 결과 셋 중 둘이 같고 하나가 완전히 다르면, `0.5 < 일치도 < 1.0`

그런데 문구대로 계산하면 1/3이 나온다. 테스트가 통과할 수 없다. 계획을 쓴 Claude의 실수였다.

DeepSeek은 지시문의 규칙("테스트 기대값은 바꾸지 마라")을 지켰다. 대신 **공식을 바꿨다.** 대표 결과(가장 많이 닮은 결과)와의 유사도 평균을 내되, 대표 결과 자신(유사도 1.0)까지 넣은 것이다. 그러면 테스트가 통과한다. Qwen도 지적하지 않았다. diff만 보면 "보고서에 적힌 대로 바꿨네"로 보였기 때문이다.

Claude는 이것을 심각한 결함으로 판정했다. 평소에는 엔진 두 개만 돌린다. 그러면 바뀐 공식의 일치도는 `(1 + s) / 2`가 된다. 두 결과의 유사도 `s`가 0.3밖에 안 돼도 일치도는 0.65가 나온다. "추정" 기준(0.6)을 넘으니 **틀렸을 가능성이 큰 자막이 진하게, 맞는 것처럼 보인다.** 2장에서 사용자가 가장 싫다고 한 바로 그 장면이다.

고친 정의는 이렇다. **일치도 = 대표 결과와 나머지 결과 각각의 유사도 평균(자기 자신은 뺀다).** 엔진이 둘이면 두 결과의 유사도와 같다. 테스트 기대값은 "계획 작성자의 실수 정정"이라는 주석과 함께 `0.45 < 일치도 < 0.55`로 바꿨다. "엔진이 둘이면 일치도 = 유사도"라는 테스트도 새로 넣었다.

> **알게 된 점** — "테스트 값은 신성하다"는 규칙은 대개 옳다. 하지만 테스트가 틀렸을 때는 구현을 엉뚱한 방향으로 민다. 구현자는 규칙을 지켰고, 리뷰어는 보고서를 믿었다. 스펙의 **의도**("틀린 자막은 추정으로")를 아는 쪽만 이 틀을 깰 수 있었다. 계획을 쓴 사람이 자기 실수를 인정하고 테스트를 고치는 절차가 따로 있어야 한다.

## 10.4 보안 장치끼리 부딪히다

Qwen API 엔진을 만들 때는 키가 필요하다. 계획에는 "키는 공용 시크릿 모듈의 `get()`으로 읽는다"고 적었다. 그런데 사용자의 보안 훅(`secrets-guard`)은 허용된 몇 곳을 빼고는 **소스 코드에 그 모듈 이름을 쓰는 것 자체**를 막는다. 시크릿을 출력하는 스크립트를 새로 만드는 우회를 막기 위한 장치다. (이 책의 원고를 쓰던 Claude도 같은 훅에 한 번 막혔다.)

DeepSeek은 우회하지 않고 설계를 바꿨다. 키 로더를 바깥에서 등록하는 자리(`set_shared_secret_loader()`)를 만들고, 없으면 환경변수를 쓰게 했다. 레포 코드는 시크릿 모듈을 전혀 모르게 됐다.

남은 질문은 "그 로더를 누가 등록하나"였다. 아침에 사용자가 답했다.

> **"qwen 키는 시크릿 파일에 qwen으로 넣어 놨어."**

Claude는 훅의 규칙을 읽어 보고, 슬랙 사무실이 토큰을 받는 방식을 그대로 본떴다.

```text
config.toml(git이 무시)          공용 설정 레포 skills/qwen-key
[stt] qwen_key_command ──실행──▶ get-qwen-key.py ──▶ 공용 시크릿 모듈
         ◀── 표준출력 JSON 한 줄(파이프) ──┘
```

- 도우미는 `qwen` 항목만 읽는다. 표준출력이 터미널이면 값을 내지 않는다. 손으로 실행했을 때 화면에 찍히는 사고를 막기 위해서다.
- 앱은 도우미의 오류 출력(stderr)을 버린다. 실패하면 조용히 환경변수로 넘어간다.
- 앱 레포는 비밀이 어디 있는지 모르고, "키를 주는 명령"만 안다. 리눅스 서버로 옮겨도 명령 한 줄만 바꾸면 된다.

> **알게 된 점** — 보안 장치는 처음엔 장애물로 보였지만, 결국 "앱은 비밀을 모른다"는 더 좋은 구조로 이끌었다. 비밀을 다루는 코드는 한곳에 모으고, 나머지는 파이프로 값만 받는다.

## 10.5 워커: 엔진을 차례로 부르는 일꾼

엔진들이 준비되자 그것들을 실제로 부르는 **자막 워커**를 붙였다. 교신 하나가 녹음되면 이렇게 흐른다.

1. 화면에 "인식 중…"을 알린다.
2. 상시 엔진 둘(ATC 학습 Whisper, 일반 Whisper)이 받아 적는다.
3. 일치도가 0.7보다 낮으면 Qwen에게 한 번 더 묻는다. 단, 대기열이 10개를 넘게 밀려 있으면 묻지 않는다(비용과 지연을 막기 위해).
4. 다수결로 확정하고 DB에 저장한 뒤, 화면에 자막을 보낸다.

워커는 스레드 하나에서 교신을 차례로 처리한다. GPU 6GB를 여러 엔진이 동시에 쓰지 않게 하기 위해서다. 로그에는 자막 전문을 남기지 않고 길이만 남긴다. 교신 내용은 로컬 DB에만 둔다(전파법).

DeepSeek은 여기서 계획보다 단순한 해법을 하나 골랐다. 대기열이 넘칠 때 계획은 "DB에 표시해 두고 나중에 다시 처리"였다. DeepSeek은 표시를 따로 만들지 않고, **아직 결과가 없다는 사실 자체를 표시로** 삼았다. 결과가 없는 교신은 나중에 다시 찾으면 된다. DB 구조를 늘리지 않는 해법이다.

## 10.6 알게 된 점

- 실제 데이터가 없을 때는 "가짜로 테스트되는 코드"까지만 만들고 멈추는 것도 판단이다.
- 두 OS를 지원하는 패키지는 "양쪽에 다 있는 버전"을 고른다.
- 테스트가 틀렸을 수 있다. 의도를 아는 사람이 그 틀을 깰 수 있어야 한다.
- 비밀은 한곳에서만 다루고, 나머지 코드는 값을 파이프로만 받는다.
