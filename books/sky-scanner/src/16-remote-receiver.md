# 16장 차 안의 수신기: 40 Mbps를 320 KB/s로 줄이고 스풀로 잇다

## 16.1 차를 타고 공항 근처로 가고 싶다

집 안의 리눅스 서버에 수신 환경을 안착시킨 뒤(15장), 사용자가 다음 목표를 꺼냈다.

> **"서버는 집에있고, 주요처리는 여전히 하되, 노트북에 동글을 연결해서 수신하되 이를 서버에 스트리밍해서 처리를 맡길수 있을까?"**  
> **"차를 타고 공항근처에 이동해서 수신을 해보고 싶어."**

처리와 데이터 저장은 계속 집에 있는 서버가 맡고, 노트북은 차 안에서 동글을 꽂아 무전을 수신해 집으로 쏘는 구조다. 그런데 계산기를 두드려 보니 만만치 않은 벽이 나타났다.

RTL-SDR 동글이 2.4 MHz 대역을 읽을 때 쏟아내는 IQ 원시 샘플은 초당 240만 개(복소수 16비트 기준)다. 바이트로 환산하면 **초당 4.8 MB, 통신 대역폭으로는 약 40 Mbps**에 달한다. 스마트폰 LTE 테더링(핫스팟)으로 2~3시간 동안 40 Mbps 스트리밍을 유지하는 것은 데이터 요금으로나 통신 안정성으로나 불가능에 가깝다.

그때 사용자가 아이디어를 냈다.

> **"그 주파수 대역만 잘라서 스트리밍 하는건 어때?"**

SDR의 본질을 꿰뚫은 제안이었다. 우리는 2.4 MHz 전체를 듣는 것이 아니라, 그 안에 있는 타워나 지상 관제 같은 특정 채널 몇 개만 듣는다. 채널마다 16 kHz 기저대역 IQ로 소프트웨어 필터링(Channelizer)을 거쳐 잘라내면 채널당 초당 64 KB, 5개 채널을 모두 합쳐도 **초당 320 KB(약 2.6 Mbps)**면 충분하다.

40 Mbps가 2.6 Mbps로, 대역폭이 1/15로 줄어들었다. 2~3시간 동안 달려도 3~5 GB 수준이라 핫스팟으로 거뜬히 감당할 수 있는 크기다. SDR의 "넓게 받아 소프트웨어로 쪼갠다"는 원리를 사용자가 스스로 응용해 원격 전송 문제를 풀어낸 장면이었다.

## 16.2 스풀이 유일한 경로다: 끊김과 재전송

달리는 차 안에서는 이동통신 전파 음영 지역이나 터널을 지나며 네트워크가 끊길 수밖에 없다. 사용자가 필수 요구사항을 덧붙였다.

> **"gpS도 같이 기록하도록 해주고, 노트북이 쌓아뒀다가 재전송하도록 하는 기능도 추가해줘. 이때 쌓이는 경우는 얼마나 쌓였는지 볼수 있는 부분도 화면에 추가해줘"**  
> **"스풀상한 1기가로 낮춰주고"**

여기서 가장 중요한 아키텍처 원칙이 세워졌다. 바로 **"스풀이 유일한 경로다"**라는 규칙이다.

실시간 전송용 소켓과 재전송용 큐를 따로 만들면, 네트워크 상태에 따라 순서가 뒤엉키거나 신호가 중복될 위험이 생긴다. 그래서 송신기는 동글에서 읽은 모든 IQ 블록과 GPS 좌표, 상태 변경을 **예외 없이 먼저 로컬 디스크 스풀(Spool)에 파일로 쓴다**. 그리고 전송 모듈(`Link`)은 오직 스풀의 가장 오래된 미확인 항목부터 차례로 서버에 보낸다.

- 네트워크가 원활하면 스풀에 쓰이자마자 서버로 나가므로 실시간과 다름없이 흐른다.
- 터널에 들어가 연결이 끊기면 스풀에 1분 단위 파일로 차곡차곡 쌓인다(1 GB 상한까지 약 50분 보관).
- 터널을 빠져나와 서버와 다시 연결되면, 서버가 보낸 마지막 `ack` 번호 다음 번호부터 오래된 순서대로 재전송이 시작된다.

실시간 경로와 재전송 경로를 분리하지 않고 하나의 디스크 스풀로 일원화함으로써, 끊김과 재연결 속에서도 단 하나의 샘플도 순서가 꼬이지 않는 구조를 완성했다.

## 16.3 데이터 절약 모드: 밖에서 쓰는 화면은 무엇을 받고 있나

> **"수신기에서는 라이브 듣기 되는거지?"**  
> **"서버 화면에도 데이터 절약 모드 를 위한 라디오 버튼 만들어줘. 이거는 외부에서 수신중 상황에서 수신기/서버 화면을 다 띄워뒀을 때 서버의 라이브화면 정보를 폴링하는 부분을 줄여서 데이터 절약은 하되, 에어밴드 스트리밍만 하려고 해."**

노트북 화면에서 실시간 소리를 들으려고 서버를 거쳐 다시 오디오를 스트리밍받는다면 무의미하게 모바일 데이터를 두 배로 쓰게 된다. 노트북은 이미 채널 IQ를 로컬에 갖고 있으므로, 송신기 자체 프로세스에서 직접 AM 복조를 거쳐 브라우저 AudioContext로 재생하게 했다. 서버를 거치지 않으니 데이터 소모는 0이고, 인터넷이 끊겨도 내 귀에는 교신이 그대로 들린다.

더 나아가 서버 웹 대시보드를 뜯어보면서 집 와이파이에서는 보이지 않던 '숨은 데이터 비용'이 드러났다.
- 서버 대시보드는 수신기 상태를 블록마다(초당 10번) 웹소켓으로 쏘고 있었다.
- 5초마다 비행기 궤적을 갱신하고, 집 동글의 실시간 오디오(초당 32 KB)를 끊임없이 받아낸다.
- 브라우저를 띄워 두기만 해도 시간당 100 MB가 넘는 데이터가 증발하고 있었다.

그래서 서버 화면에 **"데이터 절약 모드"**를 도입했다.
- 라디오 버튼으로 '데이터 절약'을 누르면 웹소켓 상태 주기를 10초로 낮추고(`/ws/status?every_s=10`), 비행기 궤적 이벤트를 차단한다(`/ws/events?aircraft=0`).
- 실시간 오디오 웹소켓을 닫고, Leaflet 지도 객체를 메모리에서 완전히 해제(`map.remove()`)하여 지도 타일 다운로드를 0으로 차단한다. 오직 새로 인식된 교신의 텍스트 자막만 가볍게 받는다.
- 노트북 송신기 화면(`127.0.0.1:8091`)에서도 지도를 끄면 Leaflet 자바스크립트 라이브러리조차 동적으로 불러오지 않으며, 모든 외부 타일 요청을 409로 칼같이 끊어냈다.

## 16.4 오케스트레이션 세션 바꾸기: Claude에서 Gemini로

이 거대한 원격 수신기 설계와 구현을 앞두고, 사용자가 깜짝 제안을 했다.

> **"이거 제미나이 결제하면 그쪽세션에 전달해서 시킬수 있어? 제미나이가 맡을 역할은 클로드와 동일하고, 제미나이에게 전달한 작업에 대한 최종검토 등은 토큰 절약을 위해 클로드는 전혀 하지마. 가능해?"**

개발 전 과정을 지휘하던 메인 세션을 Claude에서 Gemini(Antigravity)로 교체하겠다는 것이었다. 도구가 바뀌어도 프로젝트가 굴러갈 수 있을까?

놀랍게도 아무런 단절이 없었다. 사용자 지침(`AGENTS.md`)과 DeepSeek 위임 스킬(`deepseek-delegate`), 시크릿 보호 훅이 공용 레포(`golony-agent-support`)를 통해 두 도구에 함께 설치되어 있었기 때문이다. Gemini 세션은 앞서 작성된 플랜 브리프를 읽고 즉시 현황을 파악한 뒤, 묶음 A부터 D까지 8개 작업을 독립된 Orca 워크트리로 분리하여 DeepSeek(`ds-loop.py`)에 병렬로 위임했다.

- **총 8개 작업 전원 DeepSeek 구현, Qwen 듀얼 교차 검토 통과.**
- **베이스라인 284개 테스트 → 최종 398개 테스트 전원 통과.**
- **8개 작업을 전부 완료하는 데 소모된 DeepSeek 비용은 단 $0.87.**

중간에 DeepSeek이 기존 테스트의 엄격한 키 일치 검사를 통과시키기 위해 계획 외의 파일(`test_storage.py`의 `KEY_SET`)을 수정한 적이 있었다. 하네스가 이를 `unplanned_files` 예외로 감지해 올렸을 때, Gemini 오케스트레이터는 diff와 의도를 대조하여 "스펙에 맞게 필드를 확장한 정당한 수정"임을 분별하고 승인했다. 도구가 바뀌어도 규약과 도구가 단단하면 AI 개발 파이프라인은 흔들리지 않는다는 것을 입증했다.

## 16.5 끝에서 끝 시험이 밝혀낸 것: 서로의 첫 인사를 기다린 교착

하지만 마지막 묶음 D의 '끝에서 끝(E2E) 통합 시험'에서 숨어 있던 치명적인 버그가 터져 나왔다.

송신기와 서버 앱을 한 프로세스에 묶어 실제로 데이터를 흘려보내자, 교신이 하나도 저장되지 않고 송신기 `Link`가 10초마다 "서버가 첫 ack를 보내지 않았습니다"를 뿜어내며 멈춰 섰다.

원인은 **순서의 불일치(Deadlock)**였다.
- 서버(`Ingest`): 첫 메시지로 `hello`를 받아야 이 수신기가 누구인지 알고 첫 `ack`를 보낸다.
- 송신기(`Link`): 서버에서 첫 `ack`가 와야 스풀의 이전 기록을 지우고 신호를 보내기 시작한다.

서로 상대방의 첫 인사를 기다리며 무한 대기에 빠진 것이다. 단위 시험에서는 서버 시험이 가짜 클라이언트로 hello를 먼저 던져주었고, 송신기 시험은 가짜 서버가 접속하자마자 ack를 던져주었기에 각자의 단위 테스트는 100% 통과하고 있었다. 단위 테스트의 맹점이었다.

DeepSeek은 E2E 시험에서 이 교착을 정확히 짚어냈다.
- `Link`에 `hello` 공급자를 연결하여, 접속하자마자 스풀과 무관하게 현재 프리셋의 `hello`를 먼저 서버로 쏘아 올린 뒤 첫 `ack`를 기다리도록 규약을 바로잡았다.
- 덕분에 스풀에서 hello 파일이 이미 삭제된 뒤 재연결되거나, 집 서버가 재부팅되어 채널 정보가 날아간 경우에도 송신기가 연결 즉시 채널 구성을 스스로 복원해내는 견고함을 얻었다.

또한 핫스팟이 끊겨 1분 이상 지연되어 도착한 과거 교신을 현재 비행기 위치와 대조하다가 "근처에 비행기 없음"으로 엉뚱하게 강등해 버리는 결함도, 60초 이상 묵은 교신에 `stale=True` 표식을 달아 강등을 면하게 함으로써 완벽히 해결했다.

차 안에서 공항 관제를 듣겠다는 아이디어는, 채널 대역폭 압축, 디스크 스풀 스트리밍, 데이터 절약 UI, 그리고 모델 간 협업을 통한 교착 해결을 거쳐 마침내 현실로 완성되었다.
