# 17장 사설 도메인과 Nginx: URL PATH의 함정에서 sky-scanner.golony.dev까지

## 17.1 워크스페이스의 수명과 영구 프로세스: 고아 데몬의 교훈

리눅스 서버로 서비스를 이사한 뒤(15장), 원격 수신기 구현을 한참 마치고 서버 상태를 점검하던 중 이상한 징후가 포착되었다.

> **"스카이 스캐너 서버 실행중이야?"**

터미널을 열어 프로세스를 확인해 보니 PID 4860으로 Uvicorn이 포트 8090을 잡고 살아는 있었다. 그런데 CPU 점유율이 117%로 치솟아 있었고, 로그에는 1초에도 수십 번씩 에러가 쏟아지고 있었다.

작업 디렉터리를 확인한 순간 원인이 드러났다.
`/home/golony/orca/workspaces/sky-scanner/hydra (deleted)`

에이전트가 임시 워크스페이스에서 구현과 테스트를 위해 프로세스를 띄웠는데, 작업이 끝나고 워크스페이스가 삭제되면서 프로세스만 고아(Orphan) 상태로 허공에 남겨진 것이었다.
디렉터리가 사라졌으니 녹음 파일을 쓸 수도 없고(`data/recordings`), 메인 화면(`GET /`)은 500 에러를 뿜었으며, 비행기 추적기(adsb.lol)는 SSL 인증서 파일을 찾지 못해 무한 루프를 돌고 있었다.

사용자가 즉시 명확한 원칙을 세웠다.

> **"응. 그리고 항상 워크트리 말고 메인에서 프로세스를 띄우도록 해줘"**  
> **"스카이 스캐너 꺼줄래?"**  
> **"아 서비스는 다시 켜줘. 대신 동글은 빼놨어."**

기존 좀비 프로세스를 모두 정리하고, 에이전트 지침 문서(`CLAUDE.md`, `GEMINI.md`)에 "하드웨어를 잡고 포트를 여는 메인 데몬은 수시로 삭제되는 워크스페이스가 아니라 오직 영구적인 메인 저장소 디렉토리에서만 실행한다"는 철칙을 새겼다.

그리고 동글이 빠져도 서비스가 죽지 않도록 방어 로직을 점검했다. 하드웨어 동글이 없으면 수신 엔진은 조용히 `no_dongle` 상태로 대기하며, 웹 UI와 실시간 비행기 궤적 추적(adsb.lol), 이전 교신 재생과 밀린 STT 처리는 정상적으로 동작한다. 동글을 USB에 다시 꽂으면 엔진이 자동으로 감지해 수신을 재개하는 유연한 구조로 자리를 잡았다.

## 17.2 /static의 함정: PATH 분기인가, 서브도메인인가

서버에 sky-scanner뿐만 아니라 홈 대시보드, 텔레메트리 등 여러 웹 서비스가 올라가기 시작했다. 사용자는 이 서비스들을 외부에서 편하게 접근하기 위해 웹 서버 앞에 Nginx 역방향 프록시(Reverse Proxy)를 배치했다.

그리고 첫 번째 질문을 던졌다.

> **"우리 웹 앞에 nginx를 달았어. PATH에 따라 다른 서비스로 진입하도록 분기처리가 되었거든"**  
> **"sky-scanner 프로젝트가 사용하는 path는 /sky-canner 야"**  
> **"static 파일이 한 폴더에 모여있을까? 아니라면 모아주고, 이걸 /static path로 서빙할수 있도록하는 nginx 설정 스크립트 만들어줄래?"**  
> **"그리고 궁금한건 /static에 여러 폴더를 설정할수도 있을까? 떠있는 프로젝트가 여러개라서, /static으로 접근했을때 여러 폴더를 찾도록 하는게 필요해"**

단일 도메인 뒤에서 URL 경로로 서비스를 분기(`http://서버/sky-scanner/`, `http://서버/service-b/`)하고, 정적 자원은 공통 `/static` 경로에서 순차적으로 찾아 서빙하려는 구상이었다.

기술적으로 Nginx의 `try_files` 지시어나 named location fallback을 엮으면 여러 폴더를 순서대로 뒤지게 만들 수는 있다. 하지만 이것은 웹 아키텍처에서 가장 위험한 안티패턴 중 하나다.

대부분의 프론트엔드 프로젝트는 스타일시트를 `style.css`, 자바스크립트를 `app.js`라는 이름으로 저장한다. 만약 단일 `/static` 아래에서 A 프로젝트 폴더와 sky-scanner 폴더를 순차 탐색하게 두면, sky-scanner 화면을 열었을 때 A 프로젝트의 `style.css`가 로드되어 화면 레이아웃이 처참하게 깨지고, 자바스크립트 함수 충돌 에러가 터지게 된다.

더 깊은 복병은 프론트엔드 소스 코드 안에 있었다.
`index.html`과 `app.js`를 열어보니, 정적 파일뿐만 아니라 모든 API 호출과 웹소켓 연결이 `/static/...`, `/api/status`, `/ws/events`, `/review`처럼 **루트 기준 절대 경로**로 하드코딩되어 있었다.
브라우저에서 `http://서버/sky-scanner/`로 접속하더라도, 자바스크립트는 도메인 루트인 `http://서버/api/status`를 요청하게 된다. Nginx에서 URL rewrite를 하거나 프론트엔드 코드 전반에 베이스 경로(`base_path`)를 주입하도록 고치지 않는 한 모든 통신이 끊어질 운명이었다.

에이전트는 이 위험을 설명하고 서브패스 격리(A)나 서브도메인 분리를 제안했다.

> **"A로 가자"**  
> **"아 잠깐. 그렇네. 근데 저 서브도메인이 테일스케일에서 가능해?"**

## 17.3 Tailscale에 개인 도메인을 얹다: DNS Only와 사설 IP 매핑

Tailscale의 기본 MagicDNS는 기기마다 `node.tailnet.ts.net`이라는 단 하나의 고정된 주소만 준다. 사용자가 임의로 `sky.node.tailnet.ts.net` 같은 와일드카드 서브도메인을 만들 수 없다.

그때 사용자가 핵심을 찌르는 아이디어를 던졌다.

> **"아니면 가지고 있는 도메인이 있는데 이걸 테일스케일 환경에 적용할수 있을까?"**

이 질문 하나로 모든 실타래가 한 번에 풀렸다. 홈랩과 개인 인프라 구축에서 가장 우아하고 강력한 해법이 열린 순간이었다.

개인 소유 도메인(`golony.dev`)의 DNS A 레코드에 공인 IP가 아니라 **서버의 Tailscale 사설 가상망 IP(`100.107.138.35`)**를 등록하는 것이다.

```
[내 스마트폰 / 노트북 (Tailscale 연결됨)]
       │
       ▼  "sky-scanner.golony.dev" 접속
[공용 DNS (Cloudflare)]
       │  ➔ "그 주소의 IP는 100.107.138.35야"
       ▼
[Tailscale 사설 가상망 (100.64.0.0/10)]
       │  ➔ 외부 인터넷은 차단, 내 기기들끼리만 통신
       ▼
[홈서버 Nginx (포트 80/443)] ➔ [sky-scanner (127.0.0.1:8090)]
```

이 방식은 세 가지 결정적인 승리를 가져왔다:
1. **코드 수정 0줄**: 브라우저는 `sky-scanner.golony.dev`의 루트(`/`)로 들어온다. `/static`, `/api`, `/ws` 절대 경로를 단 한 줄도 손댈 필요가 없다.
2. **이름 충돌 원천 차단**: 서브도메인마다 독립된 가상 호스트(`server_name`)가 생기므로 `style.css`가 100개 있어도 서로 섞이지 않는다.
3. **완벽한 보안**: `100.x.y.z`는 공용 인터넷에 라우팅되지 않는 사설망이다. 일반인이 이 도메인으로 접속을 시도해도 서버에 닿을 수 없으며, 오직 내 Tailscale 계정에 로그인된 기기에서만 열린다.

사용자는 비용과 운영 정책을 꼼꼼하게 확인했다.

> **"클라우드 DNS는 비용 정책이 어떻게 돼?"**  
> **"그럼 클플 dns는 어떤게 유료야?"**  
> **"좋아. 클라우드 플레어 로그인하고, 내 도메인 등록했어. 도메인 구매는 porkbun에서 했느데, 설정한 dns설정이 불러와지는거 같다?"**

Cloudflare DNS는 쿼리 수와 레코드 수 제한 없이 평생 무료다. 로드 밸런싱이나 고도화된 WAF 같은 엔터프라이즈 기능만 유료다. 사설 IP를 등록할 때는 Cloudflare의 프록시(주황색 구름)를 끄고 순수 **DNS Only(회색 구름)**로 설정해야 한다는 핵심 수칙을 챙겼다.

도메인 등록처(Porkbun)에서 네임서버를 Cloudflare로 바꾸고, A 레코드에 `100.107.138.35`를 지정하자 마침내 연결이 완료되었다.

> **"우여곡절이 있었지만 sky-scanner.golony.dev로 적용 완료 했어"**

## 17.4 와일드카드와 루트 도메인: 단 하나의 통합 인증서로

도메인으로 접속하는 것은 성공했지만, 마지막 한 조각이 남아 있었다. 바로 브라우저의 HTTPS 자물쇠(SSL 인증서)였다.

> **"다 해놓고, 루트도메인 인증서를 안했네. cert로 *.golony.dev 인증서는 만들었었거든 golony.dev 인증서 등록하는 스크립트 만들어달라고 홈서버쪽에 시켜줘"**

Let's Encrypt를 사용할 때 흔히 겪는 함정이다. 와일드카드 인증서 `*.golony.dev`는 `sky-scanner.golony.dev` 같은 서브도메인은 보호해주지만, **정작 루트 도메인인 `golony.dev` 본체는 포함하지 않는다.**

로컬의 Gemini 세션이 홈서버에서 대기 중이던 에이전트 세션에게 작업을 위임했다.
홈서버 에이전트는 기존 루트 권한의 Cloudflare DNS 토큰(`/etc/letsencrypt/cloudflare.ini`)을 안전하게 활용하여, 루트와 서브도메인을 하나로 묶는 통합 인증서 갱신 스크립트(`update_ssl_cert.py`)를 작성했다.

```bash
certbot certonly --dns-cloudflare \
  --dns-cloudflare-credentials /etc/letsencrypt/cloudflare.ini \
  -d golony.dev -d "*.golony.dev" \
  --cert-name golony.dev --expand --non-interactive
```

- `-d golony.dev -d "*.golony.dev"`를 하나의 인증서 이름으로 확장(`--expand`)하여 묶었다. Nginx 설정을 여러 개로 쪼갤 필요 없이 파일 하나로 루트와 모든 서브도메인이 유효해진다.
- 갱신이 성공하면 `systemctl reload nginx`를 자동으로 호출하여 실시간 반영한다.
- 토큰이나 비밀값은 화면이나 로그에 노출하지 않도록 엄격히 가렸다.

사용자가 홈서버에서 스크립트를 실행한 뒤, 경쾌한 한마디가 돌아왔다.

> **"후후 됬다."**

## 17.5 교훈: 인프라가 소프트웨어를 자유롭게 한다

단일 포트 뒤에 여러 웹 애플리케이션을 띄우려 할 때, 초보 개발자들은 본능적으로 URL 경로 분기(`/app1`, `/app2`)를 먼저 떠올린다. 하지만 그것은 프론트엔드의 절대 경로 하드코딩과 정적 자원 이름 충돌이라는 지뢰밭을 걷는 일이다.

반면 **개인 도메인의 DNS A 레코드를 Tailscale 사설 가상망 IP로 향하게 하는 구성**은, 웹 애플리케이션의 코드를 단 한 줄도 건드리지 않고도 각 서비스에게 완벽한 독립된 도메인 루트(`/`)를 선물한다.

- `sky-scanner.golony.dev` ➔ 에어밴드 수신 대시보드
- `dashboard.golony.dev` ➔ 홈서버 통합 모니터링
- `telemetry.golony.dev` ➔ 차량 OBD-II 텔레메트리

서버 내부에서는 각각의 프로세스가 8090, 8780 등 독립된 포트에서 자유롭게 숨을 쉬고, 앞단의 Nginx는 서브도메인 이름에 맞춰 트래픽을 넘기기만 한다.
제대로 설계된 네트워크 인프라 하나가 수백 줄의 지저분한 웹 경로 예외 코드를 완벽하게 지워버린 순간이었다.
