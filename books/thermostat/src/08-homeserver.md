# 8장 토큰은 홈서버가 들고 있다: 원격 센서 API

## 8.1 이미 있는 센서를 쓰고 싶다

집에는 SmartThings에 연결된 온도 센서가 이미 있다. 보드에 센서를 새로 붙이는 것보다 그걸 쓰고 싶었다.

> **질문 노트** — "소프트웨어에 기능 하나더.
> 기존에 온도센서같은게 이미 있거든, 그걸 온도센서로 연동시킬수있을까?"

센서 종류에 따라 방법이 완전히 달라진다는 답이었다.

| 센서 | 방법 | 평가 |
|---|---|---|
| 블루투스 센서 | ESP32가 센서가 뿌리는 신호를 직접 받는다 | 인터넷·허브 없이 로컬. 가장 좋다 |
| SmartThings 연결 센서 | ESP32가 SmartThings 클라우드 API로 값을 가져온다 | 인증이 까다롭고 클라우드 의존 |
| Matter 센서 | 기기끼리 직접 구독 | Arduino Matter 라이브러리로는 어렵다 |

두 번째가 걸리는 이유는 인증이다. SmartThings 개인 액세스 토큰(PAT)은 2024년 12월 30일 이후 만든 것은 24시간 안에 만료된다(**문헌 기반**). 그래서 OAuth 리프레시 토큰으로 펌웨어가 토큰을 스스로 갱신해야 한다. 그리고 인터넷이나 삼성 서버에 문제가 생기면 값을 못 받는다.

## 8.2 이미 해 둔 일이 있었다

> "2번인제 집에 홈서버가 이미 토큰세팅이되어있고 24시간 마다 갱신시키고있어"

필자의 홈서버(Home-Dashboard)는 이미 SmartThings OAuth 토큰을 들고 매일 갱신하고 있었다. 그러면 이야기가 쉬워진다. 토큰은 홈서버가 관리하고, ESP32는 **홈서버에서 값만 받으면** 된다. ESP32에 토큰을 넣지 않으니 보안상으로도 낫다.

```text
SmartThings 클라우드 ── 홈서버(토큰 갱신, 센서 값 조회)
                            │ 로컬 네트워크
                         ESP32 (온도조절기)
```

> **웹 개발자 시선** — BFF(Backend for Frontend) 패턴이다. 클라이언트(ESP32)는 비밀을 모르고, 서버가 대신 외부 API를 부른다. 브라우저에 API 키를 넣지 않는 것과 같은 이유다.

전달 방식은 둘을 놓고 골랐다.

- **MQTT:** 홈서버에 브로커를 두고, 값이 바뀔 때마다 밀어 준다. 가볍고 확장하기 좋다.
- **HTTP:** 홈서버에 간단한 API를 열고 ESP32가 1~2분마다 가져간다. 구현이 더 간단하다.

> "2로 가자 http가 더 편할꺼야"

이 책에서 웹 개발자가 가장 자신 있는 영역이 처음 등장한 순간이다. 익숙한 도구를 골랐다.

## 8.3 API 계약

Claude Code로 넘길 때 바로 쓸 수 있게 인터페이스부터 정했다.

```text
GET http://<홈서버>/api/thermostat/sensors

{
  "sensors": [
    { "id": "livingroom", "name": "거실",
      "temperature": 21.4, "updated_at": "2026-11-24T21:15:00+09:00" },
    { "id": "bedroom", "name": "안방",
      "temperature": 20.1, "updated_at": "2026-11-24T21:14:30+09:00" }
  ]
}
```

이 계약에서 가장 중요한 한 줄은 `updated_at`이다. 여기에는 **SmartThings에서 센서가 마지막으로 값을 보고한 시각**을 넣는다. 홈서버가 조회한 시각을 넣으면, 센서 배터리가 나가서 값이 멈춰도 매번 "방금 받은 값"처럼 보인다.

> **웹 개발자 시선** — 캐시의 `Last-Modified`와 "내가 가져온 시각"을 헷갈리는 문제와 똑같다. 원본이 언제 바뀌었는지와 프록시가 언제 읽었는지는 다르다. 신선도는 원본 기준으로 판단한다.

### ESP32 쪽 규칙

| 규칙 | 값 |
|---|---|
| 조회 주기 | 1분 |
| 타임아웃 | 3초 |
| 보드 센서로 전환 | `updated_at`이 10분을 넘거나, 3번 연속 조회 실패 |
| 센서 선택 | 보드 센서 / 원격 센서 1개 / 여러 원격 센서 평균 |
| 보안 | 로컬 네트워크 전용. 필요하면 API 키 헤더 |

> **웹 개발자 시선** — 원격 센서가 죽으면 보드 센서로 넘어가는 건 서킷 브레이커와 폴백이다. "3번 연속 실패"가 차단기가 열리는 조건이다.

## 8.4 어느 센서의 몇 분 전 값인가

> "화면에는 어떤센서에서 몇분전 업데이트 된 온도인지 보여주는 기능도 넣자."

온도 숫자 아래에 출처와 경과 시간을 붙인다.

| 상황 | 표시 |
|---|---|
| 정상 | `21.4℃` / `거실 센서 · 3분 전` |
| 평균 | `20.8℃` / `평균(거실, 안방) · 최근 2분 전` |
| 대체 중 | `21.0℃` / `보드 센서 · 원격 센서 응답 없음` |

- 1분 미만은 "방금", 그 이상은 "N분 전"
- 5분이 넘으면 주의 색, 10분이 넘으면 보드 센서로 전환하고 이유 표시
- 경과 시간을 계산하려면 ESP32에 정확한 시계가 필요하다. Wi-Fi로 **NTP** 시간을 맞추고, 보드의 RTC에 저장해 재부팅해도 유지한다

> **웹 개발자 시선** — 피드의 "3분 전" 표시를 하드웨어 화면으로 옮긴 것이다. 다른 점은 브라우저처럼 시계가 저절로 맞지 않는다는 것이다. 기기가 스스로 NTP로 시간을 맞춰야 한다.

### 센서 위치 한 가지

보드에 센서를 붙이게 되면 주의할 점이 있다. 보드와 화면 백라이트에서 열이 나서, 보드 바로 옆의 센서는 실제보다 1~2℃ 높게 나온다는 조언을 받았다(**확인 필요**). SHT40은 선을 빼서 보드에서 떨어뜨려 단다.

## 알게 된 점

- 이미 있는 인프라(홈서버의 토큰 갱신)가 설계를 단순하게 만든다. 기기에 비밀을 넣지 않는다.
- 센서 값의 신선도는 "내가 받은 시각"이 아니라 "센서가 보고한 시각"으로 판단한다.
- 화면에 출처와 경과 시간을 보여 주면, 값이 이상할 때 사용자가 먼저 알아챈다.
