# 18장 레포 말고 API로: 홈서버가 주는 센서, 시각, 목록

8장에서 정한 계약을 실제로 만든 날이다. 이 장의 코드는 펌웨어 레포가 아니라 홈서버 레포(Home-Dashboard)에 들어갔다. 필자의 본업에 가장 가까운 장이기도 하다.

이날 테스트 453개가 통과한 것은 **실측**이다. 하지만 **실제 SmartThings 센서 값은 한 번도 받지 못했다.** 응답 모양은 공개 문서에 맞춘 표본이고, 실제 값 확인은 홈서버에 배포한 뒤로 남겼다.

## 18.1 센서 API는 SmartThings를 부르지 않는다 (SCRUM-239)

> "239 티켓 워크플로우로 진행해줘"

계약은 8장 그대로다.

```text
GET http://<홈서버>/api/thermostat/sensors

{
  "sensors": [
    { "id": "livingroom", "name": "거실",
      "temperature": 21.4, "updated_at": "2026-11-24T21:15:00+09:00" }
  ]
}
```

펌웨어는 1분마다 이 API를 부르고 **3초**만 기다린다. 요청이 올 때마다 홈서버가 SmartThings 클라우드에 센서 수만큼 물어보면, 클라우드가 조금만 느려도 3초를 넘긴다. 그래서 이렇게 정했다.

- 홈서버 안의 백그라운드 스레드가 60초마다 센서를 읽어 **마지막 값을 들고 있고**, API는 그 값을 바로 돌려준다.
- 한 센서 조회가 실패하면 그 센서는 **이전 값을 그대로 둔다.** `updated_at`은 홈서버가 읽은 시각이 아니라 센서가 SmartThings에 마지막으로 보고한 시각이다. 그래서 오래된 값은 펌웨어가 10분 기준으로 알아서 거른다. 판단은 펌웨어가 하고, 홈서버는 사실만 전한다.
- 한 번도 값을 얻지 못한 센서는 목록에 넣지 않는다.

> **웹 개발자 시선** — 요청 경로에서 외부 API를 부르지 않고 캐시를 내준다. 서버 쪽에서 직접 한 "stale-while-revalidate"다. 캐시가 얼마나 낡았는지는 `updated_at`으로 실어 보내고, 버릴지는 클라이언트가 정한다.

## 18.2 계약에 없던 규칙은 파서에 있었다

홈서버 계획을 쓰기 전에, 13장에서 이미 만든 펌웨어 쪽 파서(`src/sensor/sensor_logic.cpp`)부터 읽었다. 계약 문서에 없던 규칙 두 개가 나왔다.

1. `updated_at`에 `null`이 오면 **응답 전체**를 못 읽는다. 그래서 시각이 없는 센서는 `null`로 보내지 않고 목록에서 뺀다.
2. `updated_at`에는 반드시 오프셋(`Z`나 `+09:00`)이 있어야 한다. SmartThings가 주는 UTC 시각을 서울 시각(`+09:00`)으로 바꿔 초 단위로 내보낸다.

그 밖에 정한 것:

| 항목 | 정한 것 |
|---|---|
| 화씨 센서 | 섭씨로 바꾸고 소수 둘째 자리에서 자른다. 숫자가 아니거나 무한대면 값이 없는 것으로 본다 |
| API 키 | 선택(로컬 네트워크 전용). 정해 두면 `X-API-Key` 헤더가 같아야 하고, 다르면 401. 비교는 시간 차로 키를 알아낼 수 없는 `hmac.compare_digest` |
| 센서 설정이 비었을 때 | 503 `{"error": "온도조절기 센서가 설정되지 않았습니다"}` |
| 가짜 모드 | SmartThings 없이 펌웨어를 개발할 수 있게 고정 JSON을 내준다 |
| 설정 | 홈서버 `.env`에 `THERMOSTAT_SENSORS=<id>=<SmartThings 기기 ID>=<이름>,...` 한 줄 |

> **웹 개발자 시선** — 계약 문서는 "무엇을 보낸다"까지만 적는다. "무엇을 보내면 안 된다"는 받는 쪽 파서 코드에 있다. 서버를 만들기 전에 클라이언트 파서부터 읽는다.

## 18.3 토큰은 홈서버가 들고 있다

실제 데이터를 해석하는 작업이라, 구현을 맡기기 전에 실제 SmartThings 응답을 받아 표본으로 넣으려 했다. 그런데 이 노트북에 있던 SmartThings 토큰이 만료돼 있었다(`invalid_grant`).

다시 인증하지 않았다. 8장에서 정했듯 홈서버가 24시간마다 같은 토큰을 갱신하고 있다. 노트북에서 새로 인증하면 홈서버가 들고 있는 갱신 토큰이 무효가 될 수 있다. 홈서버 쪽 세션에 물어보려 했지만 그쪽 원격 실행 환경에도 닿지 않았다.

그래서 SmartThings 공개 문서의 응답 모양(`temperatureMeasurement.temperature`의 `value`, `unit`, `timestamp`)으로 표본을 만들고(**문헌 기반**), 계획에 "실제 값은 머지 뒤 홈서버에서 확인"이라고 적었다.

> **웹 개발자 시선** — 운영 서버만 가진 자격증명으로 운영 데이터를 확인해야 하는 문제다. 개발 PC에서 운영 토큰을 새로 발급하면 운영 쪽이 끊길 수 있다.

## 18.4 시각 API: NTP가 안 될 때 (SCRUM-252)

> "그리고 시간 갱신용 api도 하나 만들까? 티켓 추가해줘."

펌웨어는 NTP로 시각을 맞추고 보드 RTC로 유지한다. 그런데 공유기가 바깥 NTP 서버에 닿지 못하면? 같은 로컬 네트워크의 홈서버에서 시각을 받으면 된다. 화면의 "N분 전"도, 원격 센서의 10분 기준도 모두 시계에 기대고 있다.

```text
GET http://<홈서버>/api/thermostat/time

{ "now": "2026-11-25T10:00:00+09:00", "epoch": 1795568400 }
```

- 외부를 부르지 않고 바로 응답한다.
- `now`(오프셋이 붙은 서울 시각)와 `epoch`(UTC 초)를 **같은 한 시각**에서 만든다. 시각 함수를 두 번 부르면 초 경계에서 둘이 어긋날 수 있다.
- 센서 설정이 없어도 시각 API는 동작한다.

실수도 하나 있었다. 일감 본문에 epoch 예시를 `1764032400`으로 적었는데, 이 값은 **2025년** 11월 25일이다. 2026-11-25T01:00:00Z는 `1795568400`이다. 계산하지 않고 그럴듯한 숫자를 적은 것이다. 바로잡은 값을 계획과 일감에 남기고, 테스트 표본에는 날짜 경계(12월 31일 15:30 UTC → 서울 1월 1일)처럼 틀리기 쉬운 값을 넣었다.

> **질문 노트** — "시간 갱신용 api도 하나 만들까?" → NTP가 막힐 때 쓸 예비 시계다. 같은 네트워크의 홈서버가 시각을 준다.

## 18.5 API 목록: 레포가 아니라 API로 (SCRUM-253)

> "그리고 에이전트들이 볼수있게, api에 swagger 같은거도 만들까? 굳이 스웨거일 필요까진 없고, 그냥 어떤 종류의 API가있고 각 API에서는 어떤 정보가 제공된다 정도면 될것 같아."

처음 쓴 일감은 홈서버 레포 안에 API 목록 문서를 두는 안이었다. 필자가 바로 짚었다.

> "253은 근데 레포를 봐야 알수있잖아. 나는 그냥 api 호출로 파악하게 하고 싶은데?"

맞는 지적이다. 이 API를 쓸 에이전트는 **다른 레포**(이 펌웨어 레포 같은)에서 일한다. 홈서버 레포를 열 수 없거나, 열면 그만큼 토큰을 쓴다. 일감을 바꿨다.

```text
GET http://<홈서버>/api

{
  "service": "home-dashboard",
  "apis": [
    { "method": "GET", "path": "/api/thermostat/sensors",
      "summary": "온도조절기용 원격 온도 센서 값",
      "description": "인증: ... 응답: ... 오류: ...",
      "params": [{"name": "X-API-Key", "in": "header", "required": false}] }
  ]
}
```

- 목록을 손으로 따로 적지 않는다. 각 API 정의에 붙인 한 줄 요약과 설명(인증, 응답 필드, 오류 코드)을 서버가 읽어 목록을 만든다. 손으로 적은 목록은 언젠가 실제 API와 어긋난다.
- `/health`와 `/api`로 시작하는 것만 넣는다. 화면 페이지와 정적 파일은 뺀다.
- 인증 없이 연다. 목록만 주고, 데이터 값이나 설정값(키, 토큰, 기기 ID)은 주지 않는다.
- **설명이 빈 API가 하나라도 있으면 깨지는 테스트**를 둔다. 다음에 API를 추가하는 사람(또는 AI)이 설명을 빼먹으면 테스트가 막는다.

같은 정보로 FastAPI가 기본으로 주는 `/docs`(Swagger 화면)도 쓸 만해졌다. 처음 말한 "swagger 같은거"가 덤으로 따라왔다.

> **질문 노트** — "253은 근데 레포를 봐야 알수있잖아" → 읽는 쪽이 다른 레포의 에이전트라면, 문서가 아니라 API로 준다.

> **웹 개발자 시선** — OpenAPI와 같은 생각이다. 문서를 코드 옆에 두고 코드에서 뽑으면 둘이 어긋나지 않는다. 다른 점은 읽는 쪽이 사람보다 **에이전트**라는 것이다. 에이전트에게는 화려한 Swagger 화면보다 JSON 한 번이 낫다.

## 18.6 같은 파일, 두 일감

> "252 253 동시진행 가능할까? 가능하면 워크플로우로 돌려줘"

둘 다 같은 파일(`thermostat.py`)을 고쳐야 했다. 252는 그 파일에 시각 API를 더하고, 253은 같은 파일의 센서 API에 설명을 붙인다. 10장의 일감 그래프로 보면 둘 사이에 화살표가 없지만, 같은 파일을 만지면 부딪힌다. 화살표 대신 두 가지를 정했다.

- **파일 소유권을 나눴다.** 252는 `thermostat.py`의 새 라우트(파일 끝 `return router` 바로 앞), 그 테스트, README를 맡는다. 253은 앱 본체, 관리 API, 새 목록 모듈, 에이전트 안내 문서를 맡고, `thermostat.py`에서는 센서 API의 설명 한 줄만 만진다.
- **규칙을 먼저 공유했다.** "새 API에는 한 줄 요약과 한국어 설명(인증, 응답, 오류)을 반드시 단다"를 두 계획에 똑같이 적었다. 252는 253이 무엇을 만드는지 몰라도, 이 규칙만 지키면 253의 목록에 들어간다.

결과는 이렇다. 252를 먼저 머지하고 253 브랜치에 최신 main을 합쳤는데 **충돌이 없었다.** 합친 뒤 전체 테스트 453개가 통과했고, 18.5의 "설명 없는 API가 있으면 깨지는 테스트"가 252의 시각 API까지 검사했다.

이날은 검토를 맡는 Qwen이 세 일감 모두 예산 한도(HTTP 429)에 걸려 돌지 못했다. Claude가 각 계획의 "검토할 점"만 직접 봤고, 253은 API 설명에 적힌 필드와 오류 코드를 실제 코드와 하나씩 맞춰 봤다.

| 일감 | 내용 | 구현 비용(DeepSeek) |
|---|---|---|
| SCRUM-239 | 센서 API `GET /api/thermostat/sensors` | 0.08달러 |
| SCRUM-252 | 시각 API `GET /api/thermostat/time` | 0.02달러 |
| SCRUM-253 | API 목록 `GET /api` | 0.06달러 |

> **웹 개발자 시선** — 모노레포에서 CODEOWNERS로 소유권을 나누고, 린트 규칙으로 컨벤션을 강제하는 것과 같다. 소유권은 충돌을 막고, 테스트로 강제한 규칙은 서로 몰라도 맞물리게 한다.

## 18.7 아직 남은 것

- 홈서버에 아직 반영하지 않았다. pull, 서비스 재시작, `.env`에 센서 설정 추가가 필요하다. 서버 상태를 바꾸는 일이라 필자가 시킬 때 한다.
- 그 뒤 세 API의 실제 응답을 확인한다. 그래야 18.3의 **문헌 기반** 표본이 **실측**이 된다.
- 펌웨어 쪽: NTP가 실패하면 시각 API로 시계를 맞추는 흐름을 넣는다.

## 알게 된 점

- 느린 외부 API는 요청 경로에서 빼고, 받은 쪽이 신선도를 판단할 수 있게 시각을 함께 보낸다.
- 서버를 만들기 전에 클라이언트 파서부터 읽는다. 계약 문서에 없는 규칙이 거기 있다.
- 시각 예시는 계산해서 적는다. 사람(과 AI)이 쓴 epoch는 1년쯤 틀려도 그럴듯해 보인다.
- "누가 읽는가"를 먼저 묻는다. 레포 안 문서는 그 레포에서 일하는 사람용이고, `GET /api`는 바깥에서 부르는 쪽용이다.
- 두 작업이 서로를 기다리지 않게 하려면, 인터페이스가 아니라 **규칙**을 공유해도 된다.
