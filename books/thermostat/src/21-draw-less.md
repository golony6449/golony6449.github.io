# 21장 덜 그리기: 바뀐 것만 다시 그리는 법

20장의 버그는 "한 번 어긋나면 계속"이었다. 고친 뒤에도 "한 번 어긋나면 **한 프레임**"은 남는다. EOF 인터럽트를 놓치는 일 자체가 없어진 것은 아니기 때문이다. 이 장은 그 남은 흔들림을 줄이는 방법이다. 같은 날 홈서버 연동에서 찾은 작은 거짓말 하나도 덧붙인다.

구현은 필자가 자는 동안 끝났다. 결과는 21.5에 적는다.

## 21.1 A인가 B인가

남은 증상을 두 갈래로 나눠 물었다.

- A: 화면 전체가 한 번 툭 밀렸다가 돌아온다. 그리기 부하로 바운스 버퍼 채우기가 늦은 한 프레임이다.
- B: 누른 버튼이나 숫자 근처만 잠깐 어긋난다. 19장의 찢어짐이다.

> "A에 가까워"

A라면 처방은 하나다. 인터럽트를 놓치지 않게 **그리는 양을 줄인다.**

## 21.2 숫자 하나에 120ms가 드는 이유

19.4의 계측에서 숫자 하나만 바뀌어도 한 번 그리는 데 120ms가 넘었다. 코드를 읽어 보니 이유가 분명했다.

- 화면 갱신 함수 `update()`가 매번 `refresh_all()`을 부른다. 모든 라벨의 텍스트를 다시 넣고, 모든 버튼과 배지의 색을 다시 칠한다.
- LVGL 8은 **같은 텍스트**로 `lv_label_set_text()`를 불러도, **같은 색**으로 `lv_obj_set_style_*()`를 불러도 그 객체를 "다시 그려야 함"으로 표시한다. 스타일을 바꾸면 자식과 레이아웃까지 다시 계산한다.
- 목표온도를 한 번 누르면 **두 번** 그린다. 화면이 먼저 숫자를 바꿔 바로 반응하고(누르는 맛), 잠시 뒤 펌웨어가 같은 값으로 `update()`를 다시 부른다.

결국 숫자 하나가 바뀌어도 화면 대부분을, 그것도 두 번 그리고 있었다.

> **웹 개발자 시선** — React에서 상태가 바뀔 때마다 최상위 컴포넌트의 `key`를 바꿔 트리 전체를 새로 그리는 것과 같다. 가상 DOM이 해 주는 일, 즉 "이전과 비교해서 바뀐 것만 실제 DOM에 반영"을 여기서는 손으로 해야 한다.

## 21.3 방법

1. **화면 상태 비교.** 이전 화면 상태와 새 상태를 비교해 바뀐 구역만 갱신한다. 구역은 현재 온도, 큰 숫자, 난방 배지, 출처 배지, 모드 버튼, 설정 값, 시계 일곱 개다. 비교 함수는 LVGL 없이 컴파일되는 헤더에 두고 PC 단위 테스트로 검증한다(13장의 방식).
2. **텍스트 비교.** 라벨에 넣기 전에 지금 텍스트와 같은지 본다. 같으면 아무것도 하지 않는다.
3. **스타일 캐시.** "마지막으로 칠한 상태"(선택된 모드, 조절 가능 여부, 난방 여부, 출처 심각도)를 기억해 두고 바뀔 때만 다시 칠한다. 첫 화면에서는 반드시 칠해지도록 처음 값을 "칠한 적 없음"으로 둔다.

기대하는 결과는 이렇다. 1분마다의 시계 갱신은 시계 라벨 하나만, 목표온도 한 번은 큰 숫자 하나만 다시 그린다. 펌웨어가 뒤이어 부르는 두 번째 `update()`는 아무것도 그리지 않는다.

## 21.4 쓰지 않은 방법들

| 방법 | 효과 | 비용과 위험 |
|---|---|---|
| 바운스 버퍼 키우기(10줄 → 20줄) | 인터럽트 간격이 길어져 놓칠 확률이 준다 | 내부 SRAM을 두 배로 먹는다. 남은 힙이 약 65KB라 빠듯하다 |
| 화면 클럭 낮추기 | PSRAM을 읽는 부담이 준다 | 19장 2번 실험에서 효과가 약했다. 깜빡임 위험 |
| LVGL 그리기 버퍼를 내부 SRAM에 | PSRAM 쓰기가 준다 | 메모리가 모자란다 |
| PSRAM에서 코드 실행, 인터럽트 IRAM 안전 설정 | 플래시 쓰기 중에도 덜 흔들린다 | Arduino가 미리 빌드한 설정이라 바꿀 수 없다 |
| 더블 버퍼(19.2) | 찢어짐(B)을 막는다 | 이번 원인이 아니었다. 반응이 느려졌다 |

그래서 "덜 그리기"를 먼저 한다. 가장 싸고, 메모리를 더 쓰지 않고, 반응까지 빨라진다.

## 21.5 결과: 평소에는 아무것도 그리지 않는다

> "나 자러간다. 최대한 진행해줘"

구현은 DeepSeek에 맡겼고, Qwen 검토를 한 번에 통과했다. 화면 런타임에 닿는 일이라 마지막 확인은 Claude가 보드에서 했다. 19장의 계측 패치를 다시 넣고(커밋하지 않음), 시리얼 `sim` 명령으로 현재 온도를 바꿔 가며 쟀다(**실측**).

| 상황 | 이전 | 이후 |
|---|---|---|
| 평소(변화 없음) | 1초에 11번, 약 130ms | **0번** |
| 시계 갱신(1분마다) | 한 번 110~125ms | **11ms** |
| 현재 온도 변경 | 한 번 110~125ms | **27~54ms** |
| 같은 값 다시 보냄 | 다시 그림 | **안 그림** |

뜻밖의 발견은 첫 줄이었다. 아무것도 바뀌지 않아도 1초에 11번씩 그리고 있었다. 펌웨어가 1초마다 `update()`를 부르고, 그때마다 모든 라벨에 같은 텍스트를 다시 넣었기 때문이다. 이제는 화면이 바뀌지 않으면 아무것도 그리지 않는다.

> **웹 개발자 시선** — 브라우저 성능 탭에서 "아무것도 안 하는데 페인트가 계속 찍히는" 페이지를 본 적이 있다면 같은 이야기다. 원인은 대개 매 프레임 같은 값을 DOM에 다시 쓰는 코드다.

## 21.6 덤: "Wi-Fi is not connected"라는 거짓말

같은 날 밤, 필자가 홈서버 관리 화면의 API 목록을 건넸다.

> "이거 API 자료인데, 시간이랑, 온도 불러오도록 해줄래? 티켓 추가하고 워크플로우로 진행해줘"

18장에서 만든 두 API의 실제 응답을 이날 처음 받았다(**실측**). 18장 끝에 남겨 둔 "실제 응답 확인"이 여기서 끝났다.

```text
GET http://<홈서버>/api/thermostat/time
{"now":"2026-11-26T22:48:16+09:00","epoch":1795700896}

GET http://<홈서버>/api/thermostat/sensors
{"sensors":[{"id":"livingroom","name":"거실","temperature":21.0,"updated_at":"2026-11-26T22:41:37+09:00"}]}
```

그런데 펌웨어는 지금까지 이 값을 한 번도 받지 못했다. 19장의 계측 로그에 1분마다 `home server fetch failed: Wi-Fi is not connected`가 찍혀 있었다. 그 문장은 거짓말이었다.

- 루프는 "Matter가 Wi-Fi에 붙었거나, Arduino Wi-Fi가 붙었으면" 연결됐다고 보고 조회를 부른다.
- 그런데 조회 함수 안에서는 Arduino Wi-Fi 상태만 다시 본다. 이 펌웨어는 Matter가 Wi-Fi를 직접 잡기 때문에, 연결돼 있어도 Arduino 쪽 상태는 `254`(멈춤)다.
- 두 곳이 서로 다른 기준으로 "연결"을 판단하고 있었다.

보드에 저장된 홈서버 주소도 예시 파일의 값 그대로였다. 이 두 가지를 고치고 NTP가 안 될 때 시각 API로 시계를 맞추는 일을 새 일감으로 열었다. 받은 응답 두 개는 그대로 테스트 표본이 됐다.

> **웹 개발자 시선** — 헬스 체크가 두 군데 있는 서비스와 같다. 로드밸런서는 "살아 있다"고 보고 요청을 보내는데, 서비스 안의 미들웨어가 다른 기준으로 "준비 안 됨"을 돌려준다. 판단은 한 곳에 둔다.

고친 펌웨어를 올리자 조회 실패 로그가 사라졌다. 그런데 화면에는 여전히 원격 온도가 나오지 않았다. 원인이 두 개 더 있었다.

1. **고를 방법이 없었다.** 온도 출처 기본값이 "보드 센서만"인데, 원격 센서를 고르는 화면도 명령도 없었다. 시리얼 명령 `sensor remote livingroom`을 추가했다.
2. **새벽의 센서는 "오래됐다".** 거실 센서의 마지막 보고가 34분 전이었다. 설계 규칙 "10분 넘게 지나면 보드 센서로 전환"에 걸렸고, 보드 센서는 아직 달려 있지 않다. SmartThings 온도 센서는 값이 바뀔 때만 보고하므로, 밤에 온도가 그대로면 값이 맞아도 오래된 것으로 보인다(**추정**).

코드는 규칙대로 움직였다. 고쳐야 한다면 규칙 쪽이다. 이 결정은 다음으로 넘겼다.

## 알게 된 점

- 버그를 고친 뒤에도 남는 증상은 대개 같은 원인의 약한 형태다. 이번에는 "계속"이 "한 프레임"으로 줄었다.
- 화면 라이브러리는 "같은 값을 다시 넣었다"를 모른다. 비교는 부르는 쪽이 한다.
- 오류 메시지도 틀릴 수 있다. 메시지를 만든 조건과, 그 앞에서 판단한 조건이 같은지 본다.
- "마지막 보고 시각"과 "값이 아직 맞는가"는 다른 질문이다. 바뀔 때만 보고하는 센서에서는 오래된 보고가 곧 고장은 아니다.
