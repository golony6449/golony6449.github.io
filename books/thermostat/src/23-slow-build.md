# 23장 업로드가 느린 게 아니었다

22장의 펌웨어 판정을 DeepSeek이 구현하는 동안, 새 작업 폴더(워크트리)에서 펌웨어 빌드가 21시 5분에 시작해 22시에 끝났다. 거의 한 시간이다.

> "1시간을 빌드했는데 원래 이렇게 오래걸려?"

그리고 12시간 상한을 부탁하면서 한마디를 덧붙였다.

> "업로드도 오래걸리네... 이거 개선이 필요해."

이 장은 그 "오래 걸린다"가 어디서 오는지 잰 기록이다. 결론부터 말하면 업로드는 20초였다. 느린 건 그 앞이었다.

## 23.1 재기 전에는 모른다

Claude의 첫 설명은 "새 빌드 폴더라 전부 다시 컴파일하고, 라이브러리 탐색 단계가 길다"였다(**추정**). 이 추정은 반만 맞았다. 나머지 반이 틀렸다는 것은 25장에서 드러난다.

추정 대신 재 보기로 했다. `arduino-cli compile -v`의 출력 줄마다 시각을 붙여서, **아무것도 바꾸지 않은 빌드**가 어디에 시간을 쓰는지 봤다(**실측**).

| 구간 | 시간 |
|---|---|
| 스케치 전처리·라이브러리 탐색 | 180초 |
| 함수 프로토타입 생성 | 62초 |
| 스케치 컴파일 | 67초 |
| 라이브러리·코어 | 22초(이전 결과 재사용) |
| 링크 | 44초 |
| 합계 | **399초** |
| 업로드(플래시 쓰기) | 20초 |

바꾼 게 하나도 없는데 7분이다. 그중 약 310초가 `.ino` 스케치 **파일 하나**에 들었다.

> **질문 노트** — "업로드도 오래걸리네" → 업로드는 20초였다. 업로드 버튼을 누르면 컴파일부터 다시 하니, 느낌으로는 둘이 구분되지 않는다. 구간별로 재야 보인다.

## 23.2 캐시는 라이브러리에만

arduino-cli는 라이브러리 오브젝트는 다시 쓰지만 **스케치는 매번 다시 처리한다.** 스케치를 하나의 C++ 파일로 합치고, 함수 선언(프로토타입)을 자동으로 만들어 붙이고, 어떤 라이브러리를 쓰는지 다시 훑는다.

그런데 이 프로젝트의 스케치는 Matter, LVGL, 화면 드라이버 헤더를 직접 포함한 800줄짜리 본문이었다. 17장에서 여러 모듈을 한 펌웨어로 합칠 때 본문이 스케치에 그대로 쌓였기 때문이다.

> **웹 개발자 시선** — 번들러가 `node_modules`는 캐시하는데 엔트리 파일은 매번 처음부터 다시 파싱하는 상황이다. 그런데 그 엔트리 파일이 앱 전체를 품고 있었다.

## 23.3 처방

1. **얇은 스케치.** 본문을 `src/firmware` 라이브러리(`thermostat::firmware::setup/loop`)로 옮기고, `.ino`에는 여섯 줄만 남겼다. 코드는 옮기기만 하고 동작은 바꾸지 않았다. 이름과 include 한 줄 말고는 같은 811줄이다.
2. **`--upload-only`.** 이미 빌드했으면 컴파일 없이 업로드만 한다. 빌드 결과가 없으면 아무것도 올리지 않고 실패한다. 엉뚱한 바이너리가 올라가지 않게 하려는 것이다.
3. **구간별 시간 출력.** 빌드할 때마다 `[build] compile 113.8초`처럼 compile과 upload 시간이 따로 찍힌다. 다음에 "느리다"는 말이 나오면 이 두 줄부터 본다.

구현은 DeepSeek이 했고, Qwen 검토를 거쳐 머지했다.

## 23.4 해 보고 뺀 것

처음 계획에는 하나가 더 있었다. "새 워크트리에 메인 작업 폴더의 빌드 폴더(`.build`)를 복사해 둔다." 복사 자체는 16초였다.

실제로 복사해 보니 30분 넘게 처음부터 다시 빌드했다(**실측**). 빌드 설정 파일(`build.options.json`)에 작업 폴더의 **절대 경로**가 들어 있어서, 경로가 다르면 arduino-cli가 옵션이 바뀌었다고 보고 폴더를 지운다.

그래서 계획에서 뺐다. 어디서 빌드하든 같은 경로로 보이게 하는 방법(가상 드라이브)이 있지만, 여러 작업 폴더가 동시에 빌드하면 경로가 겹친다. 그 문제는 따로 풀기로 했다(25장).

> "새 워크트리 첫 빌드 개선 일감으로 등록해줘"

## 23.5 결과

| 상황 | 전 | 후 |
|---|---|---|
| 아무것도 안 바꾼 빌드 | 399초 | **114초** |
| 펌웨어 본문(`.cpp`) 수정 | 재지 않음 | **304초** |
| 빌드 없이 업로드만 | 방법 없음 | **20~38초** |

본문을 고치면 아직 5분이다. 그 파일이 Matter 헤더를 직접 포함하고 있어서, 고칠 때마다 무거운 전처리를 다시 하기 때문이다. 더 줄이려면 파일을 기능별로 쪼개야 한다. 이건 다음으로 미뤘다.

측정하는 동안 컴파일러는 16코어 중 약 4.6코어만 썼고 디스크는 놀았다. Windows Defender 실시간 검사가 프로세스를 수백 개 띄우는 탐색 단계를 늦출 수 있지만(**추정**), 예외 경로를 보려면 관리자 권한이 필요해 확인하지 못했다.

## 23.6 덤: 업로드 뒤 조용한 보드

`--upload-only`로 올린 직후 90초 동안 시리얼 출력이 없었다. 리셋 신호(EN)를 한 번 주자 바로 정상 부팅했다. 업로드 뒤 자동 리셋이 가끔 먹지 않는 것으로 본다(**추정**). 보드가 조용하면 먼저 리셋부터 해 본다.

## 알게 된 점

- "느리다"는 느낌은 구간을 나누지 않는다. 구간별 시간을 찍어 두면 다음 대화가 짧아진다.
- arduino-cli는 라이브러리는 캐시하지만 스케치는 매번 다시 처리한다. 무거운 코드는 스케치 밖(라이브러리)에 둔다.
- 빌드 폴더를 복사해도 경로가 다르면 쓸모없다. 캐시가 무엇을 키로 쓰는지 먼저 확인한다.
