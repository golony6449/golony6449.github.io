# 25장 50분 빌드의 진짜 범인

24장의 수정을 보드에 올릴 때 컴파일이 **3025초** 걸렸다(**실측**). 23장에서 줄여 놓은 "본문 수정 304초"의 열 배다. 이 장은 그 50분의 범인을 찾고, 새 작업 폴더의 첫 빌드 55분을 9분으로 줄인 이야기다. 중간에 범인을 한 번 잘못 지목했다.

## 25.1 첫 번째 지목: 헤더

빌드가 도는 동안 프로세스를 보니 ESP32 기본 라이브러리(Network, WiFi)와 LVGL, Matter까지 다시 컴파일하고 있었다. 이번에 바꾼 파일에는 핵심 제어 코드의 헤더가 있었다. Claude는 "헤더를 바꾸면 전부 다시 빌드한다"고 보고했다(**추정**).

> "SCRUM-333에 헤더 변경 내용 추가해줘"

일감에 사례로 적었다. 그리고 필자가 물었다.

> "최적화 작업은 아직 안한거네?"

그렇다. 등록만 해 둔 상태였다.

> "SCRUM-333 진행해줘"

## 25.2 빌드 폴더의 시각을 읽다

먼저 방금 끝난 빌드의 흔적, 즉 빌드 폴더 파일의 시각을 봤다(**실측**).

| 시각 | 일 |
|---|---|
| 08:28 | 빌드 시작(빌드 설정 파일 기록) |
| 08:56 | 감지 캐시 두 개 기록 → **라이브러리 감지 28분** |
| 08:58~09:16 | WiFi·Network·LVGL·Matter·우리 라이브러리 오브젝트 새로 생성 → **약 20분** |
| 09:19 | 링크 끝 |

Arduino 코어 오브젝트는 이틀 전 것 그대로였다. 라이브러리만 전부 다시 만든 것이다. 왜일까?

## 25.3 arduino-cli가 캐시를 버리는 조건

arduino-cli 1.6.0의 소스를 읽었다(**문헌 기반**). 캐시는 네 겹이고, 버리는 조건이 각각 다르다.

| 캐시 | 버리는 조건 | 버리면 |
|---|---|---|
| `build.options.json`(스케치·라이브러리 경로, 빌드 속성) | 한 글자라도 다르면 | 빌드 폴더 전체를 지운다 |
| `includes.cache`(파일마다 "전처리했더니 이 헤더가 없더라"를 차례로 적은 목록) | 앞에서부터 맞춰 보다 **한 항목이라도 어긋나면 그 뒤를 전부 잘라 낸다** | 잘린 뒤의 파일을 모두 다시 전처리한다. 병렬로 미리 돌리던 전처리도 취소해 **직렬로** 느려진다 |
| `libraries.cache`(include 폴더 목록) | 순서까지 한 글자라도 다르면 | "rebuilding all libraries", 라이브러리 오브젝트를 모두 지운다 |
| 오브젝트(`.o`) | 소스나 그 소스가 포함한 헤더가 `.o`보다 **새로우면** | 그 파일만 다시 컴파일한다. 컴파일 명령이 같은지는 보지 않는다 |

마지막 줄은 뒤에서 다시 중요해진다.

## 25.4 헤더 탓이 아니었다

감지 단계만 따로 재는 옵션(`--only-compilation-database`)으로 실험했다(**실측**).

| 실험 | 감지 시간 | 라이브러리 재컴파일 |
|---|---|---|
| 바꾼 것 없음 | 48초 | — |
| 그 헤더의 수정 시각만 바꿈 | 190초 | 없음 |

헤더를 바꾸면 2~3분이 더 들 뿐이었다. 그럼 50분은?

지난 명령 기록을 뒤져 보니 답이 있었다. 메인 작업 폴더의 빌드 폴더를 마지막으로 쓴 것은 전날 23장의 **계측용 빌드**였다. 그때는 아직 스케치가 두꺼웠고 `src/firmware` 라이브러리도 없었다. 얇은 스케치로 바뀐 뒤 이 폴더에서 **처음 한 빌드**가 바로 08:28 빌드였다.

- 라이브러리 목록 세 번째 자리에 `src/firmware`가 끼어들었다.
- `includes.cache`는 거의 맨 앞에서 어긋났고, 뒤를 모두 잘라 냈다. 감지 28분.
- `libraries.cache`도 달라졌다. 라이브러리를 모두 지웠다. 20분.

새 작업 폴더의 첫 빌드 55분도 같은 구조다. 캐시가 아예 없으니 감지를 직렬로 하고 라이브러리를 전부 컴파일한다. 일감에 남긴 "헤더" 댓글은 정정했다.

> **웹 개발자 시선** — "방금 머지한 PR 때문에 CI가 느려졌다"고 지목했는데, 알고 보니 그 PR 직전에 누가 캐시 키를 바꿔 놓았던 경우와 같다. 마지막 변경보다 **캐시가 마지막으로 무엇을 봤는지**를 먼저 본다.

## 25.5 두 갈래

| 방법 | 실험 | 결과 |
|---|---|---|
| 감지 건너뛰기(`--skip-libraries-discovery`, 도움말에 없는 옵션) | 감지만, 그리고 전체 빌드 | 감지는 19초로 줄었다. 그런데 **링크가 실패**했다(`ld returned 1`). 이 모드에서는 라이브러리 목록이 비어 라이브러리가 링크되지 않는다. 버렸다 |
| 고정 경로(`subst T: <작업 폴더>`) | `T:\` 경로로 빌드를 시작하고 빌드 설정 파일 확인 | `"sketchLocation": "T:\\firmware\\thermostat_main"`. arduino-cli가 가상 드라이브를 실제 경로로 바꾸지 않는다. 채택 |

Windows의 `subst`는 폴더 하나를 드라이브 글자로 보이게 한다. 어느 작업 폴더든 `T:\`로 연결하고 빌드하면, arduino-cli 눈에는 늘 같은 경로다.

> **웹 개발자 시선** — 캐시 키에 절대 경로가 들어가서 체크아웃 위치만 달라도 캐시가 다 깨지는 CI와 같다. Docker 빌드에서 소스를 늘 `/app`에 두는 것처럼, 어디서 빌드하든 같은 경로로 보이게 만든다.

## 25.6 설계: 가장 중요한 한 줄

1. compile할 때만 `T:`를 작업 폴더에 연결하고, compile 명령의 경로를 모두 `T:\` 기준으로 바꾼다. 끝나면 실패하든 예외가 나든 연결을 푼다. upload는 실제 경로를 쓴다.
2. `T:`는 사용자 세션 전체에 하나뿐이다. compile 동안 **잠금 파일**을 잡고, 다른 빌드가 잡고 있으면 기다린다. 프로세스가 죽으면 운영체제가 잠금을 풀어 준다.
3. 새 작업 폴더는 메인 작업 폴더의 빌드 폴더를 **복사해서 시작**한다.
4. 복사한 뒤 **우리 소스로 만든 오브젝트는 지운다.** 서드파티 라이브러리와 코어 오브젝트만 남긴다.

4번이 가장 중요하다. 25.3의 마지막 줄 때문이다. arduino-cli는 수정 시각만 본다. 메인에서 10시 31분에 빌드한 오브젝트를 10시에 만든 작업 폴더로 가져오면, 작업 폴더에서 **내용이 다른** 파일도 "소스가 더 오래됐다"며 메인의 오브젝트를 그대로 쓴다. 오류 하나 없이 **다른 코드로 만든 펌웨어**가 나온다. 우리 소스의 오브젝트를 지우면 그 파일들은 반드시 다시 컴파일된다.

> **웹 개발자 시선** — 다른 브랜치의 `node_modules/.cache`를 복사해 왔더니, 내 브랜치에서 바뀐 파일이 캐시 때문에 다시 빌드되지 않아 옛 코드가 배포되는 사고와 같다. 캐시를 들여올 때는 "내 코드로 만든 부분"부터 버린다.

구현은 DeepSeek이 했고 Qwen 검토를 한 번에 통과했다(비용 $0.098). 실제 빌드 시간은 DeepSeek의 작업 폴더에서 잴 수 없어서 Claude가 직접 쟀다.

## 25.7 결과 (실측)

| 상황 | 전 | 후 |
|---|---|---|
| 메인 작업 폴더를 고정 경로로 처음 빌드(한 번만) | — | 3153초 |
| **새 작업 폴더 첫 빌드** | 약 55분 | **530초(약 9분)** |
| 빌드한 작업 폴더, 바꾼 것 없음(잠금·연결 포함) | 114초 | **90초** |
| 작업 폴더 두 개 동시 빌드 | — | 첫째 89.7초. 둘째는 "다른 워크트리 빌드가 끝나기를 기다립니다"를 내고 기다렸다가 520.9초. 둘 다 성공 |

메인과 새 작업 폴더의 바이너리는 64바이트만 달랐다. 앱 설명 안의 ELF 해시 32바이트와 이미지 끝의 해시 32바이트다. 실행되는 코드와 데이터는 같고, ELF가 다른 건 디버그 정보 차이로 본다(**추정**).

> **감탄 노트** — 두 빌드를 동시에 돌리자 둘째가 "다른 워크트리 빌드가 끝나기를 기다립니다" 한 줄을 남기고 조용히 줄을 섰다. 충돌 대신 순서가 생겼다.

## 알게 된 점

- arduino-cli의 감지 캐시는 순서 있는 목록이다. 앞에서 한 번 어긋나면 뒤를 모두 버리고 직렬로 다시 한다.
- "마지막으로 바꾼 것"이 원인이라는 추정은 쉽게 틀린다. 그 빌드 직전에 무엇이 빌드 폴더를 만졌는지를 먼저 본다.
- 수정 시각만 보는 캐시에 다른 소스 트리의 결과를 들여오면 "오류 없는 잘못된 빌드"가 생긴다. 들여온 쪽의 내 코드 결과는 지우고 시작한다.
- 숨은 옵션은 이름만 보고 쓰지 않는다. 감지는 빨라졌지만 링크가 깨졌다.
